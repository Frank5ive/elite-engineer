## 1. Engineering problem

An engineer ships a feature in an afternoon with an AI assistant. Two weeks later it fails in production: the paginated endpoint returns 11 rows for a page size of 10, a Decimal-less total is off by a cent on some invoices, and the code calls a function that does not exist in the language version in use but only on the one path nobody ran. In the review, the engineer cannot explain how the pagination works, which tests exercise it, or why the design has three classes for a sum.

None of those defects is exotic. They share a cause: output was accepted because it looked plausible and passed the happy path, not because it was understood and verified. Three separate failure modes hide in that story:

1. **Dependence**: you can no longer produce, explain or debug this class of code yourself.
2. **Gullibility**: you cannot distinguish correct from plausible-wrong output, so you ship the latter.
3. **Leakage**: you pasted something you were not allowed to paste.

Your goal is a professional who uses AI as a fast, fallible junior collaborator under your authority, and who can show, with evidence, which skills stand without it. The mastery claim of this whole book (reproduce, adapt, explain, defend without the lesson) is tested here against AI as well as against the lesson.

## 2. Learning objectives

1. Classify any task as Mode A, B or C under the protocol in 3.1, justify the choice, and record it.

3. Review a 60-line AI-style listing and find at least 12 defects across five classes (fabricated API, correctness, security, design bloat, test/doc), each with a reproduction or citation and a fix, verified by running code.
4. Verify three kinds of claim made by an assistant (API existence, behaviour, performance) using only the interpreter, official documentation, or a measurement you take.
5. Generate tests with an assistant and then validate those tests by mutation (break the code on purpose and show the tests fail).
6. Run the AI-dependence audit procedure on one of your own projects and produce a scored scorecard with evidence for every score.
7. Rebuild a core component of that project without AI within a time budget and report the gaps found.
8. Maintain a register of knowledge you currently hold as unproven, with a dated plan to prove or discard each item.

## 3. First-principles explanation

### 3.1 The Modes in practice

| Mode | Rule | Use for | Evidence you keep |
|---|---|---|---|
| A | Closed book, no AI, no docs beyond what the exam says | Retrieval, core challenges, oral defences, rebuilds | Timestamped solution + what you looked up (nothing) |
| B | Docs and official references only, no AI for design or code | Projects where you need to learn the API surface | Notes of docs consulted; your design reasoning before coding |
| C | AI-assisted; **you own correctness** | Boilerplate, exploring alternatives, reviewing your design, drafting tests, unfamiliar tooling | Prompt log, what you changed, how you verified |

Rules that make the Modes real rather than decorative:

- Declare the Mode **before** starting a task, in the file or ticket. Retroactive labelling is useless.
- Mode downgrade is allowed (A -> B when stuck: record that you did it and why); silently upgrading is not.
- Mode C obligations: you run every line you keep; you can explain every line you keep; you have at least one test you wrote that does not come from the assistant; you note anything you could not verify.

### 3.2 Asking precise technical questions

An answer cannot be better than the question constrains it. A precise question contains:

1. **Context**: language and version, framework and version, relevant constraints (no new dependencies, must run on X).
2. **Goal**: what should be true afterwards, as an observable behaviour.
3. **Evidence**: the exact error, the minimal reproducing snippet, expected versus actual output.
4. **What you already tried / believe**, so the assistant can challenge your belief rather than guess.
5. **Form of the answer**: "list three hypotheses ranked by likelihood with a command to confirm each", "give me the tradeoffs, not code", "show the smallest diff".

Weak: "My pagination is broken, fix it."
Strong: "Python 3.12, no dependencies. `page(items, page_no, size=10)` returns `items[start:start+size+1]`. For 25 items and `page_no=1` I get 11 items; I expected 10. I believe the `+1` is a mistake; I intend to fetch one extra row so I can tell the client whether a next page exists. Challenge that: is there a cleaner way to signal a next page, and what do I return then? Give the smallest diff and a pytest that fails before and passes after."

The strong version also exposes your own possible misunderstanding (the `+1` trick is a real technique, but then the function must not return the extra row). Technique: after every non-trivial answer, ask the assistant to state what would make its answer wrong.

### 3.3 Reviewing AI-written code: what to look for

Treat output as a pull request from a fast junior who has read a lot, never run the code against your system, and states everything with equal confidence.

- **Fabricated or misremembered APIs**: functions, parameters, flags or config keys that do not exist or exist in another version. Check: run it, `help()`/`dir()`, official docs for your exact version. In the lab, `math.clamp` looks natural and does not exist (VERIFY with `python3 -c "import math; print(hasattr(math,'clamp'))"` on your interpreter).
- **Real but version-gated APIs**: `itertools.batched` is real, from Python 3.12. Flagging it as fabricated is itself a review error. Check the version table, then decide whether your deployment target allows it.
- **Subtle correctness bugs**: off-by-one, mutable default arguments, floating-point money, timezone-naive datetimes, integer overflow, wrong rounding mode, swallowed exceptions, iteration order assumptions. They survive happy-path tests.
- **Security flaws**: SQL built with string formatting, `shell=True` with interpolated input, non-constant-time secret comparison, fast unsalted hashes for passwords, secrets in code, missing authorisation checks, path traversal, unvalidated deserialisation (4.3).
- **Needless abstraction**: strategy/factory/interface layers for a one-line operation; configuration for values that never change; generic frameworks for one use. The cost is reading time and bug surface with no benefit. Ask: what requirement does each class serve?
- **Tests that bless bugs**: tests generated from the implementation assert whatever the code does, including its bugs. A test that was never seen failing proves nothing.
- **Confident wrong explanations**: the prose may describe different behaviour from the code. Trust the code you ran.
- **Missing edge cases**: empty input, one element, duplicates, negative numbers, unicode, huge input, concurrency.

Review procedure (fixed order): (1) read for intent; (2) run it on the happy path; (3) list every external name and verify it exists in your version; (4) hunt edge cases with inputs you design; (5) security pass on every boundary where data crosses in or out; (6) delete anything not needed; (7) write failing tests for each defect before fixing.

### 3.4 Verifying claims

For each claim an assistant makes, pick the cheapest decisive check:

| Claim kind | Decisive check |
|---|---|
| "X exists / takes argument Y" | Interpreter or compiler on your version; official docs for that version |
| "X behaves like Z" | Minimal experiment you write; compare with docs; the standard or spec for language rules |
| "X is faster" | Measure on your workload using the method of 4.4; report variance, not one run |
| "This is secure" | Threat model + attempt to break it with a test; independent reference (OWASP, library docs) |
| "This is the standard way" | Look at your team's code and the official guide; "standard" is often convention, not rule |
| "Citation/paper says..." | Open the source. Assistants can produce plausible references that do not exist |

Label your own certainty in notes using the book's categories: language guarantee, framework behaviour, implementation detail, convention, opinion.

### 3.5 Using AI to challenge your design

A high-value Mode C use: you design first (Mode A/B), then ask the assistant to attack it. Prompts that work:

- "Here is my design and its requirements. List the three most likely ways it fails in production and how I would detect each."
- "What requirement am I most likely misreading?"
- "Argue for the strongest alternative design and tell me when it wins."
- "Which of my assumptions would break at 100x load / with concurrent writers / with partial failure?"

Then you decide. Record which objections you accepted, rejected and why. If you cannot rebut an objection, you have found something to learn, not something to ignore.

### 3.6 Generating tests, then validating them

Do not stop at "the tests pass". Procedure:

1. Write your own spec of behaviour (a list of properties and edge cases) before asking for tests.
2. Ask for tests; compare to your list; note what is missing.
3. **Mutation check by hand**: introduce a deliberate bug (off-by-one, flipped comparison, deleted validation) and confirm at least one test fails. If none does, the suite does not protect that behaviour.
4. Check that tests assert behaviour, not implementation (no asserting private calls, no copying the implementation's formula into the expected value).
5. Make sure each test has been seen to fail at least once for the right reason (red-green, 1.4).

The lab shows the trap: generating tests from the listing's `page()` would plausibly assert 11 items for page size 10.

### 3.7 Confidentiality and employer policy

Your employer's policy governs, not this book. Until you have read it, assume: no customer data, credentials, tokens, private keys, internal hostnames, proprietary source or unreleased business information goes to an external AI service. Practices: ask what tools are approved and for which data classes; strip or synthesise data (fake names, generated fixtures); describe the problem abstractly (minimal reproducible example with invented identifiers); never paste secrets "just to debug" (if you did, treat the secret as leaked and rotate it, per your incident process); keep the prompt log free of sensitive content; check licence/IP terms on generated code according to policy. If the policy is silent or unclear, ask before using, and record the answer. This is a compliance matter, not a technical one; I cannot tell you what your employer's rules are.

### 3.8 The AI-dependence audit

An audit measures what you can do without AI, using evidence, not self-assessment. Procedure (run on one project at a time, ideally 1-4 weeks after finishing it):

1. **Inventory** (30 min): list the components of the project and, for each, the Mode in which it was built and how much was generated (none / snippets / most of it).
2. **Explain test** (per component, closed book): without opening the code, explain its design, data flow, failure modes and why alternatives were rejected. Score what you could not state.
3. **Reproduce test**: rebuild the component from a blank file with no AI, time-boxed to 1.5x your original Mode A/B estimate. Compare behaviour to the original through its tests.
4. **Debug test**: a colleague (or you, after a week) injects one realistic bug; you find it without AI within a budget.
5. **Review test**: review a flawed diff for the component (as in the lab).
6. Fill the scorecard; record evidence links; list gaps as register entries (3.9) with remedial exercises.

Scorecard (0-3 per row: 0 cannot, 1 with heavy help, 2 with docs only, 3 unaided; a score needs evidence):

| Dimension | Evidence needed |
|---|---|
| Explain design without code | Recording or written explanation from memory |
| Reproduce core logic blank-file | Passing original tests; elapsed time |
| Find an injected bug | Injected bug, your diagnosis log |
| Review flawed code | Findings list vs answer key |
| Verify a claim independently | The check you ran |
| Write tests that fail for the right reason | Mutation results |
| Explain the data structures / complexity | Written derivation |
| Handle an unfamiliar error from docs alone | Your doc trail |

Interpret per dimension, not as a total: a 0 on "reproduce core logic" in a P0 area is a defect to fix before taking on dependent work. Thresholds below are suggestions, not facts about you: any 0 or 1 in a P0/P1 area triggers remediation; all 2s or better to pass this lesson's audit.

### 3.9 Tracking unproven knowledge

Maintain a register (file in your repository). Entry: claim, source (lesson, AI, colleague), status (Unproven / Experiment designed / Proven by (evidence) / Discarded), date, how I will prove it. Examples of good entries: "`list.pop(0)` is O(n) in CPython: unproven; plan: time n = 1e4..1e6 and fit." Rule: unproven items may not be used as premises in a design review without being marked as assumptions. Review the register weekly; stale unproven items older than a month are escalated to a scheduled experiment or deleted.

### 3.10 Rebuild-without-AI protocols

Periodically rebuild something from nothing to keep skills real. Protocol: pick a component you wrote at least a week ago; set a time box (1.5x original); disable the assistant (Mode A or B, stated); write the tests first from the spec; build; compare with the original; log every point where you stalled and what you had to look up. Rotate topics so every P0/P1 area is rebuilt at least once per quarter (a policy suggestion). A rebuild failure is data, not shame: it tells you what to drill.

## 4. Worked example

### 4.1 Rewriting a question

Original (Mode C): "why is my FastAPI endpoint slow".

Rewrite following 3.2: "FastAPI 0.x (VERIFY exact version with `pip show fastapi`), Python 3.12, Postgres via SQLAlchemy 2.x. `GET /orders?customer=...` takes about 2 s for a customer with 40k orders; others are fast. `EXPLAIN (ANALYZE)` shows a sequential scan on `orders` (output attached). Index on `orders(customer_id)` exists? I believe not. Give me ranked hypotheses with a command to confirm each; do not rewrite the endpoint."

What changed: version and stack stated, symptom quantified, evidence supplied, a belief exposed, a form of answer requested that keeps you in control.

### 4.2 Verifying an assistant's claims by running code

Suppose an assistant says: "Use `math.clamp(x, lo, hi)`; round money with `round(x, 2)` which rounds half up; `hmac` comparisons are unnecessary because `==` is fine for tokens."

```python
import math
print(hasattr(math, "clamp"))     # False on the interpreter used to write this lesson (Python 3.13.5)
print(round(2.675, 2))            # 2.67  (not 2.68: the float 2.675 is slightly below 2.675)
print(round(0.285, 2))            # 0.28
```

Results from running that: `False`, `2.67`, `0.28`. So the first claim is fabricated for that version; the second is wrong in two ways (floats cannot represent 2.675 exactly, and Python's `round` on floats is not "half up"; use `decimal.Decimal` with `ROUND_HALF_UP` for money); the third is a security question, answered in the lab (constant-time comparison, `hmac.compare_digest`, documented in the `hmac` module docs). The cheap check for each claim was one line.

### 4.3 Validating generated tests by mutation

Suppose you accept this assistant-written test:

```python
def test_page_second_page():
    items = list(range(25))
    assert len(page(items, 1)) == 11
```

It passes on the flawed `page` (running it: 11 items for page 1 of size 10, 25 items). A test that blesses the bug. Mutation step: you wrote your own spec ("every page has at most `size` items, pages are disjoint, concatenating all pages reproduces the list") and the property test fails on the flawed code immediately. Rule: tests come from the spec, not from reading the implementation.

## 5. Production perspective

**What a senior engineer does differently.** Treats AI output as untrusted input, and applies the same gates as any contribution: tests, review, static analysis, threat model. Records which parts were generated. Keeps the assistant away from decisions that need accountability (security boundaries, data migrations, anything irreversible) unless every line has been understood. Uses the assistant for breadth (alternatives, rough edges, checklists) and the docs and experiments for depth.

**Team level.** Agree norms: disclose AI use in PRs if the team asks; never merge code you cannot explain; the author, not the tool, is accountable in incident reviews (7.2).

**Common beginner mistakes**

| Mistake | How to recognise | Diagnosis/fix |
|---|---|---|
| Accepting code because it ran once | No failing test ever seen | Mutation check; edge-case list |
| Asking the assistant to write the tests for code it wrote | Tests mirror implementation | Write the spec first |
| Pasting stack traces containing secrets | Tokens or hostnames in prompt | Redact; rotate if leaked |
| Mode creep (A -> C quietly) | Cannot reproduce in the audit | Declare Mode up front; audit |
| Confusing fluency with correctness | Confident prose, wrong behaviour | Run the code, read the docs |
| Over-trusting a claimed citation | Source not found or says otherwise | Open the source |

**Predict first** (write down before the second pass):

1. How many defects do you expect in 63 lines? Which classes (fabricated API, correctness, security, needless abstraction, other)?
2. Which single defect would you expect to survive both a happy-path test and a casual read?
3. Which line looks suspicious but is actually valid on Python 3.12+?
4. Which defects can a unit test detect, and which need a different tool (linter, review, threat model)?

### Reveal (read after predicting)

The listing contains defects in every class. Counting by class (the line-by-line key with reproduction and fix is in the solutions file; compare after your own list is written):

- Fabricated API: 1 (line 32).
- Correctness: 4 (money handled as float and rounded with float rounding; unvalidated discount percentage; mutable default argument; pagination returns one extra item).
- Security: 4 (SQL injection; non-constant-time secret comparison; unsalted fast hash for passwords; shell injection through `shell=True` with interpolated input).
- Needless abstraction: 1 (three types for a sum).
- Hygiene: 2 or more (unused `sqlite3` import; no type hints/docstrings or input validation; an unreviewed hard-coded 100-row batch size and 16% tax rate default).
- Valid but suspicious: `itertools.batched` on line 63 (real from Python 3.12, so the version requirement must be documented, not the call deleted).

Systematic diagnosis procedure that finds these reliably: (1) extract every external name (`math.clamp`, `batched`, `hashlib.md5`, `subprocess.run`) and verify each against the docs for your version; (2) mark every place data crosses a trust boundary (SQL, shell, comparison of secrets, password storage) and ask what an attacker controls; (3) for every function, test the empty case, one-element case, boundary of any index arithmetic, and a repeated call (mutable defaults reveal themselves on the second call); (4) for every number representing money, ask what type holds it; (5) for every class, ask which requirement forced it to exist; (6) write one failing test per finding before touching the code.

The second-pass experiment is part of the lesson: run `add_tags(1, 'a')` then `add_tags(2, 'b')` (the second call returns both tuples), `len(page(list(range(100)), 0))` (11), and `round(2.675, 2)` (2.67 on the interpreter used for this lesson; explain why with `decimal.Decimal(2.675)`).

## 8. Independent implementation challenge

**Mode A.** In 60 minutes, closed book, write `review_checklist.py` containing a function `scan(source: str) -> list[Finding]` that uses the `ast` module (standard library) to flag four patterns in Python source: (a) a function whose default argument is a list, dict or set literal; (b) calls to `subprocess.run/Popen/call` with `shell=True`; (c) f-strings or `%`/`.format` interpolation passed as the first argument to a method named `execute`; (d) calls to `hashlib.md5` or `hashlib.sha1`. `Finding` has `line`, `rule` and `message`.

Tests: positive and negative cases for each rule (at least 8 tests), including at least two false-positive probes you design (for example `execute("SELECT 1")` with a plain string must not be flagged, and `subprocess.run([...], shell=False)` must not be flagged). State in comments two things this scanner cannot see (for example data flow: it will miss a query string built on one line and executed on another). Do not claim it finds all vulnerabilities.

## 11. Mastery gate

Pass = 80/100 with no critical failure. Critical failures: (1) a fabricated API, SQL injection or shell injection finding missed or unverified; (2) a scorecard with a score lacking evidence; (3) real confidential data in any artefact; (4) a rebuild that quietly used AI; (5) a finding claimed without running or citing anything.

Evidence: the deliverables above and a 15-minute defence (Mode A): explain two of your findings and one scorecard score, then fix a new three-defect snippet that I choose, live, without AI.

If failed: reviewing -> take 50 lines of your own older code, plant eight defects spanning at least four classes, wait 48 hours, review it cold, and score yourself. Rebuild -> redo a smaller component under a 1x time box. Audit -> repeat on a different project with a second person verifying the injected bug.
