## Section 6 failure laboratory: scoring notes

Full credit: (a) mutant survives; (b) every 18-year-old wrongly refused, an off-by-one at the boundary; (c) mutation testing, closed by `fn(18) is True` and `fn(17) is False`. Common wrong answer: "property-based testing would find it". It may, but it is not guaranteed to generate exactly 17/18 in a short run, so explicit boundary examples are still required. Reward candidates who note that line and branch coverage were both 100% yet nothing checked the boundary.

## Section 7 retrieval answers

1. Unit: logic errors in one behavior, fast, precise location; cost: misses wiring and boundary mismatches. Integration: wrong SQL, serialization, config against a real collaborator; cost: slower, needs environment. Contract: producer and consumer disagree on an interface; cost: needs maintaining the shared contract and versioning. E2E: the assembled system fails for a real user path; cost: slow, brittle, poor localization.
2. Against a strict pyramid: mocking the database removes the thing most likely to be wrong (query semantics, constraints, transactions). Prefer integration tests against a real (disposable) database for the data layer and keep unit tests for pure logic. Argument for some units: pure computation and validation are cheap to test.
3. Coverage records execution, not verification. Example: `age >= 18` mutated to `age > 18` still passes tests with 30 and 5. Mutation testing measures it.
4. Round trip (`decode(encode(x)) == x`), idempotence of normalization, encoded output always valid under the format's grammar, `len`/ordering invariants or oracle comparison with a reference library; also "never raises on arbitrary input" for the decoder (or raises only the documented error). Shrinking reduces a failing input to a minimal one by repeatedly simplifying it while it still fails, so you get e.g. `''` or `[0]` rather than a 400-element list.
5. `Mock()` accepts any attribute, so `m.sendd("x")` returns a new mock silently and a test would pass wrongly. `Mock(spec=Mailer)` raises `AttributeError` for attributes not on `Mailer`.
6. (a) fake; (b) stub; (c) spy (a mock if it also enforces expectations itself); (d) dummy.
7. Time (inject a fake clock); shared state/order (isolate per test, randomize order to expose); concurrency (join/await deterministically, avoid sleeps, use events); network (fake the boundary, keep one separate integration test); unseeded randomness (seed and print the seed); resource conflicts (ephemeral ports, temp directories).
8. A default of `datetime.date.today()` is evaluated once at function definition (import time), freezing the date. Passing the callable defers evaluation to each call.
9. Pinning records what the code does today so change is detected; it does not claim the behavior is correct. Mark it with a comment and ticket (`# pinned: suspected bug, TICKET-123`) and keep the list in `QUIRKS.md`; changing it later is a deliberate commit that edits the pinned expectation.
10. Do not start line-by-line review. Ask the author to split it (mechanical renames/moves separate from behavior), or request a description explaining structure and a walkthrough; review the tests and the riskiest files first. Reason: review quality falls sharply with size; unreviewable PRs get rubber-stamped.
11. Treat it as a claim: ask what problem it solves here (a question, not a refusal); check whether a second variant exists; compare against the codebase's existing patterns; reply with evidence either way. Do not apply what you do not understand; do not reject without a reason. A factory with one product is ceremony (4.1).
12. A sprint stops delivery, produces large unreviewable diffs, and lacks tests to detect regressions; risk is concentrated. Continuous refactoring under a characterization suite spreads risk into small reversible commits. A rewrite is defensible when the platform is end-of-life or the design cannot meet a hard requirement, with agreement from stakeholders, the characterization suite as acceptance test, and a strangler migration path.

## 8.1 reference (characterize and extract)

Legacy function used for the reference (quirk: the coupon is applied before the staff discount):

```python
def price(qty, unit, customer_type, coupon):
    t = qty * unit
    if qty >= 50:
        t = t * 0.90
    elif qty >= 10:
        t = t * 0.95
    if coupon == "SAVE5":
        t = t - 5.0
        if t < 0: t = 0
    if customer_type == "staff":
        t = t * 0.80
    return round(t, 2)
```

Characterization table (verified: 14 passed). Notable pinned cases:

Refactor steps (each green): (1) extract `quantity_discount(qty) -> float` factor; (2) extract `apply_coupon(total, coupon)`; (3) extract `apply_customer_discount(total, customer_type)`; (4) make `price` a three-line composition. Keep the order coupon-then-staff because the table pins it. Notes: the case `(1, 6.0, "staff", "SAVE5")` is the one that distinguishes the order; a table without it would not detect an order swap, which is the lesson's point about boundary-and-interaction cases. `Decimal` migration is a separate behavior-changing step because float rounding at `.5` can differ. Marking: 14+ cases with boundaries 30%, order quirk pinned by a distinguishing case 20%, three green steps 30%, notes on `Decimal` and pinned-not-fixed 20%.

Alternative: a golden-master approach: generate a few thousand inputs from a small grid, store outputs in a file, and compare. Cheaper to build, harder to read and maintain; use it as a safety net beside named cases, not instead.

## 8.2 reference (properties and mutation)

```python
def merge_intervals(xs):                     # closed intervals; touching endpoints merge
    out = []
    for s, e in sorted(xs):
        if out and s <= out[-1][1]:
            out[-1] = (out[-1][0], max(out[-1][1], e))
        else:
            out.append((s, e))
    return out
```

```python
from hypothesis import given, strategies as st
from merge import merge_intervals

iv = st.tuples(st.integers(-20, 20), st.integers(-20, 20)).map(lambda t: (min(t), max(t)))
def covered(xs): return {p for s, e in xs for p in range(s, e + 1)}

@given(st.lists(iv, max_size=8))
def test_sorted_and_disjoint(xs):
    out = merge_intervals(xs)
    assert out == sorted(out)
    assert all(a[1] < b[0] for a, b in zip(out, out[1:]))

@given(st.lists(iv, max_size=8))
def test_same_coverage(xs): assert covered(merge_intervals(xs)) == covered(xs)

@given(st.lists(iv, max_size=8))
def test_idempotent(xs):
    once = merge_intervals(xs); assert merge_intervals(once) == once

@given(st.lists(iv, max_size=8))
def test_each_input_inside_one_output(xs):
    out = merge_intervals(xs)
    for s, e in xs: assert sum(1 for a, b in out if a <= s and e <= b) == 1
```

Verified 4 passed. Mutants run: `<=` to `<` (killed: 2 properties fail, because (1,2),(2,3) must merge), `sorted(xs)` to `xs` (killed), `max(out[-1][1], e)` to `e` (killed, nested intervals shrink). Observation for marking: the three were killed by properties, but note the properties assume *closed intervals that touch at a shared point*; the definition of "adjacent" `(1,2),(3,4)` (integer-adjacent) is a spec question. A good answer points it out and states the chosen semantics. A suite that only tested `[(1,3),(2,4)]` would not kill the `<` mutant, which is why the touching case needs to be an explicit example too.

## 8.3 reference review of the export diff

Ordered by checklist priority:

1. **Blocking, security (escalate):** No authorization. Any caller (even unauthenticated, depending on the app) can export grades for any `course_id`. Needs authentication, an instructor/teacher capability check on that course, and a negative test.
2. **Blocking, security:** SQL built with an f-string: injection risk. Although `course_id: int` is typed by FastAPI path validation (which narrows exposure), the pattern is unsafe and will be copied; use bound parameters: `text("... WHERE course = :cid")` with `{"cid": course_id}`.
3. **Blocking, security/privacy:** `log.info("exporting rows %s", rows)` writes student grades to logs: PII and academic data in logs; log counts and the course id instead.
4. **Blocking, correctness:** CSV built by string joining: values containing commas, quotes or newlines corrupt the file, and a user name beginning with `=`, `+`, `-` or `@` can become a spreadsheet formula (CSV/formula injection when opened in a spreadsheet). Use the `csv` module with proper quoting and neutralize leading formula characters per team policy.
5. **Blocking, design/API:** `fmt` falls back to `text/plain` for any unknown value; either validate against an enum (422) or drop the parameter. State response headers (`Content-Disposition`) for download.
6. **Suggestion, performance:** loads all rows into memory; for large courses use streaming (`StreamingResponse`) and select only needed columns; ask the expected row count.
7. **Suggestion, data:** `SELECT user, grade`: `user` is a reserved word in PostgreSQL (SQL keywords appendix) and needs quoting there; check your own engine's keyword list; also exports a user identifier: confirm which identifier is appropriate to export.
8. **Question, tests:** which tests cover forbidden access, empty course, and special characters? There are none in the diff.
9. **Nit:** handler named `export` shadows nothing here but is vague; prefer `export_grades`. Sync handler with blocking DB call is fine in FastAPI (runs in a threadpool) but state the intent (2.6).

Marking: authorization and injection both found as blocking (critical for the gate), log-PII found, CSV quoting found, labels used consistently, reasons given for each.

## Section 9 project: reference approach and marking notes

Reference workflow:

1. **Baseline**: run with 200 inputs from a grid and write the table to `characterization.json`; read the diff when you change anything.
2. **Hidden inputs inventory**: clock, env/config globals, files, DB, randomness, locale. For each, record technique and rejected alternative (for example parameterize rather than monkeypatch because it survives refactors; monkeypatch only as a first scaffold).
3. **Commits**: (1) tests only; (2) seams only; (3) extract functions; (4) rename for domain terms; (5) remove duplication. Each commit message states "no behavior change" and the suite result.
4. **Properties**: pick invariants with an oracle where possible (a slow reference implementation of one rule).
5. **Mutation**: list 10 mutants by hand (`>=` to `>`, `+` to `-`, delete a branch, swap rule order, change a constant, drop a `not`, off-by-one range, swap argument order, return early, replace `and` with `or`); record killed/total honestly; equivalents are excluded only with an explanation.
6. **Mid-way change**: measure effect, for example "files changed 1, lines changed 6, tests changed 3, versus estimated 4 files before refactoring". If you did not estimate beforehand, say so; do not invent the "before".
7. **Review and debt**: DEBT.md columns: item, interest (changes per quarter from `git log`), risk, fix cost, decision. "Do not fix" examples: a stable, ugly module untouched for years; style inconsistency in a file scheduled for removal; a micro-optimization with no measured impact.

Marking notes: deduct heavily for any characterization value that looks reasoned rather than observed (round numbers where the code would produce floating residue). Award full points for the injected-regression demonstration only with the failing output pasted. For PHP projects, the seam may be extract-and-override as in section 4, but credit those who move on to an injected clock interface afterward. A mutation kill rate of 100% with only 3 mutants earns little; the count and diversity matter more. Alternative approaches worth crediting: approval-testing tools (for example `approvaltests` for Python; availability varies per language), snapshot tests with strict review, and recording real production inputs (only if anonymized and permitted).
