# Solutions: Lesson 3.4 (Forms, Output, Strings, Database API)

Moodle docs basis: main/5.3 as read 2026-10-26. `VERIFY:` items from the lesson still apply. Use this only after attempting.

## Retrieval practice answers

1. Order: bootstrap (`config.php`), `require_login`, `require_capability` (in the object's own context), clean input (`required_param`/`optional_param`/moodleform), act (DB), then set `$PAGE` and output. Strictly `$PAGE->set_url()` must precede output; skipping it gives a developer-mode debugging notice and breaks things that depend on the URL (navigation, form action defaults, redirects back).
2. `get_data()` returns the cleaned data object on a valid submission. It returns `null` when (a) the form was not submitted, (b) validation (client-independent server rules and `validation()`) failed, (c) the sesskey or form-identity check failed. Also `null` after cancel (check `is_cancelled()` first).
3. Course id `PARAM_INT`; title `PARAM_TEXT`; status key `PARAM_ALPHANUMEXT`; CSV of ids `PARAM_SEQUENCE` is the traditional one (`VERIFY:` in moodlelib) or `PARAM_RAW` then explode and cast each to int; URL `PARAM_URL`; confirm flag `PARAM_BOOL`; editor rich text `PARAM_CLEANHTML` (or `PARAM_RAW` with `format_text` on output and capability-gated trust; editors normally produce an array with `text`/`format`).
4. Cleaning transforms the raw value into the declared type. Validation decides whether the value is acceptable for your business rules. `PARAM_INT` of `99999` is clean but invalid if no such item exists; `PARAM_URL` returning `https://example.org` is clean but may be invalid if your rule bans the host.
5. Result array is keyed by `status`, so 50 rows collapse to 2 entries (last row per status wins). Silent data loss. Fix: select a unique column first.
6. `LIMIT` syntax differs between engines (and is absent in some). Use `$limitfrom`/`$limitnum` on `get_records_sql` and friends.
7. `{{{title}}}` outputs unescaped HTML; `{{title}}` escapes. A value may be placed in triple braces only if it has already been made safe HTML by a sanctioned function (`format_string`, `format_text`) and you know it is not escaped twice.
8. Delegated transactions nest. The real commit occurs when the outermost delegate calls `allow_commit()`. If the inner function calls `rollback()`, the whole transaction is rolled back and the outer `allow_commit()` cannot commit; Moodle throws (the exception is rethrown) and the outer cannot swallow it safely.
9. A fresh install executes only install.xml; it never runs old upgrade steps. Sites on older versions run only the upgrade steps. If you only add the upgrade step, new installs lack the column; if you only change install.xml, upgraded sites lack it. Both must agree.
10. The comparison of `$existing->courseid` to the trusted `$courseid` (plus capability evaluated in that course's context) prevents the edit. The bug class is insecure direct object reference (IDOR), a broken access control.
11. SQLi: `$DB` placeholders/conditions arrays. Stored XSS: output escaping (`{{ }}`, `s()`, `format_string`, `format_text`) with input cleaning. CSRF: sesskey (moodleform automatic; `require_sesskey()`/`confirm_sesskey()` otherwise), state changes via POST.
12. `PARAM_RAW` removes input cleaning and `{{{ }}}` removes output escaping, so both layers vanish: stored XSS with no defence.

## Challenge reference approach: `local_shortlinks`

Schema (install.xml): table `local_shortlinks_link` with fields `id, courseid, code (char 20), target (char 1333), hits (int default 0), description (char 255 null; added later by upgrade, not in the first install version), timecreated`; keys primary and foreign to `course`; unique index on `(courseid, code)`.

Design:
- `classes/local/repository.php`: `get_by_code(int $courseid, string $code): ?stdClass` using `$DB->get_record('local_shortlinks_link', [...], '*', IGNORE_MISSING)` converted to null; `create()`; `delete()`; `hit(int $id)` which runs `$DB->execute('UPDATE {local_shortlinks_link} SET hits = hits + 1 WHERE id = :id', ['id' => $id])`.
- Atomic increment: a read-modify-write (`get_record` then `update_record` with `hits + 1` computed in PHP) loses updates under concurrency; one SQL UPDATE is atomic per row on every supported engine.
- Form: `code` `PARAM_ALPHANUMEXT` with `addRule('code', ..., 'rangelength', [3, 20], 'client')` AND server checks in `validation()` for length and uniqueness; `target` `PARAM_URL` plus scheme whitelist.
- Race: two simultaneous creates both pass the `validation()` uniqueness check; the unique index makes the second insert throw `dml_write_exception`. Catch `\dml_write_exception` around `insert_record` and re-display with an error on `code` (or `redirect` with a notification). Alternative: lock with the Lock API (`\core\lock\lock_config::get_lock_factory(...)`, `VERIFY:`), heavier and unnecessary here.
- `manage.php`: `require_login($course)`, `require_capability('local/shortlinks:manage')`, moodleform, list via `named_templatable`, delete via `$OUTPUT->confirm` and `require_sesskey()`.
- `go.php`: `require_login($course)`; capability `local/shortlinks:use` or simply course enrolment via `require_login` (document the choice); `repository::get_by_code`; if null `throw new moodle_exception('unknownlink', 'local_shortlinks')`; `hit()`; `redirect($target)`. `redirect()` with an external URL: acceptable because the target was validated as http/https at write time; mention open-redirect risk: teachers choose targets, so it is an accepted risk; if students could create links it would not be acceptable.
- Upgrade: step guarded with `field_exists`, `XMLDB_TYPE_CHAR`, precision 255, `notnull` null, then savepoint; version bump; install.xml final schema includes `description`.

Trade-off and alternative: store `hits` in a separate table to avoid row contention on hot links; unnecessary at this scale. Alternative to the repository class: static functions in `locallib.php` (the older Moodle idiom). Both acceptable; follow the codebase.

Scoring: security 30% (placeholders, sesskey, IDOR, scheme whitelist, escaping), correctness 30% (atomic increment, race handling, upgrade), API usage 25%, tests/evidence 15%.

Rubric scoring notes (100): CRUD behaviour 30 (3 points per A1-A10); security 25 (5 each: cleaning, escaping once, sesskey, capability, IDOR); DB design 15 (placeholders 5, portability 5, upgrade 5); output API 10; code quality 10; notes 10. Alternative designs worth discussing: (1) a single `edit.php` handling delete via a second moodleform with a hidden `delete` field (fewer files, more branching); (2) AJAX delete via an external function (needs 3.5); (3) storing note as HTML with an editor element (needs `format_text`, a `notes_format` column, and file handling for embedded images; more complexity than the requirement justifies).

Extension challenge reference: add `sortorder` (int, default 0) with an index on `(courseid, sortorder)`. Back-fill in the upgrade with one SQL statement per course using a window function is not portable across all supported engines (`VERIFY:`); portable approach: for each course (outer loop over distinct `courseid`, bounded), fetch ids ordered by `timecreated, id` with `get_fieldset_select` (`VERIFY:`), then `set_field` per row inside a delegated transaction per course; accept the loop in an upgrade step because it runs once; for very large tables queue an adhoc task. "Move up/down" swaps `sortorder` of two adjacent rows inside a transaction; concurrent reorders: row-level lock via `SELECT ... FOR UPDATE` is not portably available through `$DB`, so use optimistic check (update only if `timemodified` unchanged, retry once) or serialise through the Lock API. Unique index `(courseid, title)`: MySQL/MariaDB default collations are case-insensitive, PostgreSQL's are case-sensitive, so a unique index and `sql_equal(..., false)` behave differently; to be portable keep a normalised lowercase column or accept the check in code plus the index as a backstop and document the difference.

## Engineering review: model answers

- Why a repository class: one reviewable place for SQL, unit testable, keeps page scripts thin; counter-argument: unnecessary layering for tiny plugins, follow local conventions.
- Why validate in `validation()` and in the database: the first gives users field-level messages; the second is the only guarantee under concurrency.
- `named_templatable` over `templatable`: the docs describe `templatable` as not recommended and the name is explicit rather than guessed from the class name.
- Delete in two tabs: the second submission loads `repository::get` with `MUST_EXIST` and throws `dml_missing_record_exception`; a friendlier handler would catch it and show "already deleted". Both are defensible; unhandled is acceptable in an admin tool, not in a student-facing page.
- Client-side rules are bypassed by any HTTP client.
