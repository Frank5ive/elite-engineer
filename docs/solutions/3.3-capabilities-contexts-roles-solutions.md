## Section 7 Retrieval practice: answers

1. `CONTEXT_SYSTEM` 10, `CONTEXT_USER` 30, `CONTEXT_COURSECAT` 40, `CONTEXT_COURSE` 50, `CONTEXT_MODULE` 70, `CONTEXT_BLOCK` 80. `context_module::instance($cm->id)` (course module id, not the activity instance id).
2. Assignment: user X has role R in context C. Override: role R's permission for capability K is changed within context C (and below). Both are DB data; definitions of roles are global.
3. Resolution walks system -> category -> course, later non-inherit values replace earlier: Allow, Prevent, Allow gives Allow. With a Prohibit at category, the result is denied; Prohibit cannot be overridden in lower contexts.
4. Site administrators pass (`$doanything` default true), and the capability may be granted through `user`/`guest`/`frontpage` archetype roles or at a higher context, which are not enrolment roles.
5. It checks course access: hidden course/activity, availability restrictions, enrolment or `moodle/course:view`, and logs access; bare `require_login()` only checks that someone is logged in.
6. It guarantees an integer, not permission. Need: load the object, derive the context, `require_login($course, ...)`, `require_capability` in that context.
7. Course id `PARAM_INT`; flag `PARAM_BOOL`; action name `PARAM_ALPHANUMEXT`; display text `PARAM_TEXT`; local URL `PARAM_LOCALURL`. `PARAM_RAW` means no cleaning; the caller owns validation and escaping.
8. `require_sesskey();` before the change, and the form/POST so the key is not in the URL (docs warn about Referer and screenshots).
9. Any six from table 3.7, each with a test: cross-course IDOR (teacher of A requests B's object), direct URL (call the handler without UI), bare `require_login` (unenrolled logged-in user), user-id parameter (student asks for other's data), missing sesskey (call without key), `is_enrolled` for write (enrolled student without the capability).
10. Role/admin checks ignore capabilities and overrides; teachers cannot use the feature and custom roles break.
11. `is_enrolled(..., '', true)`: participation with an active enrolment. `has_capability`: permission through roles. Enrolled student without a write capability: first true, second false. Category manager with a category-level role, not enrolled: second true, first false.
12. Without a positive case "everything denied" passes all negatives; admins pass every check so cannot demonstrate denial.

## Section 8 Independent challenge: reference

`classes/access.php`:

```php
<?php
namespace local_gradeflags;

final class access {
    public static function require_can_view(int $flagid): \stdClass {
        global $DB, $USER;
        $flag = $DB->get_record('local_gradeflags', ['id' => $flagid], '*', MUST_EXIST);
        $context = \context_course::instance($flag->courseid);
        if (has_capability('local/gradeflags:viewany', $context)) {
            return $flag;
        }
        if ((int) $flag->userid === (int) $USER->id && has_capability('local/gradeflags:viewown', $context)) {
            return $flag;
        }
        // Throw the standard exception so callers and tests share one failure mode.
        require_capability('local/gradeflags:viewany', $context);
        return $flag; // unreachable unless a race changes permissions
    }
}
```

Design notes: the final `require_capability` produces the standard `required_capability_exception` for all denial cases. Alternative: throw your own exception type; the trade-off is that Moodle's error handling and tests expect the standard class. The `(int)` casts matter because Moodle DB fields often arrive as strings; a loose `==` would also work for ids but the lesson's rule is explicit conversion plus `===`.

`remove.php` follows section 4.3: params `id` (`PARAM_INT`), POST check or form, `require_sesskey()`, then `delete_records('local_gradeflags', ['id' => $flag->id])` after `access::require_can_view` and a `viewany`-type delete capability decision (document it).

Tests (use generator users and role-shortname enrolment: `enrol_user($userid, $courseid, $roleidorshortname = null, ...)` accepts a shortname, checked): six tests listed in the challenge. The "viewown overridden to Prevent" test needs `assign_capability('local/gradeflags:viewown', CAP_PREVENT, $studentroleid, $coursecontext->id, true)`; role id from `$DB->get_field('role', 'id', ['shortname' => 'student'])`.

Mutation notes: remove the `userid` comparison and the "student another student's flag" test must fail; remove the course derivation (use system context) and "teacher other course" must fail; remove `viewown` check and the Prevent test must fail.

Scoring (20): correct derived context 4; own vs any logic 4; page/action hardening 4; six tests 6; mutation explanation 2.

## Section 9 Project: reference approach

- **Capability table (SECURITY.md).** `view` (course, read, editingteacher+manager, `RISK_PERSONAL`), `add` (course, write), `delete` (course, write; own notes, enforced by comparing `userid`), `deleteany` (course, write, `RISK_DATALOSS`; manager). Document default archetypes and that admins may change them.
- **Entry-point table.** For `view.php`, `index.php?courseid`, `add.php` (form), `delete.php`, external function stub: parameters and types, object loaded, context derivation, login call, capability, sesskey/form. Every row must say where the context comes from.
- **List query.** `index.php?courseid=N`: `require_login($course)`, `require_capability('...:view', context_course::instance($course->id))` once, then `$DB->get_records('local_coursenotes', ['courseid' => $course->id], 'timecreated DESC')`. Never accept a "list all notes" query across courses without filtering by accessible courses: use `enrol_get_my_courses` or role-based course lists and `get_in_or_equal` (verified signature) then verify per course.
- **Category-manager change.** Assigning a role at the category context makes `has_capability` true in all courses beneath it (context inheritance), so no code change is needed if each check derives the course context from the note; this is the test that demonstrates the design is right.
- **Test matrix (14+).** Rows: teacher A, teacher B, student A, manager (category), unenrolled user, guest. Columns: view own-course note, view other-course note, add, delete own, delete other's, deleteany. Plus: Prevent override in course, Prohibit at system, suspended enrolment, missing sesskey, nonexistent id (`dml_missing_record_exception` for MUST_EXIST: class exists in `public/lib/dmllib.php` and `get_record` rethrows it, checked).
- **Threat model.** STRIDE-lite table: Spoofing (session/login), Tampering (CSRF), Information disclosure (IDOR, error messages, list queries), Elevation (wrong context, role changes). One mitigation per row and the test name that proves it.
- **Defect-review rubric.** For a seeded plugin: expect findings for wrong context, missing sesskey, GET state change, `PARAM_RAW`, bare `require_login`, `userid` trust, `is_siteadmin` model, capability not versioned. Each finding: file/line, impact, safe reproduction on a local instance, fix. Deduct for exploit sketches against any live system (not permitted).

Extension (external function): `db/services.php` entry (`classname`, `description`, `type`, `ajax`; structure verified), class extending `\core_external\external_api` with `execute_parameters`, `execute`, `execute_returns`, calling `validate_parameters`, loading the note, `$context = \context_course::instance(...)`, `self::validate_context($context)`, then `require_capability`. Do not call `require_login()` inside (verified warning).
