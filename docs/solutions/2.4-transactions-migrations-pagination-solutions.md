## Section 7: Retrieval practice answers

1. Atomicity: all of a transaction's changes become visible together or not at all. Durability: once commit returns, the data survives a crash. Consistency (constraints hold at commit) depends on you declaring the rules: PK, FK, unique, check, and any business invariant expressed as one of them.
2. T1 reads qty=10. T2 reads qty=10. T1 writes 9 and commits. T2 writes 9 (computed from its stale read) and commits. Two sales, one decrement. Only possible when the new value is computed in the application from an earlier read.
3. Alice and Bob each read "2 doctors on duty", each sets own `on_duty=false` (different rows), both commit, zero on duty. REPEATABLE READ in PostgreSQL is snapshot isolation: each saw a consistent snapshot, and their writes touch different rows so no write-write conflict is detected. SERIALIZABLE (SSI) detects the read/write dependency cycle and aborts one with SQLSTATE 40001 (observed). Alternatives: lock a shared parent row, or `SELECT ... FOR UPDATE` on the rows read.
4. Enough when the whole rule is expressible in one statement on one row (decrement if positive); check `rowcount`. Need `FOR UPDATE` (or version/serializable) when you must read, run application logic, then write, or the invariant spans several rows.
5. It locks matching rows and skips rows already locked by others instead of waiting. Used for work queues: many workers each claim different jobs without blocking each other (Lesson 2.6).
6. Circular wait; PostgreSQL detects it after `deadlock_timeout` and aborts one transaction with `DeadlockDetected`, SQLSTATE 40P01 (observed: A aborted, B ok; which one is not guaranteed). Fix: lock in a consistent order (ascending id), keep transactions short, retry the victim.
7. The session begins a transaction (autobegin) and the flush sends INSERT inside it, but nothing commits. When the `with Session` block exits, the session closes and the transaction is rolled back: data is not persisted. Use `with s.begin():` or call `s.commit()`.
8. The client sees 200 (response already sent); the failure is only server-side (observed). Change: `Depends(get_session, scope="function")` so exit code runs before sending (observed 500), or commit explicitly in the path function.
9. It diffs models against the live DB, so it cannot know intent: renames look like drop+add (data loss); server defaults, some type/constraint changes are missed; against a DB with other tables it proposes dropping them (observed); no batching, no lock awareness.
10. Release N: add nullable column (expand) and deploy code that writes both. Between releases: run batched backfill, verify zero NULLs, confirm no old-version instances remain. Release N+1: code reads only new column. Release N+2 (or later migration): `SET NOT NULL` (check lock/validation behaviour; the `CHECK ... NOT VALID` then `VALIDATE` pattern is an option; VERIFY), then drop old column.
11. Without a unique tiebreaker, rows sharing the same `submitted_at` have undefined relative order and `(ts) < last_ts` skips the ties not yet seen. `(submitted_at, id)` is total. Index `(submitted_at DESC, id DESC)` (observed Index Only Scan, no sort).
12. No random access/"page 37 of 200"; no cheap total count; fixed sort needs matching index per sort option; clients that need arbitrary sorting and filtering across columns; small stable tables do not benefit.

## Section 8: Challenge reference

The reference module (run: `DATABASE_URL=... python seats.py`) printed `unordered deadlocks over 20 runs: 238` and `ordered deadlocks over 20 runs: 0`, with the ownership invariants asserted on every run.

```python
"""Reference solution, Lesson 2.4 challenge. SQLAlchemy 2.x + PostgreSQL."""
import os, random, threading, time
from sqlalchemy import String, create_engine, select, text
from sqlalchemy.exc import OperationalError
from sqlalchemy.orm import DeclarativeBase, Mapped, Session, mapped_column, sessionmaker

engine = create_engine(os.environ["DATABASE_URL"], pool_size=30)
SessionLocal = sessionmaker(engine)


class Base(DeclarativeBase):
    pass


class Seat(Base):
    __tablename__ = "seat"
    id: Mapped[int] = mapped_column(primary_key=True)
    taken_by: Mapped[str | None] = mapped_column(String(50), nullable=True)


class SeatTaken(Exception):
    def __init__(self, seat_id: int) -> None:
        self.seat_id = seat_id


def reset(n: int = 10) -> None:
    Base.metadata.drop_all(engine); Base.metadata.create_all(engine)
    with SessionLocal() as s, s.begin():
        s.add_all(Seat(id=i) for i in range(1, n + 1))


def book_seats(user: str, seat_ids: list[int], ordered: bool = True) -> list[int]:
    ids = sorted(set(seat_ids)) if ordered else list(dict.fromkeys(seat_ids))
    with SessionLocal() as s, s.begin():
        for sid in ids:                                   # one lock per statement, in this order
            seat = s.scalar(select(Seat).where(Seat.id == sid).with_for_update())
            if seat is None or seat.taken_by is not None:
                raise SeatTaken(sid)                      # context manager rolls back everything
            time.sleep(0.002)                             # widen the window for the lab
            seat.taken_by = user
    return ids


def book_seats_single_update(user: str, seat_ids: list[int]) -> list[int]:
    ids = sorted(set(seat_ids))
    with SessionLocal() as s, s.begin():
        res = s.execute(text("UPDATE seat SET taken_by=:u WHERE id = ANY(:ids) AND taken_by IS NULL"),
                        {"u": user, "ids": ids})
        if res.rowcount != len(ids):
            raise SeatTaken(-1)                           # rollback releases the partial updates
    return ids


def with_retry(fn, *args, attempts: int = 5, **kw):
    for i in range(attempts):
        try:
            return fn(*args, **kw)
        except OperationalError as e:
            code = getattr(e.orig, "sqlstate", None)
            if code not in ("40001", "40P01") or i == attempts - 1:
                raise
            time.sleep(random.uniform(0, 0.02 * 2 ** i))   # exponential backoff with full jitter


def hammer(ordered: bool, retry: bool) -> tuple[int, int, list[tuple[str, list[int]]]]:
    reset(10); wins, deadlocks, lock = [], 0, threading.Lock()
    bar = threading.Barrier(20)

    def worker(i: int) -> None:
        nonlocal deadlocks
        ids = random.sample(range(1, 11), 4)
        if i % 2: ids.sort(reverse=True)
        bar.wait()
        try:
            r = with_retry(book_seats, f"u{i}", ids, ordered=ordered) if retry else book_seats(f"u{i}", ids, ordered=ordered)
            with lock: wins.append((f"u{i}", r))
        except SeatTaken:
            pass
        except OperationalError as e:
            if getattr(e.orig, "sqlstate", None) == "40P01":
                with lock: deadlocks += 1
    ts = [threading.Thread(target=worker, args=(i,)) for i in range(20)]
    [t.start() for t in ts]; [t.join() for t in ts]
    return len(wins), deadlocks, wins


if __name__ == "__main__":
    dl_unordered = sum(hammer(False, False)[1] for _ in range(20))
    print("unordered deadlocks over 20 runs:", dl_unordered)
    total_dl = 0
    for _ in range(20):
        n, dl, wins = hammer(True, False); total_dl += dl
        with SessionLocal() as s:
            owned = {r.id: r.taken_by for r in s.scalars(select(Seat)) if r.taken_by}
        assert all(owned[x] == u for u, ids in wins for x in ids)
        assert len(owned) == sum(len(ids) for _, ids in wins)
    print("ordered deadlocks over 20 runs:", total_dl)
```

Notes. (1) The ordered version sorts ids so all transactions acquire row locks in the same global order; inconsistent order is what created cycles (half the threads requested descending order, as the task required). (2) `book_seats_single_update` is one statement; Postgres locks rows as it updates them, and on `rowcount` mismatch the rollback undoes partial updates. It is not immune to deadlock if two statements touch the same rows in different internal order, so the sorted `ANY` list is not a strict guarantee of lock order (the planner decides); this is why the explicit loop is the one to trust when ordering matters. VERIFY by testing before depending on it. (3) The retry wrapper retries the whole call, only for 40001/40P01, with exponential backoff and full jitter, bounded at 5. `sqlstate` on the psycopg 3 exception is accessed through `e.orig.sqlstate`; VERIFY attribute names on other drivers. (4) The test's pass condition checks both invariants: no seat has two owners (structurally impossible with one `taken_by` column, so the stronger check is that every seat of a successful booking is owned by that user) and no partial bookings (owned seat count equals the sum of successful bookings' sizes).

Alternative: a `booking_seat(seat_id PRIMARY KEY, booking_id)` table and attempting to insert all rows in one transaction, catching `IntegrityError`; the database constraint is the arbiter, and no explicit locks are needed, though a unique violation also waits on a concurrent uncommitted insert of the same key (and deadlocks are still possible with multi-row inserts in different orders).

Scoring: 30 ordering and deadlock evidence, 25 invariants asserted, 20 retry wrapper with fault injection test, 15 single-update variant with honest caveat, 10 determinism over 20 runs.

## Section 9: Project reference approach

**Mechanisms** (DECISIONS.md model): single seat: unique `bookings(seat_id)`; multi-seat: ordered `FOR UPDATE` then insert, with the unique constraint as backstop; per-event cap of 100: lock the event row (`SELECT ... FROM event WHERE id=:e FOR UPDATE`), count, insert (serializes bookings per event: simple, contention is bounded by one event), alternative SERIALIZABLE + retry which avoids a hot lock but needs retry handling and may abort unrelated work. Mid-way "max 4 seats per user per event": same event-row lock covers it; a finer-grained alternative is a `(event_id, user)` quota row locked `FOR UPDATE` (upsert it first), or a counter column with `CHECK (n <= 4)` updated atomically (`UPDATE quota SET n = n + :k WHERE ... AND n + :k <= 4`), which is the cheapest and needs no explicit lock.

**Migration set for the split of `customer_name`**:

- 0004 expand: `ADD COLUMN first_name text NULL, ADD COLUMN last_name text NULL`. Compatible with old app (ignores) and new.
- App release A: writes `customer_name`, `first_name`, `last_name`; reads new columns falling back to splitting `customer_name` when NULL.
- Backfill script (outside the migration transaction): keyset loop `WHERE id > :last AND first_name IS NULL ORDER BY id LIMIT :n`, one commit per batch, idempotent so safe to kill and rerun; re-run after the last old-version instance is gone, because old instances can insert rows with only `customer_name` during the rollout (the listed edge case).
- Verification: `SELECT count(*) FROM bookings WHERE first_name IS NULL` must be 0.
- 0005 contract part 1 (release B, code no longer reads/writes `customer_name`): `SET NOT NULL` on the new columns after verifying; check lock behaviour for your version (VERIFY).
- 0006 contract part 2 (later release): drop `customer_name`. Downgrade for this step cannot restore data unless you keep a backup; document roll-forward as the plan.

**MIGRATIONS.md** entries must cite lock modes from the PostgreSQL docs for each statement; reject entries saying "should be fast" without a source or a measurement on a copy.

**Keyset test**: fetch page 1, insert 100 newer rows, fetch pages 2..n; assert no duplicate ids and that every row existing at the time of page 1 is seen exactly once (new rows are not seen, which is correct for a descending feed).

**Measurement**: expected conclusion shape (do not copy numbers): offset time and buffers grow with depth, keyset stays roughly flat; report both cold and warm, and include `Rows Removed`/buffer counts rather than only times. Candidates lose points for stating a ratio they did not measure.

**Rubric notes**: concurrency tests count only if they fail on the naive branch (demand the commit hash or transcript). Critical: backfill as one `UPDATE` over the whole table; contract and code change in one release; no tiebreaker in the cursor.
