# Solutions: Lesson 3.6 (PHPUnit, Behat, Style, Upgrades, Release)

Docs basis: main/5.3 as read 2026-10-26. PHPUnit versions per docs: 11.4 on Moodle 5.0, 9.6 on 4.4-4.5; the 5.3 `composer.lock` pins 11.5.x. Names checked against the Moodle 5.3 source and moodle-plugin-ci docs; any `VERIFY:` left in the lesson is still open.

## Retrieval practice answers

1. `resetAfterTest()` tells the framework to roll back/reset database and global state changes after this test; without it, a test that modifies the DB fails with an "unexpected database modification" warning. Call it before the first data change in tests that change data. Not in `setUp()` because the docs ban that: it applies reset to all tests, including those that do not need it, and hides which tests mutate state.
2. `basic_testcase`: no DB, no filesystem, no globals, fastest, pure logic. `advanced_testcase`: database and global reset, generators, `setUser`, sinks, event/message redirects, config helpers. Also `advanced_testcase` requires an initialised PHPUnit environment (init script); `basic_testcase` tests that touch nothing are cheaper to run.
3. `tests/generator/lib.php`; class extends `\component_generator_base`; obtained with `$this->getDataGenerator()->get_plugin_generator('local_readinglist')`. For activities, extend `testing_module_generator` (documented).
4. It points tests at differently-prefixed tables and a separate dataroot so they cannot clobber real data (the docs also allow a separate database). Never use the production prefix.
5. After upgrading Moodle, installing or uninstalling plugins, and adding new test files (documented).
6. Data providers run before the test database is reset/initialised; records created there would be wrong or reset. They must only return plain data; create records in the test body (documented).
7. (a) PHPUnit: capability/visibility logic, no browser needed. (b) Behat: a user-visible dialog interaction, likely needs JavaScript. (c) PHPUnit: query behaviour. (d) PHPUnit: event sink or observer effect.
8. Any five of: 4-space indent; braces same line; `else if` not `elseif`; short arrays; single-quoted strings; namespaces with component first; type hints on new code; complete docblocks; `defined('MOODLE_INTERNAL') || die();` for non-class scripts; `moodle_exception` not `print_error`; `#[\Override]`. Moodle-specific emphasis beyond raw PSR-12: component-prefixed namespaces and constants, mandatory docblocks (with `@inheritdoc` forbidden as a replacement), complete language strings, MDL references on TODOs, 132 character line target.
9. The savepoints check finds upgrade steps without `upgrade_plugin_savepoint` (or with a wrong version). Without a savepoint an interrupted upgrade cannot resume correctly and Moodle will repeat or skip steps. (The moodle-plugin-ci command is `savepoints`, per its `docs/CLI.md`.)
10. A fresh install runs install.xml only, never the upgrade steps; so a broken or duplicate upgrade step is invisible unless you test an upgrade from an older version.
11. Sites that already ran that version skip the edited step (version is recorded), so they never get the change, while new sites do: schema drift. Always add a new step with a new version.
12. `@error_reporting(E_ALL); @ini_set('display_errors', '1'); $CFG->debug = (E_ALL); $CFG->debugdisplay = 1;` (matches `config-dist.php` on 5.3; `DEBUG_DEVELOPER` is `E_ALL`). In production it discloses paths, SQL, stack traces and slows pages; set them only on dev/staging.
13. `$plugin->incompatible` is the first core branch the plugin does not support; installation on that branch or later is blocked (documented, since 3.9).
14. Reproduce or capture the exact URL and time; check the web server/PHP error log; enable developer debugging on a staging copy (not production); read the error; identify the entry script and plugin; add logging or step-debug; hypothesise and test; fix; add a regression test; record in the failure log.

## Failure laboratory notes

Scoring: 2 points per flaw explained (10), plus 3 for the upgrade explanation, plus 2 for the diagnosis procedure. Reference fixes: remove `resetAfterTest` from `setUp` and call it per test; create fixtures per test via generators; purge or avoid caches in tests; for time use a tolerance (`assertEqualsWithDelta`, a standard PHPUnit assertion) or a clock mock if verified; guard the upgrade with `field_exists`.

## Challenge reference approach

Seven tests (names state behaviour):

1. `test_capability_matrix`: three users (teacher, student, non-enrolled), assert `has_capability` outcomes for view/manage.
2. `test_edit_denies_item_from_other_course`: item in course B; call the service/edit logic with course A teacher; expect the exception from the object-level check (`moodle_exception` code `invalidrecord`).
3. `test_hostile_title_is_escaped_in_rendered_output`: render the renderable via `$PAGE->get_renderer(...)`/`render()` (needs `$PAGE->set_url` in the test; `VERIFY:`), assert the output contains `&lt;script&gt;` and not `<script>`.
4. `test_delete_emits_exactly_one_event`.
5. `test_cache_invalidated_after_update`.
6. `test_external_list_items_student_ok_nonenrolled_denied`.
7. `test_privacy_export_and_delete_isolated_per_user`.

Red-then-green proof: show the diff of the deliberately broken line, the failing test output (copy lines), then the restored pass.

Generator: as in the lesson, with a `static` counter for unique titles; alternative: accept explicit names from the test (more readable, less magic).

Behat: Background via generator steps; one scenario for the teacher-adds-student-sees journey; tags `@local @local_readinglist`; avoid `@javascript` unless required.

Style: run the checks, fix findings. Typical list for a first run: missing file-level docblock on some class files, `@package` missing, array alignment, trailing whitespace, line length, missing return type, unsorted strings.

Upgrade: provide two evidence logs: from 2.0 to 2.1 normal, and with the column pre-added (guarded step must pass).

Release checklist: use the lesson's list, attach evidence per line.

## Project reference notes: release 2.1

Suggested matrix: two branches you actually tested (for example 4.5 LTS and 5.3) with the PHP versions each supports (per the release notes: 4.5 needs PHP 8.1-8.3, 5.3 needs 8.3-8.4), and one database engine each initially; extend to the second engine as the extension challenge.

Mapping tests to contracts:

| Contract | Test |
|---|---|
| Capabilities | matrix test |
| IDOR denial | edit/delete service tests |
| Hostile input | render test, form validation test via `mock_submit` (documented in forms docs) |
| Events | one per path |
| Cache | read-edit-read |
| Web service | success/denied per role |
| Privacy | provider test case |
| Upgrade | separate script/snapshot flow |
| Search escaping | repository test |
| Duplicate title | repository `title_exists` test with exclude id |
| Task idempotency | execute twice |
| File access | callback test returns false/exception for unrelated user |

Upgrade testing method: create a Moodle site with plugin 1.0 installed, take a DB snapshot (or `mysqldump`/`pg_dump`), copy 2.0 code, upgrade, snapshot again; restore the 1.0 snapshot, copy 2.1 code, upgrade directly (skipping 2.0) to prove steps cover the gap; finally pre-add the column and re-run. The `moodle-plugin-ci` tool does not do this for you; it installs the plugin on a fresh site and runs its checks; it does not run old-to-new upgrade paths (its `install` command and `gha.dist.yml` show a fresh install).

Debugging report template and example outline for an injected "missing invalidation" fault: Symptom: student sees old title for hours. Hypotheses: (H1) browser cache; (H2) DB not updated; (H3) MUC stale. Evidence: DB row correct (H2 rejected); hard refresh unchanged (H1 rejected); purge all caches fixes it (H3 supported). Root cause: update path in the web service did not call `delete($courseid)`. Fix: single service class. Regression test: read-edit-read. Prevention: contract comment listing all write paths; review checklist item. A step-through with Xdebug set a breakpoint on `cache->get` and showed a hit with the old object. Score depends on the evidence chain, not the identity of the fault.

Rubric notes (100): tests 25 (count only tests that you have seen fail); negative/security 10; style 10; CI 10; upgrade 15; metadata and checklist 10; debugging report 15; notes 5. Hard cap 60 for any critical failure.

Extension (PostgreSQL) expectations: case sensitivity in search (use `sql_like` with case-insensitive flag, already portable), ordering ties (add `id` as a tiebreaker), empty string versus NULL handling, `GROUP BY` strictness (all selected columns must be grouped or aggregated), reserved words as column names (`status`, `note`, `url` are fine; check with the XMLDB editor's validation). Report each as: failing test, cause, fix, and whether the fix changed behaviour for MariaDB.

## Engineering review: model answers

- Why Behat once: slow and brittle; cost/benefit says journeys, not logic.
- Why `supported` is conservative: it is a promise; claim only branches in the CI matrix.
- Why a failing upgrade test blocks release: upgrades are irreversible for administrators and run at their worst time (maintenance windows); a defect here has outsized cost.
