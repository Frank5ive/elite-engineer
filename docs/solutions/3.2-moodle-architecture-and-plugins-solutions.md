# Solutions: Lesson 3.2 Moodle Architecture and Plugins

Attempt the lesson first. Verified against Moodle 5.3 docs/source as in the lesson; the one remaining unconfirmed item is the exact in-place "component mismatch" error message: run it in your own checkout.

## Section 6 Failure laboratory: scoring notes

Score each lab 0-3: prediction, mechanism, diagnostic procedure.

- **Lab A (component mismatch).** The directory-derived component is `local_greetings`; `version.php` says `local_greeting`. Moodle reports a plugin problem during the plugin check (the exact in-place message is unverified: run it, do not invent it in your answer; for ZIP installs the validator string is "Plugin name mismatch"). Full marks require the four-way comparison: type prefix + directory, `$plugin->component`, language file name, namespace.
- **Lab B (case).** Case-insensitive filesystem on the laptop, case-sensitive in CI. Expect `git mv Formatter.php formatter.php` (on case-insensitive filesystems use a temporary name) and purging caches. Bonus: Moodle coding style uses lowercase class names, so `formatter` not `Formatter`.
- **Lab C (capability not found).** Capabilities are synced at install/upgrade. Bump version, run upgrade, purge caches. Bonus: mention the `clonepermissionsfrom` option for new capabilities replacing existing ones.
- **Lab D (5.1+ layout).** From 5.1 plugins live under `public/`; a copy placed in `<root>/local/` is outside the web root and not scanned (restructure guide; upgrade docs say to relocate third-party plugins under `public/`). Check `$CFG->dirroot`, `$CFG->root`, and the real directory.

## Section 7 Retrieval practice: answers

1. Course report, so type `report` (directory `/report`): component `report_courseaudit`, directory `report/courseaudit` (under `public/` on 5.1+), language file `lang/en/report_courseaudit.php`, namespace `report_courseaudit\...`. A site-specific report could also be `local_courseaudit`; justify the choice (reports for general reuse use `report`; company-specific use `local`).
2. Required: `version.php` and the language file `lang/en/<component>.php` defining `$string['pluginname']`. (Activity modules name the file after the plugin, not the frankenstyle name.) Neither may contain `require_once` or other includes.
3. Problems: undocumented (no version history), not reproducible on other environments, bypasses `upgrade.php`/`install.xml` so fresh installs lack the table. Correct: add the table in XMLDB editor to `install.xml`, add an upgrade step with savepoint, bump version, run the upgrade CLI.
4. Scan plugins, compare file version to stored; if greater run `xmldb_<name>_upgrade($oldversion)`, resync access/tasks/events/services/hooks, store the new version; for a new plugin run install. A lower file version is refused as a downgrade (checked: `downgrade_exception` / `cannotdowngrade` "Cannot downgrade {$a->plugin} from {$a->oldversion} to {$a->newversion}." in `public/lib/upgradelib.php` and `public/lang/en/debug.php`).
5. `classes/task/purge.php`. `\local_greetings\output\main` is `classes/output/main.php`.
6. Capabilities and tasks are registered into the DB during upgrade; unchanged version means no resync (verified in the docs for both files).
7. Callbacks in `lib.php`, hooks (`db/hooks.php`), event observers (`db/events.php`), web service functions (`db/services.php`), theme overrides, settings. The Hooks API (PSR-14 based) is the documented replacement for one-to-many `lib.php` callbacks.
8. Point the document root at `public/` (Apache `DocumentRoot /srv/moodle/public`; Nginx `root /srv/moodle/public`). `$CFG->root` is read-only and points to the installation root; `wwwroot` and `dirroot` behave as before.
9. Case-sensitive Linux versus case-insensitive macOS/Windows file systems; class `formatter` in `Formatter.php` resolves on one and not the other.
10. `$CFG->phpunit_prefix` and `$CFG->phpunit_dataroot` (a separate prefix and data directory), then run the init script (`php public/admin/tool/phpunit/cli/init.php` on 5.x).
11. Run database queries at include time: it executes on every admin page load and risks failing before the plugin is installed; use lazy-loading setting classes (verified).
12. `has_capability` returns a boolean you branch on (page continues if you forget); `require_capability` throws, aborting the request. Using the former without stopping is a bug (lesson 3.3).

## Section 8 Independent challenge: reference solution (`local_courselist`)

Structure:

```
courselist/
  version.php
  lang/en/local_courselist.php
  db/access.php
  index.php
  classes/lister.php
  classes/privacy/provider.php
  tests/lister_test.php
```

`classes/lister.php`:

```php
<?php
namespace local_courselist;

final class lister {
    /** @return string[] course full names indexed by course id */
    public function names_for_user(): array {
        $out = [];
        foreach (enrol_get_my_courses('fullname') as $course) {   // 'fields': array or comma-separated string (checked)
            $out[$course->id] = format_string($course->fullname);
        }
        return $out;
    }
}
```

Notes: `enrol_get_my_courses` returns courses for the current user; the first argument selects extra fields (array or comma-separated string; the base fields are always included, checked in `public/lib/enrollib.php`). `format_string` is the standard way to display course names (`format_string($string, $striplinks = true, $options = null)`, checked in `public/lib/weblib.php`). The page: `require_login(); $context = context_system::instance(); require_capability('local/courselist:view', $context);` then calls `lister`, prints with `$OUTPUT`. `db/access.php`: `captype read`, `CONTEXT_SYSTEM`, archetype `user => CAP_ALLOW`. Test: `create_user`, `create_course`, `enrol_user`, `setUser`, `assertContains` of the course name from `names_for_user()` (note: `format_string` output may alter the name; use a plain name).

Alternative: query `{enrol}`/`{user_enrolments}` directly with `$DB`. Rejected: duplicates logic core already maintains (visibility, enrolment status), will drift; use the API.

Scoring (20): installs from scratch 5; capability and strings 3; privacy provider 2; logic in class not page 3; test valid and meaningful 4; can explain each file 3.

## Section 9 Project: reference approach (`local_coursenotes`)

1. **Schema.** Use `Site administration -> Development -> XMLDB editor` to create table `local_coursenotes` (id, courseid, userid, note TEXT, timecreated) with keys/indexes (index on `courseid`). Save generates `db/install.xml`. Do not hand-write XML (the exact XMLDB header attributes were not verified in this lesson).
2. **Upgrade steps.** `db/upgrade.php` contains `function xmldb_local_coursenotes_upgrade($oldversion)` with guarded blocks `if ($oldversion < 2026102701) { ...add field timemodified...; upgrade_plugin_savepoint(true, 2026102701, 'local', 'coursenotes'); }` and a second block for `visibility`. The XMLDB editor can generate the field/index code (copy it). Each step is idempotent through `field_exists`/`index_exists` checks (`$dbman = $DB->get_manager(); $dbman->field_exists($table, $field)` / `index_exists($table, $index)`, taking `xmldb_*` objects; checked in `public/lib/ddl/database_manager.php`) so a repeated run is safe. Update `install.xml` to the final schema and keep `version.php` at the last version.
3. **Capabilities.** As in lesson 3.3 section 3.2, contextlevel course. **Task** deleting notes older than a setting (`settings.php` with `admin_setting_configtext`, read with `get_config('local_coursenotes', 'retentiondays')`: `admin_setting_configtext` and `get_config($plugin, $name)` both exist, checked); `execute()` calls `$DB->delete_records_select` (`delete_records_select($table, $select, ?array $params=null)`, checked) with a parameterized cutoff.
4. **Privacy.** `\core_privacy\local\metadata\provider` with `get_metadata(collection $collection): collection` using `$collection->add_database_table(...)` (checked: `add_database_table($name, array $privacyfields, $summary = '')`, fields as fieldname => language-string key; the provider interface is in namespace `core_privacy\local\metadata`). Export/delete are lesson 3.5.
5. **Tests.** One per class: `access`, `retention task` (insert old and new rows, run `execute()`, assert only old rows removed), and an upgrade test is manual: install v1 tag, insert rows, check out final tag, run upgrade, assert rows survive and new column exists.
6. **Mid-way change.** Add `visibility` through a new upgrade step and `install.xml`; both must agree. Record in README which versions exist.
7. **Core clean:** `git -C <core> status --porcelain` empty.

Rubric notes: lose 10 if the schema exists only in `install.xml` or only in `upgrade.php` (critical failure); 5 for hand-edited DB on the dev site; 5 for tests that hit the live DB prefix rather than PHPUnit infrastructure.

The `mod_choice` map (expected content): entry points `index.php`, `view.php`, `report.php`; capabilities in `db/access.php` such as `mod/choice:choose` (course module context) and `mod/choice:addinstance` (course context, `RISK_XSS`); privacy provider implementing metadata, plugin request provider and userlist provider (verified); tests under `tests/`; `lib.php` callbacks; `classes/` autoloaded. Tables: read `db/install.xml` yourself.
