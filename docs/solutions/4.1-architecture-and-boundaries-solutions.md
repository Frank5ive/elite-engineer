## Section 7 retrieval answers

1. Cohesion: parts of a module belong together (same reason to change). Coupling: how much one module must know about another. Low-cohesion signal: methods split into groups that touch disjoint fields, or a `utils` module. Coupling invisible in the import graph: two services reading the same table, or two files that always change together (change coupling), or temporal coupling (A must run before B).
2. Folder-by-technology forces every feature to touch all folders (high cross-folder coupling) and each folder holds unrelated things (low cohesion). Slicing by capability keeps a feature's change local.
3. The application layer owns `OrderRepository`, declared next to the use case in domain vocabulary. So the source dependency points from infrastructure to application (adapter implements the port), the inverse of control flow. If the library owned the interface, the domain would import it.
4. A subclass overrides `add` and `add_all` while the parent's `add_all` calls `self.add`; the override of `add` is re-entered. Changing the parent's `add_all` to `self.items.extend(xs)` changes the count without editing the child.
5. A subtype must not strengthen preconditions or weaken postconditions of its parent/interface. Contract test: write one test class parameterized over adapters (`InMemoryOrders`, `SqlOrders`) asserting the port's behavior (save then get returns equal aggregate; get of unknown raises the documented error). An adapter that fails it violates LSP.
6. `Money`: value object (equality by value, immutable). `Order`: entity (identity) and the aggregate root. `CourseEnrolmentRow` mirroring a table with no rules: neither; it is a data transfer/persistence record. `EmailAddress`: value object (validated, immutable).
7. By-id references keep aggregates small and let each be loaded and saved in one transaction; holding the other object invites loading the whole graph and implies an immediate-consistency expectation across both. Consequence: invariants spanning two aggregates are eventually consistent or need a process/saga.
8. Sequence: commit succeeds, process crashes (or broker is down) before publish; the event is lost and no retry exists. Outbox: write the event row in the same transaction as the state change; a relay later reads unsent rows, publishes, marks sent. New component: the relay (and an outbox table). Semantic: at-least-once (crash after publish, before marking sent, republishes), so consumers must be idempotent.
9. (a) Compatible if consumers use a tolerant reader. (b) Incompatible (old consumers lose the field); use expand/contract. (c) Incompatible and the worst kind: silent meaning change; add `total_minor` instead. (d) Usually incompatible for consumers with exhaustive enum handling; compatible only if the contract says consumers must tolerate unknown values. State this in the contract.
10. Ceremony cases: a thin CRUD endpoint to one table (use the framework's data layer directly); a one-off script (a function); an internal helper with one implementation and no volatility (a plain class or function; add a port when a second implementation or a test need appears).

## 8.1 reference (composition refactor)

```python
from typing import Callable, Protocol

class Notifier:
    def __init__(self): self.sent = []
    def send(self, msg): self.sent.append(msg)
    def send_many(self, msgs):
        for m in msgs: self.send(m)

class RateLimitedSub(Notifier):            # inheritance version: double accounting
    def __init__(self, now: Callable[[], float], gap: float):
        super().__init__(); self.now, self.gap, self.last = now, gap, None; self.waits = 0.0
    def send(self, msg):
        t = self.now()
        if self.last is not None and t - self.last < self.gap: self.waits += self.gap - (t - self.last)
        self.last = t; super().send(msg)
    def send_many(self, msgs):
        self.waits += self.gap * max(len(msgs) - 1, 0)
        super().send_many(msgs)             # super calls self.send -> accounts again

class Sender(Protocol):
    def send(self, msg: str) -> None: ...

class RateLimited:                          # composition version
    def __init__(self, inner: Sender, now: Callable[[], float], gap: float):
        self.inner, self.now, self.gap, self.last, self.waits = inner, now, gap, None, 0.0
    def send(self, msg):
        t = self.now()
        if self.last is not None and t - self.last < self.gap: self.waits += self.gap - (t - self.last)
        self.last = t; self.inner.send(msg)
    def send_many(self, msgs):
        for m in msgs: self.send(m)
```

With a frozen clock (`lambda: 0.0`), gap 1.0 and three messages, the subclass reports 4.0 waits and the composed class 2.0 (verified). The test asserts 2.0 and so fails on the subclass. Trade-off: the composed class re-implements `send_many`; alternative is a `Sender` that only exposes `send` and a free function `send_many(sender, msgs)`, which removes the duplication and the temptation to override. Marking: injected clock (no sleeping) 25%, test fails on subclass and passes on composition 40%, explanation of why 35%.

## 8.2 reference (aggregate with invariants), Python

```python
from __future__ import annotations
from dataclasses import dataclass
from enum import Enum

@dataclass(frozen=True)
class Capacity:
    value: int
    def __post_init__(self):
        if self.value < 1: raise ValueError("capacity >= 1")

class State(Enum):
    PENDING = "pending"; ACTIVE = "active"; WITHDRAWN = "withdrawn"

ALLOWED = {(State.PENDING, State.ACTIVE), (State.ACTIVE, State.WITHDRAWN), (State.PENDING, State.WITHDRAWN)}

class RosterFull(Exception): pass

class CourseRoster:
    def __init__(self, capacity: Capacity):
        self._cap = capacity
        self._entries: dict[str, State] = {}
    def request(self, learner: str) -> None:
        if learner in self._entries and self._entries[learner] is not State.WITHDRAWN:
            raise ValueError("duplicate")
        self._entries[learner] = State.PENDING
    def _active(self) -> int:
        return sum(s is State.ACTIVE for s in self._entries.values())
    def transition(self, learner: str, to: State) -> None:
        cur = self._entries[learner]
        if (cur, to) not in ALLOWED: raise ValueError(f"{cur.value}->{to.value}")
        if to is State.ACTIVE and self._active() >= self._cap.value: raise RosterFull()
        self._entries[learner] = to
    def state(self, learner: str) -> State: return self._entries[learner]
```

Required tests include: capacity 0 rejected; duplicate request rejected; re-request after withdrawal allowed; all six disallowed transitions rejected (parametrize over `State x State` minus `ALLOWED` minus identity); activating beyond capacity raises; withdrawing frees a seat; unknown learner raises `KeyError` (or better a domain error; note the choice). The 13th "test" that mutates `r._entries` is acceptable because Python cannot enforce privacy; the guarantee is the public API, and the test documents that bypassing it is outside the contract.

PHP outline (8.2): `final class Capacity { public function __construct(public readonly int $value) { if ($value < 1) throw new InvalidArgumentException(); } }` and an `enum State: string { case Pending = 'pending'; ... }` with a `canTransitionTo(self $to): bool` method using `match`. `private array $entries` is enforced by the language, so no bypass test is needed. Design alternative: put the capacity check in the database via a counter row with a conditional update; that moves the invariant out of the aggregate and into storage, which is needed under concurrency (an in-memory check cannot stop two processes). Mention this to earn full marks.

## 8.3 reference (fitness test and ADR)

```python
import ast, pathlib

THIRD_PARTY_BLOCKED_IN_DOMAIN = {"sqlalchemy", "fastapi", "requests", "httpx", "pydantic"}
RULES = {"domain": {"application", "infrastructure"},
         "application": {"infrastructure"},
         "infrastructure": set()}

def imported(path: pathlib.Path) -> list[str]:
    out = []
    for node in ast.walk(ast.parse(path.read_text())):
        if isinstance(node, ast.Import):
            out += [a.name for a in node.names]
        elif isinstance(node, ast.ImportFrom) and node.module:
            out.append(node.module)
    return out

def check(root: pathlib.Path) -> list[str]:
    bad = []
    for pkg, banned in RULES.items():
        for f in (root / pkg).rglob("*.py"):
            for name in imported(f):
                parts = name.split(".")
                if parts[0] == "app" and len(parts) > 1 and parts[1] in banned:
                    bad.append(f"{pkg}/{f.name} imports {name}")
                if pkg == "domain" and parts[0] in THIRD_PARTY_BLOCKED_IN_DOMAIN:
                    bad.append(f"domain/{f.name} imports {name}")
    return bad
```

Verified with four temp-directory layouts (one passing, three failing: domain imports infrastructure, domain imports fastapi, application imports infrastructure via `import app.infrastructure.c`). Known gaps to state: relative imports (`from ..infrastructure import x`) are not resolved; dynamic imports are invisible. Note the decision to block `pydantic` in the domain is a judgment (some teams allow it); the reference lists it so you must justify either choice.

ADR-001 skeleton:
- Context: layer rules are only convention; two incidents of ORM imports in domain code in the last quarter (replace with your real evidence or say "assumed").
- Options: (1) convention plus review; (2) a fitness test in CI; (3) a third-party import-checking tool (VERIFY its maintenance and config format); (4) separate packages per layer, so the build enforces it.
- Decision: option 2 for now.
- Consequences: positive: failures are immediate and local; negative: custom code to maintain, blind to dynamic and relative imports, can be bypassed by editing the test; revisit if the layout grows beyond three packages or false negatives appear.
Marking: two genuine alternatives 30%, negative consequences 30%, revisit trigger 20%, brevity and clarity 20%.

## Section 9 project: reference approach and marking notes

Reference structure:

```
src/certs/domain/       model.py (Certificate, value objects, issue rule as pure function), events.py
src/certs/application/  ports.py (Protocols), issue_certificate.py
src/certs/adapters/     sqlite_repo.py (+outbox), http_completion.py, memory.py
src/certs/api/          router.py (FastAPI, Pydantic v2 models)
tests/                  domain/, application/, adapters/ (contract suite), architecture/
```

Key decisions and trade-offs:
- Rule as a pure function `decide(completion, archived, override) -> Decision` (a small sum type: `Issue`, `Refuse(reason)`), so refusals are values and testable exhaustively. Alternative: exceptions for refusal; they are fine for exceptional cases but make "record why refused" awkward.
- Idempotency: `CertificateRepository.add` raises `AlreadyExists` on the UNIQUE constraint violation; the use case catches it and returns the stored certificate. Check-then-insert in code alone fails under concurrency (two requests both see "none"). Test: two threads or two connections attempting the insert.
- Outbox: certificate insert and outbox insert in one SQLite transaction (`with conn:`). Relay: select unsent, publish, then mark sent. Crash test: run the use case, do not run relay, build a new relay over the same database file, assert the event is published exactly once or at least once as designed (state which; at-least-once is the honest answer, with the consumer deduping on event id).
- HTTP adapter: constructor takes `transport: Callable[[str, float], bytes]`; the test asserts the timeout value passed and that a `TimeoutError` becomes `CompletionUnavailable`. Validate the response with a Pydantic model inside the adapter; a malformed body becomes `CompletionUnavailable` or a distinct `BadUpstreamData`, and the choice is documented.
- Mid-way change (second approver): a new field `approvals: frozenset[AdminId]` in `OverrideRequest`; the rule requires two distinct admins. Expected blast radius: `domain/model.py`, `application/issue_certificate.py`, domain tests, and the API model if the approval arrives through the API. If your change touched the SQLite adapter beyond the event payload, explain why (the aggregate probably leaked storage shape). Event payload changes follow the v2 rule: add an optional field, never repurpose one.
- Events: v1 `{"version":1,"learner_id":..,"course_id":..,"issued_at":..}`, v2 adds `override_reason` (optional). The upcaster for v1 adds `override_reason: None`. Tests use stored literal v1 strings.

Rubric scoring notes: award domain points only where tests *attempt violation* (a test that merely constructs a valid object earns half). Ports points require the port to live in the application package and speak domain types; a repository port exposing a `Session` loses most of those points. Outbox points need the crash simulation; a prose-only claim scores at most 5 of 15. Fitness-test points need the demonstrated failure. A project that adds a service layer, a repository for `Money`, and a factory for every class should lose quality points under "ceremony": the extension challenge is where more structure is justified.

Alternative designs worth crediting: (a) single-table design with the certificate and outbox in one SQLAlchemy session using the unit-of-work pattern; (b) using a database-level insert-or-ignore plus returning for idempotency; (c) a modular monolith with `certificates` as one package of a larger app, if a short note explains the module's public API.

PHP appendix acceptance: value objects with `readonly` properties, an `IssuanceRule` class with no Moodle calls (no `$DB`, no `$CFG`), asserts or PHPUnit tests; a paragraph stating where `$DB` access would live (an adapter implementing the repository interface) and that Moodle plugin classes under `classes/` autoload by namespace and file path (VERIFY on moodledev.io for your target version). Deduct for any use of Moodle globals in the rule class.
