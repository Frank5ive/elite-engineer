# Solutions: Lesson 0.4, Communication

Do not read before attempting. Communication has no single correct text; these are reference answers plus the grading logic. Grade yourself by counting checklist items, not by impression.

## Retrieval answers

1. Done (outcome with link), Next (concrete first step), Blocked/risk (specific, who unblocks, since when). "Worked on the API" becomes "Added pagination to GET /orders (PR #230, awaiting review); next: add the limit upper-bound test."
2. So the reader can correct your inference without redoing your investigation, and so a wrong guess does not contaminate the facts. Facts are checkable; inference is yours; the request tells them what to do.
3. Any six of: ask first; context/ticket; exact symptom with copied error; environment/version; reproduction steps; what you tried and results; labelled hypothesis; specific request; urgency/impact; what you do meanwhile and when you check back.
4. Ask now when the answer exists only in someone's head (access, priorities, history of a decision), or when you are blocked on a person or approval, or when the cost of waiting is high (production impact, a shared deadline). Keep investigating when the answer is in the code, docs, or tickets and you have not yet looked.
5. State the plan, why, and a deadline: "I'll do A because ...; tell me by 15:00 if you prefer B." It converts a blocking question into a non-blocking review. Inappropriate for irreversible or high-risk decisions (data deletion, security, public API contracts) or when the person is unreachable and the work cannot be undone.
6. Why, what changed, how verified, risk and rollback, notes for reviewers. Most often missed: verification evidence (and risk).
7. Example: (a) "What is slow: the request, the file generation, or the download, and for what size? Default: request time for 10,000 rows." (b) "Target? Default: under 5 seconds at p95." (c) "Is changing the file format acceptable? Default: no, keep CSV." Credit any three that change design, each with a default.
8. A point hides uncertainty and assumptions, and becomes a commitment. Good: "1-3 days. Assumes no schema change and review within a day. If a schema change is needed, 4-6 days. Medium confidence. Biggest unknown: whether the column exists; a 1-hour spike answers it tomorrow."
9. Example: "Revising ENG-123 from 3 to 6 days. Why: the export path duplicates the calculation (found today). Options: descope export (3 days, follow-up ticket) or keep it (6 days). Your call by tomorrow noon; I'm continuing on the web path meanwhile."
10. Re-read the comment as a question about unclear code or description; verify with code, tests, or a quick experiment; reply with evidence ("I checked: find() can return None, so I added the guard") or a clarifying question; make the change or explain the trade-off; resolve only addressed threads; do not argue about taste against the team's convention.
11. (1) Tell the owners and the channel immediately that it was exposed; (2) ask for rotation or do it if you are authorised; (3) remove the message (this does not undo exposure); (4) check where else it appears (logs, history); (5) write a failure log entry on how it happened. Rotation, not deletion, is the fix.
12. Any three of: where questions go; expected response time; standup format; ticket workflow; PR size and review norms; escalation; availability and time zones.

## Failure laboratory scoring

Credit one point per valid defect found (maximum 10), plus 3 for naming the credential exposure as the most serious, 2 for the "offline immediately" problem, and 2 for a correct action order beginning with fact-gathering and the incident route. The sample answer is in the lesson's Reveal.

## Challenge reference answers (Section 8)

**1. Blocker message (about 140 words):**

```
Ask: How do you run PostgreSQL locally when a native one already uses 5432? (ENG-123 setup)
Symptom: `docker compose up` -> "Bind for 0.0.0.0:5432 failed: port is already allocated".
Env: main @ a1b2c3d, Ubuntu 24.04, Docker per README, native PostgreSQL 16 installed.
Tried: `sudo ss -ltnp | grep 5432` shows my native postgres on 5432; README does not mention this case.
Hypothesis: compose should map a different host port or I should stop the native service. Which is expected here?
Impact: not blocked for unit tests (41/41 pass); integration tests need the DB.
Meanwhile I'll try mapping the container to 5433 in a local override file (not committed) and will report which worked by 15:00.
```

Checklist count: ask first (1), context (2), exact symptom (3), env (4), reproduction (the command, 5), tried (6), hypothesis (7), specific request (8), impact (9), meanwhile and time (10). Note the choice to avoid `sudo` suggestions to others and the uncommitted local override, which respects the team's compose file.

**2. PR description:** use the structure in Section 4.4. Common errors to look for: verification described as "tested locally" with no command or count; no mention of what was deliberately not changed; risk section empty.

**3. Clarification message (grades export):**

```
Re "Users can export their grades": four questions before I start.
1. Which users: students (own grades only) or also teachers (course grades)? Default: students, own grades only.
2. Format? Default: CSV, one row per graded item, UTF-8.
3. Scope: all courses or the current course? Default: current course.
4. Should hidden grade items be excluded? Default: yes (matches what the student sees).
Unless I hear otherwise by Thursday 12:00 I'll proceed with these defaults and record them in the ticket.
```

(Questions 1, 3, 4 touch access control, a design-changing decision in Moodle's capability model; do not leave them to a guess.)

**4. Estimate for `repo_map.py`:** a good pre-start estimate: "5-9 hours: iter_files and tests 1-2 h; scanners 1-2 h; Moodle parsing 1 h; tests for edge cases 1-2 h; debugging 1-2 h. Assumes Python 3.12 available and no ast-based rewrite. Confidence medium. Biggest unknown: symlink and encoding edge cases." Record the ratio actual/estimated in your failure log; across several items it shows your personal bias (most beginners underestimate by a factor that is stable per person; measure yours, do not assume a number).

## Project: grading guide

### Blocker checklist (10 points each; average counts for 20 of the rubric points)
Award 1 per item listed in Section 3.3. Automatic zero for the "specific ask" item if the ask is "any ideas?" or "thoughts?". Deduct the item "meanwhile" if no check-back time is stated.

### Standups (15)
Full marks: five updates that read as one story; every item an outcome; at least one honest slip ("estimate moved from Thursday to Friday because X"); blockers named even when worked around. Deduct 2 per update that consists only of activity verbs ("looked into", "worked on").

### Questions (15)
5 per question: self-contained (3), shows bounded prior effort (1), correct type shape (1). The design question must have a default and a deadline, and the decision must be reversible; if it is not, deduct all points for that question and say why.

### PR descriptions (15)
Each answers why, what, verified, risk, notes (1.5 each = 7.5 per PR). The second PR must carry a deliberate risk and name it. Evidence must be commands and counts, not adjectives.

### Clarifications (10)
At most 4 questions each, every one with a default; a proceed-by time; the questions must concern behaviour that changes design (access, scope, format, failure behaviour), not trivia.

### Estimates (15)
Per estimate (3 each, 12 total) range 1, assumptions 1, confidence or unknown 1; plus 3 for the dated revision that names the cost of each option. Wednesday change: expect a revised range, the trade-off ("descoping export saves 1.5 days; cost: finance still sees the old totals in the export"), and a request for a decision with a time.

### Norms and graded sample (10)
`NORMS.md`: questions must be answerable and each must name where evidence will be sought (channel history, last ten PRs). `GRADED-SAMPLE.md`: top three defects must be credentials exposure, going offline right after reporting, and absence of evidence and impact, in that order of importance (a defensible alternative ordering is acceptable if justified).

### Mid-way requirement change (Wednesday)
Reference message:

```
ENG-123 revised. Finance needs the fix by Thursday noon and export is now in scope.
Was: 1-3 days (web path only). Now: 3-5 days with export; Thursday noon is likely only for the web path.
Options: (A) ship the web path by Thursday noon, export Monday; (B) both Friday. Risk in A: export totals stay wrong for 3 more days. Risk in B: finance misses their date.
I recommend A. Need a decision by 16:00 today; I'm continuing on the web path either way.
```

Why this works: it separates what changed from what it costs, offers options with their risks, makes a recommendation, and states the decision time.

## Rubric notes

Penalise a message for being short but incomplete as much as for being long and complete; the target is the minimum length that lets the reader act in one read. Do not reward tone words ("polite", "friendly") at the expense of content; the neutral, specific register is the standard. When a team's own norms contradict a template in this lesson, the kit should say which norm is assumed.
