# Solutions: Lesson 0.2, Git Workflow

Do not read before attempting. All scripts below were run with Git 2.47.3 on Linux with bash. They set `GIT_CONFIG_GLOBAL=/dev/null` so they cannot read or change your real Git configuration.

## Retrieval answers

1. Working tree -> index: `git add`; index -> repository: `git commit`; back: `git restore --staged` (index from HEAD), `git restore` (working tree from index).
2. `git diff --staged` shows what the next `git commit` records. `git diff main...HEAD` (three dots: since the merge base) approximates what a PR shows.
3. A commit's hash covers its tree, its parents, author, date, and message. Rebase changes the parent (new base), so each replayed commit is a new object with a new hash, even when the file content is identical.
4. During a rebase `HEAD`/ours is the upstream you are rebasing onto (the target), and theirs is your own commit being replayed. In a merge, ours is the branch you are on and theirs is the branch being merged in. The labels invert.
5. `--force` overwrites the remote ref unconditionally; `--force-with-lease` refuses if the remote ref is not where your last fetch saw it, so it will not clobber a colleague's push. Neither belongs on `main`: shared history must not be rewritten, and protected branches typically reject it.
6. Safe-order version: `git status` (clean?) then `git branch feature` (pins the commit) then `git reset --hard origin/main` while on `main` (or `git reset --hard HEAD~1` for a single commit). Alternative with less risk of discarding other work: `git switch -c feature` then `git branch -f main origin/main`.
7. `git diff --staged` shows `+x` only. `git diff` shows `+y` (the unstaged addition). `git commit -m m` records only `x`; `y` stays as an unstaged modification. (Assumes `a.txt` existed and was tracked; if new, the staged diff shows the file as added with content `x`.)
8. A commit is untestable when the check exits 125 (for example it does not build). The check must be outside the tracked tree because bisect checks out historical versions, which can overwrite, delete, or lack the script itself.
9. You need a known-good commit (or tag/date to find one), a deterministic automated check that tests the symptom and nothing else, and confirmation that the check fails on the known-bad commit and passes on the known-good one. It gives a wrong answer when the test is flaky, when two bugs exist, or when many commits are skipped around the culprit (the result is then a set of candidates).
10. `git revert -m 1 <merge-hash>`, which creates a new commit undoing the merge's changes. `-m 1` selects parent 1 (the branch that was merged into, usually `main`) as the mainline to keep. Caveat: after reverting a merge, merging the same branch again will not re-apply the reverted changes unless you first revert the revert (see `git help` for "revert-a-faulty-merge" in the howto documents).
11. It stages everything untracked or modified, including `.env`, logs, editor files, and build outputs, so secrets and noise enter the commit. Safer: `git add -p`, or explicit paths (`git add path/file`), and always `git status` first.
12. Modified but never staged or committed files (never seen by Git), and anything overwritten at the OS level; also staged-only content once garbage collection has removed the dangling blob. (Untracked files survive `reset --hard` but not `git clean`.)

## Failure laboratory notes

Scoring: 1 point per item correct with the correct mechanism: commits (reflog), staged edit (dangling blob via `fsck`, not guaranteed), unstaged edit (lost), untracked after `clean -fd` (lost). The common wrong answer is "everything is in the reflog". The reflog records pointer movements, i.e. commits, and staging creates a blob but no commit.

## Challenge reference (Section 8)

Item 1: the harder history and the oracle (`challenge.sh` creates it; `oracle.sh` is the check, saved outside the repository):

```bash
#!/usr/bin/env bash
# challenge.sh: calc.sh disappears one commit before the culprit, which restores it with the bug.
set -euo pipefail
export GIT_CONFIG_GLOBAL=/dev/null GIT_CONFIG_SYSTEM=/dev/null
D="${1:?usage: challenge.sh DIR}"; rm -rf "$D" && mkdir -p "$D" && cd "$D"
git init -q -b main && git config user.name "Lab User" && git config user.email "lab@example.invalid"
printf '#!/usr/bin/env bash\necho $(( $1 + $2 ))\n' > calc.sh; echo 1 > n; git add .; git commit -qm "feat: calc"
for i in 2 3; do echo $i > n; git commit -qam "chore $i"; done
git rm -q calc.sh; git commit -qm "chore: move calc (temporarily gone)"
echo 5 > n; git commit -qam "chore 5"
printf '#!/usr/bin/env bash\necho $(( $1 - $2 ))\n' > calc.sh; git add .; git commit -qm "refactor: restore calc, simplify"
for i in 7 8 9; do echo $i > n; git commit -qam "chore $i"; done
```

```bash
#!/usr/bin/env bash
# oracle.sh (keep OUTSIDE the repository)
[ -f calc.sh ] || exit 125          # cannot test: skip
out=$(bash ./calc.sh 2 3 2>/dev/null) || exit 125
[ "$out" = "5" ]                    # exit 0 good, 1 bad
```

Observed result: bisect finishes with "There are only 'skip'ped commits left to test. The first bad commit could be any of:" and lists three commits: "chore 5", "chore: move calc (temporarily gone)", and "refactor: restore calc, simplify". Reading the diffs resolves it: `calc.sh` was deleted in "move calc" (so those commits are untestable, not wrong) and the sign flip was introduced by "refactor". Lesson: bisect narrows the search; it does not replace reading. Skips adjacent to the culprit widen the answer to a candidate set.

Item 2: `git revert <hash-of-refactor>` creates a new commit. Trap: reverting the commit that *restored* `calc.sh` deletes `calc.sh` again (the revert undoes "file added"), so the oracle exits 125 (untestable), not 0. The correct repair here is a new commit that restores the file with `+`, ideally explaining that the revert alone is insufficient. Example message:

```
fix: restore calc.sh and correct addition

Reverting b1f2c3d (refactor: restore calc, simplify) removed calc.sh,
because that commit had re-added the file. Re-add it with the original
"a + b" behaviour. The refactor changed "+" to "-", which broke
check.sh (2 + 3 no longer printed 5).
```

(Use the real hash. Hash `b1f2c3d` above is a placeholder.)

Item 3: after `git rebase`, `git reflog` shows `rebase (start)` entries; the pre-rebase tip is the entry before `rebase (start)`. `git reset --hard 'HEAD@{N}'` (with N from the reflog) or `git reset --hard ORIG_HEAD` (Git sets `ORIG_HEAD` before rebase; `VERIFY` with `git help rebase`) restores it. Check: `git rev-parse HEAD` equals the saved pre-rebase hash.

## Project reference: drills and cleanup

`drills_reference.sh` implements the eight drills (break, recover, verify), is idempotent (each drill recreates its own directory under the lab directory), and ran clean twice in a row:

```bash
#!/usr/bin/env bash
# Reference drills for Lesson 0.2. Each drill: break -> recover -> verify (exit non-zero on failure).
# Usage: ./drills_reference.sh [LABDIR]   (default: a fresh mktemp -d directory; only that directory is modified)
set -euo pipefail
export GIT_CONFIG_GLOBAL=/dev/null GIT_CONFIG_SYSTEM=/dev/null   # never read or write real config
LAB="${1:-$(mktemp -d)}"
mkdir -p "$LAB"

new_repo() {   # new_repo NAME -> creates $LAB/NAME with one base commit, cd into it
  local d="$LAB/$1"
  [[ "$d" == "$LAB"/* && -n "$1" ]] || { echo "refusing path $d" >&2; exit 1; }
  rm -rf "$d" && mkdir -p "$d" && cd "$d"
  git init -q -b main
  git config user.name "Lab User" && git config user.email "lab@example.invalid"
  echo base > base.txt && git add . && git commit -qm "base"
}
ok() { echo "PASS: $1"; }
fail() { echo "FAIL: $1" >&2; exit 1; }

drill1_wrong_branch() {
  new_repo d1
  echo f > f.txt && git add . && git commit -qm "feat: work done on main by mistake"
  local want; want=$(git rev-parse HEAD)
  git branch feature                       # keep the commit
  git reset -q --hard HEAD~1               # (safe: clean tree) move main back
  [[ "$(git rev-parse feature)" == "$want" && ! -e f.txt ]] && ok "drill1 wrong-branch" || fail drill1
}
drill2_reset_hard() {
  new_repo d2
  git switch -q -c feature
  echo 1 > a && git add . && git commit -qm c1; echo 2 >> a && git commit -qam c2
  local want; want=$(git rev-parse HEAD)
  git reset -q --hard main                 # the mistake
  git branch rescue "HEAD@{1}"
  [[ "$(git rev-parse rescue)" == "$want" ]] && ok "drill2 reset --hard" || fail drill2
}
drill3_deleted_branch() {
  new_repo d3
  git switch -q -c topic; echo t > t && git add . && git commit -qm topic1
  local want; want=$(git rev-parse HEAD)
  git switch -q main; git branch -D topic >/dev/null     # the mistake (git also prints "was <abbrev hash>")
  local h; h=$(git reflog --format='%H %gs' | awk '/commit: topic1/{print $1; exit}')
  [[ -n "$h" ]] || fail "drill3: commit not found in reflog"
  git branch topic "$h"
  [[ "$(git rev-parse topic)" == "$want" ]] && ok "drill3 deleted branch" || fail drill3
}
drill4_bad_merge_revert() {
  new_repo d4
  git switch -q -c feature; echo bad > bad.txt && git add . && git commit -qm "feat: bad"
  git switch -q main; git merge -q --no-ff feature -m "Merge feature"
  local m; m=$(git rev-parse HEAD)
  git revert --no-edit -m 1 "$m" >/dev/null
  [[ ! -e bad.txt && "$(git rev-list --count main)" -eq 4 ]] && ok "drill4 revert merge" || fail drill4
}
drill5_detached_head() {
  new_repo d5
  echo 2 > f && git add . && git commit -qm second
  git switch -q --detach HEAD~1
  echo new > n && git add . && git commit -qm "work while detached"
  local want; want=$(git rev-parse HEAD)
  git switch -q -c saved
  git switch -q main
  [[ "$(git rev-parse saved)" == "$want" ]] && ok "drill5 detached HEAD" || fail drill5
}
drill6_rebase_abort() {
  new_repo d6
  git switch -q -c feature; echo A > x && git add . && git commit -qm "feature x=A"
  local before; before=$(git rev-parse HEAD)
  git switch -q main;       echo B > x && git add . && git commit -qm "main x=B"
  git switch -q feature
  git rebase main >/dev/null 2>&1 && fail "expected conflict" || true
  git rebase --abort
  [[ "$(git rev-parse feature)" == "$before" ]] && ok "drill6 rebase --abort" || fail drill6
}
drill7_secret_local() {
  new_repo d7
  echo "API_KEY=supersecret" > .env && git add . && git commit -qm "oops"
  git reset -q --soft HEAD~1               # not pushed: uncommit, keep staged
  git restore --staged .env
  echo ".env" >> .git/info/exclude          # local-only ignore; team may prefer .gitignore
  [[ -z "$(git status --porcelain)" ]] && ! git ls-files --error-unmatch .env >/dev/null 2>&1 \
     && ok "drill7 secret not pushed (still rotate it if it ever left your machine)" || fail drill7
}
drill8_add_dot() {
  new_repo d8
  echo code > code.py; echo junk > debug.log
  git add .                                # the mistake
  git restore --staged debug.log
  git commit -qm "feat: code only"
  [[ "$(git show --name-only --format= HEAD)" == "code.py" ]] && ok "drill8 git add ." || fail drill8
}

for d in drill1_wrong_branch drill2_reset_hard drill3_deleted_branch drill4_bad_merge_revert \
         drill5_detached_head drill6_rebase_abort drill7_secret_local drill8_add_dot; do ( $d ); done
echo "lab dir: $LAB"
```

Honest limits of these drills: they test the mechanical recovery, not a pushed state (add a bare repository as `origin` for that; `git init --bare` plus `git remote add`), and drill 7 covers only the unpushed case. If the secret was pushed, the answer is "rotate, then coordinate cleanup with the team".

`cleanup.sh` builds a messy 8-commit branch and a 3-commit clean branch with an identical final tree (`git diff --exit-code messy clean` printed "identical trees"):

```bash
#!/usr/bin/env bash
# Builds branch "messy" (8 commits incl. formatting noise and a log file) and "clean" (3 logical commits, same final tree).
set -euo pipefail
export GIT_CONFIG_GLOBAL=/dev/null GIT_CONFIG_SYSTEM=/dev/null
D="${1:?usage: cleanup.sh DIR}"; rm -rf "$D" && mkdir -p "$D" && cd "$D"
git init -q -b main && git config user.name "Lab User" && git config user.email "lab@example.invalid"
printf 'def total(items):\n    return sum(items)\n' > cart.py && printf 'x=1\n' > style.py
git add . && git commit -qm "base"
git switch -q -c messy
printf 'def total(items):\n    return sum(i for i in items if i > 0)\n' > cart.py; git commit -qam "wip"
printf 'x = 1\n' > style.py;                                     git commit -qam "format style.py"
echo "debug output" > run.log && git add run.log;              git commit -qm "more"
printf 'def total(items):\n    return sum(i for i in items if i > 0)\n\ndef count(items):\n    return len(items)\n' > cart.py; git commit -qam "fix2"
printf 'def test_total():\n    assert 1\n' > test_cart.py && git add .; git commit -qm "tests"
git rm -q run.log;                                             git commit -qm "remove log"
echo "# cart" > README.md && git add .;                          git commit -qm "docs"
printf 'def test_total():\n    from cart import total\n    assert total([1, -1]) == 1\n' > test_cart.py; git commit -qam "fix test"
# clean: same final tree, logical commits (formatting isolated, log file never present)
git switch -q -c clean main
git checkout messy -- cart.py;       git commit -qm "fix: ignore negative items in total()"
git checkout messy -- test_cart.py;  git commit -qm "test: cover negative items in total()"
git checkout messy -- style.py README.md; git commit -qm "chore: format style.py, add README"
git diff --exit-code messy clean && echo "identical trees"; git log --oneline main..clean | cat
```

Weaknesses a reviewer should call out in this reference: the first clean commit also contains the unrelated `count()` function (a purist would split it or drop it as scope creep); and the last commit bundles a formatting change with a README (two purposes). Approach alternative: `git reset --soft main` followed by `git add -p` per logical commit gives finer control per hunk; interactive rebase preserves the original authorship and dates of surviving commits, which `checkout <branch> -- <path>` does not (every clean commit has a new author date). Choose by whether authorship fidelity matters on your team.

## Rubric scoring notes

- Runbook accuracy (25): a reviewer follows each entry blind on a fresh repo; 3 points per drill, 1 for completeness of "what is NOT recoverable".
- Honesty (10): full marks require the table of recoverable states (committed, staged, unstaged, untracked) and the reflog expiry caveat.
- Script safety (10): deduct 5 for any `rm -rf` of an unchecked variable, 5 for any use of global config or an inherited `GIT_DIR`.
- Conventions discovery (10): evidence must be quotations or hashes from the repository (for example the last ten `git log --oneline` subjects and a link to `CONTRIBUTING`), not impressions.
