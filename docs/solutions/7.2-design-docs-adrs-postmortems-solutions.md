## A. Retrieval answers

1. Restate "faster" as a measurable behaviour: which operation, for which users, current vs target latency/throughput, measured how, at what percentile and load. List unknowns; rank by cost of being wrong; propose defaults. First two questions: (1) *What is slow and how is it measured now?* (without a baseline you cannot know whether you succeeded or what to fix); (2) *What target would make this good enough, and what is it worth?* (stops open-ended optimisation and sets a stopping rule).
2. It is the baseline: it forces the claim that the change is worth its cost, keeps the status quo's costs visible, and prevents choosing among bad options by default.
3. Context: forces, constraints, requirements, relevant facts (volumes, team skills, deadlines), assumptions. Not: advocacy for the decision, implementation steps, task lists, or consequences (those have their own field).
4. When a later decision replaces it: write a new ADR that states it supersedes ADR-N, set the old status to "Superseded by ADR-M", keep the old text. Editing erases the history of what was believed and why; later readers cannot tell what changed.
5. Task A (1,3,8): E = (1+12+8)/6 = 3.50, s = 7/6 = 1.17. Task B (2,3,6): E = (2+12+6)/6 = 3.33, s = 4/6 = 0.67. Sum E = 6.83; sum s under independence = sqrt(1.17^2 + 0.67^2) = 1.34. The spread is understated because tasks share unknowns (e.g. an unfamiliar API affects both), so errors are positively correlated and variances do not simply add; also the PERT formula assumes a particular shape.
6. (1) What is included (tests, review, deploy, docs)? (2) What are the assumptions and unknowns, and what happens if one is wrong? (3) What is the range, and what comparable work took before? (4) Effort or calendar time, and what availability is assumed? (Also: who else is involved, and when will you re-estimate?)
7. Example: outage after a deploy that set a wrong database pool size. Trigger: the deploy. Root cause (condition that made it possible): config is not validated and there is no staged rollout. Contributing factors: no alert on connection errors, ambiguous ownership of the config, a default that is unsafe at production load.
8. Because an unverified cause produces actions that do not prevent recurrence. Ways: reproduce the failure in a controlled environment; remove the suspected cause and show the failure disappears; predict an unobserved consequence and then observe it (for example a log line or metric); check that the cause explains the timing.
9. Prevent: CI check that runs the migration on a production-sized copy and fails if it exceeds a lock-time budget. Detect: alert on long-running locks and replication lag during migration windows. Mitigate: documented, rehearsed rollback script and an abort criterion in the runbook. Each with owner, date, verification.
10. Question and decision threshold; workload and justification; environment and versions; method (warm-up, repetitions, exclusions); variance and units; profile evidence for the explanation; limits; recommendation.
11. Typically the contract step: dropping the old column/table or removing the old code path that could read it. Before crossing: the new path has served all traffic for an agreed period, verification checks (counts, checksums, shadow comparisons) are clean, backups of the old data exist and a restore was tested, and no consumer still reads the old structure (checked via logs).
12. Say: "I do not know. This is what I would check, and here is what I would expect; my current belief is X with low confidence." Avoid: bluffing, asserting unmeasured numbers, changing the subject, defending a decision because it was already made.

## B. Challenge: ADR and estimator

ADR reference (compact):

```
ADR-012: Represent money as integer minor units
Status: Accepted
Context: A billing service (invented for this exercise) sums, splits and taxes amounts; results must match
  finance spreadsheets to the cent and be reproducible. Forces: (1) binary floats cannot represent most decimal
  fractions exactly (round(2.675, 2) gives 2.67 in Python); (2) the database and JSON must carry amounts
  without precision loss; (3) team has had rounding incidents; (4) currencies differ in minor-unit exponents.
Decision: We will store amounts as 64-bit integers in minor units with an explicit currency code, and do
  arithmetic in integers, with one documented rounding function for tax and splits.
Alternatives: DECIMAL columns with Decimal in code (exact and readable, slower, still needs explicit rounding
  rules and care at JSON boundaries); floats (rejected: inexact).
Consequences: + exact addition, cheap, portable. - every display/parse must convert; ratios and tax need rounding
  policy; currencies with other exponents need a lookup.
Revisit when: we support currencies with fractional minor units or high-precision unit pricing (e.g. per-token fees).
```

Estimator (`estimate.py`) and tests:

```python
"""Three-point estimator. Python 3.12, stdlib only."""
from __future__ import annotations
import math


def estimate(tasks: list[tuple[str, float, float, float]]) -> dict:
    if not tasks:
        raise ValueError("no tasks")
    per_task, e_total, var_total, p_total = {}, 0.0, 0.0, 0.0
    for name, o, m, p in tasks:
        if not (0 <= o <= m <= p):
            raise ValueError(f"{name}: require 0 <= O <= M <= P")
        e, s = (o + 4 * m + p) / 6, (p - o) / 6
        per_task[name] = (e, s)
        e_total += e
        var_total += s * s      # adds only if tasks are independent; shared unknowns make the
        p_total += p            # true spread larger, so this sd is a LOWER bound
    return {"per_task": per_task, "expected": e_total, "sd_independent": math.sqrt(var_total),
            "sum_pessimistic": p_total}
```

```python
import unittest
from estimate import estimate
T = [("schema+migration",1,2,5),("API endpoints",2,4,9),("auth integration",1,3,8),("tests",2,3,6),("deploy+runbook",1,2,4)]
class X(unittest.TestCase):
    def test_table(self):
        r = estimate(T)
        self.assertAlmostEqual(r["expected"], 15.83, places=2)
        self.assertAlmostEqual(r["sd_independent"], 1.96, places=2)
        self.assertEqual(r["sum_pessimistic"], 32)
    def test_invalid(self):
        with self.assertRaises(ValueError): estimate([("x", 3, 2, 5)])
        with self.assertRaises(ValueError): estimate([])
    def test_single(self):
        r = estimate([("a", 2, 2, 2)]); self.assertEqual(r["expected"], 2); self.assertEqual(r["sd_independent"], 0)
    def test_q5(self):
        r = estimate([("a",1,3,8),("b",2,3,6)])
        self.assertAlmostEqual(r["expected"], 3.5+3.3333333, places=5)
if __name__ == "__main__": unittest.main()
```

Trade-offs: PERT is simple but its assumptions (a Beta-like shape, independence) are rough; alternative is reference-class estimation from your own actuals or Monte Carlo over task distributions (needs a correlation model). Scoring: ADR 50 (forces 10, alternatives 10, decision clarity 10, consequences 10, revisit trigger 10); estimator 50 (correct formulas 15, validation 10, tests 15, comment on lower-bound 10).
