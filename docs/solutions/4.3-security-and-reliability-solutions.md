## Section 7 retrieval answers

1. Parameterization sends the statement and the values separately, so the database parses the structure before any data is seen; values can never become syntax. Hand escaping tries to make data safe *inside* the code channel, and fails on encoding quirks, unusual contexts, and developer omissions.
2. Identifiers (table/column names), sort direction, keywords, and sometimes `IN` list length. Handle with a strict allow-list mapping from user choice to a literal you wrote; build the `IN` placeholders from the count, not the values.
3. Stored: persisted then rendered to others. Reflected: echoed from the current request. DOM-based: client script reads an untrusted source (URL fragment, `postMessage`) and writes it into the DOM. In an HTML attribute, HTML-attribute-encode and always quote the attribute; in a JavaScript string, avoid inserting data into script at all (pass it as JSON in a data attribute or use a JSON script block) and otherwise use JavaScript-string encoding; URL contexts need URL encoding plus scheme allow-listing (`javascript:` URLs).
4. Not a threat when authentication is a bearer token that script must attach explicitly (an `Authorization` header), because a cross-site page cannot add it without a CORS permission. It becomes a threat again if the same endpoints also accept cookie authentication, or if CORS is configured too permissively.
5. 401: not authenticated (no or bad credentials). 403: authenticated but not allowed. 404 for forbidden objects hides existence (prevents enumeration of valid ids); trade-off: harder debugging, so log the true reason server-side.
6. Strongest to weakest: network egress policy blocking internal ranges and metadata addresses; a dedicated fetcher with no credentials in an isolated network zone; destination allow-list; resolve-validate-pin-connect with redirects disabled or re-validated plus size/time caps; (weakest) hostname string checks. DNS rebinding: an attacker's domain answers a public IP at validation time and a private IP (very short TTL) at connection time; defense is to connect to the exact address you validated, not to re-resolve.
7. The secret was already copied (clones, CI caches, forks, logs). Remediation: rotate/revoke the secret, audit use since exposure, then clean history if desired, then add prevention (scanner, secret store).
8. S: Moodle impersonated (attacker-controlled DNS or TLS interception) so you send data to the wrong party; mitigation TLS verification, pinned host. T: response tampered or malformed, trusted blindly; mitigation validate schema, TLS. R: no record of what the service asked Moodle to do; mitigation audit log of outbound calls with correlation ids. I: tokens or learner data sent to Moodle or echoed in URL/logs; mitigation least data, no secrets in URLs, redaction. D: Moodle slowness exhausts workers; mitigation timeouts, bulkhead, breaker. E: service account with admin-level web service role; mitigation least-privilege role.
9. (a) app role with SELECT/INSERT/UPDATE on specific tables only, no DDL, separate migration role; (b) Moodle web service user with a role limited to the capabilities of the exposed functions; (c) container as non-root, read-only root filesystem, dropped Linux capabilities, no host mounts.
10. Fixation: an attacker sets or learns a session id before login and the victim authenticates under it. Prevent by issuing a new session id on login (and on privilege change), invalidating the old one.
11. Closed: calls flow, failures counted. Open: calls fail immediately for the cool-down. Half-open: limited trial calls; success closes, failure re-opens. Thundering herd: when the breaker closes (or the dependency recovers) all clients retry at once and knock it over again; jitter randomizes retry timing and staggered half-open trials limit the load.
12. Safe: reads, naturally idempotent writes (PUT of a full resource), and writes with idempotency keys enforced in storage. Bounds: small attempt cap, capped exponential backoff with jitter, retry only transient errors (timeouts, 503, 429 with `Retry-After`), a global retry budget per window, retry at one layer only.
13. RPO: tolerable data-loss window (drives backup frequency or replication). RTO: tolerable time to restore service. The drill's measured elapsed time from "start restore" to "application verified healthy on restored data" is the real RTO, which is often far above the guess; record it and its conditions.
14. Bad: "Be more careful", "Developer X to double-check deploys", "Improve monitoring". Good: "Add an alert on backup age greater than 26 h; owner: ops role; due: date; verify: fire a test alert by pausing the job"; "Add a request-level timeout of N seconds to the Moodle client with a test that asserts it is passed; owner; date; verified by CI"; "Add a restore drill to the quarterly calendar and store the timing in the runbook; verified by the entry's existence".

## 8.1 reference (access-control matrix)

```python
from dataclasses import dataclass
from enum import Enum

class Role(Enum): ANON="anon"; STUDENT="student"; TEACHER="teacher"; ADMIN="admin"

@dataclass(frozen=True)
class Actor:
    id: str | None
    role: Role
    teaches: frozenset[int] = frozenset()

@dataclass(frozen=True)
class Grade:
    owner: str
    course: int

def can_read_grade(a: Actor, g: Grade) -> bool:
    if a.role is Role.ADMIN: return True
    if a.role is Role.TEACHER: return g.course in a.teaches
    if a.role is Role.STUDENT: return a.id is not None and a.id == g.owner
    return False

def can_edit_grade(a: Actor, g: Grade) -> bool:
    if a.role is Role.ADMIN: return True
    if a.role is Role.TEACHER: return g.course in a.teaches
    return False
```

Verified: all 20 rows below pass in pytest (the original 8 plus the following 12 cases): teacher with multiple courses, admin reading another's, student with `id=None`, two different courses, edit by admin, edit by revoked teacher, anonymous edit, case-variant ids (`"Ann"` vs `"ann"`: decide and test), and a teacher who is also the owner. Design notes: default is `False` at the end of each function (deny by default); the authoritative actor comes from the session, never a request field; "revoked teacher" is modeled by an empty `teaches` set, which implies that the set is loaded fresh per request (a stale token claim would be a bug; mention the trade-off with JWT role claims). HTTP-level test: parametrize (actor, grade_id) to expected status; assert that `403`/`404` policy produce identical bodies for "missing" and "forbidden". Marking: pure function 20%, deny-by-default 20%, 20+ rows with the named cases 30%, HTTP parity test 20%, rationale 10%.

## 8.2 reference (ResilientClient)

```python
import random
from collections import deque
from typing import Callable, TypeVar
T = TypeVar("T")
class Transient(Exception): ...
class Permanent(Exception): ...
class CircuitOpen(Exception): ...

class ResilientClient:
    def __init__(self, *, attempts=3, base=0.1, cap=2.0, threshold=3, reset_after=30.0,
                 budget=5, window=10.0, now=lambda: 0.0, sleep=lambda s: None, rng=None, fallback=None):
        self.attempts, self.base, self.cap = attempts, base, cap
        self.threshold, self.reset_after = threshold, reset_after
        self.budget, self.window = budget, window
        self.now, self.sleep, self.rng = now, sleep, rng or random.Random(0)
        self.fallback = fallback
        self.fails, self.opened_at = 0, None
        self._retries: deque[float] = deque()
    def _budget_ok(self) -> bool:
        t = self.now()
        while self._retries and t - self._retries[0] >= self.window: self._retries.popleft()
        return len(self._retries) < self.budget
    def _call_once_guarded(self, fn: Callable[[], T]) -> T:
        if self.opened_at is not None and self.now() - self.opened_at < self.reset_after:
            raise CircuitOpen()
        try:
            r = fn()
        except Transient:
            self.fails += 1
            if self.fails >= self.threshold or self.opened_at is not None: self.opened_at = self.now()
            raise
        self.fails, self.opened_at = 0, None
        return r
    def call(self, fn: Callable[[], T]) -> T:
        try:
            for n in range(self.attempts):
                try:
                    return self._call_once_guarded(fn)
                except Transient:
                    if n == self.attempts - 1 or not self._budget_ok(): raise
                    self._retries.append(self.now())
                    self.sleep(self.rng.uniform(0, min(self.cap, self.base * 2 ** n)))
        except (CircuitOpen, Transient):
            if self.fallback is not None: return self.fallback
            raise
        raise AssertionError
```

Verified tests: success on third attempt with two sleeps in bounds; `Permanent` propagates without retry or breaker effect; two failures at threshold 2 open the breaker, the next call returns the fallback without invoking the function; after the clock passes `reset_after` the trial succeeds and closes it; a failed half-open trial re-opens (`opened_at` equals the new time); with `budget=2`, only two sleeps happen across three failing calls. Known simplifications to discuss for full marks: not thread-safe (would need a lock around state changes and a single-trial rule in half-open); `CircuitOpen` inside the retry loop is not retried (correct: failing fast is the point); a fallback hides errors, so emit a metric when it is used. Alternative: wrap retry and breaker as decorators/middleware; the trade-off is hidden control flow versus reuse.

|---|---|---|---|---|---|

## Section 9 project: reference approach and marking notes

Reference sequence: (1) commit `v0` with the five weaknesses and a test file that currently *fails* for each (tag `v0-red`); (2) commit the threat model; (3) fix class by class, each commit turning exactly one red test green; (4) tag `v1`; (5) resilience layer and fault-injection tests; (6) drill, incident, postmortem.

SSRF test list (all with an injected resolver or a local test server you run): loopback v4/v6, `169.254.169.254`, RFC 1918 ranges, IPv4-mapped IPv6 (`::ffff:127.0.0.1`; checked on Python 3.13: `is_global` is False for mapped private/loopback addresses and True for mapped public ones; normalise with `.ipv4_mapped` anyway), decimal/octal/hex IP forms in the hostname (document how your parser treats them: `urlsplit` leaves the string; resolution decides), a redirect from a public stub to a private address, an oversized body, a slow body (timeout), a hostname with both public and private A records (reject: all addresses must be public), `file://` and `gopher://`.

Mid-way change reference: add an explicit allow-list entry `{host: "onprem.customer.example", ports: {443}, pinned_cidr: "10.20.0.0/24"}`; the fetcher permits a private address only if the hostname is in the allow-list AND the resolved address is within the entry's CIDR; every other host keeps the public-only rule. ADR must list alternatives (VPN/tunnel with a relay service; customer pushes instead of pull; separate fetcher instance with its own network policy) and negative consequences (the allow-list is now a sensitive config that must be reviewed and audited; DNS control by the customer is a trust assumption).

Postmortem model structure (all numbers must be your own measured values; none are given here):

- Summary and impact: which feature, which users, duration from first error to recovery (from your logs).
- Timeline: timestamped entries (fault injected or begun, first alert or symptom, first human notice, hypotheses tried, mitigation, recovery, verification).
- Detection: how found, time to detect; what alert should have fired.
- Contributing factors: e.g. no timeout on one code path; breaker threshold too high; dashboard lacked breaker state.
- What went well; where we got lucky.
- Action items: each with owner, due date, and a verification method (test, alert, drill).
Penalize "root cause: human error"; reward factors about system conditions.

Restore drill rubric: full marks require integrity check, row counts, checksum or business invariant, elapsed time from start to verified, and a note on what was not restored (files, secrets). A drill that only prints "restored" earns at most 2 of 7.

Dependency audit: record the exact tool and command used, its raw output summary, and a triage per finding (reachable? fix available? decision and date). If the tool is unavailable offline, the entry "not run: reason" is acceptable and honest; a fabricated clean report is a critical failure.

PHP/Moodle design note acceptance: lists `require_login`, a capability check in the correct context, `required_param`/`optional_param` with `PARAM_*` types, `require_sesskey` on mutating actions, `$DB` placeholders, output escaping/mustache, web service parameter and capability declarations; every Moodle API name is accompanied by the Moodle version it was checked against or a moodledev.io citation. Deduct if the note suggests reading raw `$_GET`/`$_POST` directly.

Alternative defenses worth crediting: using an ORM/query builder exclusively for data access (provided no raw SQL strings), a web application firewall as an *additional* layer (not a substitute), Content-Security-Policy with a report-only phase, and a dedicated egress proxy for outbound fetches.
