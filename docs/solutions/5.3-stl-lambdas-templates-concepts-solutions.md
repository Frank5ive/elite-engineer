## Section 7: Retrieval answers

1. Queue with front removal: `std::deque` (or `std::queue`), O(1) both ends; erasing in the middle invalidates all iterators. Unordered unique string keys: `std::unordered_map`, O(1) average, rehash invalidates iterators (not references). Sorted iteration: `std::map`, O(log n), insertion invalidates nothing. Fixed 3-vector: `std::array<double,3>`, O(1) index, no allocation.
2. `vector::push_back`: invalidates everything if it reallocates; otherwise only `end()`. `deque`: iterators invalidated by any insertion; references survive insertion at either end but not in the middle (cppreference). `map::insert`: nothing.
3. It returns the new logical end; it only moves kept elements forward, so the container size is unchanged and the tail is moved-from. `erase(new_end, end)` shrinks. `std::erase_if(container, pred)` (C++20).
4. Algorithms and ordered containers assume irreflexive, transitive ordering with transitive equivalence; a comparator returning true for equal elements (`<=`) breaks this and the behavior is undefined (sort may read out of bounds).
5. Order by age: names `al`, `bo`, `cy`; the first is `al` (verified).
6. A view does its work during iteration, each time it is iterated. If the source changes between passes, the two passes see different data. `filter_view` also caches its first match; mutating the source after the first `begin()` can leave that cached iterator invalid (cppreference documents the caching; the consequence follows from ordinary invalidation rules).
7. `std::function<int()> mk() { int local = 41; return [&local]{ return local + 1; }; }`. Fixes: `[local]` by value; or return the value and not a closure; or capture a `shared_ptr` owner.
8. It captures `this` (a pointer), not copies of members. C++20 deprecates implicit capture of `this` via `[=]`: GCC warns.
9. When you must store different callables in one variable or container, register callbacks at run time, or keep an interface stable. Costs: indirect call that cannot inline; possible heap allocation when the callable exceeds the implementation's small buffer.
10. `f(const int&)`: `T = int`. `f("hi")`: `T = const char*`. `g(x)` with lvalue `int x`: `T = int&` (parameter `int&`). `g(5)`: `T = int` (parameter `int&&`).
11. `template <typename T> concept Number = requires(T a, T b) { { a + b } -> std::convertible_to<T>; { a * b } -> std::convertible_to<T>; T(0); };`. A strict weak ordering is a semantic property of runtime behavior, not a syntactic one; a concept checks that expressions compile, so you document it and test it.
12. Lvalue argument: `Args` deduced as `X&`, so `forward` yields an lvalue (copy). Rvalue argument: `Args` deduced as `X`, so `forward` yields an rvalue (move). Verified with `make<Widget>(s)` vs `make<Widget>(std::move(s))`.
13. A concrete type suffices; runtime polymorphism is the requirement; a single instantiation exists; ABI stability or hidden implementation needed; team does not use metaprogramming. (Any three.)

## Section 8: `algo.hpp` reference solution (verified, tests under ASan+UBSan)

```cpp
#pragma once
#include <concepts>
#include <cstddef>
#include <functional>
#include <iterator>
#include <optional>
#include <ranges>
#include <utility>

namespace algo {

// Forward iteration: a later match must be able to overwrite an earlier one.
template <std::forward_iterator It, std::sentinel_for<It> S, typename Pred>
    requires std::indirect_unary_predicate<Pred, It>
It find_last_if(It first, S last, Pred pred) {
    It result = first;
    bool found = false;
    for (; first != last; ++first) {
        if (std::invoke(pred, *first)) { result = first; found = true; }
    }
    if (found) return result;
    return first;   // first == last here
}

// Single pass; copies the extremes out, hence copy_constructible.
template <std::ranges::forward_range R, typename Comp = std::ranges::less>
    requires std::indirect_strict_weak_order<Comp, std::ranges::iterator_t<R>> &&
             std::copy_constructible<std::ranges::range_value_t<R>>
auto min_max(R&& r, Comp comp = {})
    -> std::optional<std::pair<std::ranges::range_value_t<R>, std::ranges::range_value_t<R>>> {
    auto it = std::ranges::begin(r);
    const auto last = std::ranges::end(r);
    if (it == last) return std::nullopt;
    auto lo = it, hi = it;
    for (++it; it != last; ++it) {
        if (std::invoke(comp, *it, *lo)) lo = it;
        if (std::invoke(comp, *hi, *it)) hi = it;
    }
    return std::pair{*lo, *hi};
}

template <std::ranges::input_range R, typename T>
    requires std::equality_comparable_with<std::ranges::range_value_t<R>, T>
std::size_t count_equal(R&& r, const T& value) {
    std::size_t n = 0;
    for (auto&& x : r) if (x == value) ++n;
    return n;
}

}  // namespace algo
```

Verified tests: `find_last_if` on `{1,4,2,4,3}` finds index 3; none and empty ranges return `end()`; `min_max` on `std::list<std::string>` gives `("apple","zebra")`; empty gives `nullopt`; single element gives equal pair; `std::greater<>` swaps the roles; `count_equal` on `std::string "banana"` and `'a'` gives 3; on an empty vector 0; on `list<string>` with a string literal `"fig"` 1.

Rejection tests (a bare `requires` outside a template is a hard error on GCC 14.2, verified; wrap in a concept):

```cpp
template <typename R, typename T>
concept CanCount = requires(R&& r, const T& t) { algo::count_equal(std::forward<R>(r), t); };
static_assert(CanCount<std::vector<int>&, int>);
static_assert(!CanCount<std::vector<int>&, std::string>);
template <typename R>
concept CanMinMax = requires(R&& r) { algo::min_max(std::forward<R>(r)); };
static_assert(!CanMinMax<std::vector<std::unique_ptr<int>>&>);   // move-only rejected
```

Iterator categories: `find_last_if` forward (needs multipass: the saved iterator must remain valid after advancing; an input iterator would not guarantee that); `min_max` forward (saves `lo`/`hi` iterators while advancing); `count_equal` input (single pass, no saved iterators). Move-only `min_max` is rejected because the function returns copies; an alternative design returns iterators (no element requirement at all) and is better for move-only and expensive types; discuss as a trade-off.

Alternative designs: `std::ranges::minmax_element` already exists; real code would use it (checked: `std::ranges::minmax_element(range)` returns `ranges::minmax_element_result`, members `min` and `max`; `max` is the last of equal maxima). The exercise is to practice constraints.

## Section 9: Project reference solution (`FlatMap`, verified)

Verified implementation core (full header compiled clean; tests under ASan+UBSan passed):

```cpp
template <typename K, typename V, typename Compare = std::less<K>>
    requires std::strict_weak_order<Compare, const K&, const K&>
class FlatMap {
public:
    using value_type = std::pair<K, V>;
    using container_type = std::vector<value_type>;
    using const_iterator = typename container_type::const_iterator;

    FlatMap() = default;
    explicit FlatMap(Compare cmp) : cmp_{std::move(cmp)} {}
    std::size_t size() const noexcept { return items_.size(); }
    bool empty() const noexcept { return items_.empty(); }
    const_iterator begin() const noexcept { return items_.begin(); }
    const_iterator end() const noexcept { return items_.end(); }

    const_iterator find(const K& key) const {
        auto it = lower(key);
        return (it != items_.end() && !cmp_(key, it->first)) ? it : items_.end();
    }
    bool contains(const K& key) const { return find(key) != end(); }

    template <typename VV> requires std::constructible_from<V, VV&&>
    std::pair<const_iterator, bool> insert(const K& key, VV&& value) {
        auto it = lower_mut(key);
        if (it != items_.end() && !cmp_(key, it->first)) return {it, false};
        it = items_.emplace(it, key, V(std::forward<VV>(value)));
        return {it, true};
    }
    V& operator[](const K& key) requires std::default_initializable<V> {
        auto it = lower_mut(key);
        if (it == items_.end() || cmp_(key, it->first)) it = items_.emplace(it, key, V{});
        return it->second;
    }
    const V& at(const K& key) const {
        auto it = find(key);
        if (it == end()) throw std::out_of_range("FlatMap::at");
        return it->second;
    }
    bool erase(const K& key) {
        auto it = lower_mut(key);
        if (it == items_.end() || cmp_(key, it->first)) return false;
        items_.erase(it);
        return true;
    }
private:
    auto lower(const K& k) const { return std::lower_bound(items_.begin(), items_.end(), k,
        [this](const value_type& e, const K& x) { return cmp_(e.first, x); }); }
    auto lower_mut(const K& k) { return std::lower_bound(items_.begin(), items_.end(), k,
        [this](const value_type& e, const K& x) { return cmp_(e.first, x); }); }
    container_type items_;
    [[no_unique_address]] Compare cmp_{};
};
```

(Includes: `<algorithm> <concepts> <cstddef> <functional> <stdexcept> <utility> <vector>`.)

Known issues the learner should find and discuss (these are review points, not bugs in the verified tests):
- `insert` returns a `const_iterator` converted from the mutable iterator: fine. The `std::pair<K,V>` key is non-const; the class exposes only const iteration to protect the sort invariant.
- `operator[]` default-constructs `V` when the key is absent, so it carries `requires std::default_initializable<V>`. Without the constraint the member would still be lazily instantiated only on use, but `requires { m[k]; }` and generic code would wrongly report the operation as available, and the error would surface inside the library body. Checked: with the constraint, `FlatMap<int, NoDefault>` still supports `insert`/`find`/`at`/`erase`, and `m[1]` fails with `constraints not satisfied` naming `std::default_initializable<NoDefault>`; the test below pins this with a `static_assert` (compiled and run with g++ 14.2, `-std=c++20 -Wall -Wextra -Wpedantic -fsanitize=address,undefined`, plus a 10,000-operation differential test against `std::map`).

```cpp
struct NoDef { explicit NoDef(int x) : v(x) {} int v; };
template <class M> concept HasSubscript = requires(M m) { m[1]; };
static_assert(HasSubscript<FlatMap<int, int>>);
static_assert(!HasSubscript<FlatMap<int, NoDef>>);
```
- `insert(const K&, VV&&)` with a move-only `V` works through `V(std::forward<VV>(value))`; test with `std::unique_ptr<int>`.
- Exception safety: `vector::emplace` in the middle provides the strong guarantee only when inserting a single element at the end and `T` is CopyInsertable or nothrow-move-constructible, and only if no exception comes from `T`'s copy/move operations; otherwise the effects are unspecified (cppreference `vector/emplace`). Document that. Strong guarantee for `insert` can be offered only conditionally.
- A throwing `Compare` leaves the container unchanged for lookups and `insert` before the emplace (comparisons happen before mutation).

Heterogeneous lookup change: add `template <typename Q> const_iterator find(const Q& q) const requires requires { typename Compare::is_transparent; }` and use `std::lower_bound` with a comparator lambda `cmp_(e.first, q)`. With `std::less<>` as `Compare` this lets `std::string_view` keys query `std::string` storage. Test both and keep old tests passing. Scoring: 10 points for doing this without duplicating the entire lookup path (a private template helper shared by both overloads).

Differential test design: seeded `std::mt19937` (fixed seed), 10,000 operations picked from insert/erase/operator[]/find on small key ranges (0..99) so collisions occur; after every operation compare `size()`, and every 100 operations compare full iteration order against `std::map`. A failing differential test prints seed and step.

Iterator conformance: `static_assert(std::forward_iterator<FlatMap<int,int>::const_iterator>)` is true because it is `vector::const_iterator`; `static_assert(std::ranges::forward_range<const FlatMap<int,int>>)`. For a hand-rolled iterator (as in `RingBuffer`), failures are usually a missing `difference_type`, missing default constructor, or non-const `operator==`.

Documented contract (README table): lookup O(log n) comparisons; insert/erase O(n) element moves in the worst case (O(log n) compares plus shift); iteration O(n) over contiguous memory; all mutations invalidate all iterators, pointers and references; no stability guarantees across mutation.

Reject any numbers without the harness.

## Worked example `RingBuffer`: answers to defense questions

- Why slots keep moved-from `T` after `pop`: the next `push` assigns over the slot; it is the cost of `std::array` storage requiring default-constructible `T`.
- Why `push` returns `bool`: a full buffer is an expected condition for a bounded queue; an exception would make a producer loop pay unwinding cost for normal backpressure.
- Wrap-around test: push 1,2,3, pop, push 4 yields logical order 2,3,4 (verified).
- Iterator invalidation: documented, not enforced.
