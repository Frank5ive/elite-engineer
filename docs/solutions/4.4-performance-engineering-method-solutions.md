## Section 7 retrieval answers

1. Example: "p95 of `POST /export` for a 5,000-row course under 3 s, with 5 concurrent exports, on staging with the production-size dataset, measured over 200 requests after warmup." Missing from the original: metric, percentile, data size, load, environment, threshold, and who decided "faster" is needed.
2. Overall speedup is limited by the fraction affected: `1 / ((1 - f) + f / s)`. With f = 0.2, s = 4: 1 / (0.8 + 0.05) = 1.176, about 18% faster at best.
3. `tottime` is time inside the function itself excluding callees; `cumtime` includes callees. Start with `cumtime` to find which call trees dominate, then `tottime` to find the hot leaf.
4. `py-spy`: a running or production-like process, no code change, low overhead, hangs (`dump`). `cProfile`: exact call counts, scripts/tests you can launch, small programs; but overhead distorts functions called very often.
5. The plan changed from a full table scan to an index search on `idx_grades_user_course`. That is a statement about the access path, not elapsed time; small tables, low selectivity, or the real bottleneck elsewhere may mean no gain. Measure.
6. B-tree entries are ordered by user_id then course_id, so a prefix (user_id) is a contiguous range; course_id alone is scattered across the index (a full index scan at best). Some engines can use skip-scan; check your planner.
7. mean = (99*1 + 1000)/100 = 10.99; p50 = 1; p99 = 1 (rank 99 of 100); p100 = 1000. The mean (10.99) matches no request: 99 take 1, one takes 1000.
8. Percentiles are not linear; the p95 of the union is not the mean of per-server p95s (weights, distribution shapes differ). Merge histograms with identical buckets (or raw samples) and compute the percentile from the merged data.
9. A generator that waits for a slow response before issuing the next request stops sending during the stall, so the requests that would have queued behind it are never measured. Reported tail is too good. Fix: open model with a fixed arrival schedule, latency measured from intended send time.
10. L = 80 * 0.25 = 20 in flight on average. With 16 workers, demand exceeds capacity: the queue grows without bound (latency rises) until clients time out or shedding occurs. Need at least 20 plus headroom, or reduce service time.
11. CPU frequency scaling / thermal (pin governor, warm up, repeat); background processes (isolate, close apps); cache state (warmup, state which you measure); GC/allocator (repeat, report spread); network jitter (local loopback or repeated, percentiles); shared cloud neighbors (dedicated host, interleaved A/B).
12. Hit rate too low (overhead without benefit); staleness serves wrong data; unbounded memory; stampede at expiry; shared key leaks per-user data; hides dependency problems; added invalidation bugs.
13. Query counts are deterministic and machine-independent, so they never flake and catch N+1 immediately. They do not detect slow individual queries, CPU hot loops, lock contention, or a missing index with unchanged count.

## 8.1 reference (percentiles and histogram)

Nearest-rank (verified): sorted `s`, index `ceil(p/100*n) - 1`. Linear method choice (document one): position `h = (p/100)*(n-1)`, result `s[floor(h)] + (h - floor(h)) * (s[ceil(h)] - s[floor(h)])`. Verified facts on 1..100: nearest-rank p50, p95, p99, p100 = 50, 95, 99, 100; single-element list returns that element for any p; empty list and p outside (0,100] raise `ValueError`.

Histogram: fixed bucket upper bounds `b_0 < b_1 < ...` plus an overflow bucket; `add` increments the bucket by `bisect_left`; `merge` adds counts elementwise (requires identical bounds; raise otherwise); `quantile_estimate(p)` walks cumulative counts and returns the bucket's upper bound. Error bound: the estimate is within one bucket width of the true value (unbounded for the overflow bucket; say so). Property tests: monotone in p; `min <= result <= max`; `hist(a).merge(hist(b)) == hist(a + b)` counts. Averaging demonstration (verified): with `a = [1.0]*100`, `b = [1.0]*98 + [100.0, 100.0]`, p99(a)=1, p99(b)=100, but p99(a+b)=1.0, not 50.5. Marking: method documented 20%, properties 30%, merge equality 25%, error bound 15%, averaging demo 10%.

## 8.3 reference (query plan investigation)

Verified plan change (SQLite 3.46): `SCAN grades` becomes `SEARCH grades USING INDEX idx_grades_user_course (user_id=? AND course_id=?)`. Other expected behaviors to verify yourself: `WHERE LOWER(email) = ?` does not use a plain index on `email` (create an expression index or store a normalized column; SQLite and PostgreSQL both support indexes on expressions, e.g. `CREATE INDEX ix ON users (LOWER(email))`, checked on SQLite below); an index on `(course_id, user_id)` is not used for a `user_id`-only filter as a rule; a join aggregate benefits from an index on the join/filter column of the larger table. Non-helping index example: an index on a low-cardinality column such as a boolean `passed` where most rows match, or an index duplicating a prefix of an existing composite; explain with the plan and write cost (insert timing measured with your harness). PostgreSQL: compare estimated vs actual rows from `EXPLAIN (ANALYZE, BUFFERS)`; large mismatches suggest stale statistics (`ANALYZE`); ANALYZE executes the statement, so wrap writes in a rolled-back transaction. Marking: predictions written before measuring 25%, plan output captured 25%, measurements with spread 25%, the non-helping index explained 25%.

## Section 9 project: reference approach and marking notes

Reference sequence:
1. Requirement in writing (metric, percentile, load, data size, environment); get it from a stakeholder or declare it an assumption.
2. v0 with N+1 queries, no index on `grades(course_id)`, and an O(n^2) Python step; tag `v0`.
3. Harness first, and test the harness (percentile function with known inputs; a controlled `sleep` workload to validate that the harness reports roughly what was injected; state the tolerance you observed).
4. Baseline on 3 dataset sizes; query count per request via a SQLAlchemy `before_cursor_execute` event counter (`before_cursor_execute`, tested on SQLAlchemy 2.x: it fires once per statement on the Engine).
5. Locate: query count, cProfile, plans. Write `HYPOTHESES.md` entries (H1 N+1, H2 index, H3 hot loop) with predicted mechanism and effect before coding, committed before the change commit.
6. One change per commit, equivalence test (v0 output equals new output on all sizes), re-measure with identical harness.
7. Caching experiment: key includes teacher id and filters; TTL with injected clock; invalidation on grade write; test staleness bound; stampede test in the extension. Keep it only if the uncached best version still misses the requirement and hit-rate evidence supports it.
8. Guard: a test asserting query count `<= K` for the dashboard (K chosen from the measured optimized count plus a stated margin), shown failing when N+1 is reintroduced; benchmark rule with `regressed` using a threshold derived from your measured MAD.
9. Mid-way change (median grade, date range): median is awkward in portable SQL; options are fetching grades per course and computing in Python (simple, memory cost), a window or percentile function (engine-specific: PostgreSQL has `percentile_cont(0.5) WITHIN GROUP (ORDER BY x)`; stock SQLite has no median function), or a precomputed summary table (staleness trade-off). Re-baseline; report which earlier optimizations still hold and why.
10. Load test: state open or closed model, steady-state window, generator CPU check, and say whether your tool measures from intended send time (wrk2 and k6's arrival-rate executors do; see the lesson's section on coordinated omission).

Marking notes: deduct heavily for numbers without environment or spread; a negative result reported honestly is worth full marks in that row, while a project in which every hypothesis succeeded should prompt the reviewer to ask how hypotheses were chosen. Credit alternative explanations (for example the endpoint's cost is serialization, not SQL) when supported by a profile. PHP/Moodle note acceptance: names at least two profilers and Moodle's query counters (`$CFG->perfdebug`, `$DB->perf_get_reads()`), proposes `get_in_or_equal` or a single SQL for per-row lookups, and MUC for repeated computation, each tied to the Moodle version checked.
