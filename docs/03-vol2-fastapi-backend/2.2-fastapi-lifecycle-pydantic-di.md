## 1. Engineering problem

You inherit an endpoint written in a hurry:

```python
@app.post("/users")
async def create_user(request: Request):
    data = await request.json()
    user = db.execute(f"INSERT INTO users VALUES ('{data['name']}', {data['age']})")
    return {"user": user, "password_hash": user.pw}
```

It crashes with a `KeyError` (HTTP 500) when `name` is missing, accepts `age: "abc"` until the database complains, is open to SQL injection, leaks `password_hash`, uses a global `db`, and cannot be tested without a database. Each flaw is a different lesson, but the *structural* fix is one idea: **declare the boundary**. Put the input shape, the output shape, and the collaborators in the function signature, and let the framework validate, serialize, document and inject them. FastAPI plus Pydantic v2 is a machine for doing that. If you do not know where each of those steps happens, you cannot debug a 422 you did not expect, a field that silently vanished from a response, or a test that mutates another test's data.

## 2. Learning objectives

After this lesson you can:

1. Trace one request through Uvicorn, ASGI, middleware, routing, dependency resolution, validation, your function, response serialization, and exception handlers, naming where each failure becomes which status code.
2. Build a CRUD API from a blank repository with a router package, Pydantic v2 schemas separating create/replace/patch/output models, and `response_model` filtering.
3. Distinguish Pydantic lax from strict validation with a runnable example, and use `Annotated` constraints, `extra="forbid"`, and `model_dump(exclude_unset=True)` to implement correct PATCH semantics.
4. Write dependencies, including a `yield` dependency and a sub-dependency, and explain their cache and scope behaviour.
5. Write pytest tests with `TestClient` and `app.dependency_overrides` that are isolated from each other, and prove isolation with a test that would fail if state leaked.
6. Install exception handlers so that validation errors, framework HTTP errors and domain exceptions all return RFC 9457 problem+json (Lesson 2.1).
7. Choose `def` versus `async def` for a path operation and justify it.

## 3. First-principles explanation

### 3.1 ASGI, Uvicorn, Starlette, FastAPI

**ASGI** is a Python interface between a server and an async application: the app is a callable `async def app(scope, receive, send)`. `scope` describes the connection (type `http`, `websocket`, or `lifespan`; path; headers), `receive` yields incoming events (request body chunks), `send` emits outgoing events (response start with status and headers, then body chunks). **Uvicorn** is an ASGI server: it owns sockets, parses HTTP, and calls your app. **Starlette** is a toolkit implementing routing, middleware, requests and responses on ASGI. **FastAPI** subclasses Starlette and adds: parameter extraction from function signatures, dependency injection, Pydantic validation and serialization, and OpenAPI generation. Framework behaviour: FastAPI builds on Starlette; when something about requests, responses, middleware or test client seems odd, the answer is often in the Starlette docs.

Process model: `uvicorn app.main:app` runs one process with one event loop. For multiple CPU cores you run multiple worker processes (Uvicorn `--workers`, or run one process per container and scale by replicas; the FastAPI deployment docs (checked October 2026) show `fastapi run --workers N` and `uvicorn --workers N` and no longer present Gunicorn as the default). Each process has its own memory: a module-level `dict` is *per process*, which is why this lesson's in-memory store is a teaching device only.

### 3.2 The request lifecycle

```
client -> Uvicorn -> [ASGI middleware stack] -> router -> match path+method
      -> resolve dependencies (sub-dependencies first, cached per request)
      -> parse + validate path / query / header / cookie / body (Pydantic)
           any failure -> RequestValidationError -> 422 handler
      -> call your function (def: threadpool; async def: event loop)
           HTTPException / domain exception -> exception handlers
      -> response_model: validate + filter + serialize return value
      -> response middleware -> Uvicorn -> client
      -> exit code of `yield` dependencies (timing: see 3.6)
```

Important consequences: validation runs *before* your function, so your function only sees valid data; dependencies run before validation of the body completes in the sense that FastAPI collects errors from all of them and reports together; and the return value is validated *again* against `response_model`, which is how you catch your own serialization bugs and also how you filter fields.

**Lifespan.** Startup and shutdown work (create a connection pool, load a model) belongs in a lifespan context manager, not in import-time code:

```python
from contextlib import asynccontextmanager

@asynccontextmanager
async def lifespan(app: FastAPI):
    app.state.pool = make_pool()      # startup
    yield
    app.state.pool.close()            # shutdown

app = FastAPI(lifespan=lifespan)
```

`TestClient` only runs the lifespan if used as a context manager (`with TestClient(app) as c:`); verified in this lesson's environment.

### 3.3 Routing and parameters

Parameters are classified *by where they appear in the signature*:

- Name appears in the path template (`/tasks/{task_id}`): **path** parameter, always required.
- A scalar type (or `list` with `Query`) not in the path: **query** parameter.
- A Pydantic model type: **JSON body**. Multiple body models are nested by parameter name.
- `Header(...)`, `Cookie(...)`, `Form(...)`, `File(...)` explicitly.

Constraints go in `Annotated[int, Path(ge=1)]` or `Annotated[int, Query(ge=1, le=100)]`. Annotated is the current documented style (it composes and is reusable as a named type alias). Route order matters: Starlette matches routes in registration order, so `/tasks/me` must be declared before `/tasks/{task_id}`.

### 3.4 Pydantic v2 validation and serialization

Pydantic v2 compiles each model into a validator written in Rust (`pydantic-core`). Key behaviours (Pydantic v2; verify against docs.pydantic.dev for your version):

- **Lax mode (default) coerces.** `"4"` becomes `4` for an `int` field. In lax mode Python-side validation also accepts `True` for an `int` field and gives `1` (observed in this lesson's testing). Use `Field(strict=True)` or `StrictInt` to reject both; strict rejects `"4"` and `True`. For a money or quantity field, strict is usually what you want. Note JSON input and Python input follow slightly different conversion tables; the documented conversion table is the authority. Checked on Pydantic 2.14.1: `TypeAdapter(int)` gives `1` for Python `True` and for JSON `true` in lax mode, and `strict=True` rejects `True`.
- **Unknown fields**: ignored by default. `ConfigDict(extra="forbid")` makes them errors, which catches client typos (`priorty`).
- **Constraints**: `Field(ge=1, le=5)`, `StringConstraints(strip_whitespace=True, min_length=1)`.
- **Optional is not default**: in v2, `x: int | None` with no default is *required but nullable*; give `= None` to make it optional.
- **`model_dump(exclude_unset=True)`** returns only the fields the client actually sent. That is the only way to tell "field omitted" from "field set to null" (PATCH).
- **`from_attributes=True`** lets `Model.model_validate(obj)` read attributes from ORM objects or dataclasses (v1 called this `orm_mode`).
- **Validators**: `@field_validator("title")` and `@model_validator(mode="after")` for rules not expressible as constraints. Keep them pure (no I/O).

Use separate models per purpose: `TaskCreate` (what the client may set), `TaskUpdate` (full replacement), `TaskPatch` (all optional), `TaskOut` (what you reveal). One model for everything leaks internal fields and makes PATCH impossible to express.

### 3.5 `response_model`

`response_model=TaskOut` (or the return type annotation `-> TaskOut`) tells FastAPI to validate and filter the returned object through `TaskOut`. Returning an object with a `password` attribute through a model that lacks it drops the field. Observed output in this lesson's testing: `{'name': 'a'}` for an object with `name` and `password`. This filtering is a safety net, not a substitute for designing output models properly. `status_code=201` sets the success code; `response_model_exclude_unset` and friends exist but explicit models are clearer.

### 3.6 Dependency injection

A dependency is any callable; declare it with `Depends(callable)`. FastAPI calls it per request, passes its own parameters (themselves resolved from path/query/body/other dependencies), and injects the result. Properties:

- **Caching per request**: the same dependency used twice in one request is called once (`use_cache=True` default).
- **Sub-dependencies**: dependencies can depend on dependencies; FastAPI resolves the graph.
- **`yield` dependencies** give setup/teardown, like a context manager (Lesson 1.2): code before `yield` runs before your function; code after runs on exit. Behaviour matters for databases: by default (scope `"request"`) the exit code runs **after the response has been sent**; with `Depends(dep, scope="function")` it runs after your function returns but **before** the response is sent (documented at fastapi.tiangolo.com, "Dependencies with yield", and in the `Depends` signature in FastAPI 0.162). An exception raised in post-response exit code cannot change the response the client already received. Lesson 2.4 shows the practical consequence for commits and has a lab that demonstrates it.
- **Overrides**: `app.dependency_overrides[original] = replacement` swaps a dependency for the whole app. This is the testing seam. Key by the *original callable object*, and always clear in teardown.
- **Dependencies are not magic globals**: they make the collaborator visible in the signature, which is what makes tests and reasoning possible. Alternative: constructor injection via classes with `__call__`, or a dependency returning a service object. Avoid inventing a container framework (Lesson 4.1 on unnecessary complexity).

### 3.7 `def` versus `async def`

Plain `def` path operations run in a threadpool so they do not block the event loop; `async def` runs *on* the event loop and must never call blocking code (a sync database driver, `time.sleep`, `requests.get`). If a function does blocking I/O, use `def`. Use `async def` only when everything you await is truly async. The wrong choice does not fail loudly: it makes the whole server stall under load. Lesson 2.6 measures this.

### 3.8 Exception handlers

`HTTPException` (Starlette's, which FastAPI's subclasses) produces a response with `{"detail": ...}` by default. `RequestValidationError` produces 422 with a list of errors. You override with `@app.exception_handler(ExcType)`. To catch routing 404/405 you must register a handler for **Starlette's** `HTTPException`, not only FastAPI's, because the router raises Starlette's (the code below does this and the tests confirm it). Domain exceptions (`TaskNotFound`) keep route code free of HTTP details: raise a domain error, map it once.

### 3.9 Structure and testing

`APIRouter(prefix=..., tags=[...])` groups related operations; `app.include_router(router)` mounts it. Suggested layout: `app/main.py` (assemble), `app/routers/` (HTTP layer), `app/schemas.py` (Pydantic), `app/deps.py` (wiring), `app/errors.py`, a store/service layer with no FastAPI imports (testable alone). `TestClient` (Starlette) drives the ASGI app in-process, no sockets. Note: with Starlette 1.10 the test client emits a `StarletteDeprecationWarning` when it uses `httpx` and asks for `httpx2` instead (seen in this lesson's environment). Checked on Starlette 1.10.0: the warning text is "Using `httpx` with `starlette.testclient` is deprecated; install `httpx2` instead", plain `httpx` 0.28.1 still works (warning only) and the Starlette docs say `httpx2` is included in `starlette[full]`. Install `httpx2` to silence it; the test code below is unchanged either way.

### 4.1 Schemas: one model per purpose (`app/schemas.py`)

```python
from datetime import datetime
from typing import Annotated, Literal
from pydantic import BaseModel, ConfigDict, Field, StringConstraints

Title = Annotated[str, StringConstraints(strip_whitespace=True, min_length=1, max_length=120)]

class TaskCreate(BaseModel):
    model_config = ConfigDict(extra="forbid")
    title: Title
    priority: int = Field(default=3, ge=1, le=5)

class TaskUpdate(BaseModel):          # PUT: full replacement, every field required
    model_config = ConfigDict(extra="forbid")
    title: Title
    priority: int = Field(ge=1, le=5)
    done: bool

class TaskPatch(BaseModel):           # PATCH: only fields the client sent are applied
    model_config = ConfigDict(extra="forbid")
    title: Title | None = None
    priority: int | None = Field(default=None, ge=1, le=5)
    done: bool | None = None

class TaskOut(BaseModel):
    model_config = ConfigDict(from_attributes=True)
    id: int
    title: str
    priority: int
    done: bool
    created_at: datetime

class TaskPage(BaseModel):
    items: list[TaskOut]
    total: int
    limit: int
    offset: int

StatusFilter = Literal["open", "done", "all"]
```

Design notes: `Title` is a reusable annotated type, so the trimming rule lives in one place. `TaskCreate` has no `done` or `id`: clients cannot set them (with `extra="forbid"` they get a 422, not silent ignoring). `TaskPatch` fields are `X | None = None`, with `exclude_unset` doing the real work. Pagination envelope is an object (Lesson 2.1).

### 4.2 Store and errors

```python
# app/store.py: framework-free, replaced by a database in Lesson 2.3/2.4
from dataclasses import dataclass, field
from datetime import UTC, datetime

@dataclass
class Task:
    id: int
    title: str
    priority: int
    done: bool = False
    created_at: datetime = field(default_factory=lambda: datetime.now(UTC))

class TaskStore:
    def __init__(self) -> None:
        self._rows: dict[int, Task] = {}
        self._next_id = 1
    def add(self, title: str, priority: int) -> Task:
        task = Task(id=self._next_id, title=title, priority=priority)
        self._rows[task.id] = task
        self._next_id += 1
        return task
    def get(self, task_id: int) -> Task | None:
        return self._rows.get(task_id)
    def list(self, status: str, limit: int, offset: int) -> tuple[list[Task], int]:
        rows = sorted(self._rows.values(), key=lambda t: t.id)
        if status == "open":
            rows = [t for t in rows if not t.done]
        elif status == "done":
            rows = [t for t in rows if t.done]
        return rows[offset : offset + limit], len(rows)
    def delete(self, task_id: int) -> bool:
        return self._rows.pop(task_id, None) is not None
```

```python
# app/errors.py: one error format for everything (Lesson 2.1)
from fastapi import FastAPI, Request
from fastapi.exceptions import RequestValidationError
from fastapi.responses import JSONResponse
from starlette.exceptions import HTTPException as StarletteHTTPException

class TaskNotFound(Exception):
    def __init__(self, task_id: int) -> None:
        self.task_id = task_id

def _problem(request: Request, status: int, title: str, detail: str | None = None, **extra):
    body = {"type": "about:blank", "title": title, "status": status, "instance": request.url.path}
    if detail:
        body["detail"] = detail
    body.update(extra)
    return JSONResponse(body, status_code=status, media_type="application/problem+json")

def install_error_handlers(app: FastAPI) -> None:
    @app.exception_handler(TaskNotFound)
    async def _not_found(request: Request, exc: TaskNotFound):
        return _problem(request, 404, "Task not found", f"No task with id {exc.task_id}")

    @app.exception_handler(RequestValidationError)
    async def _invalid(request: Request, exc: RequestValidationError):
        errors = [{"loc": list(e["loc"]), "msg": e["msg"], "type": e["type"]} for e in exc.errors()]
        return _problem(request, 422, "Validation failed", errors=errors)

    @app.exception_handler(StarletteHTTPException)
    async def _http(request: Request, exc: StarletteHTTPException):
        resp = _problem(request, exc.status_code, str(exc.detail))
        if exc.headers:
            resp.headers.update(exc.headers)
        return resp
```

Choices: we return only `loc`, `msg`, `type` from validation errors (Pydantic's error dict can include `input` and `ctx`, which may echo user data back; omitting them is a deliberate security/privacy decision, review it for your data). The `_http` handler copies `exc.headers` so that a 405 keeps its `Allow` header (a 405 should carry `Allow`, Lesson 2.1). Observed in this lesson's environment: `DELETE /tasks` answers `Allow: POST` although `GET /tasks` also exists, and `POST /tasks/1` answers `Allow: GET` although PUT, PATCH and DELETE exist. With separate routes per method on one path, the framework-generated `Allow` listed only one method. The header is therefore incomplete for contract purposes (re-checked on FastAPI 0.162.0 and Starlette 1.10.0: the value is the method set of a single partially matching route, so route declaration order decides which one you see); Section 8 and the solutions show how to compute it yourself..

### 4.3 Dependencies (`app/deps.py`)

```python
from collections.abc import Iterator
from typing import Annotated
from fastapi import Depends, Query
from .store import TaskStore

_STORE = TaskStore()      # process-wide for this lesson only

def get_store() -> Iterator[TaskStore]:
    yield _STORE          # a yield dependency; with a DB session, cleanup goes after yield

Store = Annotated[TaskStore, Depends(get_store)]

class Pagination:
    def __init__(self, limit: Annotated[int, Query(ge=1, le=100)] = 20,
                 offset: Annotated[int, Query(ge=0)] = 0) -> None:
        self.limit, self.offset = limit, offset

Page = Annotated[Pagination, Depends()]
```

`Store` and `Page` are named `Annotated` aliases, so route signatures read `store: Store, page: Page`. `Depends()` with no argument uses the annotated class itself as the dependency, so FastAPI reads `Pagination.__init__`'s parameters as query parameters, and the limit cap (2.1: enforced maximum) lives in one place.

### 4.4 Router and app

```python
# app/routers/tasks.py
from typing import Annotated
from fastapi import APIRouter, Path, Query, Response, status
from ..deps import Page, Store
from ..errors import TaskNotFound
from ..schemas import StatusFilter, TaskCreate, TaskOut, TaskPage, TaskPatch, TaskUpdate

router = APIRouter(prefix="/tasks", tags=["tasks"])
TaskId = Annotated[int, Path(ge=1)]

@router.post("", response_model=TaskOut, status_code=status.HTTP_201_CREATED)
def create_task(body: TaskCreate, store: Store, response: Response) -> TaskOut:
    task = store.add(body.title, body.priority)
    response.headers["Location"] = f"/tasks/{task.id}"
    return TaskOut.model_validate(task)

@router.get("", response_model=TaskPage)
def list_tasks(store: Store, page: Page,
               status_: Annotated[StatusFilter, Query(alias="status")] = "all") -> TaskPage:
    rows, total = store.list(status_, page.limit, page.offset)
    return TaskPage(items=[TaskOut.model_validate(r) for r in rows],
                    total=total, limit=page.limit, offset=page.offset)

@router.get("/{task_id}", response_model=TaskOut)
def get_task(task_id: TaskId, store: Store) -> TaskOut:
    task = store.get(task_id)
    if task is None:
        raise TaskNotFound(task_id)
    return TaskOut.model_validate(task)

@router.put("/{task_id}", response_model=TaskOut)
def replace_task(task_id: TaskId, body: TaskUpdate, store: Store) -> TaskOut:
    task = store.get(task_id)
    if task is None:
        raise TaskNotFound(task_id)
    task.title, task.priority, task.done = body.title, body.priority, body.done
    return TaskOut.model_validate(task)

@router.patch("/{task_id}", response_model=TaskOut)
def patch_task(task_id: TaskId, body: TaskPatch, store: Store) -> TaskOut:
    task = store.get(task_id)
    if task is None:
        raise TaskNotFound(task_id)
    for name, value in body.model_dump(exclude_unset=True).items():
        setattr(task, name, value)
    return TaskOut.model_validate(task)

@router.delete("/{task_id}", status_code=status.HTTP_204_NO_CONTENT)
def delete_task(task_id: TaskId, store: Store) -> Response:
    if not store.delete(task_id):
        raise TaskNotFound(task_id)
    return Response(status_code=status.HTTP_204_NO_CONTENT)
```

```python
# app/main.py
from fastapi import FastAPI
from .errors import install_error_handlers
from .routers import tasks

app = FastAPI(title="Task API", version="0.1.0")
install_error_handlers(app)
app.include_router(tasks.router)
```

Notes. The query parameter is aliased to `status` but the Python name is `status_`, because `status` is the imported module. Operations are plain `def` because the store is synchronous. DELETE of a missing task returns 404 here; Lesson 2.1 allowed either, and the choice is the API policy. A weakness to notice: `PATCH` with `{"title": null}` passes validation (the field is `Title | None`), and then `setattr` sets `title = None`. The test list below does not cover it; Section 6 and Section 8 pick it up.

## 5. Production perspective

**Maintainability.** Thin routers; logic in framework-free functions/classes; schemas in one place; no business rules in validators beyond data shape. Name dependency aliases (`Store`, `Page`) so signatures stay readable.

**Correctness.** Validate at the boundary (Pydantic), enforce invariants in the domain/database (2.3), never trust client-supplied ids or flags. Be explicit about lax versus strict for money, quantities and flags.

**Security.** Output models are an allow-list; never return ORM objects directly. `extra="forbid"` stops mass-assignment style bugs (client sets `is_admin`). Do not echo `input` back in error bodies for secrets-bearing fields. CORS, authentication and secrets: Lesson 2.5.

**Performance.** Pydantic v2 validation is fast but not free: very large payloads, deep nesting and huge lists cost. Cap sizes. Choose `def`/`async def` correctly (3.7). Measure with a profiler or load test before optimizing (Lesson 4.4); do not quote speed numbers you have not measured.

**Failure handling and observability.** Register a catch-all handler for unexpected `Exception` that logs with a request id and returns a generic 500 problem (no stack trace in body). Log route templates, status and latency. Add `/healthz` (Lesson 2.7).

**Testing.** Unit-test the store directly; test the HTTP contract through `TestClient`; override dependencies instead of monkeypatching modules. Add one test per documented status code.

**Senior habits.** Reads the generated `/openapi.json` as the contract and checks it matches intent. Avoids global mutable state; notices when worker count multiplies a "singleton". Treats a 422 on an unexpected field as a *contract* bug to investigate, not noise.

**Beginner mistakes and diagnosis.**

| Mistake | Symptom | Diagnosis |
|---|---|---|
| One model for create/update/output | Clients can set `id`; passwords appear in output | Read the model in `/docs`: any field in more than one role? |
| Blocking call inside `async def` | Whole API stalls under concurrent load; single requests are fine | Run two slow requests in parallel and compare total time; look for sync drivers or `time.sleep` in `async def` |
| Mutable default or module-global state in tests | Tests pass alone, fail together or in a different order | `pytest -p no:randomly` versus `pytest -x --lf`; look for missing `dependency_overrides.clear()` |
| Wrong handler class for 404/405 | Unknown routes return `{"detail": "Not Found"}` while your errors are problem+json | Register against `starlette.exceptions.HTTPException` |
| Route order | `/tasks/me` is matched as `task_id="me"` and returns 422 | Move static routes before parameterized ones |

## 6. Failure laboratory

Here is a test suite for the Tasks API plus one change. **Predict** the outcome of each numbered step before running anything.

```python
# bug_lab.py: place beside the app and run with pytest
from fastapi.testclient import TestClient
from app.main import app

client = TestClient(app)               # module-level, no overrides, no `with`

def test_a_creates():
    r = client.post("/tasks", json={"title": "a"})
    assert r.json()["id"] == 1

def test_b_creates():
    r = client.post("/tasks", json={"title": "b"})
    assert r.json()["id"] == 1

def test_c_patch_null():
    t = client.post("/tasks", json={"title": "c"}).json()
    r = client.patch(f"/tasks/{t['id']}", json={"title": None})
    assert r.status_code == 422
```

Predict: (1) Which of the three tests fail when run in file order? (2) Do the results change under `pytest -k test_b_creates` alone? (3) For `test_c_patch_null`, what status does the current code return and what does a subsequent `GET` of that task return? (4) Name two ways to fix the ordering problem and one fix for the null problem. (5) After the fixes, what should the test suite prove for PATCH `{"title": null}`?

### Reveal (read after predicting)

1. `test_a_creates` passes. `test_b_creates` fails (id is 2) because the module-level `_STORE` in `app/deps.py` survives across tests. `test_c_patch_null` fails (see 3).
2. Run alone, `test_b_creates` passes: the failure is order-dependent state, the worst kind of flaky test.
3. `TaskPatch.title` is `Title | None`, so `null` validates; `exclude_unset` keeps it because it *was* set; `setattr` stores `None`; then `TaskOut.model_validate(task)` raises a Pydantic `ValidationError` (`title: Input should be a valid string`). Under a real server that is an unhandled exception, so a 500; `TestClient` re-raises it into the test by default, which is what you see (observed). Either way the status is not 422, and the store has already been mutated: the task now holds `title=None` and every later read of it fails. The bug is both a validation hole and a data-corruption path.
4. Isolation: use the `client` fixture with `dependency_overrides` and a fresh store (the conftest above), or reset the module store in an autouse fixture. Null: reject explicit nulls for non-nullable fields, for example a `@model_validator(mode="after")` on `TaskPatch` that raises if any *set* field is `None`, or `Annotated` field types that do not include `None` combined with a different mechanism for omission (a sentinel). The validator approach is simplest.
5. That PATCH with an explicit `null` for `title`, `priority` or `done` returns 422 with the field's `loc`, that the stored task is unchanged, and that omitting the field still works. Prove "unchanged" by a follow-up GET.

Systematic diagnosis for flaky or order-dependent tests: (a) rerun the failing test alone; (b) rerun the file in reversed or random order; (c) search for module-level mutable state and for overrides never cleared; (d) print object ids of shared stores; (e) fix the isolation, then re-run the whole suite 20 times (`for i in $(seq 20); do pytest -q || break; done`).
