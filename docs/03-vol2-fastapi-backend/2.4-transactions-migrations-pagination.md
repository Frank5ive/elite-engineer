## 1. Engineering problem

A ticketing service sells the last 100 seats. Load testing with one client shows it is correct. On launch day, 400 concurrent buyers produce 112 confirmed tickets for 100 seats. The code was `seats = get(); if seats > 0: set(seats - 1)`: each request read the same value, and each wrote back its own decrement. Nothing crashed; no log line is wrong; the invariant is simply false.

Two more incidents in the same family. A deploy adds `NOT NULL` column `email_verified` to a 200 million row table with a default; the migration holds a lock for 25 minutes and the API times out while old application instances, still running, insert rows without the column. And an infinite-scroll feed using `OFFSET` shows duplicates and skips posts because new posts arrive while the user scrolls, and page 4000 takes seconds because the database walks and discards 80,000 rows.

All three come from treating the database as a variable store instead of a concurrent system with rules. This lesson gives you the rules (ACID, isolation levels), the tools (atomic SQL, row locks, version columns, retry), the discipline for changing schemas while running (expand/contract), and a pagination method that does not degrade.

## 3. First-principles explanation

### 3.1 ACID, in practice

- **Atomicity**: a transaction's changes all become visible or none do. `COMMIT` or `ROLLBACK`. In PostgreSQL even DDL is transactional (MySQL/MariaDB commit implicitly on DDL, Lesson 2.3).
- **Consistency**: constraints hold at commit (PK, FK, unique, check). This is why Lesson 2.3 put rules in the schema. It does not mean your *business* invariants hold unless you encode them.
- **Isolation**: concurrent transactions behave as if (to a degree set by the isolation level) they ran one at a time.
- **Durability**: after commit returns, the data survives a crash (WAL flushed, subject to configuration such as `synchronous_commit`).

Mechanism in PostgreSQL (MVCC): writers create new row versions rather than overwriting; each statement or transaction sees a snapshot of committed data. Readers do not block writers and vice versa. Writers to the *same row* do block each other: the second `UPDATE` waits for the first to commit or roll back. Most concurrency bugs live in the gap between a read and the write that depends on it.

### 3.2 Isolation levels and anomalies

Anomalies:

- **Dirty read**: reading uncommitted data. PostgreSQL never allows it (its READ UNCOMMITTED behaves as READ COMMITTED).
- **Non-repeatable read**: the same row read twice in a transaction returns different values because another transaction committed in between.
- **Phantom**: re-running a range query returns different rows.
- **Lost update**: two transactions read a value, each writes a function of what it read; one overwrite is lost.
- **Write skew**: two transactions read overlapping data, make disjoint writes based on it, and together violate an invariant neither alone violates (two doctors both go off call because each saw the other on call).

PostgreSQL levels (per the PostgreSQL docs, chapter "Transaction Isolation"; verify the details for your version):

| Level | Snapshot taken | Prevents | Still allows |
|---|---|---|---|
| READ COMMITTED (default) | per statement | dirty reads | non-repeatable reads, phantoms, lost update (read-modify-write in app), write skew |
| REPEATABLE READ | per transaction | the above plus phantoms (in PostgreSQL's snapshot implementation); a concurrent update of a row you also update fails with a serialization error | write skew |
| SERIALIZABLE | per transaction plus conflict tracking (SSI) | all, including write skew; may abort with serialization failure | nothing, but you must retry |

The SQL standard's table differs from PostgreSQL's implementation (for example, PostgreSQL's REPEATABLE READ is snapshot isolation). MySQL/InnoDB's default is REPEATABLE READ with different locking behaviour (gap locks); do not transfer conclusions between engines without testing (check the MySQL manual for the version you run).

**Observed results** (labs in Section 4, PostgreSQL 18.6): the naive read-modify-write lost updates under READ COMMITTED (985 left where 800 expected); write skew committed on both transactions at READ COMMITTED and at REPEATABLE READ (0 doctors on duty); SERIALIZABLE aborted one with `SerializationFailure`, leaving 1 on duty.

### 3.3 Fixing a lost update: four tools

1. **Atomic update in SQL**: `UPDATE stock SET qty = qty - 1 WHERE id = 1 AND qty > 0`. The read and write happen in one statement under the row lock; check `rowcount` to see if it applied. Best option when the rule is expressible as one statement. No retries needed.
2. **Pessimistic lock**: `SELECT ... FOR UPDATE` locks the selected rows until the transaction ends; competing transactions wait. Use when you must read, compute in application code, then write. Cost: waiting, deadlock risk, and holding locks across slow work (never call external services while holding locks). Variants: `FOR UPDATE NOWAIT` (error instead of waiting) and `SKIP LOCKED` (skip locked rows; the basis of job queues, Lesson 2.6).
3. **Optimistic concurrency**: add a `version` column; `UPDATE ... SET qty = ?, version = version + 1 WHERE id = ? AND version = ?`; if zero rows updated, someone else won, so reload and retry (or return `412`/`409` to the client, Lesson 2.1 `If-Match`). Good with low contention and long user think-time; bad under high contention (wasted work: observed 2,373 retries for 200 successful updates under 20 threads). SQLAlchemy supports it through `version_id_col` and raises `StaleDataError`.
4. **Higher isolation + retry**: REPEATABLE READ or SERIALIZABLE and retry on serialization failure (SQLSTATE `40001`) and deadlock (`40P01`). Needed for multi-row invariants (write skew) that no single-row trick covers.

For multi-row invariants there are also explicit constraints (a unique or exclusion constraint turns the invariant into something the database enforces), advisory locks, and locking a parent row as a mutex. Prefer the database enforcing the invariant over every code path remembering it.

### 3.4 Deadlocks

Transaction A locks row 1 then wants row 2; B locks row 2 then wants row 1. Neither can proceed. PostgreSQL detects the cycle (after `deadlock_timeout`, default 1s; confirmed with `SHOW deadlock_timeout` on PostgreSQL 18 and in the docs) and aborts one with `DeadlockDetected` (SQLSTATE 40P01). Fix by **acquiring locks in a consistent global order** (lock the lower id first), keeping transactions short, and retrying the aborted one. Diagnosis: the database log records both statements; reproduce with two transactions and a sleep between statements (lab below).

### 3.5 SQLAlchemy 2.x transactions

`Session` is a unit of work with an identity map; it begins a transaction lazily on first use. Preferred, explicit forms (SQLAlchemy 2.x):

```python
with Session(engine) as session:
    with session.begin():          # commit on success, rollback on exception
        ...
# equivalent shorthand:
with Session(engine) as session, session.begin():
    ...
```

Rules: one session per unit of work (per request), never shared between threads; do not keep a session open across user think-time; `expire_on_commit=False` is common in web code so objects remain readable after commit without a new query (decide consciously; it hides staleness). Engine-level: `engine.begin()` for Core. Isolation can be set per engine (`isolation_level="REPEATABLE READ"`) or per connection (`execution_options(isolation_level=...)`, used in the labs). `session.get(Model, 1, with_for_update=True)` and `select(...).with_for_update()` give row locks.

**Where to commit in FastAPI.** A `yield` dependency that opens the session and begins a transaction commits in its exit code. With the default dependency scope, exit code runs after the response is sent (Lesson 2.2, FastAPI docs "Dependencies with yield"). Consequence, verified here: if the commit itself fails, the client has already received `200`, and the failure is lost to the client. With `Depends(get_session, scope="function")` the exit code runs before the response is sent, and the same commit failure surfaced as `500` in my test. For a write endpoint where the client must know the commit result, use `scope="function"` or commit explicitly inside the path function. Minimal verified dependency:

```python
def get_session() -> Iterator[Session]:
    with SessionLocal() as session:
        with session.begin():          # commit on success, rollback on exception
            yield session

Db = Annotated[Session, Depends(get_session, scope="function")]
```

Verified behaviour: an exception raised in the endpoint rolls back (the counter stayed at 1 after a failing request that had incremented it).

### 3.6 Migrations with Alembic

A migration is versioned, ordered, reviewed code that evolves the schema; the database stores the current revision in `alembic_version`. Commands: `alembic revision --autogenerate -m "msg" --rev-id 0001`, `alembic upgrade head`, `alembic downgrade <rev>`, `alembic current`, `alembic history`. Setup: edit `migrations/env.py` to set `target_metadata = Base.metadata` and the URL (from the environment, never committed).

**Autogenerate is a draft**, not an answer. It compares your models with the live database. Observed trap: pointed at a shared database that also contained other tables, it generated `op.drop_table(...)` for every table not in the models. Always run it against a database containing only your schema, read every line, and restrict it with `include_object` when needed. It does not detect everything (server defaults, some type changes, renames appear as drop+add: data loss).

**Safe schema change = expand / migrate / contract**, because during a deploy old and new application versions run at once and the schema must work for both:

1. **Expand**: add the new thing in a backward-compatible way (nullable column, new table, new index created concurrently). Old code ignores it.
2. **Migrate**: deploy code that writes both old and new (dual-write) and reads the new with fallback; **backfill** existing rows in small batches (each batch its own short transaction) so no long locks and replication lag stays bounded.
3. **Contract**: after all code uses the new shape and a verification query shows no old-shape data, remove the old column or constraint in a *later* release; add `NOT NULL` once no nulls remain.

Lock facts to look up before any DDL on a big table (PostgreSQL docs "Explicit Locking" and `ALTER TABLE` notes; re-check for your version, since improvements land often; I ran these on PostgreSQL 18 and read `pg_locks`): `ALTER TABLE ... ADD COLUMN` (with or without a constant default) takes `AccessExclusiveLock` but only briefly, because modern PostgreSQL does not rewrite the table for a constant default; `ALTER COLUMN TYPE` takes `AccessExclusiveLock` and usually rewrites the table; `SET NOT NULL` scans the table under `AccessExclusiveLock` unless a valid `CHECK (col IS NOT NULL)` constraint already proves it; `ADD CONSTRAINT ... CHECK ... NOT VALID` is quick, and `VALIDATE CONSTRAINT` runs under `ShareUpdateExclusiveLock`, which does not block normal reads and writes. Adding a foreign key validates all rows too (`NOT VALID` then `VALIDATE CONSTRAINT` splits the work). `CREATE INDEX CONCURRENTLY` avoids blocking writes but cannot run inside a transaction block, which interacts with Alembic's transactional DDL (use `with op.get_context().autocommit_block():`, which exists in Alembic 1.20 and is documented under `MigrationContext.autocommit_block()`). Set `lock_timeout` for migrations so a blocked DDL fails fast instead of queuing behind a long query and blocking everyone behind *it*.

Downgrades: write them when cheap, but in production the real rollback plan for data changes is roll-forward or restore; a downgrade that drops a column destroys data.

### 3.7 Pagination: offset versus keyset

`OFFSET n LIMIT k` makes the database produce and discard n rows: cost grows linearly with page depth, and results shift when rows are inserted or deleted between requests (duplicates, gaps). **Keyset (seek) pagination** orders by a unique key and asks for rows after the last one seen:

```sql
SELECT id, submitted_at FROM submission
WHERE (submitted_at, id) < (:last_ts, :last_id)
ORDER BY submitted_at DESC, id DESC LIMIT :n + 1;
```

The row-value comparison with a matching composite index `(submitted_at DESC, id DESC)` gives a bounded index range scan (verified plan: `Index Only Scan` with `Index Cond: ROW(submitted_at, id) < ROW(...)`, no sort). The unique tiebreaker `id` makes the order total; without it, rows with equal timestamps can be skipped or repeated. Fetch `limit + 1` rows to know if a next page exists without a count. The cursor is an opaque encoding of the last row's sort key (base64 JSON in the lab); validate it strictly, and sign or bind it to the authenticated user if it could widen access. Limits: no jump to page N, no cheap total count, sort order is fixed by the index (each supported sort needs its own index), and mixed `ASC`/`DESC` keys need care (MySQL before 8.0 parsed but ignored `DESC` in index definitions; 8.0 supports real descending indexes). Offset remains fine for small, stable, human-paged tables (admin screens under a few thousand rows).

### 4.1 Race lab: the lost update and its four fixes (`race.py`)

```python
"""Lesson 2.4 race lab. Python 3.12+, SQLAlchemy 2.x, psycopg 3, PostgreSQL."""
import os
import threading
import time
from sqlalchemy import Integer, create_engine, select, text, update
from sqlalchemy.orm import DeclarativeBase, Mapped, Session, mapped_column
from sqlalchemy.orm.exc import StaleDataError

engine = create_engine(os.environ["DATABASE_URL"], pool_size=20)


class Base(DeclarativeBase):
    pass


class Stock(Base):
    __tablename__ = "stock"
    id: Mapped[int] = mapped_column(primary_key=True)
    qty: Mapped[int] = mapped_column(Integer)
    version: Mapped[int] = mapped_column(Integer, default=1)
    __mapper_args__ = {"version_id_col": version}   # SQLAlchemy optimistic locking


def reset(qty: int) -> None:
    Base.metadata.drop_all(engine)
    Base.metadata.create_all(engine)
    with Session(engine) as s, s.begin():
        s.add(Stock(id=1, qty=qty))


def read_qty() -> int:
    with Session(engine) as s:
        return s.scalar(select(Stock.qty).where(Stock.id == 1))


def naive_sell() -> None:               # read-modify-write in Python: lost update
    with Session(engine) as s, s.begin():
        row = s.get(Stock, 1)
        current = row.qty
        time.sleep(0.001)               # widen the race window (makes the bug reproducible)
        s.execute(text("UPDATE stock SET qty = :q WHERE id = 1"), {"q": current - 1})


def atomic_sell() -> None:              # push the arithmetic into the database
    with Session(engine) as s, s.begin():
        s.execute(update(Stock).where(Stock.id == 1, Stock.qty > 0)
                  .values(qty=Stock.qty - 1).execution_options(synchronize_session=False))


def locked_sell() -> None:              # pessimistic: SELECT ... FOR UPDATE
    with Session(engine) as s, s.begin():
        row = s.scalar(select(Stock).where(Stock.id == 1).with_for_update())
        time.sleep(0.001)
        row.qty -= 1


retries = 0
def optimistic_sell() -> None:          # version check + retry
    global retries
    while True:
        try:
            with Session(engine) as s, s.begin():
                row = s.get(Stock, 1)
                time.sleep(0.001)
                row.qty -= 1
            return
        except StaleDataError:
            retries += 1                # lost the race; reload and try again


def run(fn, n_threads=20, per_thread=10, start=1000) -> None:
    reset(start)
    ts = [threading.Thread(target=lambda: [fn() for _ in range(per_thread)]) for _ in range(n_threads)]
    t0 = time.perf_counter()
    for t in ts: t.start()
    for t in ts: t.join()
    expected = start - n_threads * per_thread
    print(f"{fn.__name__:16} expected={expected} actual={read_qty()} "
          f"elapsed={time.perf_counter()-t0:.2f}s")


if __name__ == "__main__":
    for f in (naive_sell, atomic_sell, locked_sell, optimistic_sell):
        run(f)
    print("optimistic retries:", retries)
```

Observed on my machine: `naive_sell expected=800 actual=985`; the other three reached 800; optimistic needed 2,373 retries and was the slowest. Elapsed times depend on your hardware and are not a benchmark; the correctness column and the retry count are the lesson. Why each choice: the `sleep` only widens a window that exists anyway (real network latency does the same); `retries` is a plain global incremented from threads, which is itself racy, acceptable for an approximate counter in a lab but not in production code. `synchronize_session=False` is correct here because no ORM objects depend on the result. Notice `atomic_sell` has `qty > 0`: that is the "never oversell" rule in the same statement; production code should check the `rowcount` and report "sold out".

### 4.2 Deadlock and write skew (`deadlock_skew.py`)

```python
import os, threading, time
from sqlalchemy import create_engine, text
from sqlalchemy.exc import DBAPIError

engine = create_engine(os.environ["DATABASE_URL"], pool_size=10)

def setup():
    with engine.begin() as c:
        c.execute(text("DROP TABLE IF EXISTS acct, oncall"))
        c.execute(text("CREATE TABLE acct (id int primary key, bal int)"))
        c.execute(text("INSERT INTO acct VALUES (1,100),(2,100)"))
        c.execute(text("CREATE TABLE oncall (doctor text primary key, on_duty bool)"))
        c.execute(text("INSERT INTO oncall VALUES ('alice',true),('bob',true)"))

def transfer(first, second, name, out):
    try:
        with engine.begin() as c:
            c.execute(text("UPDATE acct SET bal = bal - 1 WHERE id=:i"), {"i": first})
            time.sleep(0.3)
            c.execute(text("UPDATE acct SET bal = bal - 1 WHERE id=:i"), {"i": second})
        out[name] = "ok"
    except DBAPIError as e:
        out[name] = type(e.orig).__name__

def deadlock():
    setup(); out = {}
    a = threading.Thread(target=transfer, args=(1, 2, "A", out))
    b = threading.Thread(target=transfer, args=(2, 1, "B", out))
    a.start(); b.start(); a.join(); b.join()
    print("deadlock:", out)

def go_off_duty(me, level, barrier, out):
    try:
        with engine.connect().execution_options(isolation_level=level) as c:
            with c.begin():
                n = c.execute(text("SELECT count(*) FROM oncall WHERE on_duty")).scalar_one()
                barrier.wait()                       # both have read n=2
                if n >= 2:
                    c.execute(text("UPDATE oncall SET on_duty=false WHERE doctor=:d"), {"d": me})
        out[me] = "committed"
    except DBAPIError as e:
        out[me] = type(e.orig).__name__

def skew(level):
    setup(); out = {}; bar = threading.Barrier(2)
    ts = [threading.Thread(target=go_off_duty, args=(d, level, bar, out)) for d in ("alice", "bob")]
    [t.start() for t in ts]; [t.join() for t in ts]
    with engine.connect() as c:
        left = c.execute(text("SELECT count(*) FROM oncall WHERE on_duty")).scalar_one()
    print(f"{level:16} {out} on_duty_left={left}")

deadlock()
skew("READ COMMITTED"); skew("REPEATABLE READ"); skew("SERIALIZABLE")
```

Observed: `deadlock: {'A': 'DeadlockDetected', 'B': 'ok'}`; `READ COMMITTED` and `REPEATABLE READ` both committed with `on_duty_left=0`; `SERIALIZABLE` gave one `SerializationFailure` and `on_duty_left=1`. Which transaction is the victim of a deadlock or serialization failure is not specified; do not write code that assumes it. The `Barrier` forces the interleaving so the demonstration is deterministic.

### 4.3 Alembic expand/contract (verified sequence)

Setup in an empty project directory against a fresh database `migdb`:

```bash
pip install alembic sqlalchemy "psycopg[binary]"
alembic init migrations
# edit migrations/env.py: import your Base, set target_metadata = Base.metadata,
# and config.set_main_option("sqlalchemy.url", os.environ["DATABASE_URL"].replace("%", "%%"))
alembic revision --autogenerate -m "create app_user" --rev-id 0001
alembic upgrade head
```

Model change 1 (expand): add `first_name: Mapped[str | None] = mapped_column(String(100), nullable=True)`; autogenerate produced exactly `op.add_column('app_user', sa.Column('first_name', sa.String(length=100), nullable=True))` with a matching `drop_column` downgrade. Revision 0003 (hand-written, migrate step), tested on 25,000 rows (zero NULLs afterwards, then downgrade to 0001 worked):

```python
"""backfill first_name in batches"""
from alembic import op
import sqlalchemy as sa

revision = "0003"; down_revision = "0002"; branch_labels = None; depends_on = None
BATCH = 10_000

def upgrade() -> None:
    conn = op.get_bind()
    last_id = 0
    while True:
        res = conn.execute(sa.text(
            "WITH b AS (SELECT id FROM app_user WHERE id > :last AND first_name IS NULL "
            "ORDER BY id LIMIT :n) "
            "UPDATE app_user u SET first_name = split_part(u.full_name, ' ', 1) "
            "FROM b WHERE u.id = b.id RETURNING u.id"), {"last": last_id, "n": BATCH})
        ids = [r[0] for r in res]
        if not ids:
            break
        last_id = max(ids)

def downgrade() -> None:
    pass  # data backfill is not reversed
```

Be honest about what this does *not* do: Alembic runs the whole migration in one transaction by default on PostgreSQL, so these batches are not separately committed, and locks and WAL accumulate for the full run. For a real large table, run the backfill as a separate, resumable job (a script or background task) outside the migration transaction, committing per batch, and keep the migration for the schema change only. Alembic detail (checked in 1.20): by default one `alembic upgrade` runs the whole series of pending migrations in a single transaction on PostgreSQL; set `transaction_per_migration=True` in `env.py` (`context.configure`) to get one transaction per revision, and use `autocommit_block()` for statements that cannot run in a transaction. The keyset loop (`id > :last ... ORDER BY id LIMIT`) is the same technique as pagination, and for the same reason: it does constant work per batch regardless of progress.

The contract step (a later release, after verifying `SELECT count(*) FROM app_user WHERE first_name IS NULL` is 0 and all code reads/writes the new column): `ALTER COLUMN first_name SET NOT NULL`, then drop the old if applicable. Check the lock behaviour of `SET NOT NULL` on your PostgreSQL version first.

### 4.4 Keyset pagination (`keyset.py`)

```python
import base64, json, os
from datetime import datetime
from sqlalchemy import create_engine, select, tuple_, MetaData, Table
engine = create_engine(os.environ["DATABASE_URL"])
sub = Table("submission", MetaData(), autoload_with=engine)

def enc(ts: datetime, id_: int) -> str:
    return base64.urlsafe_b64encode(json.dumps([ts.isoformat(), id_]).encode()).decode()

def dec(cur: str) -> tuple[datetime, int]:
    ts, id_ = json.loads(base64.urlsafe_b64decode(cur))
    return datetime.fromisoformat(ts), id_

def page(conn, limit=1000, cursor=None):
    q = (select(sub.c.id, sub.c.submitted_at)
         .order_by(sub.c.submitted_at.desc(), sub.c.id.desc()).limit(limit + 1))
    if cursor:
        ts, id_ = dec(cursor)
        q = q.where(tuple_(sub.c.submitted_at, sub.c.id) < tuple_(ts, id_))
    rows = conn.execute(q).all()
    nxt = enc(rows[limit - 1].submitted_at, rows[limit - 1].id) if len(rows) > limit else None
    return rows[:limit], nxt

with engine.connect() as c:
    seen, cur, n = set(), None, 0
    while True:
        rows, cur = page(c, 5000, cur); n += 1
        assert not any(r.id in seen for r in rows); seen.update(r.id for r in rows)
        if not cur: break
    print("pages", n, "rows", len(seen))
```

Prerequisite index: `CREATE INDEX sub_time_id ON submission (submitted_at DESC, id DESC);`. Observed: `pages 60 rows 300000`, no duplicates, matching the 300,000 rows. The `dec` function trusts its input: a malformed cursor raises, which your API must turn into a `422` problem+json (Lesson 2.1), and a tampered cursor must not be able to read data the caller may not see (scope the query by user regardless of the cursor). `datetime.isoformat()` keeps the timezone offset; round-tripping a naive timestamp would silently shift ordering, so keep everything `timestamptz`.

Measuring offset against keyset (do this yourself, do not trust a number from a book): run `EXPLAIN (ANALYZE, BUFFERS) SELECT ... ORDER BY submitted_at DESC, id DESC OFFSET 250000 LIMIT 1000` and the keyset form for the same logical position, and compare `Buffers` and execution time, cold and warm.

## 5. Production perspective

**Correctness.** Decide per operation: which invariant, which mechanism (constraint, atomic update, lock, version, isolation+retry). Document it next to the code. Prefer constraints and single-statement updates; they are the cheapest to reason about. Every retry loop must be bounded, with jitter, and must be around the *whole* transaction (re-reading state), never just the failing statement.

**Idempotency.** A retried transaction or a retried HTTP request can run twice; combine these with idempotency keys (Lesson 2.6) so a commit whose response was lost is not repeated.

**Performance.** Hold transactions open as briefly as possible; no network calls, no `sleep`, no user waiting inside. Long transactions block vacuum and bloat tables, and keep locks. Keep connection pool size in mind: each waiting transaction holds a connection, so lock contention turns into pool exhaustion and 503s. Observe lock waits with `pg_stat_activity` and `pg_locks` (columns such as `mode` and `granted`; reference for your version in the docs).

**Operations.** Migrations run as a deployment step with `lock_timeout` and `statement_timeout` set, tested against a production-sized copy, with a written rollback or roll-forward plan. Never edit a migration that has run anywhere shared; add a new one. One head: merge conflicts on revision ids (two branches) need `alembic merge`. Back up before destructive contract steps.

**Security.** Migrations execute with elevated rights; the runtime role should not have DDL privileges. Do not put secrets in `alembic.ini`. Cursors: opaque, validated, authorization re-checked each request.

**Testing.** Concurrency tests must force the interleaving (barriers, sleeps in the test, explicit isolation) so they fail deterministically on the buggy version; a test that passes "most of the time" proves nothing. Test migrations by upgrading an empty DB to head and by upgrading a populated snapshot, then running the app's test suite against both. Keyset: property-style test inserting rows between page fetches and asserting the union has no duplicates and (for pre-existing rows) no gaps.

**Senior habits.** Asks "what is the invariant, and what enforces it when two requests arrive together?" in design review. Treats `SELECT` followed by `UPDATE` as a smell. Splits every risky schema change into releases. Reads `ALTER TABLE` lock documentation before touching a big table. Does not use SERIALIZABLE everywhere out of fear, nor READ COMMITTED everywhere out of ignorance: chooses per transaction.

**Common beginner mistakes and diagnosis.**

| Mistake | Symptom | Diagnosis |
|---|---|---|
| Read-modify-write in Python | Counts drift under load; fine in single-user tests | Threaded test with a barrier; compare expected and actual |
| Retry only the failing statement | Second attempt runs on stale reads | Check that the loop encloses the whole transaction function |
| Commit in post-response dependency exit | Client sees 200 but data missing | Force a commit failure in a test; compare `scope="request"` and `"function"` |
| Autogenerate applied unreviewed | Dropped tables, dropped columns (rename seen as drop+add) | Read the generated file before running; run `alembic upgrade head --sql` (offline mode; the `--sql` flag exists, checked) to see the SQL |
| Backfill in one UPDATE | Lock for minutes, replication lag, timeouts | Look at `pg_stat_activity`; batch with keyset on the PK |
| OFFSET paging on a feed | Duplicates/gaps; deep pages slow | Insert rows between page fetches in a test; EXPLAIN deep offset |
| Non-unique sort key in keyset | Rows silently skipped at ties | Add duplicate timestamps to test data |
| Different lock order in two code paths | Rare deadlocks in production logs | Find both paths, define one global lock order (for example ascending id) |

## 6. Failure laboratory

Here is a "seat booking" function and its test. The team says it is "tested and safe".

```python
def book(session_factory, seat_id: int, user: str) -> bool:
    with session_factory() as s, s.begin():
        seat = s.get(Seat, seat_id)           # Seat(id, taken_by: str | None)
        if seat.taken_by is not None:
            return False
        seat.taken_by = user
        return True

def test_book_only_once(session_factory):
    assert book(session_factory, 1, "alice") is True
    assert book(session_factory, 1, "bob") is False
```

**Predict before running:** (1) Does the test pass? (2) With 50 threads each calling `book(..., 1, f"u{i}")` against PostgreSQL at READ COMMITTED, how many return `True`, and is that deterministic? (3) Would raising the isolation level to REPEATABLE READ change the answer, and in what way? (4) Name three distinct correct fixes with their trade-offs. (5) Design a test that fails reliably on the flawed code.

### Reveal (read after predicting)

1. It passes: single-threaded, the check and write never interleave. This is the central trap: sequential tests cannot see concurrency bugs.
2. Possibly more than one `True`. `s.get` reads the row without locking; several threads read `taken_by is None` before any commits. SQLAlchemy then issues `UPDATE seat SET taken_by=... WHERE id=...` and the last writer wins, but every thread already returned `True`. The count depends on timing: nondeterministic. I ran this function with 50 barrier-released threads and a 2 ms sleep between check and write: it returned `True` twice in one run (observed; other runs will differ, and without the sleep the window is much narrower). The nondeterminism is itself the finding.
3. Under REPEATABLE READ, concurrent updates to the same row cause the second transaction to fail with a serialization error rather than silently overwrite, so at most one `True` is returned, but others raise exceptions you must catch and treat as "not booked" or retry. It turns silent corruption into explicit errors, which is better but not free.
4. (a) Atomic conditional update: `UPDATE seat SET taken_by = :u WHERE id = :id AND taken_by IS NULL`; success iff `rowcount == 1`. Cheapest and simplest. (b) `SELECT ... FOR UPDATE` then check then write: allows complex logic between read and write; costs waiting and deadlock risk if multiple seats are locked in inconsistent order. (c) Optimistic `version_id_col` with retry: no blocking; wasteful under contention and the semantics of "someone else won" must be handled (here: after reload, `taken_by` is set, so return `False`). A unique constraint on a booking table `(seat_id)` is a fourth option: attempt `INSERT`, catch `IntegrityError`.
5. Start N threads released together by a `threading.Barrier`, each calling `book` on the same seat, with a small `time.sleep` between the read and the write injected through a hook or a patched session to widen the window. Assert `sum(results) == 1`. The test must fail on the original code on most runs; run it 20 times to confirm.

Diagnosis procedure for "works alone, fails under load": (1) state the invariant; (2) list every read-then-write on it; (3) write a barrier-based test that forces the interleaving; (4) confirm it fails; (5) choose the mechanism; (6) confirm it passes 20 consecutive runs; (7) record which anomaly it was (lost update, write skew) in the failure log.
