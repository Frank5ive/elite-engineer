## 1. Engineering problem

It is 02:10. An alert says "checkout errors up". You open the logs: a wall of unstructured lines like `Error processing request`, no request id, no user, no route, and four instances interleaved. You cannot tell whether one customer is failing or everyone, whether the database or the payment provider is at fault, whether it started with Tuesday's deploy. You restart pods "to see if it helps". It does, briefly, and you now have no evidence.

The same team deploys with a Dockerfile that runs as root, installs dev dependencies, has no health check, and starts `uvicorn` through a shell wrapper so `SIGTERM` never reaches the Python process. Each deploy drops in-flight requests. The load balancer routes to new pods before the database pool is warm, causing a burst of 502s. Nobody knows the service's p99 latency, so nobody can say whether the new release is slower.

This lesson covers what to build so that, at 02:10, you can answer in five minutes: *what is broken, for whom, since when, and why*, and so that deploys and restarts are boring.

## 3. First-principles explanation

### 3.1 Observability: the question it answers

**Monitoring** tells you *that* something is wrong (known failure modes, alerts). **Observability** is the property that lets you ask new questions of a running system from its outputs, without shipping new code, to find *why*. The three classic signal types:

| Signal | Shape | Answers | Cost driver |
|---|---|---|---|
| Logs | Discrete events with context | What happened in this request? | Volume (bytes stored) |
| Metrics | Numeric time series, aggregated | Is the system healthy? How much, how fast? | Cardinality (distinct label combinations) |
| Traces | Tree of timed spans across services for one request | Where did the time go? Which dependency? | Sampling rate |

Use them together: a metric alerts you, a trace localizes the slow dependency, logs explain the specific failure. Opinion: if you can only do one thing well at the start, do structured logs with request ids, then RED metrics; add tracing when you have more than one service or need dependency latency breakdowns.

### 3.2 Structured logging and request ids

Plain-text logs are for humans; structured logs (one JSON object per line) are for queries: "all `level=ERROR` for `route=/payments` in the last hour grouped by `error_type`". Fields to standardize: timestamp, level, logger, message, **request_id**, route, method, status, duration_ms, user id (if authenticated and policy allows), error type, and a stable event name. Rules:

- Log to **stdout/stderr**, not files, in containers; the platform collects them (twelve-factor convention).
- Never log secrets, tokens, passwords, full card numbers or whole request bodies. Redact by allow-list rather than deny-list.
- Levels mean something: `ERROR` = a human or alert should look; `WARNING` = unexpected but handled; `INFO` = significant lifecycle/request events; `DEBUG` off in production by default.
- One request, one access-log line with the final status and duration; do not log every internal step at INFO.
- Python's `logging` is global and thread-safe; use `contextvars.ContextVar` for the request id so concurrent requests on one event loop (and the threadpool, since contextvars propagate through AnyIO's thread dispatch; checked on AnyIO 4.15.1: a context variable set in a pure ASGI middleware was visible in a sync `def` dependency) do not mix ids. A global variable would be a bug here.

The **request id** is generated at the edge (or accepted from an upstream `X-Request-ID` after length validation), returned in the response header, attached to every log line, and forwarded on outbound calls. Support can then ask a customer for the id in the response and find every line.

### 3.3 Metrics, cardinality, RED and USE

A **counter** only increases (requests); a **gauge** goes up and down (in-flight requests, queue depth); a **histogram** buckets observations (latency), which lets the server compute percentiles from aggregated data across instances. (Summaries computed in-process cannot be averaged across instances.)

**Cardinality** is the number of distinct label-value combinations; each is a separate time series. Labelling by raw URL path (`/items/1`, `/items/2`, ...) or user id creates unbounded series and takes down the metrics backend. Use the **route template** (`/items/{item_id}`), a bounded status class or code, and method.

**RED** (for request-driven services): **R**ate (requests/s), **E**rrors (failed requests/s or ratio), **D**uration (latency distribution). **USE** (for resources: CPU, memory, DB pool, thread pool, queue): **U**tilization (fraction busy), **S**aturation (queued/waiting work), **E**rrors. A service dashboard puts RED on top and USE for each critical resource beneath. For FastAPI the interesting USE resources are the DB connection pool (in use / waiting), threadpool threads in use, the outbox backlog and event-loop lag.

Alert on **symptoms** (error ratio, p99 latency over SLO, backlog age) rather than causes (CPU 80%); causes go on dashboards for diagnosis.

### 3.4 Tracing concepts (overview level)

A **trace** is the story of one request; a **span** is one timed operation with a name, start/end, attributes and a parent, forming a tree. Context (trace id, parent span id) crosses process boundaries in headers (W3C `traceparent`). **OpenTelemetry (OTel)** is the vendor-neutral standard and SDK for traces, metrics and logs: you instrument (manually or with auto-instrumentation for FastAPI, httpx, SQLAlchemy) and an exporter sends OTLP data to a collector or backend. Decisions: sampling (head-based fixed rate is cheap; tail-based keeps interesting traces but needs a collector), which attributes are safe (no PII), and linking trace ids into logs. Package names checked on PyPI in October 2026: `opentelemetry-api`, `opentelemetry-sdk`, `opentelemetry-exporter-otlp`, `opentelemetry-instrumentation-fastapi` (plus `-httpx` and `-sqlalchemy` variants); instrumentation packages are still versioned 0.x ("beta"), so read opentelemetry.io/docs/languages/python/ before adding it, and use whatever tracing the team already runs.

### 3.5 Health, liveness, readiness

Orchestrators (Kubernetes, ECS, load balancers) need to ask your process questions:

| Probe | Question | On failure | Must check |
|---|---|---|---|
| Liveness | Is this process stuck beyond recovery? | Kill and restart it | Only that the process responds (loop alive). **Not** dependencies |
| Readiness | Can this instance serve traffic right now? | Remove from load balancer; do not kill | Startup done, critical dependencies reachable (cheap check), not draining |
| Startup (K8s) | Has it finished booting? | Delay other probes | Slow init (migrations, cache warm) |

The classic outage: the liveness probe checks the database; the database has a blip; every pod fails liveness; the orchestrator restarts *all* of them; they stampede the recovering database. Keep liveness shallow. Readiness checks should be **fast, bounded by a short timeout, and cached for a second or two** so probes do not become load. Readiness also must flip to *not ready* on shutdown (3.6).

### 3.6 Graceful shutdown

On deploy, the orchestrator sends `SIGTERM`, waits a grace period (K8s default 30 s), then `SIGKILL`. A graceful process: (1) **stops being routed to** (readiness goes false; the load balancer needs time to notice, so a short pre-stop delay helps), (2) **stops accepting new connections**, (3) **finishes in-flight requests** up to a limit, (4) **flushes and closes** resources (DB pool, HTTP clients, background workers, log handlers), (5) exits within the grace period. The exit status varies: when I ran uvicorn 0.54.0 under a drill, the process drained and then terminated by the re-raised `SIGTERM` (Python `returncode == -15`), not 0 (confirmed again on the host; inside a container started by `docker stop`, the same app image reported exit code 0, so check what your platform records).

uvicorn handles `SIGTERM`: it stops accepting new connections and waits for in-flight requests, bounded by `--timeout-graceful-shutdown` (framework behavior; I verified an in-flight 3 s request completed after `SIGTERM` with this flag set). Your code's part is the **lifespan** (2.2): everything after `yield` runs at shutdown. Two classic breaks: (a) the container's entrypoint is a shell script or shell-form `CMD`, so the shell is PID 1 and does not forward `SIGTERM` to Python; fix with **exec-form** `CMD ["uvicorn", ...]` or `exec uvicorn` in scripts; (b) the platform's grace period is shorter than your longest request, so slow requests are killed anyway; align `--timeout-graceful-shutdown` below the grace period and keep requests bounded (2.6 timeouts).

### 3.7 Configuration and secrets

Twelve-factor: configuration lives in the environment, strictly separated from code, one build artifact for all environments. Build on 1.3 and 2.5: define a typed `Settings` (pydantic-settings), load once, validate at startup, **fail fast** on missing or placeholder values, mask secrets in `repr` (`SecretStr`). Configuration drift between environments is a classic source of "works in staging". Log the *non-secret* effective configuration at startup (environment, version, feature flags) so incidents can start from facts.

### 3.8 Timeouts, deadlines and circuit breakers

From 2.6: every outbound call has a timeout; retries are bounded, jittered and idempotent-only. A **circuit breaker** adds fast failure when a dependency is known to be down:

```
CLOSED --(N consecutive failures)--> OPEN --(cooldown elapsed)--> HALF-OPEN
   ^                                   ^                              |
   |                                   +------ probe fails -----------+
   +---------------- probe succeeds -----------------------------------+
```

While OPEN, calls fail immediately (no queueing behind a dead dependency, no extra load on it). HALF-OPEN lets one probe through. Trade-offs: thresholds need tuning; a breaker per dependency (not global); in a multi-instance fleet each instance trips independently; and you must decide the fallback (error, cached value, degraded response) *before* you ship it. It pairs with timeouts: without a timeout a hung call never registers as a failure. Related patterns: **bulkheads** (separate concurrency limits per dependency), **load shedding** (reject early with `503` when saturated rather than let latency grow unbounded), and **deadline propagation**.

### 3.9 Docker for a FastAPI service

Principles: small, reproducible, non-root, cache-friendly layers, exec-form entrypoint, no secrets baked in, one process per container.

```dockerfile
# Dockerfile (built and run with fastapi 0.162.0 and uvicorn 0.54.0 on python:3.12-slim: it builds, HEALTHCHECK reports healthy, runs as uid 10001)
FROM python:3.12-slim AS base
ENV PYTHONUNBUFFERED=1 PYTHONDONTWRITEBYTECODE=1 PIP_NO_CACHE_DIR=1
WORKDIR /app

# 1. dependencies first: this layer is cached until requirements change
COPY requirements.txt .
RUN pip install -r requirements.txt

# 2. then source: changes often, so it comes last
COPY app/ ./app/

# 3. drop root
RUN useradd --system --uid 10001 appuser
USER appuser

EXPOSE 8000
HEALTHCHECK --interval=30s --timeout=3s --start-period=10s \
  CMD python -c "import urllib.request,sys; sys.exit(0 if urllib.request.urlopen('http://127.0.0.1:8000/healthz', timeout=2).status==200 else 1)"

# exec form: uvicorn is PID 1 and receives SIGTERM directly
CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000", "--timeout-graceful-shutdown", "20"]
```

Notes. Pin dependencies. Multi-stage builds pay off only when compiling wheels. Never copy `.env` (use `.dockerignore`). One worker per container is the orchestrator-friendly default; scale by replicas. With multiple worker processes, in-process state (caches, rate limiters, the Prometheus default registry) is per process and needs special handling (prometheus-client multiprocess mode: set `PROMETHEUS_MULTIPROC_DIR`; its docs list limitations, including that gauges cannot use `set_function`). In Kubernetes use platform probes rather than Docker `HEALTHCHECK`.

### 3.10 Load testing and percentiles

Goal: find the load at which latency/error SLOs break and which resource saturates first. Method: (1) define the SLO ("p99 under 300 ms at X req/s, under 0.1% errors"); (2) test production-like infrastructure, not just your laptop; (3) ramp in steps while watching RED and USE; (4) change one thing at a time; (5) repeat for variance.

pN is the value below which N% of observations fall. p99 is "the worst 1 in 100"; at 10 requests per page view most users meet a p99 experience regularly. Averages hide tails. Never average percentiles across instances; aggregate histograms and compute the percentile afterwards.

Traps: **coordinated omission** (a closed-loop generator waits for each response, so when the server stalls it stops sending and under-records the slow period; use constant-rate open-loop tools for latency claims; term from Gil Tene's talk "How NOT to Measure Latency"; the wrk2 repository, github.com/giltene/wrk2, has a CoordinatedOmission directory), **warm-up** (discard cold-start requests), and **generator limits** (a client sharing the server's CPU produces false numbers). Use an established tool (k6, wrk2, Locust, hey; read each tool's docs for open-loop or constant-rate support) for claims.

## 4. Worked example

### 4.1 Naive logging vs structured logging with request ids

Naive: `print(f"error: {e}")` and `logging.basicConfig()` text lines. You cannot filter, correlate or aggregate.

Improved `obs.py` (Python 3.12+; `pip install fastapi uvicorn prometheus-client`). Verified with FastAPI 0.162.0 / Starlette 1.10.0.

```python
from __future__ import annotations
import contextvars, json, logging, sys, time, uuid
from contextlib import asynccontextmanager
from fastapi import FastAPI, Request, Response
from prometheus_client import CONTENT_TYPE_LATEST, Counter, Histogram, generate_latest
from starlette.types import ASGIApp, Message, Receive, Scope, Send

request_id_var: contextvars.ContextVar[str] = contextvars.ContextVar("request_id", default="-")

class JsonFormatter(logging.Formatter):
    def format(self, record: logging.LogRecord) -> str:
        doc = {"ts": self.formatTime(record, "%Y-%m-%dT%H:%M:%S"), "level": record.levelname,
               "logger": record.name, "msg": record.getMessage(), "request_id": request_id_var.get()}
        extra = getattr(record, "fields", None)
        if extra: doc.update(extra)
        if record.exc_info: doc["exc"] = self.formatException(record.exc_info)
        return json.dumps(doc)

def configure_logging(level: str = "INFO") -> None:
    h = logging.StreamHandler(sys.stdout); h.setFormatter(JsonFormatter())
    root = logging.getLogger(); root.handlers[:] = [h]; root.setLevel(level)

log = logging.getLogger("app")
```

Why a **pure ASGI middleware** rather than `@app.middleware("http")` (which uses `BaseHTTPMiddleware`)? `BaseHTTPMiddleware` has documented limitations around `contextvars` propagation (the Starlette docs say changes to a `ContextVar` do not propagate upwards through it, and it can disrupt contextvars for pure ASGI middleware placed after it); a pure ASGI middleware sidesteps them and adds less overhead. The cost is more verbose code.

### 4.2 Metrics and the request context middleware

```python
REQS = Counter("http_requests_total", "Requests", ["method", "route", "status"])
LAT = Histogram("http_request_duration_seconds", "Latency", ["method", "route"],
                buckets=(0.005, 0.01, 0.025, 0.05, 0.1, 0.25, 0.5, 1, 2.5, 5))

class RequestContextMiddleware:
    def __init__(self, app: ASGIApp) -> None: self.app = app
    async def __call__(self, scope: Scope, receive: Receive, send: Send) -> None:
        if scope["type"] != "http":
            return await self.app(scope, receive, send)
        headers = dict(scope["headers"])
        rid = headers.get(b"x-request-id", b"").decode()[:64] or uuid.uuid4().hex
        token = request_id_var.set(rid)
        status = 500; start = time.perf_counter()
        async def send_wrapper(message: Message) -> None:
            nonlocal status
            if message["type"] == "http.response.start":
                status = message["status"]
                message["headers"] = [*message["headers"], (b"x-request-id", rid.encode())]
            await send(message)
        try:
            await self.app(scope, receive, send_wrapper)
        finally:
            dur = time.perf_counter() - start
            tmpl = getattr(scope.get("route"), "path", "unmatched")   # template, NOT raw path
            REQS.labels(scope["method"], tmpl, str(status)).inc()
            LAT.labels(scope["method"], tmpl).observe(dur)
            log.info("request", extra={"fields": {"method": scope["method"], "path": scope["path"],
                     "route": tmpl, "status": status, "duration_ms": round(dur * 1000, 2)}})
            request_id_var.reset(token)
```

Decisions: status defaults to 500 so an exception that escapes is counted as an error; `scope["route"]` is set by the router after matching (observed on Starlette 1.10.0 and FastAPI 0.162.0, re-checked: `scope["route"].path` is the template, e.g. `/r`; older versions may need a different lookup); unmatched routes share one label so scanners cannot create unbounded series; the inbound id is truncated to 64 characters (log injection and memory); the id is reset in `finally`.

### 4.3 Health endpoints, lifespan, metrics route

```python
@asynccontextmanager
async def lifespan(app: FastAPI):
    configure_logging()
    app.state.ready = True
    yield
    app.state.ready = False          # shutdown: stop advertising readiness first
    log.info("shutting down")        # then close pools, clients, workers here

app = FastAPI(lifespan=lifespan)
app.add_middleware(RequestContextMiddleware)

@app.get("/healthz")                 # liveness: no dependency checks
def healthz(): return {"status": "ok"}

@app.get("/readyz")                  # readiness: can I serve right now?
def readyz(request: Request, response: Response):
    if not request.app.state.ready:
        response.status_code = 503; return {"status": "not ready"}
    return {"status": "ready"}

@app.get("/items/{item_id}")
def item(item_id: int):
    log.info("fetching item", extra={"fields": {"item_id": item_id}})
    return {"id": item_id}

@app.get("/metrics")
def metrics(): return Response(generate_latest(), media_type=CONTENT_TYPE_LATEST)
```

The test (ran green): call `/items/7` with `X-Request-ID: abc123`, assert the response echoes it; call `/items/8` and assert a 32-character generated id; read `/metrics` and assert it contains `route="/items/{item_id}"` and does **not** contain `item_id="7"`; capture stdout, parse each JSON line and assert a `"fetching item"` record carries `request_id == "abc123"` and the `"request"` record has `status == 200`. In a real readiness check add a cheap `SELECT 1` with a 1 s timeout, cached for 2 s, and expose `/metrics` only on an internal network or behind auth, since it reveals your route structure.

### 4.5 Circuit breaker with an injectable clock

Interface (full class in the solutions file; I ran its tests green): `CircuitBreaker(failure_threshold=5, cooldown=10.0, clock=time.monotonic)` with `before_call()` (raises `CircuitOpen` while open, and in half-open lets exactly one probe through), `on_success()` and `on_failure()`. Usage: `before_call()`, the call with a timeout, then `on_success()` or `on_failure()`; map `CircuitOpen` to `503` with `Retry-After`. Count only failures that indicate dependency trouble (timeouts, connection errors, 5xx), not your own 4xx.

The test drives a fake clock: three failures open it; calls fail fast; after the cooldown one probe passes and a concurrent second is refused; a failed probe reopens; a successful probe closes. Caveat: it is not thread-safe as written. In a single-loop async service it is safe because no `await` sits between check and update; with sync handlers in the threadpool add a lock. Libraries exist (check maintenance before choosing one), but understand the state machine first.

### 4.6 A learning-grade load generator

`load.py` (in the solutions file) is a closed-loop asyncio/httpx generator printing request count, errors, rps and p50/p95/p99 via `statistics.quantiles(lat, n=100)` (`q[49]`, `q[94]`, `q[98]`). I ran it against the local app to confirm it works, and I do not quote the numbers: a generator and server sharing one laptop with per-request logging say nothing about your production system. ## 5. Production perspective

**Operations.** On call, the first five minutes: RED dashboard, recent deploys, an error log sample by request id, dependency health, saturation. Make each one click. Every alert links to a runbook an exhausted person can follow.

**Security.** Redact logs; decide deliberately whether `/metrics` and `/docs` are public; non-root containers; scan images and dependencies (tooling such as `pip-audit` and `trivy`; both actively maintained, read their docs for usage); no secrets in image layers (`docker history` reveals them).

**Deploys.** Rolling deploys need backward-compatible schema changes (expand, deploy, contract; 2.4) because old and new versions overlap. Put the git SHA in a startup log or metric label to correlate regressions with releases.

**Performance.** Logging has cost; do not log in hot loops. Histogram buckets should bracket your SLO. Measure with instrumentation on, as that is what runs in production.

**Testing.** Test that: the request id round-trips and appears on every log line; metrics labels stay bounded; readiness flips false at shutdown; the breaker transitions; configuration fails fast; the Docker image starts, serves `/readyz`, and stops within the grace period when sent `SIGTERM` (script this: `docker run -d`, `docker kill --signal=TERM`, `docker inspect` exit code; run them locally).

**What a senior engineer does differently.** Adds the log field or metric *before* the incident; alerts on user-visible symptoms; knows the saturation point from measurement; counts the runbook and dashboard as part of done; distrusts dashboard averages.

**Common beginner mistakes and diagnosis.**

| Mistake | Symptom and diagnosis |
|---|---|
| Raw path as metric label | Metrics backend memory/cost explodes; count series per metric; inspect label values |
| Liveness checks the database | Fleet-wide restarts during a DB blip; correlate restarts with dependency alerts |
| Shell-form `CMD` / wrapper script | Deploys drop requests, container takes the full grace period to die; `docker exec <c> ps` shows `sh` as PID 1 |
| Logging secrets or whole bodies | Audit/grep production logs for known token prefixes; add redaction tests |
| Quoting averages or max only | Complaints with a "healthy" dashboard; plot p50/p95/p99 |
| Same machine for load generator and server | Results shift when you change the generator; watch CPU of both |
| Unbounded retries plus no breaker | Outage amplified; plot outbound call rate during a dependency failure |
| Global request id variable | Ids mixed between concurrent requests; test with two concurrent requests and compare |

## 6. Failure laboratory

Save as `lab27.py`:

```python
import logging, time
from fastapi import FastAPI, Request
from sqlalchemy import create_engine, text

log = logging.getLogger("lab")
logging.basicConfig(level=logging.INFO)
engine = create_engine("sqlite:///lab.db")
app = FastAPI()
LAST_ID = {"v": None}

@app.middleware("http")
async def mw(request: Request, call_next):
    LAST_ID["v"] = request.headers.get("x-request-id", "none")
    response = await call_next(request)
    return response

@app.get("/livez")
def livez():
    with engine.connect() as c:
        c.execute(text("SELECT 1"))
    return {"ok": True}

@app.get("/work/{user_id}")
async def work(user_id: int):
    time.sleep(0.2)
    log.info("working for %s id=%s", user_id, LAST_ID["v"])
    return {"user": user_id}
```

Dockerfile for the lab: `CMD uvicorn lab27:app --host 0.0.0.0` (shell form) and Kubernetes `livenessProbe` pointing at `/livez` with a 1 s timeout.

**Predict, in writing:**

1. Two requests arrive concurrently with ids `A` and `B`. Which id can the log line for request A show, and why? Name at least two separate reasons the logged id can be wrong.
2. The database becomes unreachable for 20 seconds. What does the orchestrator do, and what happens when the database comes back?
3. A deploy rolls out. What happens to requests in flight on terminating pods, and why does the shell-form `CMD` matter?
4. List the observability gaps if this service runs 4 replicas and users report "sometimes slow".

### Reveal (read after predicting)

1. It can show B's id: `LAST_ID` is a module-level global overwritten by each request (use a `ContextVar`). Also `time.sleep` in `async def` blocks the loop so interleaving is coarse and unpredictable, and each worker process has its own copy.
2. `/livez` queries the database, so the probe fails and after the failure threshold every replica is killed at once; when the database returns they all reconnect together, and restarts destroy in-memory evidence. Put the DB check in readiness (remove from rotation, do not kill).
3. With shell-form `CMD`, `/bin/sh -c` may be PID 1 and not forward `SIGTERM` (shell-dependent; checked: with shell-form `CMD`, `/proc/1/cmdline` was `/bin/sh -c uvicorn ...` and `docker stop` ended in exit code 137 after the grace period; `ps` is not installed in `python:*-slim`, so read `/proc/1/cmdline` or use `docker top`), so the app is killed with `SIGKILL` after the grace period and in-flight requests drop. There is also no readiness flip or drain delay, so the load balancer may still send traffic to a terminating pod.
4. No replica or version label, no per-request latency/status metrics, no route, no request id for the user, no trace to split app vs DB time, and no event-loop lag metric to expose the blocking `sleep`.

**Systematic diagnosis procedure** for "sometimes slow":

1. Quantify: pull p50/p95/p99 and error ratio per route and per replica for the window; is the tail on one replica (bad node, noisy neighbor) or everywhere?
2. Correlate with events: deploys, config changes, traffic shape, dependency incidents.
3. Pick a slow request id from user reports or logs; follow it through logs and trace; find the span or log gap with the time.
4. Check saturation: DB pool waits, thread pool, event-loop lag, CPU throttling, GC pauses, queue depth.
5. Form one hypothesis, change one thing, re-measure; record in the failure log.

## 11. Mastery gate

Pass = 80/100 and no critical failure.

**Critical failures:**

1. Unbounded metric label cardinality, or secrets in logs or image layers.
2. Liveness probe depends on an external dependency.
3. Container does not shut down gracefully (in-flight request dropped or PID 1 is a shell) with no documented, justified reason.
4. Load-test claims without environment, method and percentiles, or with fabricated or unreproducible numbers.
5. Outbound calls with no timeout.

**Required evidence:** shutdown drill output; cardinality test; readiness behavior with the DB stopped; breaker state-transition evidence; the load report; the checklist with links; a 10-minute defense including a live kill/restart of the container.

**If failed:** remedial exercise matched to the failure: for logging/metrics, instrument a 3-endpoint toy app from scratch in 90 minutes (Mode A, docs allowed) with a cardinality test; for shutdown, run the drill against shell-form and exec-form images and explain the difference using `ps` output; for load testing, redo one test from a second machine or with a constant-rate tool and explain every difference from the first result.
