## 1. Engineering problem

A mobile client posts `POST /payments`. The connection to your server drops after the request was processed but before the client received the 201. The client's HTTP library retries, as it should. You now have two payment rows and one angry customer.

A second incident: the email provider has a slow day (30 s per call). `POST /signup` calls it synchronously inside an `async def`. Within a minute every endpoint, including `/healthz`, stops responding, the orchestrator restarts the pod, and signups are lost.

A third: a retry loop with a fixed `time.sleep(1)` and no jitter. When the provider recovers, 400 instances retry in lock-step and flatten it again.

Three problems, one lesson:

1. **Do not block the event loop** (and know what "blocking" means).
2. **Retry with discipline**: timeouts, backoff, jitter, and only for operations that are safe to repeat.
3. **Make repeats safe**: idempotency keys, duplicate-tolerant consumers, and an outbox so that "write to DB" and "tell the outside world" cannot diverge.

## 3. First-principles explanation

### 3.1 The event loop and why `async def` is a contract

An `asyncio` event loop is **one thread** that runs ready tasks. A task runs until it hits an `await` on something not yet ready; then the loop switches to another task. This gives high concurrency for *I/O-bound* work with small memory per task. The cost: it is **cooperative**. If a task never reaches an `await` (a CPU loop, `time.sleep`, `requests.get`, a synchronous DB driver call, `hasher.verify`), *nothing else on that loop runs*: not other requests, not the health check, not timeouts.

```
Loop thread:  [A: parse][A: await db ...........][B: parse][B: await ...][A resumes]...
Blocking A:   [A: time.sleep(1) ======================================][B starts]
                           everyone waits 1 s
```

FastAPI (framework behavior, built on Starlette/AnyIO) treats the two function kinds differently:

| Declaration | Where it runs | Rule |
|---|---|---|
| `async def` endpoint/dependency | directly on the event loop | Must only `await` non-blocking things. Blocking here freezes the whole worker process |
| `def` endpoint/dependency | in a threadpool worker thread | May block, but each blocked call consumes a pool thread; the pool is finite (AnyIO's default limiter is 40 threads; checked on AnyIO 4.15.1 via `current_default_thread_limiter().total_tokens`) |

So `async def` is not "faster"; it is a promise that you will not block. When uncertain, a plain `def` handler is the safer default, which surprises people.

**Mixing.** From async code, call blocking code via `await anyio.to_thread.run_sync(fn, *args)` or `await asyncio.to_thread(fn, *args)`. From threads, you cannot `await`; use `anyio.from_thread.run`. For CPU-heavy work, threads do not help (the GIL; free-threaded builds are an evolving topic, see the free-threading HOWTO on docs.python.org) and you want a process pool or a separate worker.

**Database drivers.** SQLAlchemy 2.x supports both a sync engine (`psycopg`/`psycopg2` with `def` handlers; simple, battle-tested) and an async engine (`create_async_engine("postgresql+asyncpg://...")` or psycopg async with `AsyncSession`). Do not use a sync `Session` inside an `async def` handler. Pick one style per service unless you have a reason; for most CRUD backends the sync stack with `def` handlers is perfectly adequate, and the concurrency ceiling is the DB connection pool anyway, not the loop.

### 3.2 Timeouts: the first line of defense

Without a timeout, a dead dependency holds your resources forever; slow failures consume every worker. Every network call needs a **bound**. For `httpx`, the default is a 5 second timeout for each of connect, read, write and pool (framework behavior; checked on httpx 0.28.1: `httpx.Client().timeout == Timeout(timeout=5.0)`) but you should set it explicitly and distinguish the phases:

```python
timeout = httpx.Timeout(connect=2.0, read=5.0, write=5.0, pool=1.0)
```

`pool` bounds waiting for a free connection from the client's pool: it protects you from queueing behind your own saturation. Also set an **overall deadline** per user request that is shorter than the caller's timeout: if the mobile app gives up after 10 s, spending 25 s on retries serves nobody. Timeout budgets must nest: the inner timeouts times retry count must fit under the outer deadline.

### 3.3 Retries: when, how, how many

Retries turn transient failures into successes; they also multiply load and cause duplicates. Rules:

1. **Retry only transient errors**: connection errors, timeouts, `502/503/504`, `429` (respecting `Retry-After`). Never retry validation errors (`4xx`), authentication failures, or business rejections.
2. **Retry only idempotent operations** (GET, PUT, DELETE by HTTP semantics, 2.1) **or operations carrying an idempotency key**. A POST without a key is *unsafe to retry*: a timeout means "unknown outcome", not "failed".
3. **Exponential backoff with jitter**: sleep `uniform(0, min(cap, base * 2**attempt))` ("full jitter"). Without jitter, clients synchronize. Cap the attempts (3-5) and the total elapsed time.
4. **Retry at one layer.** If the client, a service mesh and your wrapper each retry 3 times, one failure becomes 27 calls. Know where retries live.
5. **Budget**: when the dependency is down, retries add load exactly when it is weakest. Pair with a circuit breaker (2.7) so you stop calling.

### 3.4 Idempotency

An operation is **idempotent** if performing it N times has the same effect as once. `PUT /users/7 {…}` and `DELETE /users/7` are idempotent by definition of the method; `POST /payments` is not. Make it so with an **idempotency key**: the client generates a unique key (UUID) per *logical* operation and sends it (`Idempotency-Key` header, the convention used by Stripe and in an IETF Internet-Draft, draft-ietf-httpapi-idempotency-key-header-08, still not an RFC when checked in October 2026) on every retry of that operation. The server stores the outcome keyed by it and replays it.

Design questions and the answers this lesson uses:

| Question | Decision |
|---|---|
| Where do you store keys? | In the **same database and the same transaction** as the business effect. A separate store (Redis) can disagree with the DB after a crash |
| How do you handle concurrent duplicates? | A **unique constraint** on `(scope, key)`; the loser gets `IntegrityError`, rolls back, and reads the winner's stored response |
| What if the same key arrives with a different body? | `422` (or `409`): it is a client bug, never silently replay a different request's answer. Store a hash of the canonical request body |
| What is the scope of a key? | Per authenticated principal (user or API client), so users cannot collide with or probe each other's keys |
| How long do keys live? | A TTL (commonly 24 h or more), cleaned by a periodic job; document it |
| What if the first request is still running? | With a single transaction, the duplicate blocks on the unique index until commit, then reads. If your effect spans a network call, you need an `in_progress` state and a `409`/`Retry-After` for the duplicate (see 3.6) |

Idempotency applies on the **consuming** side of messages too: queues generally deliver **at-least-once**, so the same message can arrive twice. The consumer records processed message ids (unique constraint) or makes the effect naturally idempotent (`SET status = 'shipped'` rather than `counter += 1`). "Exactly-once delivery" is not something you can assume across a network; "at-least-once delivery plus idempotent processing" gives exactly-once *effect*.

### 3.5 Background work: options and trade-offs

| Option | What it is | Good for | Weaknesses |
|---|---|---|---|
| FastAPI `BackgroundTasks` | Runs a function after the response is sent, in the same process | Tiny, loss-tolerant work: cache warm, audit ping | Lost if the process dies or restarts; no retry, no visibility, no scheduling; async tasks share your loop, sync tasks use the threadpool and compete with requests |
| Celery | Mature distributed task queue (broker: RabbitMQ/Redis), schedules, retries, routing, canvas | Large, many-feature systems; existing Celery teams | Heavy, config surface and operational complexity; sync-first |
| RQ | Simple Redis-backed queue | Small teams, simple jobs | Redis only; fewer features; sync workers |
| arq | asyncio-native Redis queue | Async codebases wanting light weight | Smaller ecosystem; check maintenance status before adopting (checked: the repository is not archived; last push April 2026, so releases are slower than other options; re-check) |
| DB-backed outbox + poller | Rows in your own DB drained by a worker | Reliable "do this after commit" with no new infrastructure | You build polling, locking, backoff; throughput ceiling lower than a broker |

Selection principle (opinion, but standard): choose the *least* machinery that satisfies **durability** (must survive restarts?), **retry** semantics, **visibility** (can I see failures?) and **scheduling**. If a lost job is acceptable, `BackgroundTasks`. If not, you need persistence: a broker or the outbox. Do not adopt Celery because a tutorial did; and in an existing codebase use what the team already runs.

### 3.6 The dual-write problem and the outbox

```python
db.add(order); db.commit()
broker.publish("order.created", order.id)   # crash here: order exists, nobody hears about it
```

Reverse the order and you may announce an order that never committed. You cannot make a DB commit and a broker publish atomic without distributed transactions. **Transactional outbox**: in the *same DB transaction* that writes the order, insert an `outbox` row describing the event. A separate worker reads unpublished rows, publishes them, then marks them sent. The worker can crash between publish and mark, so the message may be published twice: **at-least-once**, hence consumers must be idempotent (3.4). Row claiming with multiple workers uses `SELECT ... FOR UPDATE SKIP LOCKED` on PostgreSQL (SQLAlchemy: `.with_for_update(skip_locked=True)`; not available on SQLite).

```mermaid
sequenceDiagram
  participant API
  participant DB
  participant W as Outbox worker
  participant X as External service
  API->>DB: BEGIN; INSERT order; INSERT outbox(event); COMMIT
  loop poll
    W->>DB: claim unsent rows (FOR UPDATE SKIP LOCKED)
    W->>X: deliver (with idempotency key = outbox.id)
    W->>DB: mark sent (or increment attempts, set next_attempt_at)
  end
```

Use the outbox row's id as the idempotency key towards the external service, so a duplicate publish is harmless.

### 3.7 Caching and invalidation

A cache trades freshness for latency and load. **Invalidation**: after `PATCH /products/3` the cached `GET /products/3` is wrong. Options: TTL only (bounded staleness), delete-on-write, versioned keys (`product:3:v17`). Delete *after* commit; otherwise a concurrent reader can re-populate the cache with the old value between your delete and your commit. **Stampede**: when a hot key expires, N requests miss at once and hammer the database; mitigate with jittered TTLs, single-flight loading (one loader per key, others await it) or serve-stale-while-revalidate. Never cache per-user data under a shared key (an authorization bug, 2.5), bound memory, and remember an in-process cache is per-instance so instances disagree.

### 3.8 External integration failure modes

Slow, down, wrong (malformed or drifted schema), partial (success but response lost), duplicate or out-of-order (webhooks), rate limited (429), credentials expired, clock skew. For each integration write down: timeout, retry policy, idempotency story, error translation (`502`/`503`/`504` with a stable error body) and degraded behavior (queue, fail fast, serve stale).

## 4. Worked example

### 4.1 Blocking vs non-blocking: measure it

`blocking.py` (Python 3.12+, `pip install fastapi httpx`):

```python
import asyncio, time
from fastapi import FastAPI
app = FastAPI()

@app.get("/bad")
async def bad():
    time.sleep(1)               # blocks the event loop thread
    return {"ok": True}

@app.get("/good-async")
async def good_async():
    await asyncio.sleep(1)      # yields to the loop
    return {"ok": True}

@app.get("/good-sync")
def good_sync():
    time.sleep(1)               # runs in the threadpool
    return {"ok": True}
```

`probe.py` fires 5 concurrent requests per route in-process through `httpx.ASGITransport` (no server needed) and prints the wall time:

```python
import asyncio, time, httpx
from blocking import app

async def run(path, n=5):
    transport = httpx.ASGITransport(app=app)
    async with httpx.AsyncClient(transport=transport, base_url="http://t") as c:
        t0 = time.perf_counter()
        await asyncio.gather(*[c.get(path) for _ in range(n)])
        return time.perf_counter() - t0

async def main():
    for p in ("/bad", "/good-async", "/good-sync"):
        print(p, round(await run(p), 2), "s for 5 concurrent 1s requests")
asyncio.run(main())
```

On my run, `/bad` took about five times as long as the other two (serialized), while the other two finished in about one second. Run it yourself and record your numbers; the *ratio* is the lesson, absolute values depend on your machine. This is a harness, not a benchmark: it measures scheduling behavior, not server throughput (for that see load testing in 2.7).

### 4.2 Retry with backoff and jitter

Naive version: `for i in range(5): try: return await call() except Exception: time.sleep(1)`. Problems: blocks the loop, fixed delay (synchronization), retries every exception including bugs, no cap on total time.

Improved (`retry.py`; Python 3.12 generic function syntax):

```python
import asyncio, random
from collections.abc import Awaitable, Callable
import httpx

RETRYABLE_STATUS = {502, 503, 504}

async def call_with_retry[T](
    fn: Callable[[], Awaitable[T]],
    *, attempts: int = 4, base: float = 0.2, cap: float = 5.0,
    sleep: Callable[[float], Awaitable[None]] = asyncio.sleep,
    rng: random.Random | None = None,
) -> T:
    rng = rng or random.Random()
    for attempt in range(attempts):
        try:
            return await fn()
        except (httpx.TimeoutException, httpx.TransportError):
            if attempt == attempts - 1:
                raise
        except httpx.HTTPStatusError as e:
            if e.response.status_code not in RETRYABLE_STATUS or attempt == attempts - 1:
                raise
        await sleep(rng.uniform(0, min(cap, base * 2 ** attempt)))   # full jitter
    raise AssertionError("unreachable")
```

Design choices: `sleep` and `rng` are injected so tests are instant and deterministic (1.4); only transient exceptions are retried, so 4xx propagates at once. `httpx.TimeoutException` is a subclass of `httpx.TransportError`; both are listed for clarity (checked on httpx 0.28.1: `issubclass(httpx.TimeoutException, httpx.TransportError)` is `True`).

Tests (`pytest-asyncio`, `asyncio_mode = auto` in `pytest.ini`) assert: succeeds on the third try with exactly two recorded sleeps, each within its jitter bound; a `400` is not retried (1 call); exhaustion re-raises the last error. I ran these three tests green.

Note httpx's own `AsyncHTTPTransport(retries=n)` only retries *connection establishment* failures; it does not retry read timeouts or 5xx. Do not mistake it for a full retry policy.

### 4.3 Shared client and lifespan

```python
from contextlib import asynccontextmanager
import httpx
from fastapi import FastAPI, Request

@asynccontextmanager
async def lifespan(app: FastAPI):
    app.state.http = httpx.AsyncClient(
        base_url="https://api.example-provider.test",
        timeout=httpx.Timeout(connect=2.0, read=5.0, write=5.0, pool=1.0),
        limits=httpx.Limits(max_connections=50, max_keepalive_connections=20),
    )
    yield
    await app.state.http.aclose()

app = FastAPI(lifespan=lifespan)

def get_http(request: Request) -> httpx.AsyncClient:
    return request.app.state.http
```

One client per process: connection pooling and keep-alive only work if the client is reused. Creating `httpx.AsyncClient()` per request defeats pooling and costs a TLS handshake each time. Closing it in the lifespan prevents leaked sockets at shutdown.

### 4.4 DB-backed idempotency (naive, then correct)

**Naive:** `if db.scalar(select(Payment).where(Payment.client_ref == ref)): return it` then insert. Two concurrent requests both see "not found" and both insert (a classic check-then-act race). Fix: let the database arbitrate with a unique constraint.

Runnable module `idem.py` (full file with models, engine and tests in the solutions file; a SQLite *file* DB is used so threads get separate connections; `StaticPool`/in-memory shares one connection and breaks under threads, which I hit while verifying). The core:

```python
class IdempotencyRecord(Base):
    __tablename__ = "idempotency_keys"
    __table_args__ = (UniqueConstraint("scope", "key", name="uq_idem_scope_key"),)
    id: Mapped[int] = mapped_column(primary_key=True)
    scope: Mapped[str] = mapped_column(String(64))        # e.g. user id
    key: Mapped[str] = mapped_column(String(128))
    request_hash: Mapped[str] = mapped_column(String(64))
    response_code: Mapped[int]
    response_body: Mapped[dict] = mapped_column(JSON)

def fingerprint(body: BaseModel) -> str:
    canonical = json.dumps(body.model_dump(mode="json"), sort_keys=True, separators=(",", ":"))
    return hashlib.sha256(canonical.encode()).hexdigest()

@app.post("/payments", status_code=201)
def create_payment(body: PaymentIn, response: Response, db: Annotated[Session, Depends(get_db)],
                   idempotency_key: Annotated[str, Header(min_length=8, max_length=128)]):
    scope, h = "demo-user", fingerprint(body)       # scope comes from auth in real code (2.5)
    try:
        pay = Payment(account=body.account, amount_cents=body.amount_cents)
        db.add(pay); db.flush()
        result = {"id": pay.id, "account": pay.account, "amount_cents": pay.amount_cents}
        db.add(IdempotencyRecord(scope=scope, key=idempotency_key, request_hash=h,
                                 response_code=201, response_body=result))
        db.commit()                                 # effect + key commit atomically
        return result
    except IntegrityError:
        db.rollback()                               # lost the race, or a plain retry
        return _replay(db, scope, idempotency_key, h, response)
```

`_replay` loads the stored record by `(scope, key)`, raises `422` if `request_hash` differs, otherwise sets the stored status code, adds `Idempotent-Replayed: true`, and returns the stored body.

Test (`test_idem.py`): a sequential retry returns the same body with `Idempotent-Replayed: true` and one row; same key with different amount gives 422; and the concurrency test:

```python
from concurrent.futures import ThreadPoolExecutor
def test_concurrent_duplicates():
    before = count()
    def go(_): return c.post("/payments", json={"account": "B", "amount_cents": 9},
                             headers={"Idempotency-Key": "key-0003-aaa"})
    with ThreadPoolExecutor(8) as ex: rs = list(ex.map(go, range(8)))
    assert {r.status_code for r in rs} == {201}
    assert len({r.json()["id"] for r in rs}) == 1
    assert count() == before + 1
```

I ran the three tests green, three times in a row. Honest caveats: SQLite serializes writers, so this proves the *logic*; on PostgreSQL the duplicate waits on the unique index entry of the uncommitted first transaction, then fails with a unique violation after it commits. I re-ran these three tests against PostgreSQL 18 (psycopg 3, pool of 10, eight threads) five times: all green. The reference tests initially failed in about half the runs once `pytest-randomly` shuffled the order, because one test asserted an absolute row count; the solutions now compare against a count taken at the start of the test. A non-obvious point: a crash between the business insert and the commit rolls both back, so the retry is a clean first attempt; this atomicity is exactly why key and effect share a transaction.

**When the effect calls an external service** (charge a card), you cannot hold a DB transaction open across it. Use two phases: (1) insert the key row with `status='in_progress'` and commit; (2) call the provider, passing *your key* as the provider's idempotency key; (3) update the row to `done` with the response. A duplicate arriving during (2) sees `in_progress` and gets `409` with `Retry-After`; a crash during (2) leaves a stale `in_progress` that a reaper job resolves by re-querying the provider using the same key. This is the design you will implement in the project.

## 5. Production perspective

**Correctness.** The dangerous region is "unknown outcome": the request timed out, so did it happen? Design cross-boundary writes so the answer can be determined (idempotency key, provider lookup by reference) rather than guessed.

**Performance.** Bound concurrency toward each dependency with an `asyncio.Semaphore` (bulkheading) so a spike does not open thousands of sockets. In sync services watch the threadpool: 40 slow requests occupy all threads and request 41 waits; the symptom is rising latency with low CPU. Measure with load tests (2.7).

**Security.** Scope idempotency keys to the principal; never treat the header as authorization. Webhook receivers verify signatures and are idempotent (providers retry). Do not log stored replay bodies containing personal data.

**Failure handling.** When the provider is down, the outbox keeps accepting writes and the backlog grows: alert on backlog age (oldest unsent row), not just error rate. After N attempts move poison rows to a dead-letter state and alert; never retry forever at full speed.

**Testing.** Inject clocks, sleeps and RNGs. Use a fake provider (a small FastAPI app or `httpx.MockTransport`) that fails N times, times out, returns 429 with `Retry-After`, or succeeds but "loses" the response. Deliver every message twice and assert the end state is unchanged. Use PostgreSQL in CI for concurrency tests (SQLite cannot show `SKIP LOCKED`).

**What a senior engineer does differently.** Asks "what if this runs twice, never, or out of order?" for every message and endpoint; refuses retry loops without a timeout and a cap; starts with the simplest durable mechanism (outbox) before adding a broker; keeps `async` out of code that does not need it.

**Common beginner mistakes and diagnosis.**

| Mistake | Symptom and diagnosis |
|---|---|
| `requests`/`time.sleep`/sync ORM in `async def` | Latency spikes and failing health checks with idle CPU. Run a lag monitor task (sleep 100 ms, log overshoot); enable asyncio debug mode (`PYTHONASYNCIODEBUG=1`), which logs callbacks slower than `loop.slow_callback_duration` (default 0.1 s) |
| `httpx.AsyncClient` per request | Many TLS handshakes, socket exhaustion; search for `AsyncClient(` inside handlers |
| Retry on all exceptions | Bugs retried and load multiplied; log the retry reason |
| Retrying un-keyed POST | Duplicate side effects; replay every mutation twice in tests |
| `BackgroundTasks` for must-happen work | Missing emails after deploys; compare job counts across a restart |
| Check-then-insert dedup | Rare duplicates; concurrent-thread test, then add a unique constraint |
| Cache delete before commit | Stale value reappears; reproduce with two threads and a barrier |

## 6. Failure laboratory

Save as `lab26.py`:

```python
import time, requests
from fastapi import FastAPI

app = FastAPI()
CHARGES = []

@app.get("/healthz")
async def healthz():
    return {"ok": True}

@app.post("/signup")
async def signup(email: str):
    r = requests.post("https://email-provider.invalid/send", json={"to": email}, timeout=30)
    return {"sent": r.status_code}

def charge_with_retry(amount: int):
    for attempt in range(5):
        try:
            CHARGES.append(amount)          # the provider "charges", then the response is lost
            raise TimeoutError("response lost")
        except TimeoutError:
            time.sleep(0.5)
    return "gave up"
```

**Predict, in writing, before running anything:**
1. The email provider hangs for 30 s. You send one `POST /signup` and, one second later, `GET /healthz` against a single-worker server. What does the health check do, and for how long?
2. Call `charge_with_retry(100)` once. What does `CHARGES` contain, and what does the customer see on their statement?
3. If you change `signup` to `def`, what changes for `/healthz` and what new limit appears?
4. Name three defects in `charge_with_retry` beyond the missing idempotency key.

### Reveal (read after predicting)

1. `/healthz` hangs until the blocking call returns (up to 30 s): `requests.post` never yields, so the single loop thread is busy and even timeouts cannot fire. The liveness probe fails and the pod is killed. (To reproduce, point it at a slow local server you write; the `.invalid` host fails fast on DNS.)
2. `CHARGES == [100, 100, 100, 100, 100]`: five charges for one purchase. "Response lost" is indistinguishable from "failed" without a key.
3. `/healthz` answers (the blocking call moves to a pool thread), but slow signups can exhaust the pool, after which new `def` requests queue. An `async def` health check avoids the pool.
4. Constant delay (no backoff or jitter); `time.sleep` blocks a thread (and the loop in `async def`); only `TimeoutError` is handled; no total-time cap; gives up with a string instead of an error; the effect sits inside the retried region.

**Systematic diagnosis procedure** for "service freezes under load":
1. Is CPU high or low? Low CPU with high latency means waiting/blocking, not compute.
2. Is the event loop lagging? Add the lag monitor; if lag tracks latency, something is blocking the loop.
3. Find the blocker: `py-spy dump --pid <pid>` shows the stack of the main thread (`pip install py-spy`; it is actively maintained and may need ptrace permission, e.g. `--cap-add SYS_PTRACE` in Docker); or run with asyncio debug.
4. If threads are the bottleneck: count busy threads versus the limiter; check pool exhaustion.
5. Check dependency timeouts and connection-pool wait times (`pool` timeout hits in logs).
6. Fix, then write a regression test that asserts a second request completes while the first is stuck.

## 7. Retrieval practice

Mode A. Answers are in the solutions file.

## 11. Mastery gate

Pass = 80/100 and no critical failure.

**Critical failures:**
1. Any test (or a reviewer-run duplicate script) that produces two effects for one idempotency key.
2. A blocking call inside an `async def` path in the shipped service.
3. Retries applied to non-idempotent, un-keyed operations, or retries without timeouts or jitter.
4. A "must-not-lose" job executed via `BackgroundTasks` or an in-memory queue.
5. A business effect and the event announcing it written without a shared transaction or an outbox.

**Required evidence:** green test output including the concurrent-duplicate and crash-recovery tests, run against PostgreSQL; `DESIGN.md` failure table; a recording or transcript of the worker killed mid-delivery and the system converging; a 10-minute defense answering the review questions without notes.

**If failed:** remedial exercise: take the fake provider and write a script that sends the same logical transfer 50 times from 8 threads with random client-side disconnects; instrument and show how many effects occurred; then fix the specific gap and rerun until the count is exactly one. For blocking-call failures: build the event-loop lag monitor, show a freeze reproduced by one planted blocking call, and show it fixed two ways.
