## 1. Engineering problem

A course dashboard shows "average score per course for learner X". In development (200 rows) it takes 2 ms. In production (300 million rows in the submissions table) it takes 40 seconds and holds a connection from a pool of 20, so after twenty page loads the whole API returns 503. A developer "fixes" it by adding an index on every column; writes slow down, disk grows, and the dashboard query is still slow because none of the indexes match its shape. Another team stores `course_name` in every enrolment row; a rename now requires updating 8 million rows, and two rows disagree after a partial failure. A third uses `LEFT JOIN ... WHERE e.status = 'completed'` and silently loses every course with no completed enrolments.

These are not exotic. They come from four gaps: not modelling data so that invalid states are unrepresentable, not knowing how the database finds rows, not reading the plan, and guessing instead of measuring. This lesson fixes all four on a small, realistic dataset.

## 3. First-principles explanation

### 3.1 The relational model, keys and constraints

A table is a set of rows with the same columns; a **primary key** (PK) uniquely identifies a row. A **foreign key** (FK) says a column's value must exist in another table's key; the database enforces it. A **unique constraint** forbids duplicates. **NOT NULL** and **CHECK** constrain values. The purpose is to make invalid states unrepresentable *in the one place every writer must pass through*. Application validation (Lesson 2.2) is for good error messages; constraints are for correctness, because there are always other writers: a migration script, an admin console, a second service, a bug.

Key choices:

- **Surrogate key** (`bigint GENERATED ALWAYS AS IDENTITY`, or a UUID): stable, small, meaningless. **Natural key** (email, course code): meaningful but changes (people change email). Typical design: surrogate PK plus a unique constraint on the natural key.
- **Composite PK** for pure link tables (`enrolment(learner_id, course_id)`): the pair is the identity and prevents duplicate enrolments for free.
- FK actions: `ON DELETE RESTRICT` (default behaviour: `NO ACTION`) protects history; `CASCADE` deletes dependants (right for owned data, dangerous for shared data); `SET NULL` for optional links.
- NULL semantics: `NULL` means unknown. `x = NULL` is never true; use `IS NULL`. `NULL` in a `NOT IN (subquery)` makes the whole predicate unknown and returns no rows: prefer `NOT EXISTS`. `count(*)` counts rows, `count(col)` counts non-null values.
- Money: `numeric(12,2)` or integer minor units, never `float`/`double precision`.
- Time: `timestamptz` in PostgreSQL (stored as UTC instant), not naive `timestamp`.

### 3.2 Normalization

Normalization removes redundancy so each fact is stored once. In practice:

- **1NF**: atomic values, no repeating groups (no comma-separated list of course ids in a column).
- **2NF**: every non-key column depends on the whole key (in `enrolment(learner_id, course_id, course_title)`, `course_title` depends only on `course_id`, so move it).
- **3NF**: no non-key column depends on another non-key column (`learner(zip, city)` where `zip` determines `city`).

Informal rule: a fact has one home. Why: update anomalies (rename in 8 million places), insert anomalies (cannot record a course until someone enrols), delete anomalies (deleting the last enrolment deletes the course name). **Denormalize deliberately** only for a measured read problem, and then own the consistency (trigger, materialized view, or application rule plus a reconciliation check). Moodle itself denormalizes in places for speed, which is one reason its schema cannot be treated as a textbook model (Lessons 3.2, 3.4).

### 3.3 Joins and aggregation

```
learner (20k) --< enrolment >-- course (50)
                     |
                     +--< submission (FK to the enrolment pair)
```

- `INNER JOIN`: rows with a match on both sides.
- `LEFT JOIN`: every left row; right columns are NULL when no match. **Trap**: a `WHERE` condition on the right table's columns discards the NULL rows and turns the query into an inner join. Put right-table conditions in the `ON` clause: `LEFT JOIN enrolment e ON e.course_id = c.id AND e.status = 'completed'`.
- Anti-join ("learners not enrolled in course 1"): `NOT EXISTS (SELECT 1 FROM enrolment e WHERE e.learner_id = l.id AND e.course_id = 1)`.
- Join explosion: joining two one-to-many tables multiplies rows and corrupts sums. Aggregate each side in a subquery first, then join.
- `GROUP BY` collapses rows; every selected column must be grouped or aggregated (PostgreSQL enforces this; see 3.8 for MySQL). `WHERE` filters rows before grouping; `HAVING` filters groups after.
- Logical order: FROM/JOIN, WHERE, GROUP BY, HAVING, SELECT, ORDER BY, LIMIT. This explains why a select-list alias cannot be used in `WHERE`.

**Window functions** compute over a set of rows related to the current row *without collapsing them*: `rank() OVER (PARTITION BY course_id ORDER BY score DESC)` ranks within each course; `sum(x) OVER (ORDER BY t)` is a running total. Ties: `rank` leaves gaps (1,2,2,4), `dense_rank` does not, `row_number` has no ties. Observed on the lab data: for course 7, ranks `1, 2, 2` appear for scores `99.99, 99.96, 99.96`.

### 3.4 How a B-tree index works

A B-tree index stores keys in sorted order in a balanced tree of pages; each leaf entry points at the table row (in PostgreSQL, a heap tuple identifier). Lookup descends from the root in O(log n) page reads (a handful of pages even for hundreds of millions of rows), and leaves are linked, so a range scan walks them in order.

What a B-tree on `(a, b)` can do:

- `WHERE a = 1`, `WHERE a = 1 AND b = 2`, `WHERE a = 1 AND b > 5` (equality on the prefix, range on the next).
- `ORDER BY a, b` and `WHERE a = 1 ORDER BY b` without a sort node, and with `LIMIT 10` it reads only ten entries. This is the "top-N newest per course" pattern.
- It cannot efficiently serve `WHERE b = 2` alone (no leading column), `WHERE a > 1 AND b = 2` beyond the first column (the range on `a` breaks the ordering for `b`). Rule for column order: equality columns first, then the range or sort column. Exception noted in 3.6: PostgreSQL 18 can sometimes "skip scan".

Costs: every index slows INSERT/UPDATE/DELETE (all indexes must be maintained), occupies disk and cache, and complicates vacuuming. The unique constraint and PK already create indexes; FK columns are **not** automatically indexed in PostgreSQL (they are in MySQL/InnoDB), so deleting a parent row or joining children by FK may need one.

Variants: **partial** (`WHERE status = 'open'`; small index for a hot subset; PostgreSQL), **expression** (`ON learner (lower(email))`), **covering** (`INCLUDE (score)` so an index-only scan avoids the table). **Selectivity**: an index helps when the predicate returns a small fraction of rows. If 99% of rows match, scanning the table is cheaper than hopping between index and heap, and the planner is right to ignore the index.

Things that defeat an index: a function on the column (`lower(email) = ...` with only a plain index), a leading wildcard (`LIKE '%x'`), a type mismatch forcing a cast on the column, low selectivity, and (sometimes) `OR`. Other index types (hash, GIN for arrays/JSONB/full-text, GiST/BRIN) exist; use a B-tree until a plan shows otherwise.

### 3.5 Reading EXPLAIN

`EXPLAIN` shows the plan the optimizer chose, with *estimated* cost and rows. `EXPLAIN ANALYZE` **executes the query** and adds actual time and row counts; wrap data-modifying statements in `BEGIN; ... ROLLBACK;`. `BUFFERS` adds page counts (cache hits versus reads). Read bottom-up and inside-out: the most indented nodes run first and feed their parents.

Node types you will meet:

- `Seq Scan`: read the whole table. Fine for small tables or when most rows match.
- `Index Scan` / `Index Only Scan` / `Bitmap Index Scan` + `Bitmap Heap Scan`: using an index; bitmap scans batch heap visits for mid-selectivity predicates.
- Joins: `Nested Loop` (good with a small outer side and an indexed inner), `Hash Join` (builds a hash table of one side; good for large unsorted inputs), `Merge Join` (both inputs sorted).
- `Sort`, `HashAggregate`/`GroupAggregate`, `Limit`, `Gather` (parallel workers).

What to look at: (1) **estimated versus actual rows**: a large mismatch (10 estimated, 100,000 actual) means stale or insufficient statistics (`ANALYZE`) or correlated columns, and the planner then makes bad join choices. (2) `Rows Removed by Filter`: a large number means you read many rows to keep few, so an index or a better one is likely. (3) `loops`: actual time and rows in a node are *per loop*; multiply. (4) `Buffers: shared hit/read`: how much data was touched. (5) planning versus execution time.

Honest limits: costs are in arbitrary planner units, not milliseconds; timings vary with cache state (run twice, report the second, or report both); a tiny table may legitimately choose a sequential scan even with an index available, so test on realistic volumes. **Never quote a speed-up you did not measure on data shaped like production.**

### 3.6 What I observed on the lab data (PostgreSQL 18.6)

The dataset (Section 4): 20,000 learners, 50 courses, 60,000 enrolments, 300,000 submissions. Results by plan shape only (timings are machine-specific, so measure your own):

- `WHERE learner_id = 4242` on `submission` without an index: a parallel `Seq Scan` that removed about 150,000 rows per worker to return 15. With an index on `learner_id`: `Bitmap Index Scan` + `Bitmap Heap Scan`, 15 heap blocks.
- Composite `(course_id, submitted_at)` with `WHERE course_id = 7 ORDER BY submitted_at DESC LIMIT 10`: `Index Scan Backward` under `Limit`, no `Sort`, ten rows read.
- `WHERE submitted_at > '2025-10-01'` alone on that composite index: a `Bitmap Index Scan` using the composite index (the second column). I had expected a sequential scan from the leading-prefix rule. PostgreSQL 18 added B-tree skip scan (confirmed in the PG 18 release notes; I also reproduced it on 18: with an index on `(a, b)` where `a` has 10 distinct values, `WHERE b = 777` used an `Index Scan` on that index; skip scan pays off when the leading column has few distinct values). On PostgreSQL 17 or older expect a `Seq Scan` here, and in MySQL, check your version. Treat the leading-prefix rule as the portable design rule, and skip scan as an optimization you do not rely on.
- `WHERE lower(email) = '...'` with only a plain unique index on `email`: `Seq Scan` with `Filter: (lower(email) = ...)`. `WHERE email = '...'`: `Index Scan`.
- `WHERE status = 'active'` (about 99% of rows) with an index on `status`: `Seq Scan`; `WHERE status = 'completed'` (1%): `Index Scan`.
- `LIKE '%5@example.test'`: `Seq Scan`.
- `SELECT avg(score) ... WHERE course_id = 7` with `CREATE INDEX ... (course_id) INCLUDE (score)` after `VACUUM`: `Index Only Scan`, `Heap Fetches: 0`.

### 3.7 Measure, do not guess

Workflow: (1) capture the real slow query with its parameters (from a slow query log, `pg_stat_statements`, or the APM; the extension must be installed and listed in `shared_preload_libraries`); (2) `EXPLAIN (ANALYZE, BUFFERS)` on production-shaped data; (3) form a hypothesis from the plan (missing index? bad estimate? too many rows? N+1 from the application?); (4) change one thing; (5) re-measure and keep the evidence; (6) check write cost and other queries affected. An application-level N+1 (one query per row in a loop, e.g. an ORM lazy-loading a relation) will not show up as a slow plan at all, only as thousands of fast queries: count queries per request.

### 3.8 MySQL and MariaDB differences relevant to Moodle

Moodle supports PostgreSQL, MariaDB, MySQL and Microsoft SQL Server; the minimum versions per release are at moodledev.io (checked: Moodle 5.1 needs PostgreSQL 15, MySQL 8.4, MariaDB 10.11, SQL Server 2017; Moodle 5.0 needed PostgreSQL 14), so older Moodle-era versions below differ. Differences that bite:

- **InnoDB clustered primary key**: the table *is* the PK B-tree, and secondary indexes store the PK value. A wide or random PK enlarges every secondary index. FK columns get indexes automatically.
- **No partial indexes**; functional indexes exist in MySQL 8.0.13+; MariaDB has virtual columns that can be indexed.
- **`GROUP BY` strictness**: MySQL's `ONLY_FULL_GROUP_BY` mode (default since 5.7.5) is stricter than older behaviour, but sql_mode is configurable, so a query that passes on one server may fail on another. Write standard-conforming queries.
- **Collation and case**: default collations are case-insensitive, so `WHERE email = 'A@x.com'` matches `a@x.com`; PostgreSQL's default is case-sensitive. Character set should be `utf8mb4` (MySQL's old `utf8` is 3 bytes).
- **DDL is not transactional** in MySQL/MariaDB (implicit commit), whereas PostgreSQL rolls back DDL. This changes migration safety (Lesson 2.4).
- **Window functions and CTEs**: MySQL 8.0+, MariaDB 10.2+ (windows) and 10.2+ (CTEs). Older installations lack them.
- **Plan tools**: MySQL 8.0 has `EXPLAIN ANALYZE` (since 8.0.18) and `EXPLAIN FORMAT=TREE`; MariaDB uses `ANALYZE <statement>` and `EXPLAIN`. Output formats differ from PostgreSQL's, but the reading skill (rows removed, estimated vs actual, index used or not) is the same.
- **Implicit type conversion** (`WHERE varchar_col = 123`) is more permissive and can silently defeat an index or match unexpected rows.
- **Moodle specifics**: tables are prefixed (default `mdl_`), and Moodle code uses its own database abstraction (`$DB`, Lesson 3.4) and XMLDB schema definitions rather than raw SQL, so portability is handled for you only if you use that API. Moodle's core schema does not declare database-level foreign keys everywhere (still unverified here; read install.xml in your Moodle version, and do not assume DB-level foreign keys exist), so integrity is application-enforced there; for your own FastAPI services, declare them.

### 4.2 Schema (`schema.sql`)

```sql
-- PostgreSQL 15+ (tested on 18)
DROP TABLE IF EXISTS submission, enrolment, course, learner CASCADE;

CREATE TABLE learner (
    id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    email      text        NOT NULL UNIQUE,
    full_name  text        NOT NULL,
    created_at timestamptz NOT NULL DEFAULT now()
);
CREATE TABLE course (
    id    bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    code  text NOT NULL UNIQUE,
    title text NOT NULL
);
CREATE TABLE enrolment (
    learner_id  bigint NOT NULL REFERENCES learner(id) ON DELETE CASCADE,
    course_id   bigint NOT NULL REFERENCES course(id),
    enrolled_at timestamptz NOT NULL DEFAULT now(),
    status      text NOT NULL DEFAULT 'active'
                CHECK (status IN ('active','suspended','completed')),
    PRIMARY KEY (learner_id, course_id)
);
CREATE TABLE submission (
    id           bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    learner_id   bigint NOT NULL,
    course_id    bigint NOT NULL,
    submitted_at timestamptz NOT NULL,
    score        numeric(5,2) CHECK (score BETWEEN 0 AND 100),
    FOREIGN KEY (learner_id, course_id) REFERENCES enrolment (learner_id, course_id)
);

INSERT INTO learner (email, full_name)
SELECT 'user' || g || '@example.test', 'User ' || g FROM generate_series(1, 20000) g;
INSERT INTO course (code, title)
SELECT 'C' || lpad(g::text, 3, '0'), 'Course ' || g FROM generate_series(1, 50) g;
INSERT INTO enrolment (learner_id, course_id)
SELECT l.id, ((l.id * 7 + k * 13) % 50) + 1
FROM learner l, generate_series(0, 2) k ON CONFLICT DO NOTHING;
INSERT INTO submission (learner_id, course_id, submitted_at, score)
SELECT e.learner_id, e.course_id,
       timestamptz '2025-01-01' + (random() * interval '300 days'),
       round((random() * 100)::numeric, 2)
FROM enrolment e, generate_series(1, 5);
ANALYZE;
```

Design reasoning: `submission` references the *enrolment pair*, so a submission cannot exist for a learner who is not enrolled in that course: the database enforces a business rule. `random()` makes scores and dates differ per run, so your numbers will differ from mine; the plan shapes should not. The `ON CONFLICT DO NOTHING` handles the generator producing the same pair twice. `ANALYZE` refreshes the statistics the planner uses; forgetting it after a bulk load is itself a common cause of bad plans.

### 4.3 Queries and the measurement loop

```sql
-- Q1: all submissions of one learner
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM submission WHERE learner_id = 4242;
-- observe: Seq Scan, large "Rows Removed by Filter"
CREATE INDEX submission_learner_idx ON submission (learner_id);
ANALYZE submission;
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM submission WHERE learner_id = 4242;
-- observe: Bitmap Index Scan; compare Buffers and Execution Time

-- Q2: ten newest submissions in a course (composite order matters)
CREATE INDEX submission_course_time_idx ON submission (course_id, submitted_at);
EXPLAIN (ANALYZE) SELECT * FROM submission WHERE course_id = 7 ORDER BY submitted_at DESC LIMIT 10;
-- observe: Index Scan Backward under Limit, no Sort node

-- Q3: average score per learner in a course, top 5 (joins + aggregate)
EXPLAIN (ANALYZE, COSTS OFF, TIMING OFF, SUMMARY OFF)
SELECT l.full_name, c.title, avg(s.score)
FROM submission s JOIN learner l ON l.id = s.learner_id JOIN course c ON c.id = s.course_id
WHERE c.code = 'C007' GROUP BY l.full_name, c.title ORDER BY 3 DESC LIMIT 5;
-- observe (this run): Nested Loop (course -> Bitmap scan on submission via the Q2 index),
-- Hash Join to learner, HashAggregate, top-N heapsort

-- Q4: count of courses per status, preserving courses with none (LEFT JOIN trap)
SELECT c.code, count(e.learner_id)
FROM course c LEFT JOIN enrolment e ON e.course_id = c.id AND e.status = 'completed'
GROUP BY c.code ORDER BY c.code LIMIT 3;     -- condition in ON keeps zero-count courses
-- Move "e.status = 'completed'" to WHERE and the zero-count courses vanish.

-- Q5: window: top 3 scores per course
SELECT * FROM (
  SELECT learner_id, course_id, score,
         rank() OVER (PARTITION BY course_id ORDER BY score DESC) AS r
  FROM submission) t WHERE r <= 3 ORDER BY course_id, r;
```

Q3's join plan was *not* what a naive reading of the SQL suggests (the planner started from `course`, not `submission`): the plan is an output of statistics, not a transcription of your query. Q5 uses a subquery because window results cannot be filtered in the same `SELECT`'s `WHERE` (logical order, 3.3).

Naive versus improved: the naive fix for Q1 is `CREATE INDEX` on everything; the improved approach creates one index justified by a plan, re-measures, and records the evidence (what changed: node type, rows removed, buffers). Another improvement: replace `SELECT *` with the needed columns so a covering index (`INCLUDE`) can give an `Index Only Scan`.

## 5. Production perspective

**Correctness.** Constraints first, in the schema: PK, FK, unique, not null, check. Decide delete behaviour per relationship. Use `timestamptz`, `numeric`. Normalize until a measured need says otherwise.

**Performance.** Index for the queries you have, not those you imagine. For each index record: the query it serves, the plan before/after, the write cost. Remove indexes that no query uses (`pg_stat_user_indexes` shows scan counts in `idx_scan`). Keep statistics fresh (autovacuum/`ANALYZE`). Limit result sizes (Lesson 2.1) and prefer keyset pagination for deep paging (Lesson 2.4). Check connection pool exhaustion when queries are slow: slow SQL appears as 503s.

**Security.** Always pass values as bound parameters, never f-strings (SQL injection; the opening snippet of Lesson 2.2 had one). The application DB role should not own the schema or be a superuser. Least privilege per service. Do not log full parameter values for sensitive columns.

**Operations.** Index creation on a large table locks writes unless you use `CREATE INDEX CONCURRENTLY` (PostgreSQL; cannot run inside a transaction block, waits for existing transactions that could use the index, does two table scans, and only one concurrent build per table is allowed; checked in the CREATE INDEX docs and reproduced: inside `BEGIN` it fails with "cannot run inside a transaction block"); it takes longer but avoids blocking. Schema changes are migrations (Lesson 2.4). Back up and test restores.

**Observability.** Slow query logging (`log_min_duration_statement`) and `pg_stat_statements` identify the top offenders by total time, not just single slow calls (the extension must be installed and preloaded). Track queries per request to catch N+1.

**Senior engineer habits.** Reads the plan before touching the schema. Asks for row counts and data distribution. Tests on production-shaped data, because a plan at 1,000 rows says little about 100 million. Treats an index as a cost with a justification, and drops it when the justification disappears. Works within the team's existing schema conventions and migration tooling rather than redesigning them.

**Beginner mistakes and diagnosis.**

| Mistake | Symptom | Diagnosis |
|---|---|---|
| Index on every column | Slow writes, large disk, queries still slow | `EXPLAIN` the slow query: does the plan use any of them? Compare index usage statistics |
| Function or cast on indexed column | Seq Scan despite an index | `Filter:` line shows the expression instead of `Index Cond:` |
| LEFT JOIN + WHERE on right table | Missing rows (parents with no children) | Compare row counts with the condition moved into `ON` |
| `NOT IN` with nullable subquery | Empty result | Run the subquery alone; look for NULLs; use `NOT EXISTS` |
| `SELECT *` and no `LIMIT` | Huge payloads, memory pressure | Check rows and width in the plan |
| Stale statistics | Estimated rows wildly different from actual | `ANALYZE table`, re-explain |
| Row-by-row loops in application code | Fast queries, slow request | Count queries per request |

## 6. Failure laboratory

Run the schema, then consider this dashboard query and a developer's three "optimizations":

```sql
SELECT c.title, count(*) AS submissions, avg(s.score) AS avg_score
FROM course c
LEFT JOIN submission s ON s.course_id = c.id
WHERE s.submitted_at >= '2025-06-01'
GROUP BY c.title
ORDER BY avg_score DESC;
```

Optimization A: `CREATE INDEX ON submission (score);` Optimization B: `CREATE INDEX ON submission (lower(course_id::text));` Optimization C: `CREATE INDEX ON enrolment (status);` then querying `WHERE status = 'active'` where 99% of rows are active.

**Before running anything, predict:** (1) Does the query list courses with zero submissions since June? Why? (2) Which index, if any, can the dashboard query use, and what plan node would you expect for `submission`? (3) For each of A, B, C: does the planner use it for the query it was meant to help, and what is the cost? (4) How would you rewrite the query to preserve the intent "all courses, with their counts since June"? (5) What index would you try, and what would you check before keeping it?

### Reveal (read after predicting)

1. No. The `WHERE s.submitted_at >= ...` runs after the left join; unmatched courses have `s.submitted_at = NULL`, the comparison is unknown, and the row is discarded. The `LEFT JOIN` has become an inner join. Rewrite with the date condition in `ON`.
2. An index with `submitted_at` as its leading column (or `course_id, submitted_at`, serving the join side). The index `score` (A) is irrelevant: `avg(score)` needs every row's score, and no predicate or order uses it. `lower(course_id::text)` (B) is an expression index that matches no query: the join compares `course_id` itself. C: low selectivity, so the planner prefers `Seq Scan` (observed: 99% `active` gave Seq Scan; 1% `completed` gave Index Scan).
3. A, B and C are all unused by this dashboard (C helps only for the rare-value predicate). All three still cost writes and disk. Measuring would have shown this: confirm with `EXPLAIN` and index scan counters.
4. `FROM course c LEFT JOIN submission s ON s.course_id = c.id AND s.submitted_at >= '2025-06-01'` and `count(s.id)` instead of `count(*)` (count(*) would count the null-extended row as 1). Verify the result has 50 rows.
5. Try `(course_id, submitted_at)` or `(course_id, submitted_at) INCLUDE (score)`; check the plan changed, `Heap Fetches` after `VACUUM`, that execution actually improved on realistic volume, and the write cost on insert-heavy paths. If the query reads most of the table anyway (a six-month window in a one-year dataset), a seq scan with parallel workers may win, and then the right answer is "no new index" or a pre-aggregated summary table.

Diagnosis procedure for a slow query: (1) get the exact SQL and parameters; (2) `EXPLAIN (ANALYZE, BUFFERS)`; (3) find the node with the highest actual time x loops; (4) compare estimated and actual rows on that node; (5) check `Rows Removed by Filter`, scan type, join type; (6) hypothesize one change; (7) apply it in a copy; (8) re-measure; (9) decide with evidence; (10) record in the failure log.

## 7. Retrieval practice

Mode A. Answers in the solutions file.

1. Why are constraints in the database needed when the API already validates input?
2. A table `enrolment(learner_id, course_id, course_title)` has PK `(learner_id, course_id)`. Which normal form does it violate, and what anomaly does it allow?
3. Predict the row count: `course` has 50 rows, 3 have no enrolments. `SELECT count(*) FROM course c LEFT JOIN enrolment e ON e.course_id = c.id WHERE e.status = 'completed'`. Then say what changes if the condition is in `ON`.
4. `NOT IN (SELECT x FROM t)` returns no rows although some `x` values do not match. Likely cause and fix?
5. For `WHERE course_id = 7 AND submitted_at > T ORDER BY submitted_at`, choose the best index and explain why `(submitted_at, course_id)` is worse.
6. Why might the planner ignore an index on `status` when 99% of rows are `active`?

## 11. Mastery gate

Pass = 80/100 and no critical failure. Evidence: all deliverables, a transcript that regenerates the database and re-runs every query, and Mode A answers to Section 7 questions 1-9 at 8/9 or better.

Critical failures: an index justified by intuition rather than a recorded plan; a LEFT JOIN silently turned inner in a delivered query; string-concatenated SQL; missing FK or PK in the core entities; a reported speed-up with no before/after plan or measured on tiny data only; unexplained claims about MySQL/MariaDB stated as fact without being checked or marked unverified.

If failed: remedial exercise (2 hours). On the lab schema, take three queries you did not previously optimize. For each, write a hypothesis *before* running EXPLAIN, record the plan, then record whether the hypothesis was right. At least one hypothesis must be wrong in your log, or you did not choose hard-enough queries.
