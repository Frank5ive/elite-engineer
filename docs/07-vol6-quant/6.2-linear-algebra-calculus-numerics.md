## 1. Engineering problem

Four failure patterns:

1. A risk job computes variance of 100,000 prices near 1e9 as `mean(x*x) - mean(x)^2` and gets **-128.0**; the true value is about 1.0007. `sqrt` of it gives NaN.
2. A test `0.1 + 0.2 == 0.3` fails; the "fix" `abs(a-b) < 1e-9` then equates two prices of magnitude 1e-12.
3. A nightly sum of 10 million small amounts differs by 1.6e-4 from a compensated sum; reconciliation breaks.
4. A Newton solver for an implied rate cycles forever on one input in ten thousand; the service times out.

All come from treating floats as real numbers. This lesson gives the linear algebra and calculus a quant needs (vectors, matrices, covariance eigenstructure, gradients, root finding, integration) together with what the machine does to them, and ends with a small tested numerics library, the first piece of the Capstone D toolbox.

## 2. Learning objectives

By the end you can:

3. Compute eigenvalues and eigenvectors of a 2x2 covariance matrix by hand, interpret them as variance along principal axes, and implement a symmetric eigen-solver tested by `Av = lambda v`.
4. Derive Newton's method from the Taylor expansion; implement bisection and Newton with documented failure modes; exhibit a Newton failure.
5. Implement trapezoid and Simpson rules and verify their order empirically (error ratios near 4 and 16 when n doubles).

7. Distinguish forward error, residual and condition number with a Hilbert-matrix experiment.

## 3. First-principles explanation

### 3.1 Vectors and matrices as machines

A vector x in R^n is a list of n numbers (positions, returns of n assets, portfolio weights). The **dot product** x.y = sum x_i y_i measures alignment; the **norm** |x| = sqrt(x.x) is length; x.y = |x||y| cos(theta). Portfolio return is weights . returns; portfolio variance is a quadratic form w^T C w (3.4).

A matrix A (m x n) is a linear map from R^n to R^m: it takes a vector and returns a vector, preserving addition and scaling. Matrix product C = AB means "apply B, then A": C_ij = sum_k A_ik B_kj. Shapes must chain: (m x n)(n x p) = (m x p). Because applying maps in a different order gives a different result, AB != BA in general: rotate then stretch is not stretch then rotate. Example A = [[1,2],[3,4]], B = [[0,1],[1,0]]: AB = [[2,1],[4,3]] (swaps A's columns), BA = [[3,4],[1,2]] (swaps A's rows). The code multiplies in i-k-j loop order so the inner loop walks rows of B and C contiguously; whether that is faster on your machine is a measurement (Lesson 5.6), and I give no number.

Row-major flat storage: element (i,j) of an r x c matrix lives at `a[i*c + j]`. Choosing one `std::vector<double>` over `vector<vector<double>>` removes a pointer indirection and keeps the matrix contiguous.

### 3.2 Solving Ax = b

Gaussian elimination turns the system into upper-triangular form by subtracting multiples of rows, then back-substitutes. Worked example (verified by the code in section 4 and by numpy):

    2x +  y -  z =   8
   -3x -  y + 2z = -11
   -2x +  y + 2z =  -3        solution (x, y, z) = (2, 3, -1)

Without swapping, for clarity: Row 2 += 1.5 Row 1 and Row 3 += Row 1 give 0.5y + 0.5z = 1 and 2y + z = 5; eliminate once more and back-substitute z = -1, y = 3, x = 2.

**Partial pivoting**: before eliminating column k, swap in the row with the largest absolute entry in that column. Without it, a tiny pivot produces enormous multipliers and destroys accuracy; with a zero pivot, as in [[0,1],[1,0]], the algorithm divides by zero. It costs O(n^2) comparisons and is what LAPACK-style solvers do (the general-purpose library routine is LU with partial pivoting; for your library see section 4).

**Never solve by computing A^-1 b**: it costs more and is usually less accurate; for many right-hand sides factor once and reuse. Dense elimination is O(n^3); triangular, banded or symmetric positive definite (Cholesky) structure lowers it.

Failure: a singular matrix such as [[1,2],[2,4]] has no pivot in column 2 after elimination. Detect "numerically singular" with a pivot threshold relative to the matrix scale, return an error, never divide.

### 3.3 Conditioning: the problem, not the algorithm

The **condition number** kappa(A) = |A| |A^-1| bounds how much relative error in the input can be amplified in the solution. Rule of thumb: you lose about log10(kappa) of your 16 decimal digits. The Hilbert matrix H_ij = 1/(i+j+1) is the textbook ill-conditioned matrix. Measured with numpy `cond` (2-norm): n = 4: 1.55e4; n = 8: 1.53e10; n = 12: 1.81e16 (about 1/eps, the end of double precision).

Experiment (C++ library, solve H x = H * ones, true x = all ones; error = max |x_i - 1|; residual = max |Hx - b|):

    n = 4    error 6.1e-13   residual 1.1e-16
    n = 8    error 4.2e-7    residual 4.4e-16
    n = 12   error 0.356     residual 8.9e-16

The **residual stays at rounding level while the answer is 36% wrong**. Lesson: a small residual does not prove a small error; condition number connects them. This is why regression with near-collinear predictors (6.3) is unstable and why you inspect conditioning before trusting any solve. A backward-stable algorithm (partial-pivoting elimination) gives the exact answer to a slightly perturbed problem; whether that is close to your answer depends on kappa, not on the code.

### 3.4 Eigenvalues and covariance matrices

A vector v is an **eigenvector** of A with **eigenvalue** lambda if Av = lambda v: A merely stretches v. Find lambda from det(A - lambda I) = 0.

Take the covariance matrix of two assets, C = [[4,2],[2,3]] (variances 4 and 3, covariance 2). det(C - lambda I) = (4 - lambda)(3 - lambda) - 4 = lambda^2 - 7 lambda + 8 = 0, so lambda = (7 +- sqrt 17)/2 = 5.5616 and 1.4384. Checks you should always do: trace 7 = sum of eigenvalues; determinant 8 = product. For lambda = 5.5616: (4 - 5.5616) v1 + 2 v2 = 0 gives v2 = 0.7808 v1, normalized (0.7882, 0.6154); the second eigenvector is perpendicular, (-0.6154, 0.7882).

Meaning: C is symmetric, so by the spectral theorem its eigenvalues are real and its eigenvectors orthogonal. The eigenvectors are the **principal axes** of the return cloud and the eigenvalues are the variances along them: 5.5616/7 = 79.5% of total variance lies along one direction, so the two assets mostly move together. Portfolio variance w^T C w, for unit-length w, is smallest along the eigenvector of the smallest eigenvalue. A covariance matrix estimated from data must have all eigenvalues >= 0; negative ones are a data-quality alarm, and a zero eigenvalue means two assets are perfectly dependent (a singular matrix, as in 3.2).

Computation: Jacobi's method applies plane rotations that each zero one off-diagonal entry; the matrix converges to diagonal while the rotations accumulate into the eigenvector matrix. It is simple and accurate for small symmetric matrices; production code calls LAPACK (VERIFY routine names such as `dsyev` in the LAPACK docs).

### 3.5 Derivatives, gradients and optimization intuition

The derivative f'(x) = lim (f(x+h) - f(x))/h is the slope of the tangent line, the best linear approximation: f(x+h) ~ f(x) + f'(x) h. For many variables the **gradient** is the vector of partial derivatives; it points in the direction of steepest increase.

Numerical differentiation by central difference, (f(x+h) - f(x-h))/(2h), has truncation error O(h^2) but rounding error about eps |f|/h. Measured for f = exp at x = 1 (true derivative e):

    h        1e-1     1e-3     1e-5     1e-8     1e-11    1e-14
    error    4.5e-3   4.5e-7   5.9e-11  6.6e-9   1.0e-5   9.3e-3

Error falls then rises; the best h is near eps^(1/3), about 6e-6. Choosing h = 1e-14 "because smaller is more accurate" is the classic mistake. Alternatives: analytic derivatives, automatic differentiation (outside this volume).

**Gradient descent**: x <- x - lr * grad f(x). On f(x,y) = (x-3)^2 + 10(y+1)^2 (minimum at (3,-1); the curvature in y is 20, in x is 2), it converges with lr = 0.05. For lr = 0.2 the y-update multiplies the error by (1 - lr*20) = -3 each step, so it diverges: measured |y| = 2.66e95 after 200 steps. Rule: stability needs lr < 2/(largest curvature) = 0.1 here, while progress in the flat direction needs many steps (slow when curvatures differ by orders of magnitude - ill-conditioning again, with the Hessian's eigenvalue ratio playing the role of kappa). Use it when the gradient is cheap and the function smooth; avoid it as a root finder.

### 3.6 Root finding: bisection and Newton

**Bisection**: if f is continuous and f(a), f(b) have opposite signs, a root lies between; halve the interval, keep the half with the sign change. Guaranteed. Iterations to reach width tol: ceil(log2((b-a)/tol)); for [1,2], tol = 1e-12 the code needed 40 (2^-40 = 9.1e-13). Linear convergence, no derivative needed, needs a bracket.

**Newton**: from f(x + h) ~ f(x) + f'(x) h = 0 solve h = -f/f'; iterate x <- x - f(x)/f'(x). Near a simple root the error squares each step (quadratic convergence): the number of correct digits roughly doubles. For f = x^2 - 2 from x0 = 1 it reached sqrt 2 = 1.4142135623730951 in 5 iterations versus 40 for bisection. But it can fail: f = x^3 - 2x + 2 from x0 = 0 gives 0 -> 1 -> 0 -> 1... forever (the tangent at 0 lands on 1; the tangent at 1 lands on 0), f' = 0 at the turning points divides by zero, and a bad start can leap outside the region where the function is monotone. Production practice: hybrid methods - take a Newton step, fall back to bisection if the step leaves the bracket or fails to shrink it (Brent's method is the standard; I describe, not derive). Always cap iterations and return a convergence flag.

### 3.7 Numerical integration

Approximate the integral of f over [a,b] by sampling. **Trapezoid**: connect points by lines, h(f_0/2 + f_1 + ... + f_n/2), error O(h^2). **Simpson**: fit parabolas through triples, weights 1,4,2,4,...,4,1 times h/3, error O(h^4), n even. Test with the integral of sin from 0 to pi = 2:

    n    trapezoid err   simpson err   ratios when n doubles
    8    2.58e-2         2.69e-4
    16   6.43e-3         1.66e-5       4.01   16.22
    32   1.61e-3         1.03e-6       4.00   16.06

Ratios 4 and 16 confirm second- and fourth-order accuracy. This **ratio test** is how you verify any numerical method without knowing a closed form: halve the step, see the error divide by 2^order. Use Simpson (or Gauss-Legendre) for smooth integrands; avoid on integrands with kinks or singularities - there, split at the kink. Monte Carlo (6.3) wins when dimension is high: its error does not depend on dimension.

### 3.8 IEEE 754 doubles

A `double` is 64 bits: 1 sign, 11 exponent, 52 fraction. A normal value is (-1)^s x 1.f x 2^(e - 1023), so there are 53 significant bits (about 15.95 decimal digits). **Machine epsilon** = 2^-52 = 2.220446049250313e-16 is the gap between 1.0 and the next double. Consequences (Python 3.13.5 on this machine; same on any IEEE 754 binary64 platform):

- 0.1 is not representable. Its double is 0x1.999999999999ap-4 = 0.1000000000000000055511151231257827...; 0.1 + 0.2 = 0.30000000000000004 != 0.3.
- Absorption: `1 + 1e-16 == 1` is True; `1 + 2.3e-16` gives 1.0000000000000002. Integers are exact only to 2^53 = 9007199254740992; `2**53 + 1.0 == 2**53` is True.
- Each operation rounds to nearest (ties to even), giving relative error at most eps/2.
- Non-associativity: (1e100 + 1) - 1e100 is 0.0 while 1 + (1e100 - 1e100) is 1. Compilers must preserve order unless you allow `-ffast-math`.
- Special values: infinities, NaN (`NaN != NaN`, comparisons with NaN are false), signed zero (0.0 == -0.0 is True but 1/-0.0 is -inf).
- Compound growth: (1 + 1/n)^n at n = 1e8 is 2.7182817983473577, which is 3.0e-8 below e (the exact expression is itself 1.4e-8 below e; the rest is rounding), and at n = 1e16 it is exactly 1.0, because 1 + 1e-16 rounds to 1.

Whether C++ `double` is IEEE binary64 is implementation-defined; check `std::numeric_limits<double>::is_iec559` (VERIFY on your toolchain). Compilers may also fuse multiply-add (`-ffp-contract`), changing last bits between builds.

### 3.9 Cancellation and stable reformulation

Subtracting nearly equal numbers loses significant digits ("catastrophic cancellation") because the leading digits cancel and what is left is rounding error promoted to the front. Three measured cases:

1. Quadratic x^2 - 1e8 x + 1 = 0: small root true value about 1e-8. Textbook (-b - sqrt(b^2 - 4ac))/2a gives 7.45e-9, **25.5% wrong**. Reformulate using the product of roots, x_small = 2c / (-b + sqrt(b^2 - 4ac)), getting 1e-8.
2. (1 - cos x)/x^2 at x = 1e-8: direct formula returns 0.0; the identity 1 - cos x = 2 sin^2(x/2) gives 0.5, the correct limit.
3. The variance example of section 1: -128.0. Use Welford's update (6.1) or a two-pass method.

Method: whenever you subtract two quantities of similar size, ask whether algebra can avoid the subtraction. This is the main skill of stable numerics.

### 3.10 Comparing floats

Never use `==` on computed floats. Combine tolerances: equal if |a - b| <= abs_tol or |a - b| <= rel_tol * max(|a|, |b|). Relative alone fails near zero (1e-20 vs 2e-20 differ by 100%); absolute alone fails across scales (1e-9 is huge at magnitude 1e-12 and invisible at 1e12). Choose from the problem: rounding error is a few eps x magnitude x operations, so rel_tol 1e-9 is generous for one sum and too tight for an ill-conditioned solve (the Hilbert error above is 0.356). Document each tolerance; handle NaN and equal infinities explicitly.

### 3.11 Summation

Summing n numbers naively has worst-case error that grows with n. Measured: 10,000,000 copies of 0.1 summed in a `double` loop differ from the correctly rounded 1e6 by -1.61e-4; with Kahan-Neumaier compensation the difference is exactly 0 (to the digits printed, `kahan err 0.000e+00`).

Idea: keep a running correction c holding the low-order bits lost by each addition. Neumaier's variant compares magnitudes, so it also works when a new term exceeds the running sum: for {1e100, 1, -1e100} naive gives 0.0, Neumaier 1.0. Python's `math.fsum` is exactly rounded; since Python 3.12 built-in `sum` on floats is documented to be compensated (VERIFY in the release notes; measured: `sum([0.1]*10)` is 1.0 while a manual loop gives 0.9999999999999999). Alternatives: pairwise summation (used by numpy), ascending sort, `long double`.

**Compiler trap (measured, GCC 14.2.0):** compiling the same test with `-Ofast` (which implies `-ffast-math`) made the Kahan result -8.9e-5, identical to the naive one, and two tests failed: the compiler is allowed to reassociate floating-point math, so `(t - s) - x` simplifies to 0 and the compensation vanishes. Do not compile numerics with `-ffast-math`; if you must for speed, isolate and test that translation unit.

## 4. Worked example

Build the library in the order of risk: comparison and summation first (they are used by every test), then root finding, then integration. Full library (matrix, solver, eigen-solver, gradient descent) is the project; reference in the solutions file. Design choices:

1. **Header-only, `namespace num`, free functions with `std::function` for callbacks.** `std::function` costs an indirect call per evaluation and may allocate; a template parameter `F` would be faster. I chose clarity first; the extension asks you to measure the difference (no number given here).
2. **Error handling by type:** `std::optional` for "no solution" (singular matrix), a result struct with a `converged` flag for iterative methods, `std::invalid_argument` for violated preconditions (bracket without sign change, odd n for Simpson).
3. **Tolerances are parameters with documented defaults**, not hidden constants.
4. **Tests assert known answers with stated tolerances** and print the measured numbers once so tolerances are justified rather than guessed.

```cpp
// numerics.hpp (excerpt) - C++20
#include <algorithm>
#include <cmath>
#include <functional>
#include <span>
#include <stdexcept>

namespace num {

inline bool almost_equal(double a, double b, double rel_tol = 1e-9, double abs_tol = 0.0) {
    if (a == b) return true;                          // equal infinities, exact matches
    if (!std::isfinite(a) || !std::isfinite(b)) return false;   // NaN, mismatched infinities
    const double d = std::fabs(a - b);
    return d <= abs_tol || d <= rel_tol * std::max(std::fabs(a), std::fabs(b));
}

inline double kahan_sum(std::span<const double> xs) {   // Neumaier variant
    double s = 0.0, c = 0.0;
    for (double x : xs) {
        const double t = s + x;
        c += (std::fabs(s) >= std::fabs(x)) ? (s - t) + x : (x - t) + s;
        s = t;
    }
    return s + c;       // WARNING: breaks under -ffast-math / -Ofast
}

struct RootResult { double x; int iterations; bool converged; };

inline RootResult bisect(const std::function<double(double)>& f, double a, double b,
                         double tol = 1e-12, int max_iter = 200) {
    double fa = f(a), fb = f(b);
    if (fa == 0) return {a, 0, true};
    if (fb == 0) return {b, 0, true};
    if ((fa < 0) == (fb < 0)) throw std::invalid_argument("bisect: root not bracketed");
    for (int i = 1; i <= max_iter; ++i) {
        const double m = a + (b - a) / 2;             // not (a+b)/2: avoids overflow
        const double fm = f(m);
        if (fm == 0 || (b - a) / 2 <= tol) return {m, i, true};
        if ((fm < 0) == (fa < 0)) { a = m; fa = fm; } else { b = m; }
    }
    return {a + (b - a) / 2, max_iter, false};
}

inline RootResult newton(const std::function<double(double)>& f, const std::function<double(double)>& df,
                         double x0, double tol = 1e-12, int max_iter = 50) {
    double x = x0;
    for (int i = 1; i <= max_iter; ++i) {
        const double fx = f(x), d = df(x);
        if (fx == 0) return {x, i, true};
        if (d == 0 || !std::isfinite(d)) return {x, i, false};   // flat tangent
        const double step = fx / d;
        x -= step;
        if (!std::isfinite(x)) return {x, i, false};
        if (std::fabs(step) <= tol * (1 + std::fabs(x))) return {x, i, true};
    }
    return {x, max_iter, false};                        // never loop forever
}
} // namespace num
```

Reasoning notes: the `a == b` shortcut precedes the finiteness test so `inf == inf` is true; `(b - a)/2 <= tol` stops on interval half-width; the Newton stopping rule is relative on the step, `tol * (1 + |x|)`, so it works for x near 0 and for large x.

Tests (build: `g++ -std=c++20 -O2 -Wall -Wextra -Wpedantic -Wconversion -fsanitize=address,undefined`; zero warnings on GCC 14.2.0). Key assertions, each with the measured value that justifies its tolerance:

```cpp
CHECK(!(0.1 + 0.2 == 0.3));                      // documents the hazard
CHECK(num::almost_equal(0.1 + 0.2, 0.3));
CHECK(!num::almost_equal(1e-20, 2e-20));         // relative-only keeps tiny values distinct
CHECK(num::almost_equal(1e-20, 2e-20, 1e-9, 1e-15));
CHECK(!num::almost_equal(std::nan(""), std::nan("")));
CHECK(num::kahan_sum(std::vector<double>{1e100, 1.0, -1e100}) == 1.0);
auto b = num::bisect(f, 1, 2); auto n = num::newton(f, df, 1.0);   // f = x*x - 2
CHECK(b.converged && n.converged && n.iterations < b.iterations);  // measured 40 vs 5
```

Naive vs improved: the naive Newton loops `while (|f| > 1e-12) x -= f/df;`: no iteration cap (infinite loop in the cycling case), a division by zero when `df == 0`, and a residual test that never succeeds for steep functions where |f| cannot get below 1e-12 in double. The improved version caps iterations, checks the derivative, tests the step size, and reports convergence.

## 5. Production perspective

**Correctness.** Separate method error (Simpson's h^4), floating-point error (cancellation, summation) and model error, and verify each separately: ratio test for order; an extended-precision or exact reference for rounding.

**Testing.** Known closed forms (sqrt 2; integral of sin = 2; eigenvalues (7+-sqrt 17)/2; the tridiagonal [[2,-1,0],[-1,2,-1],[0,-1,2]] with eigenvalues 2+-sqrt 2 and 2), properties (Av = lambda v within 1e-10; solve residuals) and failures (singular matrix gives `nullopt`; unbracketed bisection throws; Newton on x^2+1 from 0 reports non-convergence). Print the measured error once, set the tolerance a safe factor above it, and write down why.

**Performance and operations.** Dense O(n^3) kernels are memory-bound at scale; production code uses BLAS/LAPACK (Eigen, Armadillo, MKL are options; VERIFY team standards before adding a dependency). Measure before optimizing. Return a status, never a silent NaN; check `std::isfinite` on results entering downstream systems; log iteration counts and residuals (rising Newton iteration counts warn of data drift).

**What a senior engineer does differently.** Looks up the library routine before writing one; reports a residual or condition estimate with every solve; writes the cancellation-free formulation; refuses `==` on floats in review; documents tolerances; uses compensated sums, and for money prefers integer minor units or decimals (a design decision beyond this lesson).

**Common beginner mistakes and diagnosis.**

- Inverting to solve: compare residuals against a direct solve.
- One global `1e-9` epsilon: scale inputs by 1e6 and watch the results flip.
- Finite-difference step too small: sweep h as in 3.5.
- `float` where `double` was intended: eps is 1.19e-07 (numpy `finfo(float32).eps` = 1.1920929e-07), and 16,777,216 + 1 stays 16,777,216 in float32 (measured with numpy).
- `-ffast-math`: diff results between `-O2` and `-Ofast` over the test suite.

## 6. Failure laboratory

A teammate writes a statistics helper and a solver. Predict the behaviour of each before reading on.

```cpp
// (A) variance of daily prices near 1e9
double variance_naive(const std::vector<double>& x) {
    double s = 0, s2 = 0;
    for (double v : x) { s += v; s2 += v * v; }
    const double n = static_cast<double>(x.size());
    return s2 / n - (s / n) * (s / n);
}
// data: 100,000 values 1e9 + Normal(0,1)

// (B) Newton on f(x) = x^3 - 2x + 2 starting at x0 = 0, stop when |f(x)| < 1e-12, no iteration cap
```

Write down: (1) the sign and rough size of (A) relative to the true value ~1.0; (2) whether the result changes with n; (3) what (B) does; (4) which one a test with `almost_equal(result, expected, 1e-9)` would catch.

### Reveal (read after predicting)

(A) On a Python replica of the same formula (same IEEE doubles, same accumulation order; 100,000 draws of 1e9 + Normal(0,1), seed 1) the result was -128.0, while the true variance was 1.0007. Both terms are near 1e18, and doubles between 2^59 and 2^60 are 128 apart, so anything computed at that scale carries errors in multiples of 128; the true answer, 1, is far below that resolution. Expect -128, 0 or +128, never 1. It is catastrophic cancellation: each term is accurate to 16 digits, and the subtraction leaves only the rounding noise. More data does not fix it, and the result can be negative.

(B) The iteration alternates 0 -> 1 -> 0 -> 1 forever (the tangent at 0 hits 1, the tangent at 1 hits 0). Without an iteration cap the program hangs; with the library's cap it returns `converged = false`. The real root is about -1.7693, so any test against it fails for (B). For (A), a test with `abs_tol` of a few hundred "because prices are big" would pass the wrong answer: tolerances must come from the problem, not from what makes the test green.

Diagnosis procedure for suspect numerics: (1) look for impossible outputs (negative variance, NaN, probability > 1); (2) rescale the inputs (divide by 1e9, subtract the mean): if the answer changes, suspect cancellation or absorption; (3) recompute against a higher-precision or exact reference (`math.fsum`, `fractions`, `long double`, mpmath); (4) reformulate algebraically to remove the subtraction; (5) add an iteration cap and convergence flag before debugging convergence.
