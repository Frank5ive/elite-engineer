Version discipline for this lesson. Moodle's *principles* (never trust input, escape on output, parameterise SQL, check capability, use the DB abstraction, keep strings out of code) have been stable for over a decade. The *APIs* that carry them are not. Each time this lesson names a function, class or file, treat it as "true for Moodle 5.3 docs as read on 2026-10-26" and confirm on your target site's version (`version.php` in the Moodle root, or Site administration > Notifications). Function signatures and file paths in this lesson were checked against the Moodle source (`MOODLE_503_STABLE`) and the developer-docs repository (github.com/moodle/devdocs). Anything still marked `VERIFY:` could not be confirmed from a primary source and you must check it before relying on it. Never fix a Moodle problem by editing core; every technique here lives inside your own plugin.

Directory layout note: from Moodle 5.1 onward the web-accessible code is served from a `public/` subdirectory (Moodle 5.1 release notes; the web server document root points at `public/`). Third-party plugins therefore live at `<moodleroot>/public/local/readinglist/` on 5.1+ and at `<moodleroot>/local/readinglist/` on 4.5 and 5.0. Paths inside this lesson are written relative to the plugin directory (`local/readinglist/...`). Plugin page scripts still use `require(__DIR__ . ## 1. Engineering problem

On your second week you are asked: "Teachers want to keep a reading list per course. Each item has a title, a URL, a note and a status. Only teachers edit; students view. Make it a plugin."

A developer who knows PHP but not Moodle produces something like this in `index.php`:

```php
$title = $_POST['title'];
$res = mysqli_query($link, "INSERT INTO readinglist (title) VALUES ('$title')");
echo "<li>" . $_GET['q'] . "</li>";
echo "Reading list";
```

That fragment contains at least six production defects, each of which a Moodle review will catch:

1. Reads superglobals directly (no cleaning, no typing).
2. Builds SQL by concatenation (SQL injection, and breaks on a title containing an apostrophe).
3. Bypasses `$DB` (the plugin works only on one database engine, ignores the table prefix, and ignores transactions and the debug query log).
4. Echoes unescaped input (reflected and stored XSS).
5. Hard-codes English (no translation, fails the Moodle "strings" review).
6. Has no `sesskey` check on a state-changing request (CSRF: any page the teacher visits can submit the form for them).

A seventh defect is silent: no capability check, so students can edit. Defects like these do not fail on your laptop. They fail when a security researcher or an automated scanner finds the instance, when an administrator runs PostgreSQL instead of MariaDB, or when a Chinese-language site shows `Reading list` in English.

This lesson gives you the mechanisms that make each of those defects structurally difficult: the Forms API (typed, validated, sesskey-protected input), `PARAM_*` cleaning (typed input outside forms), the output API (renderers, Mustache templates, `$PAGE`/`$OUTPUT`), the string API, the `$DB` API (placeholders, portability, transactions) and XMLDB (schema as versioned data).

## 3. First-principles explanation

### 3.1 The request lifecycle you are plugging into

```
Browser
  |  GET/POST /local/readinglist/edit.php?courseid=2&id=5
  v
config.php  -> boots Moodle: $CFG, $DB, $USER, $PAGE, $OUTPUT, sessions
  v
require_login($course)           (authentication + enrolment, from 3.3)
require_capability(..., $context) (authorisation, from 3.3)
  v
Input:  required_param / optional_param   OR   moodleform get_data()
  v
Model:  $DB->...   (placeholders, transactions)
  v
Output: $PAGE->set_*  ->  $OUTPUT/renderer->header() ... footer()
                              |
                              +-> Mustache template  +  get_string()
```

Order is a design rule, not a style choice: authenticate, authorise, clean input, act, then output. `$PAGE->set_url()` must be called before any output (Moodle warns in debug mode if the page URL is not set), and no HTML may be echoed before `header()`.

### 3.2 Input cleaning: PARAM_*

What: every value from outside the process (query string, POST body, form submission) is untrusted text. A `PARAM_*` constant is a *declared type* with a cleaning function behind it. `required_param($parname, $type)` fetches a request parameter and cleans it to that type; it throws (`missingparam`) only when the parameter is absent. `optional_param($parname, $default, $type)` falls back to the default when the parameter is absent. (Checked in `lib/moodlelib.php`; on 5.3 the `PARAM_*` constants are aliases of the `\core\param` enum, e.g. `PARAM_INT` is `\core\param::INT->value`, and these functions delegate to it. The constants and functions remain the API to use.)

Why: PHP's weak typing makes `$_GET['id']` a string that may be `"5 OR 1=1"`. Cleaning converts untrusted input into a value of a type your code can reason about.

How it behaves internally: `clean_param($param, $type)` applies a type-specific transformation (for example `PARAM_INT` casts to integer; `PARAM_ALPHANUMEXT` strips every character except letters, digits, underscore and hyphen; `PARAM_URL` validates and returns an empty string on failure). It *cleans*, it does not *validate*: `PARAM_INT` on `"5abc"` returns `5` rather than raising an error (the implementation is a plain `(int)` cast in `lib/classes/param.php`). A value that is clean but wrong is still your job to reject.

Types you will use constantly (full list in `lib/moodlelib.php`, defined via `lib/classes/param.php`):

| Type | Use for | Not for |
|---|---|---|
| `PARAM_INT` | ids, counts, page numbers | decimals |
| `PARAM_BOOL` | flags such as `confirm=1` | tri-state values |
| `PARAM_ALPHANUMEXT` | action keys, status keys (`todo`, `done`) | free text |
| `PARAM_TEXT` | single-line display text such as titles (strips tags, keeps multilang spans) | HTML |
| `PARAM_NOTAGS` | text where all tags must go | HTML |
| `PARAM_URL` | URLs entered by users | arbitrary strings |
| `PARAM_RAW` | values you will handle yourself (passwords, already-validated blobs) | anything echoed to a page |
| `PARAM_CLEANHTML` | rich text you must store as HTML | text you could store as plain |

Trap: `PARAM_RAW` is not "safe default". It is "I will take responsibility". Using it so that "the value stops being modified" is the most common cause of stored XSS in plugins.

When to avoid PARAM_* alone: PARAM_* cleans a request value; it does not check that the id you were given belongs to the course the user is allowed to edit. Authorization on the *object* is still your job (see worked example).

### 3.3 Forms API (moodleform)

What: a PHP class that declares fields once and gets rendering (HTML), client-side checks, server-side cleaning, `sesskey` insertion and submission detection.

Verified skeleton (docs for main/5.3):

```php
namespace local_readinglist\form;

require_once("$CFG->libdir/formslib.php");   // moodleform lives here

class item_form extends \moodleform {
    public function definition() {
        $mform = $this->_form;                // note the underscore
        $mform->addElement('text', 'title', get_string('title', 'local_readinglist'));
        $mform->setType('title', PARAM_TEXT);
        $this->add_action_buttons();          // method of moodleform, not of $mform
    }
    public function validation($data, $files) { return []; }
}
```

Page-script usage pattern (documented): check `is_cancelled()` first, then `get_data()`, otherwise `set_data()` and `display()`:

```php
if ($mform->is_cancelled()) { /* redirect */ }
else if ($data = $mform->get_data()) { /* save, redirect */ }
else { $mform->set_data($existing); $mform->display(); }   // display() must come after $OUTPUT->header()
```

How it works internally (principles; names are version-specific but the sequence is stable):

- Construction calls `definition()` and builds an element tree.
- On construction the form checks whether the request is a submission of *this* form (a hidden `_qf__<classname>` field) and whether the `sesskey` hidden field matches the session. `get_data()` returns `null` if the form was not submitted *or* validation failed *or* the session key was wrong. That is why `get_data()` is the single gate for "safe to save".
- Submitted values are cleaned to the type you gave via `setType()`. An element without `setType()` produces a debugging notice in developer mode and, for text elements, leaves the value uncleaned in older behaviour; always call it. (The docs I fetched do not state "mandatory"; treat it as mandatory by convention and by the security guideline that says to call `setType` for each field.)
- `validation($data, $files)` returns an array `['elementname' => 'error text']`; non-empty means the form is redisplayed with errors and `get_data()` returns `null`.
- Client-side rules (`addRule`) are convenience only. They are bypassed by anyone with `curl`. Anything that matters must be re-checked server-side. `addRule(...,'server')` and `validation()` are server-side.

Elements you will meet (from the docs): text, textarea, select, hidden, static, header, checkbox, advcheckbox, editor, filepicker, filemanager, date_selector, autocomplete, passwordunmask, selectyesno. Helpers: `setDefault`, `addRule`, `addHelpButton`, `hideIf`, `disabledIf`, `add_action_buttons`, `add_sticky_action_buttons` (since 4.3), `mock_submit` for unit tests.

Passing data into the form constructor: `new item_form($url, ['courseid' => $courseid, 'id' => $id])`; inside, `$this->_customdata['courseid']`. (`$_customdata` is a protected property of `moodleform`, `lib/formslib.php`.) Hidden fields carry `courseid` and `id` back; remember they come back through the same cleaning (`setType('id', PARAM_INT)`) and are *untrusted* like everything else.

When not to use moodleform: tiny state-changing actions such as "toggle done" or "delete". Use a POST single button plus `require_sesskey()`. A whole form for one button is over-engineering.

### 3.4 Output API

What the pieces are (all verified against the output API docs for main/5.3):

- `$PAGE` is the `moodle_page` instance describing the page being built: `set_url`, `set_title`, `set_heading`, `set_context` and `set_pagelayout('standard')`; the allowed layout names (`base`, `standard`, `incourse`, ...) are defined in the theme's `config.php` (see `theme/boost/config.php`).
- `$OUTPUT` is the generic core renderer. Plugins should get their own renderer: `$PAGE->get_renderer('local_readinglist')`, class `\local_readinglist\output\renderer` in `classes/output/renderer.php`, extending `\core\output\plugin_renderer_base`.
- Renderables hold *data*; renderers turn data into HTML. Queries and access checks happen before the renderable is created, so a theme override cannot change what is authorised.
- `named_templatable` (documented as the recommended interface for Mustache) provides `get_template_name(renderer_base $renderer): string` and `export_for_template(renderer_base $renderer): stdClass`.
- `$renderer->render($widget)` resolution order (documented): matching `render_<classname>()` method on the renderer, then `react_component_renderable`, then `named_templatable`, then `templatable`.
- `render_from_template('component/name', $context)` renders a Mustache template directly. Templates live in the plugin's `templates/` folder as `name.mustache` (for example `mod/forum/templates/`).

Why Mustache and not echoing HTML: themes can override templates, the same template can be rendered by JavaScript on the client, and Mustache escapes by default. `{{title}}` is HTML-escaped; `{{{title}}}` is raw. Rule: triple braces only for content already passed through `format_text()` or another sanctioned cleaner.

Language strings: `get_string('identifier', 'component', $a)`. Strings live in `lang/en/<component>.php` as `$string['identifier'] = '...';`. The coding-style page requires that strings are complete sentences (no concatenating UI fragments, no leading or trailing whitespace). Placeholders: `{$a}` for a scalar, `{$a->name}` for an object property. Required strings: `pluginname` (plugin list and admin screens), capability names (`$string['readinglist:manage']`: `get_capability_string()` in `lib/accesslib.php` builds the key `<pluginname>:<cap>` in component `<type>_<pluginname>`, matching core's `$string['forum:addinstance']` in `mod/forum/lang/en/forum.php`), `privacy:metadata` (3.5), cache definition descriptions (3.5). Mustache templates request strings with the `{{#str}}key, component{{/str}}` helper (as in core's `mod/forum/templates/discussion_favourite_toggle.mustache`).

Core-owned versus your string: strings you reuse from core (`get_string('save')`, `get_string('delete')`, `get_string('cancel')`) are in component `moodle` (core `lang/en/moodle.php`). Prefer reusing the generic ones for buttons, but never rely on a core string that is not a stable generic word: core strings get deprecated.

### 3.5 Database API ($DB)

Verified method signatures (DML docs and `lib/dml/moodle_database.php`, 5.3):

```
get_record($table, array $conditions, $fields = '*', $strictness = IGNORE_MISSING)
get_records_sql($sql, ?array $params = null, $limitfrom = 0, $limitnum = 0)
insert_record($table, $dataobject, $returnid = true, $bulk = false)
update_record($table, $dataobject, $bulk = false)
delete_records($table, ?array $conditions = null)
record_exists($table, array $conditions = null)
count_records($table, ?array $conditions = null)
get_field($table, $return, array $conditions, $strictness = IGNORE_MISSING)
set_field($table, $newfield, $newvalue, ?array $conditions = null)
execute($sql, ?array $params = null)
get_in_or_equal($items, $type = SQL_PARAMS_QM, $prefix = 'param', $equal = true, $onemptyitems = false)
sql_like($fieldname, $param, $casesensitive = true, $accentsensitive = true, $notlike = false, $escapechar = '\\')
```

Facts about behaviour (documented):

- Table names are written without the prefix and wrapped in curly braces in raw SQL: `{local_readinglist_item}`. Moodle replaces braces with the configured prefix. In the `get_record`-family you pass the bare name.
- `MUST_EXIST` throws `dml_missing_record_exception` for no rows and `dml_multiple_records_exception` for several. `IGNORE_MISSING` returns `false`.
- `get_records_sql` returns an array keyed by the **first selected column**, so select a unique id first. If the first column repeats, rows overwrite each other silently. This is a classic data-loss bug.
- Placeholders: question marks (`SQL_PARAMS_QM`) or named (`SQL_PARAMS_NAMED`); you must not mix styles in one query. Named placeholder names must be unique in a query even when the value is the same.
- `$limitfrom/$limitnum` implement paging portably. Do not write `LIMIT` in the SQL.
- `execute()` must not be used for schema changes; use `database_manager` in install/upgrade code.

Portability. Moodle supports several database engines and the set changes between releases: Moodle 5.3 lists PostgreSQL 17+, MySQL 8.4+, MariaDB 11.4+ and Microsoft SQL Server 2019+ (Oracle support ended with 5.0; moodledev.io/general/releases/5.3). Read the requirements for your exact release in the release notes or in Site administration > Server > Environment. The portability principle is stable: write SQL only through `$DB` methods and the `sql_*` helpers; do not use engine-specific functions (`GROUP_CONCAT`, `ILIKE`, `LIMIT` in SQL, backtick quoting, `||` concatenation) unless you gate them. Use `$DB->sql_like()` for text search, `$DB->sql_concat()`, `$DB->sql_compare_text()` when comparing large text columns (all present in `lib/dml/moodle_database.php`). Identifier length, reserved-word and empty-string-versus-NULL behaviours differ between engines; XMLDB constraints keep you inside a common subset. Test on at least two engines before declaring a plugin portable (3.6).

Transactions (documented): `$transaction = $DB->start_delegated_transaction();`, then work, then `$transaction->allow_commit();`. On exception, call `$transaction->rollback($exception)`; it rolls back and re-throws. "Delegated" means transactions nest: the real commit happens only when the outermost delegate calls `allow_commit()`. If any inner delegate calls `rollback()`, the whole outer transaction is doomed. Not every engine/storage supports transactions (the docs name MyISAM), so use them to protect consistency, not as control flow. Do not catch the exception and swallow it: that leaves the transaction open and Moodle will throw a "transaction not closed" error at the end of the request.

### 3.6 XMLDB: schema as versioned data

What: `db/install.xml` describes the tables created at install. `db/upgrade.php` contains incremental steps for sites already installed. `version.php` carries the version number whose increase triggers the upgrade. A site on version N installing version M runs, in order, every `if ($oldversion < X)` block with X <= M.

Verified `version.php` fields (docs main/5.3): `component` (required, frankenstyle), `version` (YYYYMMDDXX integer, must increase), `requires` (minimum core version, recommended), `supported` (since 3.9, lowest and highest branches, e.g. `[405, 503]`), `incompatible` (since 3.9), `maturity` (`MATURITY_ALPHA|BETA|RC|STABLE`), `release` (human string), `dependencies`. Copy the `requires` build number for your target branch from the `$version` in the target site's `version.php` (`public/version.php` on 5.1+); do not compute it. Real examples: 4.5.0 is `2024100700`, 5.0.0 is `2025041400`, 5.3.0 is `2026100500`.

Verified DDL methods (docs): `$dbman = $DB->get_manager();` then `table_exists`, `create_table`, `field_exists`, `add_field`, `drop_field`, `index_exists`, `add_index`, `change_field_*`, `rename_field`. Objects: `new xmldb_table('name')`, `new xmldb_field('name', XMLDB_TYPE_INTEGER, '10', null, XMLDB_NOTNULL, null, '0')` (constructor arguments in order: name, type, precision, unsigned, notnull, sequence, default, previous; checked in `lib/xmldb/xmldb_field.php`). Upgrade function skeleton: `function xmldb_local_readinglist_upgrade($oldversion)`, with the savepoint call `upgrade_plugin_savepoint(true, 2026102601, 'local', 'readinglist');` at the end of each step (signature `upgrade_plugin_savepoint($result, $version, $type, $plugin, $allowabort=true)` in `lib/upgradelib.php`). The savepoint records progress so a failed upgrade resumes after the last completed step.

Rule you will be graded on: **never edit an earlier upgrade step or reuse a released version number.** install.xml must always describe the *final* schema, and upgrade.php must reach that same schema from every prior version. Both are needed; a fresh install does not run old upgrade steps.

### 3.7 XSS, SQLi and CSRF in Moodle terms

| Attack | Mechanism that defends | Where it fails |
|---|---|---|
| SQL injection | `$DB` placeholders and conditions arrays; never interpolate request values | Interpolating an "already cleaned" PARAM into `ORDER BY` or table names (placeholders cannot parameterise identifiers; whitelist them) |
| Stored/reflected XSS | Clean on input to the type you need; escape on output: Mustache `{{ }}`, `s()`/`p()` for plain text, `format_string()` for short names, `format_text()` for HTML | `PARAM_RAW` + `{{{ }}}`; echoing `$_GET`; building HTML by concatenation in JavaScript |
| CSRF | `moodleform` sesskey (automatic), `require_sesskey()` / `confirm_sesskey()` on every state-changing request (the security guideline recommends `data_submitted() && confirm_sesskey()`) | GET links that delete; AJAX/web service endpoints that bypass the sesskey flow (web services use tokens; see 3.5) |
| Broken access control | `require_login` + `require_capability` on *every* script and every object (3.3) | Checking the course but not that `$item->courseid` equals it (IDOR) |

Defence is layered: input cleaning reduces what gets in; output escaping decides what comes out; they are independent and you need both. Never use "I cleaned it on input" as a reason to skip output escaping.

### 3.8 Trade-offs

Forms API versus hand-written HTML: the API gives CSRF protection and consistent UX. Own table versus admin setting or user preference: use a table only for related records. Renderer plus Mustache versus echo: Mustache wins on theming, JS reuse and default escaping. SQL versus simple getters: use SQL for joins and aggregates, getters for single-table lookups. Typical production failures: missing `{}` around table names, dereferencing a `false` from `get_record`, reused version numbers in upgrade steps.

Transaction pattern (documented API), for atomic multi-statement writes: `$t = $DB->start_delegated_transaction(); try { ...writes...; $t->allow_commit(); } catch (\Throwable $e) { $t->rollback($e); }`.

### 4.2 version.php

```php

// (full GPL header required by the coding style; omitted here for space.)

defined('MOODLE_INTERNAL') || die();

$plugin->component = 'local_readinglist';
```

### 4.3 install.xml

Do not hand-write the header; create the file with the XMLDB editor (Site administration > Development > XMLDB editor, requires developer mode) so the schema reference path is right for your layout. The table body:

```xml
<TABLE NAME="local_readinglist_item" COMMENT="Reading list items">
  <FIELDS>
    <FIELD NAME="id" TYPE="int" LENGTH="10" NOTNULL="true" SEQUENCE="true"/>
    <FIELD NAME="courseid" TYPE="int" LENGTH="10" NOTNULL="true" DEFAULT="0" SEQUENCE="false"/>
    <FIELD NAME="userid" TYPE="int" LENGTH="10" NOTNULL="true" DEFAULT="0" SEQUENCE="false" COMMENT="Creator"/>
    <FIELD NAME="title" TYPE="char" LENGTH="255" NOTNULL="true" SEQUENCE="false"/>
    <FIELD NAME="url" TYPE="char" LENGTH="1333" NOTNULL="true" SEQUENCE="false"/>
    <FIELD NAME="note" TYPE="text" NOTNULL="false" SEQUENCE="false"/>
    <FIELD NAME="status" TYPE="char" LENGTH="20" NOTNULL="true" DEFAULT="todo" SEQUENCE="false"/>
    <FIELD NAME="timecreated" TYPE="int" LENGTH="10" NOTNULL="true" DEFAULT="0" SEQUENCE="false"/>
    <FIELD NAME="timemodified" TYPE="int" LENGTH="10" NOTNULL="true" DEFAULT="0" SEQUENCE="false"/>
  </FIELDS>
  <KEYS>
    <KEY NAME="primary" TYPE="primary" FIELDS="id"/>
    <KEY NAME="courseid" TYPE="foreign" FIELDS="courseid" REFTABLE="course" REFFIELDS="id"/>
    <KEY NAME="userid" TYPE="foreign" FIELDS="userid" REFTABLE="user" REFFIELDS="id"/>
  </KEYS>
  <INDEXES>
    <INDEX NAME="course-status" UNIQUE="false" FIELDS="courseid, status"/>
  </INDEXES>
</TABLE>
```

Design choices: plain integer timestamps (`timecreated`, `timemodified`) are the Moodle convention; `char` for bounded text and `text` for unbounded (core's `mod_url` stores its URL in a `text` field, `externalurl`; `char(1333)` is the length core uses for names such as `mod_wiki.name` and `mod_workshop.name`, so it is a convention for "long short text", not a URL rule. We use `char(1333)` here so the URL can be part of an index later if needed; use `text` if you never filter on it); a composite index matching the query we will actually run (`WHERE courseid = ? AND status = ?`); foreign keys declare intent and are used by tooling, but Moodle does not rely on engine-level FK enforcement for portability, so *you* must delete child rows when a course is deleted (an event observer, 3.5).

### 4.4 Language strings (`lang/en/local_readinglist.php`)

```php
<?php
defined('MOODLE_INTERNAL') || die();
```

### 4.5 Repository (all `$DB` in one place)

Why a class: one place to review every query, easy to unit-test (3.6), and the page scripts stay thin. This is a convention, not a Moodle requirement; do not impose it on a codebase that does it differently.

```php
<?php
namespace local_readinglist\local;

defined('MOODLE_INTERNAL') || die();

class repository {
    public const TABLE = 'local_readinglist_item';

    /** @return \stdClass[] keyed by id */
    public static function get_for_course(int $courseid, string $search = '', int $limit = 0): array {
        global $DB;
        $params = ['courseid' => $courseid];
        $where = 'courseid = :courseid';
        if ($search !== '') {
            $where .= ' AND ' . $DB->sql_like('title', ':search', false, false);
            $params['search'] = '%' . $DB->sql_like_escape($search) . '%';
        }
        $sql = "SELECT id, courseid, userid, title, url, note, status, timecreated, timemodified
                  FROM {" . self::TABLE . "}
                 WHERE $where
              ORDER BY timecreated DESC, id DESC";
        return $DB->get_records_sql($sql, $params, 0, $limit);
    }

    public static function get(int $id): \stdClass {
        global $DB;
        return $DB->get_record(self::TABLE, ['id' => $id], '*', MUST_EXIST);
    }

    public static function title_exists(int $courseid, string $title, int $excludeid = 0): bool {
        global $DB;
        $sql = "SELECT 1 FROM {" . self::TABLE . "}
                 WHERE courseid = :courseid AND " . $DB->sql_equal('title', ':title', false) . "
                   AND id <> :excludeid";
        return $DB->record_exists_sql($sql, ['courseid' => $courseid, 'title' => $title, 'excludeid' => $excludeid]);
    }

    public static function save(\stdClass $item): int {
        global $DB;
        $now = time();
        $item->timemodified = $now;
        if (empty($item->id)) {
            $item->timecreated = $now;
            return $DB->insert_record(self::TABLE, $item);
        }
        $DB->update_record(self::TABLE, $item);
        return (int) $item->id;
    }

    public static function delete(int $id): void {
        global $DB;
        $DB->delete_records(self::TABLE, ['id' => $id]);
    }
}
```

Review notes you should be able to give: the search term uses a named placeholder and `sql_like_escape` so `%` and `_` typed by the user are literals; `sql_like` with `casesensitive = false, accentsensitive = false` yields portable case/accent-insensitive matching (signature verified above); `sql_equal($fieldname, $param, $casesensitive, $accentsensitive, $notequal)`, `record_exists_sql($sql, ?array $params)` and `sql_like_escape($text, $escapechar)` are real `$DB` helpers (signatures checked in `lib/dml/moodle_database.php`); the first selected column is `id` so the result array is keyed correctly; limit is passed through `$limitnum`, not SQL.

Naive versus improved: the naive version is `$DB->get_records_sql("SELECT * FROM {local_readinglist_item} WHERE title LIKE '%$q%'")`. It fails on apostrophes, is injectable, and `LIKE` case-sensitivity differs per engine. Every change above fixes exactly one of those.

### 4.6 The form

```php
<?php
namespace local_readinglist\form;

class item_form extends \moodleform {
    public function definition() {

        $mform->setType('url', PARAM_URL);
        $mform->addRule('url', null, 'required', null, 'client');

        $mform->addElement('textarea', 'note', get_string('itemnote', 'local_readinglist'), ['rows' => 4, 'cols' => 60]);
        $mform->setType('note', PARAM_TEXT);

        $mform->addElement('select', 'status', get_string('itemstatus', 'local_readinglist'), [
            'todo' => get_string('status_todo', 'local_readinglist'),
            'done' => get_string('status_done', 'local_readinglist'),
        ]);
        $mform->setType('status', PARAM_ALPHANUMEXT);
        $mform->setDefault('status', 'todo');

        $this->add_action_buttons();
    }

    public function validation($data, $files) {
        $errors = parent::validation($data, $files);
        $title = trim($data['title']);
        if ($title === '') {
            $errors['title'] = get_string('required');
        } else if (repository::title_exists((int) $data['courseid'], $title, (int) $data['id'])) {
            $errors['title'] = get_string('errorduplicatetitle', 'local_readinglist');
        }
        $scheme = strtolower((string) parse_url($data['url'], PHP_URL_SCHEME));
        if (!in_array($scheme, ['http', 'https'], true)) {
            $errors['url'] = get_string('errorinvalidurl', 'local_readinglist');
        }
        if (!in_array($data['status'], ['todo', 'done'], true)) {
            $errors['status'] = get_string('invaliddata', 'error');
        }
        return $errors;
    }

```

Choices to defend: client-side rules are marked `'client'` and *also* re-checked server-side in `validation()` because a client rule is not a security control. The `select` is validated against the allowed list because a forged POST can submit any value for a select. The URL scheme is checked explicitly: `PARAM_URL` accepts what the cleaner considers a URL, and you must decide whether `javascript:` or `data:` links are acceptable (here: no, because the URL will be rendered into `href`). The duplicate check runs in `validation()` so the user sees a field error, but a database-level uniqueness guarantee would still be needed under concurrent requests (see the Failure laboratory and the Extension challenge).

### 4.7 The page script `edit.php`

```php
<?php
require(__DIR__ . '/../../config.php');   // Same depth on 4.5 and on 5.1+ (public/local/readinglist/).

use local_readinglist\form\item_form;
use local_readinglist\local\repository;

$courseid = required_param('courseid', PARAM_INT);
$id = optional_param('id', 0, PARAM_INT);

$course = get_course($courseid);
require_login($course);
$context = context_course::instance($courseid);
require_capability('local/readinglist:manage', $context);

$url = new moodle_url('/local/readinglist/edit.php', ['courseid' => $courseid, 'id' => $id]);
$listurl = new moodle_url('/local/readinglist/index.php', ['courseid' => $courseid]);
$PAGE->set_url($url);
$PAGE->set_context($context);
$PAGE->set_title(get_string($id ? 'edititem' : 'additem', 'local_readinglist'));
$PAGE->set_heading($course->fullname);

$existing = null;
if ($id) {
    $existing = repository::get($id);
    if ((int) $existing->courseid !== $courseid) {          // object-level authorisation (IDOR guard)
        throw new moodle_exception('invalidrecord', 'error');
    }
}

$mform = new item_form($url, ['courseid' => $courseid]);

if ($mform->is_cancelled()) {
    redirect($listurl);
} else if ($data = $mform->get_data()) {
    $item = (object) [
        'id' => (int) $data->id,
        'courseid' => $courseid,                 // taken from the verified variable, NOT from $data
        'userid' => $existing ? $existing->userid : $USER->id,
        'title' => trim($data->title),
        'url' => $data->url,
        'note' => $data->note,
        'status' => $data->status,
    ];
    repository::save($item);
    redirect($listurl, get_string('changessaved'), null, \core\output\notification::NOTIFY_SUCCESS);
}

if ($existing) {
    $mform->set_data($existing);
}
echo $OUTPUT->header();
echo $OUTPUT->heading($PAGE->title);
$mform->display();
echo $OUTPUT->footer();
```

Reasons, in order: `require_login` before anything; capability before input is acted on; `$PAGE` set before `header()`; the id read from the request is *re-checked* against the course because `PARAM_INT` only guarantees it is an integer; `courseid` for the saved record comes from the trusted variable, so a forged hidden field cannot move an item into another course; `redirect()` after a successful POST avoids re-submission on refresh (Post/Redirect/Get). `redirect($url, $message='', $delay=null, $messagetype=\core\output\notification::NOTIFY_INFO)` and `\core\output\notification::NOTIFY_SUCCESS` are standard (checked in `lib/weblib.php` and `lib/classes/output/notification.php`).

One known sharp edge: a record where `$existing->id` is set and the form's hidden `id` is `0` on first display. `set_data($existing)` fills it. That is why `set_data` happens in the third branch only.

### 4.8 Delete with CSRF protection

```php
<?php
require(__DIR__ . '/../../config.php');
use local_readinglist\local\repository;

$id = required_param('id', PARAM_INT);
$confirm = optional_param('confirm', 0, PARAM_BOOL);

$item = repository::get($id);
$course = get_course($item->courseid);
require_login($course);
require_capability('local/readinglist:manage', context_course::instance($course->id));

$listurl = new moodle_url('/local/readinglist/index.php', ['courseid' => $course->id]);
if ($confirm) {
    require_sesskey();                       // throws if the session key is missing or wrong
    repository::delete($id);
    redirect($listurl, get_string('deleted'), null, \core\output\notification::NOTIFY_SUCCESS);
}

$PAGE->set_url('/local/readinglist/delete.php', ['id' => $id]);
$PAGE->set_context(context_course::instance($course->id));
$PAGE->set_title(get_string('deleteitem', 'local_readinglist'));
$PAGE->set_heading($course->fullname);
echo $OUTPUT->header();
echo $OUTPUT->confirm(
    get_string('deleteconfirm', 'local_readinglist', format_string($item->title)),
    new moodle_url($PAGE->url, ['confirm' => 1]),
    $listurl
);
echo $OUTPUT->footer();
```

Mechanism: the object is loaded first, and the capability is checked in the *item's own course context* (not a context supplied by the request). `$OUTPUT->confirm()` builds a POST `single_button` for the continue action, and `single_button` adds the `sesskey` parameter automatically for POST (`lib/classes/output/single_button.php`), so `require_sesskey()` passes for the real button and fails for a forged request. `$PAGE->set_url($url, ?array $params = null)` accepts a string plus params array (`lib/pagelib.php`). `format_string()` is the right escaper for a short name passed into a string.

## 5. Production perspective

Correctness: every state-changing path has (a) authentication, (b) capability in the object's own context, (c) sesskey or a moodleform, (d) cleaned typed input. Missing any one of the four is a bug a reviewer should reject.

Maintainability: keep page scripts thin; put SQL in one class; keep strings and templates out of PHP. Do not build a framework: the Moodle core already is one.

Performance: `get_records_sql` with an index that matches the `WHERE`; select only needed columns; paginate with `$limitfrom/$limitnum`; never run a query inside a loop over rows (N+1). Measure with the query count shown in the footer when debugging is enabled (3.6) and with `EXPLAIN` through your database client; do not guess.

Security: see 3.7. Add `defined('MOODLE_INTERNAL') || die();` to non-entry PHP files that have side effects and could otherwise be executed directly. The `moodle.Files.MoodleInternal` sniff in moodle-cs (used by moodle-plugin-ci, 3.6) errors on a side-effect file with neither that check nor a `config.php` inclusion, and *warns* ("Unexpected MOODLE_INTERNAL check") on a file that has the check but declares only one class or function and no side effects. So class-only files in `classes/` should not carry it, which is why the listings below omit it there.

Failure handling: throw `moodle_exception` with a language string key rather than `die()`; let Moodle render the error page and log it. `MUST_EXIST` is good when absence is a bug; `IGNORE_MISSING` when absence is a valid state you handle.

Observability: Moodle events are the audit trail (3.5). Add them after CRUD works; they are not optional in a plugin that changes teacher-visible data.

What a senior engineer does differently: reads an existing plugin of the same type first and copies its conventions; writes the install.xml with the editor, not by hand; adds a unit test for every query before changing it; treats `validation()` as security code; never trusts a hidden field.

Beginner mistakes and diagnosis:

| Symptom | Likely cause | Diagnose |
|---|---|---|
| Works locally, `Table 'x' doesn't exist` in staging | Missing `{}` around table name, hard-coded prefix | Enable debugging; read the SQL in the error; grep for `FROM local_` without braces |
| List shows fewer rows than the table | First selected column not unique | `SELECT`'s first column; print `count($rows)` vs `count_records` |
| Form saves but cancel loops | `is_cancelled()` checked after `get_data()` or no redirect | Re-read the documented order |
| Debug notice "Coding problem: Missing setType" style | `setType()` missing | Turn on developer debugging |
| "Transaction not closed" error | Exception swallowed after `start_delegated_transaction` | Search for `catch` without `rollback` |
| Upgrade does not run | `version.php` not bumped, or caches | Compare DB `config_plugins` version to file; run the upgrade page |

## 6. Failure laboratory

Predict first. Write your prediction for each in your notebook before reading the reveal.

Flawed snippet A (search):

```php
$q = optional_param('q', '', PARAM_RAW);
$rows = $DB->get_records_sql("SELECT title, url FROM {local_readinglist_item}
                               WHERE courseid = $courseid AND title LIKE '%$q%'");

```

Flawed snippet B (title in the template): the exporter passes `'title' => s($item->title)` and the template writes `{{title}}`.

Flawed snippet C (delete by GET):

```php

```

Questions: (1) Name at least four distinct defects in A, and say what happens for the input `O'Brien` and for `' OR '1'='1`. (2) What does B display for the title `Fish & Chips`? (3) What attack works against C that works without the attacker ever seeing the site, and which line of Moodle API defeats it? (4) In A, two items in the course share the same title; what happens to the list?

### Reveal (read after predicting)

A: (a) SQL built by concatenation: `O'Brien` ends the string literal and causes an SQL error; `' OR '1'='1` returns every row in the course (and with `UNION` payloads could read other tables); (b) `PARAM_RAW` removes the only cleaning step; (c) `courseid` is interpolated (here it came from `required_param(PARAM_INT)` upstream so is safe, but the pattern is unsafe and reviewers reject it); (d) the first selected column is `title`, so `get_records_sql` keys the result by title and two items with the same title collapse into one: silent data loss; (e) `echo "<li>$r->title</li>"` is stored XSS if `title` contains markup; (f) no `sesskey` is needed for a read-only search, correct, but there is also no `require_login`, no capability check, no `$PAGE` set up and no `header()`; (g) hard-coded string; (h) `LIKE` semantics differ between engines.

B: the exporter escapes (`Fish &amp; Chips`) and Mustache escapes again, so the browser shows `Fish &amp; Chips` literally. Double-escaping is the sign you escaped at the wrong layer. The fix is to escape exactly once: either pass raw and use `{{ }}`, or pass `format_string()` output and use `{{{ }}}`. Do not do both.

C: CSRF. A third-party page containing `<img src="https://site/local/readinglist/delete.php?delete=5">` makes the logged-in teacher's browser delete item 5. GET must never change state. Defeat with POST plus `require_sesskey()`; moodleform and `$OUTPUT->confirm()` supply the key. The raw `$_GET` read is a separate defect (use `required_param`). There is also no capability or object check (IDOR).

Systematic diagnosis procedure for any "weird data" bug in a Moodle page: (1) turn on developer debugging and read every notice; (2) print the final SQL and params (the DML exception message contains them; in debug mode the footer can show queries); (3) run the SQL by hand against the database with the same params; (4) check the first-column keying; (5) check the type the input was cleaned to; (6) check the output layer for double or missing escaping by viewing page source, not the rendered page.

## 10. Engineering review

Self-review checklist (tick each with evidence, not belief):

- Every script: `require_login` (or documented exception), `require_capability` in the object's context, `$PAGE->set_url` before output.
- Every request value read through `required_param`/`optional_param` or a moodleform, and every form element has `setType`.
- Every identifier the user supplies is re-validated against the trusted course (IDOR).
- No SQL string contains a request-derived value; table names have braces; no engine-specific function.
- Every state-changing request is POST with sesskey (form or `require_sesskey`).
- Each output value escaped exactly once; you can point to the layer.
- Every user-visible string is in the language file; strings are complete.
- install.xml equals the final schema; upgrade step guarded and has a savepoint; version bumped.
- No debug output, no `var_dump`, no `print_r`, no `@` suppression.
- You can run the plugin with developer debugging and see no notices.

Explain-your-design prompts: Why a repository class and not queries in the page? Why validate in `validation()` and also constrain in the database? Why `named_templatable` rather than `templatable`? What happens to your delete flow if the user opens it in two tabs? Why is a client-side `required` rule insufficient?

## 11. Mastery gate

Pass = 80/100 on the project rubric with no critical failure. Required evidence: the plugin repository, the `NOTES.md` with resolved `VERIFY` items and tested Moodle version, the A1-A10 demonstration log, and a 10-minute oral or written defence of the five design decisions above chosen by the reviewer.

Critical failures (any one means not passed regardless of score): SQL built by concatenating request data; a state-changing action reachable by GET or without sesskey; a missing capability check on any script; an IDOR on edit or delete; unescaped output of user text; core code modified; an upgrade step that edits a released version or lacks a version bump; table names without braces in raw SQL.

If failed: remedial exercise within 48 hours. Take the `local_shortlinks` challenge (section 8), deliberately re-introduce exactly the failed critical defect in a branch, write the manual test that exposes it, and fix it. Then explain in writing which Moodle mechanism the fix relies on, citing the documentation page. Re-submit only the changed parts plus the failing test.
