## 1. Engineering problem

On Monday you are told: "The attendance-summary report in our Moodle needs a new column and a permission so only course managers see it." You open the repository. It has 40,000 files. Nothing resembles a FastAPI project: no `main.py`, no router, no dependency injection container you can point at. Pages are individual PHP files, helpers are global functions in files named `lib.php`, and there is a directory called `local/` containing things your company wrote.

What goes wrong when this is handled poorly:

- **Core edited in place.** A developer fixes a bug by editing `lib/moodlelib.php`. Six months later the site upgrades; the fix is overwritten and nobody remembers it existed. Or worse, the upgrade is skipped forever because "we patched core". Customization belongs in a plugin; core changes belong upstream in the Moodle tracker.
- **Wrong component name.** A plugin named `local_my_report` (underscore in the name part) or with a folder name that does not match `component` in `version.php` fails to install with an error that looks unrelated.
- **Schema drift.** Someone adds a table by hand-running SQL on production. The next developer's local install does not have it; the plugin works on one machine only.
- **Dead code that is not dead.** A function in `lib.php` looks unused; it is a callback Moodle discovers by naming convention. Deleting it silently breaks a feature.

This lesson gives you the map: what Moodle is architecturally, how plugins are named, located, installed, upgraded and loaded, and how to set up a local instance you can safely break.

## 3. First-principles explanation

### 3.1 What Moodle is, architecturally

Moodle is a monolithic PHP web application (a learning management system) with: a bootstrap (`config.php` -> `lib/setup.php`) that builds the global environment per request; a **core** (`lib/`, subsystems such as `user`, `course`, `enrol`, `grade`, `message`); and several hundred **plugins** of many **types** that implement activities, authentication, enrolment methods, reports, themes and more. It runs per request, shared-nothing, exactly as in lesson 3.1. **[Stable]**

```
Browser -> web server (docroot = public/) -> PHP-FPM
              |
              v  e.g. /local/greetings/index.php
        require_once(.../config.php)       <- reads site's config.php, bootstraps core
              |    sets globals: $CFG $DB $USER $COURSE $PAGE $OUTPUT $SESSION
              v
        your page code  -> core APIs (access, DML, output, files, events ...)
              |
              v
        $DB -> MySQL/MariaDB/PostgreSQL/SQL Server     moodledata/ (files, caches, sessions?)
```

Key facts **[Stable]**:

- **Globals are the API surface.** `$CFG` (config), `$DB` (database), `$USER` (current user), `$PAGE` (page setup), `$OUTPUT` (renderer), `$COURSE`. They exist because the request is single-user, single-process. Inside functions you write `global $DB;`. This is unlike FastAPI's dependency injection; testability comes from Moodle's PHPUnit infrastructure resetting state, not from injection. In new classes, you may pass `$DB` in or use `\core\di` (checked: moodledev.io Dependency Injection page documents `\core\di::get()`, a PSR-11 wrapper over PHP-DI; `\core\di::make()` is new in 5.3; `\core\di::set()` injects mocks in tests) but be consistent with surrounding code.
- **Two storage areas.** The database, and `$CFG->dataroot` ("moodledata"): uploaded files (File API, lesson 3.5), caches, temp files. `moodledata` must not be web-accessible.
- **Three entry-point styles.** Web pages (`something.php`), web services/AJAX (`lib/ajax/service.php` dispatching to external functions; lesson 3.5), CLI scripts (`admin/cli/*.php`, `cli/` in plugins) and cron/tasks. Mostly everything funnels through `config.php`, which refuses to continue if you forgot to define `CLI_SCRIPT` for CLI usage.
- **Versioning.** Each component has a `version` integer in `version.php` (format `YYYYMMDDXX`: `public/mod/choice/version.php` in 5.3 comments it as "Date: YYYYMMDDXX", checked). Moodle compares the file's version to the stored one in the DB to decide whether to upgrade.

### 3.2 Core vs plugin vs subsystem

- **Core** lives in `lib/` and the top-level subsystem directories. Core subsystem frankenstyle names begin with `core_` (e.g., `core_enrol`, `core_user`).
- **Plugins** are installable components with a **type** and a **name**. Moodle ships several hundred standard plugins (these are "core plugins"); administrators add third-party ones.
- **Rule of thumb [opinion, widely held]:** if you need to change behavior, find an extension point first: callbacks in `lib.php`, **hooks** (`db/hooks.php`, verified on moodledev.io; the page presents the PSR-14 based Hooks API as the replacement for one-to-many `lib.php` callbacks), **events and observers** (`db/events.php`), web service/external functions, settings, theme layers. Edit core only in an upstream patch that goes through the tracker and peer review (lesson 3.6).

### 3.3 Frankenstyle naming

A component name is `<plugintype>_<pluginname>`. The type is a fixed prefix from the list Moodle defines; the name is chosen by the author. **[Stable principle]**: lowercase letters and digits; the name part of a **module** (`mod_*`) must match `^[a-z][a-z0-9]*$` (no underscores); other plugin types may contain single underscores (checked against `core_component::is_valid_plugin_name()`, regex `^[a-z](?:[a-z0-9_](?!__))*[a-z0-9]+$`, in `public/lib/classes/component.php`). Avoid underscores anyway: the first underscore is the type/name separator and names stay short and descriptive. The component name is used everywhere:

| Where | Form | Example for `local_greetings` |
|---|---|---|
| Directory | type directory + name | `local/greetings/` |
| `version.php` | `$plugin->component = 'local_greetings';` | |
| Language file | `lang/en/local_greetings.php` | (verified rule: file named after the frankenstyle name; **activity modules** are the exception: `mod/forum/lang/en/forum.php`) |
| Class namespace | `local_greetings\...` | `\local_greetings\task\purge` |
| Capability | `local/greetings:view` | (format `plugintype/pluginname:capabilityname`, verified) |
| Lang key for capability | `greetings:view` | (verified: key is `pluginname:capabilityname`, e.g. `$string['folder:managefiles']`) |
| Settings | `local_greetings/settingname` | stored in `config_plugins` (verified) |
| DB tables | `local_greetings_*` by convention | (convention; the table-name prefix is the plugin's choice: `local_greetings_*` is the habit, not a checked rule) |

**Plugin types and directories [5.3, from moodledev.io "Plugin types" page, which lists 56 types; the common ones]:**

| Type (prefix) | Directory | Use |
|---|---|---|
| `mod` | `/mod` | activities (quiz, forum, assign) |
| `block` | `/blocks` | sidebar blocks |
| `local` | `/local` | site-specific customization; the default home for your own code |
| `tool` | `/admin/tool` | admin tools |
| `report` | `/report` | site/course reports |
| `auth` | `/auth` | authentication |
| `enrol` | `/enrol` | enrolment methods |
| `theme` | `/theme` | themes |
| `filter` | `/filter` | text filters |
| `format` | `/course/format` | course formats |
| `qtype` | `/question/type` | question types |
| `gradereport` | `/grade/report` | gradebook reports |
| `assignsubmission`, `assignfeedback` | `/mod/assign/submission`, `/mod/assign/feedback` | subplugins of assign |
| `quizaccess` | `/mod/quiz/accessrule` | subplugins of quiz |

Subplugins live inside a parent plugin; their type is declared by the parent in `db/subplugins.json` (file exists in core, e.g. `public/mod/assign/db/subplugins.json`, `public/lib/editor/tiny/db/subplugins.json`; only `mod`, `editor`, `tool`, `local` support subplugins per `core_component::$supportsubplugins`).

**Important [5.3] directory change.** Since Moodle 5.1 (verified on the 5.1 developer update and restructure guide), "most code, including all plugins" lives in a `public/` directory of the installation, and the web server document root must point at `public/`. So the physical path of `local_greetings` on a 5.1+ site is `<moodle-root>/public/local/greetings/`. The paths in the table above are relative to `public/` on 5.1+ (on 4.x and 5.0 there is no `public/`). `$CFG->wwwroot` and `$CFG->dirroot` "should continue to behave as before"; `$CFG->root` is new, read-only, and points to the installation root (verified). `config.php` for the site sits in the installation root: the file `public/config.php` loads `__DIR__ . '/../config.php'` (verified from the source). Consequence for plugin pages: `require_once(__DIR__ . '/../../config.php');` from `public/local/greetings/index.php` resolves to `public/config.php`, which then loads the real one. Core's own `mod/choice/index.php` uses `require_once("../../config.php");` (verified).

### 3.4 Directory layout of one plugin

```
public/local/greetings/
  version.php              REQUIRED. component, version, requires, maturity, release
  lang/en/local_greetings.php   REQUIRED. must define $string['pluginname']
  index.php                an entry-point page (optional; any name)
  lib.php                  legacy callback bridge (keep small; loaded by core for all plugins of the type)
  settings.php             admin settings (must not run DB queries at include time)
  db/
    install.xml            schema (generate/edit with the XMLDB editor)
    upgrade.php            function xmldb_local_greetings_upgrade($oldversion)
    access.php             $capabilities = [...]
    services.php           $functions = [...]  external (web service) functions
    events.php             $observers = [...]
    hooks.php              $callbacks = [...]  (Hooks API)
    tasks.php              $tasks = [...]  scheduled task schedule
    install.php / uninstall.php   post-install / pre-uninstall hooks
  classes/                 autoloaded namespaced classes (the place for new code)
    task/  external/  output/  privacy/provider.php  local/ ...
  templates/               Mustache templates
  amd/src, amd/build       JavaScript (AMD) modules  (lesson 3.4+)
  tests/                   PHPUnit (*_test.php), Behat (behat/*.feature), generators
  pix/icon.svg  styles.css  readme / UPGRADING.md ...
```

All of these file names are verified on the "Plugin files" page except `templates/` and `tests/`, which that page does not describe (the testing guide verifies `tests/*_test.php`; `templates/` is standard: e.g. `public/mod/forum/templates` exists in the source). `version.php` and the language file must never contain `require_once` or other inclusion (verified). The page marks `locallib.php` as legacy and "not recommended": use autoloaded classes.

**Look at the real thing.** `public/mod/choice/` in the 5.x tree contains `backup/ classes/ db/ lang/en/ pix/ tests/`, plus `index.php lib.php locallib.php mod_form.php renderer.php report.php version.php view.php` and `UPGRADING.md` (verified by listing on GitHub). Its `db/access.php` defines capabilities like `mod/choice:addinstance` (contextlevel `CONTEXT_COURSE`, `riskbitmask => RISK_XSS`, `clonepermissionsfrom => 'moodle/course:manageactivities'`) and `mod/choice:choose` (`CONTEXT_MODULE`, archetypes student, teacher, editingteacher: `CAP_ALLOW`) (verified, lesson 3.3 explains these).

### 3.5 Autoloading of `classes/`

Moodle registers an autoloader. **[Stable]** A class named `\<component>\<rest>` is found in `<component directory>/classes/<rest as path>.php`, where namespace separators after the component become directory separators. A page of older documentation gives the example `\mod_forum\some_class` -> `mod/forum/classes/some_class.php`, and says the old underscore-prefixed style (`core_user_example`) is deprecated; The rule is implemented in `core_component::classloader()` / `psr_classloader()` in `public/lib/classes/component.php` (checked in source, 5.3); read it for the exact current rules and the "level 2 namespace" rules for core subsystems. Practical rules that follow:

- File name = class name, lowercase by convention (Moodle style uses lowercase class names with underscores: `class greeting_helper` in `greeting_helper.php`), directory = sub-namespace.
- The autoloader **caches the class map**; after adding a new class in a *new* directory or moving classes, purge caches (`php admin/cli/purge_caches.php`) before concluding the code is wrong.
- Classes must not include other classes with `require`; rely on autoloading. Legacy code that does `require_once($CFG->dirroot . '/mod/choice/locallib.php')` is the pre-autoload style you will encounter.
- Compare to lesson 3.1 PSR-4: same idea, different registration. Moodle's rule is its own convention, not a literal PSR-4 `composer.json` mapping.

### 3.6 `config.php` and `$CFG`

`config.php` (site root, generated by the installer or copied from `config-dist.php`/a template) defines `$CFG->dbtype`, `dbhost`, `dbname`, `dbuser`, `dbpass`, `prefix`, `wwwroot`, `dataroot`, `admin`, and ends with `require_once(__DIR__ . '/lib/setup.php');` (checked: `config-dist.php` on 5.3 has exactly this line; `lib/setup.php` is in the repository root, outside `public/`). Developer settings you will meet: `$CFG->debug = (E_ALL | E_STRICT); $CFG->debugdisplay = 1;` for development only; `$CFG->phpunit_prefix` and `$CFG->phpunit_dataroot` for tests (verified). Plugin settings are not in `config.php`; they are in the DB (`config`, `config_plugins`) and read with `get_config('local_greetings', 'name')` (checked: `get_config($plugin, $name = null)` in `public/lib/moodlelib.php`).

**Never hardcode secrets in plugin code**; read from settings or environment per team standards.

### 3.7 The upgrade mechanism (what happens on version bump)

**[Stable]** The core algorithm:

```
admin visits site OR runs admin/cli/upgrade.php
  -> core scans plugin dirs, reads each version.php
  -> compares $plugin->version (file) with stored version (DB: config_plugins 'version')
  -> new plugin (no stored version)  : run db/install.xml, db/install.php, db/access.php (capabilities),
                                       db/events|tasks|services registration, then store version
  -> file version > stored version   : run db/upgrade.php function xmldb_<name>_upgrade($oldversion),
                                       then re-sync access.php, tasks.php, events.php, services.php, hooks.php;
                                       then store new version
  -> file version < stored version   : refuses ("downgrade")
  -> checks $plugin->requires against the core version and $plugin->dependencies
```

Facts verified on moodledev.io: bump the version after changing `db/access.php` (capabilities reload on upgrade) and after adding or changing `db/tasks.php`; hook registrations are cached so bump the version or purge caches; `db/upgrade.php` defines `xmldb_[pluginname]_upgrade` called with the old version number; keep `install.xml` in sync with upgrade steps. **Rule:** schema changes go in both `install.xml` (for fresh installs) and `upgrade.php` (for existing sites), each upgrade step guarded `if ($oldversion < N) {...; upgrade_plugin_savepoint(true, N, 'local', 'greetings'); }` (checked: `upgrade_plugin_savepoint($result, $version, $type, $plugin, $allowabort=true)` in `public/lib/upgradelib.php`).

The CLI route for dev and production deployments: `php admin/cli/upgrade.php --non-interactive` (checked in 5.3 source: `--non-interactive` and `--help` exist; CLI scripts live in `admin/cli/` at the repository root, not under `public/`).

### 3.8 Why never modify core

1. Upgrades overwrite it, or you stop upgrading (security patches are released against core; General support and Security support windows exist per release: verified on the releases page, e.g. 5.3 LTS security support until 1 October 2029; 4.5 LTS security support ends 4 October 2027).
2. Your change is untested by upstream's PHPUnit/Behat suite, and conflicts with every merge.
3. It is invisible: the next engineer sees stock Moodle and a mystery bug.
4. Alternatives: plugin extension points, theme overrides, hooks, observers, web services, or upstream contribution. If no extension point exists, the right deliverable is a tracker issue with a patch, then a temporary documented local patch under version control with a plan to remove it.

### 3.9 Local development environment

The Moodle HQ project `moodlehq/moodle-docker` provides containers (verified from its README):

```bash
git clone https://github.com/moodlehq/moodle-docker.git && cd moodle-docker
export MOODLE_DOCKER_WWWROOT=$HOME/dev/moodle        # your clone of moodle core
export MOODLE_DOCKER_DB=pgsql                        # pgsql | mariadb | mysql | mssql
export MOODLE_DOCKER_PHP_VERSION=8.3                 # optional; README default 8.3
git clone -b <MOODLE_BRANCH> https://github.com/moodle/moodle.git $MOODLE_DOCKER_WWWROOT
cp config.docker-template.php $MOODLE_DOCKER_WWWROOT/config.php
bin/moodle-docker-compose up -d
bin/moodle-docker-wait-for-db
bin/moodle-docker-compose exec webserver php admin/cli/install_database.php \
    --agree-license --fullname="Dev" --shortname="dev" --adminpass="test" --adminemail="admin@example.com"
```

`<MOODLE_BRANCH>` is the branch name for your target release: use the stable branch naming from the Moodle GitHub repository (branches are named like `MOODLE_405_STABLE`; `MOODLE_503_STABLE` exists, checked with `git ls-remote --heads`). Do not clone `main` for stable-version work: it is 6.0dev (verified: `public/version.php` on `main` says `6.0dev`; `MOODLE_503_STABLE` says `5.3+`, branch `503`). The README documents `--adminpass`, `--adminemail`, `--adminuser` options; `admin/cli/install.php` also documents `--fullname` and `--shortname` (checked in source). The README's PHPUnit init: `bin/moodle-docker-compose exec webserver php admin/tool/phpunit/cli/init.php`; on 5.1+ the moodledev.io testing page uses `php public/admin/tool/phpunit/cli/init.php` (verified): check which path your container's working directory needs. To get the site's URL and mail catcher ports, read the moodle-docker README (VERIFY).

Alternative setups and trade-offs: native LAMP/LEMP (full control, painful to reproduce), Docker (reproducible, slower file I/O on some hosts), a team-provided VM. Whatever you pick, Git-track **your plugin directory** as its own repository mounted into `public/local/`; do not commit into the core clone.

### 3.10 When not to build a plugin

If an admin setting, role override, or existing core feature achieves the goal, do that. A plugin is permanent maintenance: it must be upgraded with every Moodle release (lesson 3.6).

## 4. Worked example

We build `local_greetings` from nothing. Purpose: a page `/local/greetings/index.php` showing "Hello, <full name>" to logged-in users who hold the capability `local/greetings:view`, a scheduled task that does nothing harmful, and a privacy statement. Design choices explained as we go. Work in a Git repository separate from core:

```bash
mkdir -p ~/dev/local_greetings && cd ~/dev/local_greetings && git init
mkdir -p db lang/en classes/task classes/privacy tests
```

Mount or copy it into `<moodle-root>/public/local/greetings` (a bind mount or symlink; note the directory name is `greetings`, not `local_greetings`).

### 4.1 `version.php`

```php
<?php
defined('MOODLE_INTERNAL') || die();

$plugin->component = 'local_greetings';
$plugin->version   = 2026102600;       // YYYYMMDDXX; bump on every schema/capability/task change
$plugin->requires  = 2026100200;       // from mod_choice in 5.3; set to the minimum core $version you support
$plugin->maturity  = MATURITY_ALPHA;
$plugin->release   = '0.1.0';
```

`$plugin` is predefined by Moodle's plugin loader (the file is included in a scope that defines it). `component` must equal the frankenstyle name or Moodle reports a mismatch. `requires` is the minimum core version number; the value `2026100200` above is copied from the 5.x `mod_choice` file's `requires` to show the shape (verified), but for your plugin choose the oldest core you will test against: read that number from that release's `public/version.php`. `$plugin->supported` and `$plugin->incompatible` exist since 3.9 (verified) to declare supported branch ranges; `incompatible` is compared with `$CFG->branch` (so a branch number such as `503`, checked in `public/lib/upgradelib.php`); I did not trace how `supported` is used.

### 4.2 `lang/en/local_greetings.php`

```php
<?php
defined('MOODLE_INTERNAL') || die();

$string['pluginname'] = 'Greetings';
$string['greeting'] = 'Hello, {$a}';
$string['greetings:view'] = 'View the greetings page';
$string['privacy:metadata'] = 'The Greetings plugin does not store any personal data.';
$string['taskpurge'] = 'Purge old greetings';
```

`pluginname` is mandatory (verified). `{$a}` is Moodle's string placeholder, filled by `get_string('greeting', 'local_greetings', $name)`. Why strings and not literals: internationalization, and admins can override strings. Core language files keep keys sorted alphabetically; the moodledev.io coding style page does not state this rule, so treat it as convention.

### 4.3 `db/access.php`

```php
<?php
defined('MOODLE_INTERNAL') || die();

$capabilities = [
    'local/greetings:view' => [
        'captype' => 'read',
        'contextlevel' => CONTEXT_SYSTEM,
        'archetypes' => [
            'user' => CAP_ALLOW,
        ],
    ],
];
```

This follows the verified structure (`captype`, `contextlevel`, `archetypes`; docs recommend using only `CAP_ALLOW` in archetypes). Choice of `user` archetype: any authenticated user gets it by default; an admin can remove it by role override. The more restrictive alternative is `manager`. We think about the principle of least privilege in lesson 3.3.

### 4.4 `index.php` (the page)

```php
<?php
require_once(__DIR__ . '/../../config.php');

require_login();
$context = context_system::instance();
require_capability('local/greetings:view', $context);

$PAGE->set_url(new moodle_url('/local/greetings/index.php'));
$PAGE->set_context($context);
$PAGE->set_title(get_string('pluginname', 'local_greetings'));
$PAGE->set_heading(get_string('pluginname', 'local_greetings'));

echo $OUTPUT->header();
echo $OUTPUT->heading(get_string('greeting', 'local_greetings', fullname($USER)));
echo $OUTPUT->footer();
```

Reasoning: `config.php` first (bootstrap); `require_login()` before anything else touches user data (verified signature: `require_login($courseorid = null, $autologinguest = true, $cm = null, $setwantsurltome = true, $preventredirect = false)`; the docs say call it after setting `PAGE->url` for correct redirect behavior; many core scripts call `$PAGE->set_url` first, so set the URL first, then `require_login()`); `require_capability` throws an access-control exception if denied (verified); `set_url`, `set_context`, `set_title`, `set_heading` are standard `$PAGE` setup calls (checked: all four are methods in `public/lib/pagelib.php`); `fullname($USER)` returns the formatted name; the output API (`$OUTPUT->heading`, `header`, `footer`) escapes through its own conventions: we pass already-localized text and not user HTML. Note the improvement over a naive version: a naive page would `echo "Hello " . $_GET['name'];` which breaks lesson 3.1's rule on superglobals and escaping.

### 4.5 Scheduled task

`db/tasks.php` (verified structure: keys `classname`, `blocking`, `minute`, `hour`, `day`, `month`, `dayofweek`; `R` allowed for random):

```php
<?php
defined('MOODLE_INTERNAL') || die();

$tasks = [
    [
        'classname' => 'local_greetings\task\purge',
        'blocking'  => 0,
        'minute'    => 'R',
        'hour'      => '3',
        'day'       => '*',
        'month'     => '*',
        'dayofweek' => '*',
    ],
];
```

`classes/task/purge.php` (verified: class extends `\core\task\scheduled_task`, in `classes/task`, implements `get_name()` and `execute()`):

```php
<?php
namespace local_greetings\task;

defined('MOODLE_INTERNAL') || die();

class purge extends \core\task\scheduled_task {
    public function get_name(): string {
        return get_string('taskpurge', 'local_greetings');
    }

    public function execute(): void {
        mtrace('local_greetings: nothing to purge yet');
    }
}
```

(`mtrace` is Moodle's output function for CLI/cron logging: checked, `mtrace($string, $eol="\n", $sleep=0)` in `public/lib/moodlelib.php`.) The file path is `classes/task/purge.php` for class `\local_greetings\task\purge` - the autoloader rule from 3.5.

## 5. Production perspective

**Maintainability.** One plugin, one repository, semantic release strings, `UPGRADING.md`-style notes for API changes you consume. Follow Moodle coding style (lesson 3.6); run `phpcs` with the Moodle standard if the team does (check which tooling it uses). Keep `lib.php` tiny: core loads it for every plugin of that type (verified warning on the Plugin files page).

**Correctness and compatibility.** `requires`/`supported` declare what you support. Test on the oldest and newest branch you claim. Read each release's developer update (`moodledev.io/docs/<version>/devupdate`) and the per-component `UPGRADING.md` notes; deprecations accumulate.

**Performance.** Pages run after the whole core bootstrap; the cost is in your queries and loops. Use the DB API's recordsets and `IN` helpers (e.g. `get_in_or_equal`), never a query in a loop without reason. Cache with MUC (lesson 3.5). Measure with the debugging/performance footer (the admin setting is "Performance info", `perfdebug`, per the 5.3 lang strings) before optimizing.

**Security.** Every entry point: `require_login`, a capability check on the correct context, validated params, `require_sesskey()` on state change (lesson 3.3). A `settings.php` or `lib.php` that executes DB queries at include time is both a performance and a robustness defect (verified rule for settings).

**Failure handling.** Moodle throws `moodle_exception` / `dml_exception`; do not catch broadly. For tasks, throw to mark failure so it appears in the task log (checked: `core\cron` catches `\Throwable` from a task and calls `\core\task\manager::scheduled_task_failed()`; the failure is recorded in the task log).

**Testing.** PHPUnit for logic, Behat for UI flows (lesson 3.6). **Operations.** Plugins are deployed by copying the directory and running the upgrade CLI during a maintenance window; take a DB backup first. Never "hotfix" on production by editing files without committing.

**What a senior engineer does differently.** Reads the nearest core plugin that does something similar before writing a line; copies its structure, not its legacy habits; checks the tracker for a known API before inventing one; keeps customizations in `local_` plugins with their own version history; never assumes a function exists in older versions.

**Beginner mistakes**

| Mistake | Symptom | Diagnosis |
|---|---|---|
| Directory name does not match component | Install error mentioning "version.php" or component mismatch | compare directory, `$plugin->component`, language file name |
| Forgot to bump `version` after editing `db/access.php` / `db/tasks.php` | Capability or task missing | upgrade only syncs when version increases (verified) |
| Class in wrong path/namespace | "Class not found" | check FQCN -> path rule, lowercase file name, purge caches |
| Language string key missing | `[[key]]` shown on page | define it in `lang/en/<component>.php`, purge string cache |
| Code in `lib.php` runs for every request | slow site | move into autoloaded class |
| Editing core to "just fix this" | gone after upgrade | revert; move to plugin/hook; file a tracker issue |
| Using `master`/`main` checkout for stable work | APIs differ from docs | check `public/version.php` `$release` |

## 6. Failure laboratory

Predict before reading the reveal.

**Lab A.** Plugin tree:

```
public/local/greetings/version.php        // $plugin->component = 'local_greeting';
public/local/greetings/lang/en/local_greetings.php
```

You run the upgrade CLI. What does the admin see and why?

**Lab B.** You add `local/greetings/classes/helper/Formatter.php` containing `namespace local_greetings\helper; class formatter {...}` and call `\local_greetings\helper\formatter::run()`. It worked on your Mac and fails on the Linux CI container. Why?

**Lab C.** You edit `db/access.php` to add a second capability `local/greetings:manage`, reload the page, and `require_capability('local/greetings:manage', $context)` throws a "coding error: capability not found" style exception even for admin. Version number unchanged. Why? What exactly do you do?

**Lab D.** After moving your plugin from a Moodle 5.0 site to a 5.3 site by copying it to `<root>/local/greetings`, the admin UI does not list it at all. Why?

### Reveal (read after predicting)

- **Lab A.** The plugin is not installed cleanly: Moodle expects the component in `version.php` to match the plugin's directory-derived component (`local_greetings`); a mismatch is reported as an error during the plugin check on the upgrade page/CLI (the ZIP-install validator has a "Plugin name mismatch" message, `validationmsg_componentmismatchname`; the exact message for an in-place directory is still unverified: run it, do not quote from memory). *Diagnosis procedure:* compare four strings: directory name + type prefix, `$plugin->component`, language file name, namespace. They are all the same component string.
- **Lab B.** macOS default filesystems are case-insensitive, Linux is case-sensitive. The class `formatter` must be in `formatter.php` (lowercase, Moodle's convention), but the file is `Formatter.php`. Also check the namespace matches the directory. *Diagnosis:* `ls` the real names; rename with `git mv` (two-step on case-insensitive FS); purge caches.
- **Lab C.** Capabilities are loaded from `db/access.php` into the DB only during install/upgrade (verified: bump the version after changing `access.php`). Fix: increment `$plugin->version`, run `admin/cli/upgrade.php`, then re-test. *Diagnosis:* look in the role definition UI or query `capabilities` table for the name.
- **Lab D.** From 5.1 all plugins must be in `public/` (verified: web docroot is `public/`, and the 5.1 restructure says plugins moved there); a plugin in `<root>/local/` is outside the web root and the plugin scanner looks under `public/` (the official upgrade guide says third-party plugins left in their old location must be relocated into their relative path under `public/`: from docs.moodle.org upgrade page). *Diagnosis:* `$CFG->dirroot` and `$CFG->root`; `ls <root>/public/local`.
