## 1. Engineering problem

A teacher at school A can open `local/coursenotes/view.php?id=7` and read a private note about a student. Note 7 belongs to a course at school B (a different course on the same Moodle). The page checked that the user was logged in and had the capability `local/coursenotes:view`, but it checked the capability in the **system context** (where the teacher holds it through a site-wide role) and not in the **course context of the note**. Moodle did exactly what it was told. This is an IDOR (insecure direct object reference) caused by a wrong context.

Other real-world forms of the same problem:

- The "Delete" link is hidden from students in the template, but `delete.php?id=7` has no capability check: anyone who guesses the URL deletes data.
- A form handler checks permission, but there is no `sesskey` check: a teacher visiting a malicious page deletes their notes through a forged request (CSRF).
- `is_siteadmin()` is used as the whole security model: nobody except site admins can use the feature, or worse, `is_enrolled()` is used instead of a capability, so a suspended-but-listed enrolment, or a role override that removes the right, does not apply.
- `$userid = optional_param('userid', $USER->id, PARAM_INT)` lets a student request another student's data.

Authorization is not a UI feature, it is a server-side invariant: **every entry point that reads or changes protected data must (1) establish who the user is, (2) establish the context of the thing being accessed, (3) check a capability in that context, and (4) for changes, prove the request was intended by the user**. This lesson teaches the Moodle model that implements those four steps and how to prove with automated tests that it holds.

## 2. Learning objectives

1. Draw the Moodle context hierarchy and state, for any plugin object (a note, a quiz attempt, a user profile page), which context level it belongs to and how to obtain that context object from an id.
2. Write a `db/access.php` defining capabilities with correct `captype`, `contextlevel`, `riskbitmask` and archetypes, bump the version and verify the capability appears in a role definition.
3. Resolve a permission by hand: given role assignments and overrides across contexts, determine whether `has_capability()` is true, including the effect of Prevent and Prohibit.
4. Protect a page, a form handler and an external function with the correct sequence of `require_login`, `require_capability`/`has_capability`, `require_sesskey`, and parameter cleaning with `required_param`/`optional_param` and `PARAM_*` types.
5. Identify and fix at least six common authorization defects in provided code (wrong context, missing check, IDOR, missing sesskey, GET state change, trusting a user id parameter).
6. Write PHPUnit tests that demonstrate a permission boundary: an allowed role passes, a disallowed role in the same course fails, an allowed role in a different course fails, and an unauthenticated/guest user fails.

## 3. First-principles explanation

### 3.1 Contexts: where something lives

**What.** A *context* is a node in a tree that represents a place where permissions can be set or checked. **Why.** A user can be a teacher in one course and a student in another; permissions must depend on *where* the action happens. **[Stable]**

**Hierarchy [5.3].** The context classes and their level constants (verified in `accesslib.php` and the Access API page):

```
CONTEXT_SYSTEM    = 10  context_system     the whole site (exactly one)
 +- CONTEXT_USER      = 30  context_user       one user's profile/data (child of system)
 +- CONTEXT_COURSECAT = 40  context_coursecat  a course category (may nest)
     +- CONTEXT_COURSE    = 50  context_course     one course
         +- CONTEXT_MODULE   = 70  context_module     one activity instance
             +- CONTEXT_BLOCK    = 80  context_block      a block (can also sit in other contexts)
```

(Level numbers 10, 30, 40, 50, 70, 80 verified in source. The tree position of `context_user` and `context_block` is simplified here: `context_user` is directly under system; blocks attach to the context they are displayed in. VERIFY in the Roles docs page if it matters for your design.)

Getting a context object [5.3, verified]:

```php
$syscontext    = context_system::instance();
$coursecontext = context_course::instance($course->id);
$modcontext    = context_module::instance($cm->id);          // note: course MODULE id, not instance id
$context       = context::instance_by_id($contextid);       // when you only have a contextid
```

**Rule 1: derive the context from the object being accessed, not from convenient globals.** For a note row `$note`, the context is `context_course::instance($note->courseid)`. Not `context_system`. Not `$PAGE->context` (which reflects what the *page* set up, possibly from a different request parameter).

### 3.2 Capabilities

A capability is a named permission, `plugintype/pluginname:action`, e.g. `mod/choice:choose` or `moodle/course:manageactivities` (naming format verified). Each capability has:

- **captype**: `read` or `write`. Write capabilities are blocked for guest and not-logged-in users (verified).
- **contextlevel**: the typical context level where it is checked. It can be checked at lower levels too (verified).
- **riskbitmask**: flags for dangerous capabilities (`RISK_MANAGETRUST` 0x1, `RISK_CONFIG` 0x2, `RISK_XSS` 0x4, `RISK_PERSONAL` 0x8, `RISK_SPAM` 0x10, `RISK_DATALOSS` 0x20; values verified in source). The role UI shows risk icons and warns admins; `RISK_XSS` is for capabilities that allow input that bypasses HTML cleaning; `RISK_PERSONAL` for exposing personal data.
- **archetypes**: default allow for standard roles. The docs recommend using only `CAP_ALLOW` here (verified).
- **clonepermissionsfrom** (optional): copy the permissions an existing capability has on the site when yours is *added* (verified; used by `mod/choice:addinstance`).

Definition [5.3, structure verified; the specific example is mine]:

```php
<?php
defined('MOODLE_INTERNAL') || die();

$capabilities = [
    'local/coursenotes:view' => [
        'captype' => 'read',
        'contextlevel' => CONTEXT_COURSE,
        'riskbitmask' => RISK_PERSONAL,
        'archetypes' => [
            'editingteacher' => CAP_ALLOW,
            'manager' => CAP_ALLOW,
        ],
    ],
    'local/coursenotes:add' => [
        'captype' => 'write',
        'contextlevel' => CONTEXT_COURSE,
        'archetypes' => [
            'editingteacher' => CAP_ALLOW,
            'manager' => CAP_ALLOW,
        ],
    ],
];
```

You must also provide the language string `$string['coursenotes:view'] = '...';` (key is `pluginname:capabilityname`, verified) and **bump `version.php`** so the upgrade syncs capabilities into the database (verified requirement). Capabilities in code but not in the DB cause a runtime error when checked; the DB definition is what the role UI shows (Lab C in lesson 3.2).

Archetype defaults apply when the capability is first added (and when an admin resets a role); later, admins can change the permission in role definitions, so your code must never assume that "teachers can do X"; it must ask whether *this user has this capability in this context*. The Roles API docs say it plainly: do not think in terms of which roles or users hold a capability; check whether a specific user holds it in a given context (paraphrase of verified text).

### 3.3 Roles, assignments, overrides

- A **role** (e.g., `student`, `editingteacher`) is a global definition: for each capability a permission value (verified wording: role definitions are global and apply to all context levels).
- A **role assignment** gives a user a role *in a context* (user X is `editingteacher` in course 5). Assignments in a parent context inherit downward (site-level `manager` is manager everywhere; a category-level assignment covers its courses).
- An **override** changes a role's permission for one capability *within one context* (and below).
- **Archetypes** (verified list): `manager`, `coursecreator`, `editingteacher`, `teacher`, `student`, `guest`, `user` (every authenticated user, system-level), `frontpage` (authenticated users on the site front page). The `user` archetype and the `guest` role are not enrolment roles.
- **Enrolment is not a role.** Enrolment (`user_enrolments` via an enrolment method) says "this user participates in this course"; the role assignment determines what they may do. A student role is usually assigned automatically when enrolling; but a user can be enrolled with no role, or have a role without an active enrolment (e.g., via category assignment). Therefore `is_enrolled()` and `has_capability()` answer different questions.

**Permission values [5.3, verified]:** `CAP_INHERIT` 0, `CAP_ALLOW` 1, `CAP_PREVENT` -1, `CAP_PROHIBIT` -1000. **Resolution [Stable, per Roles docs]:** for each of the user's roles, walk from system down to the target context; at each level a role's value (from the role definition or an override) replaces an inherited value unless the value is Inherit; Allow in any role grants, unless **Prohibit** was set at any level on the path (Prohibit cannot be overridden lower); Prevent removes an inherited Allow *for that role* but another role of the same user may still Allow. Final result is true if at least one role ends in Allow and none is Prohibited. (This summary follows the docs: "Prohibit always wins"; the full algorithm in `accesslib.php` also handles admin and other special cases: VERIFY any edge case in the docs rather than from this summary.)

Worked resolution:

```
User Dana. Roles: system-level 'user' (authenticated), course 5: editingteacher.
Capability local/coursenotes:view.
 role editingteacher (from archetype): ALLOW
 override in category 'Archive': role editingteacher PREVENT   (category contains course 5)
 override in course 5: role editingteacher ALLOW
Check in course 5: walk system(ALLOW) -> category(PREVENT) -> course(ALLOW) => ALLOW  (lower override wins)
If instead the category override were PROHIBIT: => denied even though the course override says ALLOW.
Check in course 9 (same category, Dana is only a student there): student role has no value -> not allowed.
```

**Site administrators.** Users listed in `$CFG->siteadmins` pass `has_capability()` for almost everything (docs: "will return true for admin users", verified), controlled by the `$doanything` parameter. Never pass `false` for `$doanything` unless you know why (docs: not recommended; verified). Tests that "prove" a boundary must use non-admin users, or the test passes for the wrong reason.

### 3.4 The checking functions

Signatures from the 5.x source (`public/lib/accesslib.php`, `public/lib/enrollib.php`) [5.3 verified]:

```php
has_capability($capability, context $context, $user = null, $doanything = true)       // bool
has_any_capability(array $capabilities, context $context, $user = null, $doanything = true)
require_capability($capability, context $context, $userid = null, $doanything = true,
                   $errormessage = 'nopermissions', $stringfile = '')                   // throws if denied
is_enrolled(context $context, $user = null, $withcapability = '', $onlyactive = false)  // bool
require_login($courseorid = null, $autologinguest = true, $cm = null,
              $setwantsurltome = true, $preventredirect = false)                         // redirects / throws
```

Behavior:

- `has_capability` returns bool; `$user` null means the current user (`$USER`). Use it to *decide what to show* or to branch.
- `require_capability` throws `\core\exception\required_capability_exception` (namespace and class verified in source; it extends `moodle_exception`) when denied. Use it as a gate at the top of an entry point or service method. In tests: `$this->expectException(\core\exception\required_capability_exception::class);`.
- `is_enrolled($context, $user, $withcapability, $onlyactive)`: true if the user has an enrolment record (verified description: "enrolled (is participating) in course"; intended for students and teachers; `$onlyactive` restricts to active enrolments in enabled plugins and time windows; `$withcapability` additionally requires that capability). Use `is_enrolled(..., '', true)` when "currently participating" is the question. Do not use it as an authorization substitute for a capability on write operations.
- `require_login($courseorid, $autologinguest, $cm, ...)` (verified): checks the user is logged in; verifies access to hidden courses/activities and availability restrictions; checks enrolment or the `moodle/course:view` capability; logs course access. **Pass the course (or id) and `$cm` for course pages**: `require_login()` with no arguments only guarantees "someone is logged in", which is far weaker. The docs also say call it after setting `$PAGE->url` (verified); `require_course_login()` is for activities with public read access (verified).
- `has_capability` does not check login or enrolment itself; `require_login` does not check your plugin's capability. Both are needed. The order that works: `require_login($course, false, $cm)` -> context -> `require_capability`.

### 3.5 Request parameters and CSRF

**Parameters.** Never read `$_GET`/`$_POST` directly in Moodle code. Use:

```php
required_param($parname, $type)              // verified signature; error if missing
optional_param($parname, $default, $type)    // verified signature
```

(`required_param_array`/`optional_param_array` exist for array inputs: VERIFY signatures; `PARAM_*` list below is verified from `moodlelib.php`.) The `$type` is a `PARAM_*` constant that both validates and cleans. Types defined in 5.x (verified list): `PARAM_ALPHA`, `PARAM_ALPHAEXT`, `PARAM_ALPHANUM`, `PARAM_ALPHANUMEXT`, `PARAM_AUTH`, `PARAM_BASE64`, `PARAM_BOOL`, `PARAM_CAPABILITY`, `PARAM_CLEANHTML`, `PARAM_EMAIL`, `PARAM_FILE`, `PARAM_FLOAT`, `PARAM_LOCALISEDFLOAT`, `PARAM_HOST`, `PARAM_INT`, `PARAM_LANG`, `PARAM_LOCALURL`, `PARAM_NOTAGS`, `PARAM_PATH`, `PARAM_PEM`, `PARAM_PERMISSION`, `PARAM_RAW`, `PARAM_RAW_TRIMMED`, `PARAM_SAFEDIR`, `PARAM_SAFEPATH`, `PARAM_SEQUENCE`, `PARAM_TAG`, `PARAM_TAGLIST`, `PARAM_TEXT`, `PARAM_THEME`, `PARAM_URL`, `PARAM_USERNAME`, `PARAM_STRINGID`; several older ones (`PARAM_CLEAN`, `PARAM_INTEGER`, `PARAM_NUMBER`, ...) are deprecated. Choose the **most restrictive type that fits**: ids `PARAM_INT`; flags `PARAM_BOOL`; short action names `PARAM_ALPHANUMEXT`; free text meant for display `PARAM_TEXT` (strips tags, keeps multilang); `PARAM_RAW` means "no cleaning at all: you take responsibility" and must be justified. Exact cleaning behavior for malformed input (e.g., non-numeric `PARAM_INT`) is defined in `clean_param()`: VERIFY by reading it before depending on it, or test it.

Critical point: **cleaning is not authorization.** `PARAM_INT` makes `id` an integer; it says nothing about whether this user may access object `id`. That is steps 2-3 of the pipeline.

**CSRF and `sesskey`.** Cross-site request forgery makes a logged-in user's browser perform an action unintentionally. Moodle's defense is the session key. Verified usage from the CSRF documentation:

```php
$url = new moodle_url('/local/coursenotes/delete.php', ['id' => $id, 'sesskey' => sesskey()]);
// in delete.php:
require_sesskey();      // throws if the submitted sesskey is missing or wrong
```

Rules [verified from the docs, plus Stable principle]: Moodle's Form API (`moodleform`) automatically checks the sesskey and request method (verified statement) - prefer forms for anything that changes data. For link-based actions (delete, hide), use `$OUTPUT->single_button`/`confirm` patterns or include `sesskey` explicitly, **and require POST where feasible**. The docs warn that putting sesskey in URLs risks leaking it via the Referer header and that GET requests carrying a sesskey are acceptable only in limited cases (AJAX or sub-requests) (verified). `require_sesskey()` proves intent, not permission: you still need the capability check. Web service/AJAX external functions use their own token/session mechanism and `validate_context()` (verified, lesson 3.5); they must **not** call `require_login()` inside the function (verified warning).

### 3.6 The access-control pipeline

```
request -> [bootstrap config.php]
        -> clean params (required_param/optional_param, PARAM_*)         what is being asked
        -> load object by id (MUST_EXIST), derive course/cm from the OBJECT  what it really is
        -> require_login($course, false, $cm)                            who, and may they be in this course
        -> $context = context from the object                             where
        -> require_capability('plugin:action', $context)                  may they do this here
        -> if state change: require_sesskey() (or moodleform)             did they mean to
        -> act, then log event / output (escaped)
```

Memorize the order. Load-by-id then derive context is the step most plugins get wrong (they trust a `courseid` parameter that the user supplied separately from the object id).

### 3.7 Common authorization bugs and their signatures

| # | Bug | Symptom / how to find | Fix |
|---|---|---|---|
| 1 | Capability checked in wrong context (system, or a `courseid` the user supplied) | Teacher of course A reads data of course B | derive context from the loaded object |
| 2 | UI hides the control, handler unprotected | Direct URL works | enforce in every handler; test with direct calls |
| 3 | `require_login()` without course/cm on course-scoped pages | Not-enrolled logged-in users can open the page | pass `$course` and `$cm` |
| 4 | `optional_param('userid', $USER->id, PARAM_INT)` then use as-is | Reading others' data | `if ($userid != $USER->id) require_capability('...:viewother', context_user::instance($userid))` |
| 5 | State change on GET without `require_sesskey()` | Action performed by loading an image URL | POST + sesskey/form |
| 6 | `is_siteadmin()` or role-shortname checks as the model | Custom roles/overrides ignored; unusable for non-admins | use capabilities |
| 7 | `is_enrolled()` used instead of capability for write | Any student can edit | require the write capability |
| 8 | `has_capability` result ignored (called, not used) | Unprotected despite a visible check | use `require_capability` or branch on result and stop |
| 9 | Using `$doanything = false` or `PARAM_RAW` casually | Unexpected denials or XSS | use defaults; justify RAW |
| 10 | Capability added to code without version bump | "Capability not found" or open access defaults | bump version, upgrade |
| 11 | Check done before loading the right object, then object swapped (TOCTOU between check and use of a *different* id) | Intermittent cross-object access | check the same object you act on |
| 12 | Query returns rows without filtering by course/enrolment | Lists leak other courses' rows | join/filter by contextual ids; test with two courses |

## 4. Worked example

We harden `local_coursenotes` (project of lesson 3.2). Table `local_coursenotes` has `id, courseid, userid (author), note, timecreated`. Entry points: `view.php?id=<noteid>` and `delete.php` (POST with `id` and `sesskey`).

### 4.1 Naive version (do not copy)

```php
<?php
require_once(__DIR__ . '/../../config.php');
require_login();                                              // (a)
$id = required_param('id', PARAM_INT);
$courseid = optional_param('courseid', 0, PARAM_INT);         // (b) user-supplied
$context = context_system::instance();                        // (c)
if (!has_capability('local/coursenotes:view', $context)) {    // (d)
    echo 'no access';                                         // (e)
}
$note = $DB->get_record('local_coursenotes', ['id' => $id]);  // (f)
echo $note->note;                                             // (g)
```

Defects: (a) any logged-in user passes (weak). (b) The course is supplied independently of the object. (c) System context: a site-wide role grants access to every course's notes. (d)+(e) check result printed but execution continues: the note is still shown. (f) Not `MUST_EXIST`: a missing note gives `false` and then a PHP warning on `$note->note`. (g) Output unescaped (lesson 3.1: use the Output API and correct formatting; note content handling in lesson 3.4). Each of these is a distinct, testable bug.

### 4.2 Improved version

```php
<?php
require_once(__DIR__ . '/../../config.php');

$id = required_param('id', PARAM_INT);

$note   = $DB->get_record('local_coursenotes', ['id' => $id], '*', MUST_EXIST);
$course = get_course($note->courseid);          // VERIFY name in the course API (widely used helper)
$context = context_course::instance($course->id);

$PAGE->set_url(new moodle_url('/local/coursenotes/view.php', ['id' => $id]));
require_login($course);                          // who + may be in this course
require_capability('local/coursenotes:view', $context);   // may view notes here
$PAGE->set_context($context);
$PAGE->set_title(get_string('note', 'local_coursenotes'));

echo $OUTPUT->header();
echo \html_writer::div(s($note->note));          // s(): escape for HTML output (VERIFY helper name/behavior)
echo $OUTPUT->footer();
```

What changed and why:

- The note is loaded first with `MUST_EXIST` (verified strictness constant): a non-existent id raises a Moodle exception instead of a warning.
- `$course` and the context come **from the note**, closing the cross-course IDOR. The `courseid` parameter is gone.
- `require_login($course)` makes Moodle enforce course access (hidden course, enrolment or `moodle/course:view`) (verified behavior).
- `require_capability` stops execution by throwing.
- Output uses an escaping helper; the full output and format APIs are lesson 3.4. (`s()` is the commonly used escape helper in Moodle code: VERIFY in the output docs.)

### 4.3 Delete handler

```php
<?php
require_once(__DIR__ . '/../../config.php');

$id = required_param('id', PARAM_INT);
$note = $DB->get_record('local_coursenotes', ['id' => $id], '*', MUST_EXIST);
$course = get_course($note->courseid);
$context = context_course::instance($course->id);

$PAGE->set_url(new moodle_url('/local/coursenotes/delete.php'));
require_login($course);
require_capability('local/coursenotes:add', $context);   // or a dedicated :delete capability
if ($_SERVER['REQUEST_METHOD'] !== 'POST') {              // VERIFY: Moodle may offer a helper; a form is better
    throw new \moodle_exception('invalidrequest');       // VERIFY: string key exists; else use another error string
}
require_sesskey();

$DB->delete_records('local_coursenotes', ['id' => $note->id]);
redirect(new moodle_url('/local/coursenotes/index.php', ['courseid' => $course->id]));
```

Points: order matches the pipeline; deletion deletes the **loaded** note's id; `delete_records` signature `($table, array $conditions = null)` verified (mind: passing an empty conditions array deletes all rows; always pass a non-empty one). A dedicated `local/coursenotes:delete` capability is a better least-privilege design than reusing `:add`; the trade-off is more capabilities to manage. In production prefer the Form API or Moodle's confirmation components rather than hand-checking the request method (VERIFY exact helper names in lesson 3.4).

### 4.4 Tests that prove the boundary

`tests/access_test.php` (shape verified from the Moodle testing guide: namespace = component, class name = file name, extends `\advanced_testcase`, `resetAfterTest`, generators, `setUser`):

```php
<?php
namespace local_coursenotes;

use core\exception\required_capability_exception;

/**
 * @covers \local_coursenotes\access
 */
final class access_test extends \advanced_testcase {

    /** Create two courses, a note in course B, and users with roles in course A only. */
    private function scenario(): array {
        global $DB;
        $gen = $this->getDataGenerator();
        $courseA = $gen->create_course();
        $courseB = $gen->create_course();
        $teacherA = $gen->create_user();
        $studentA = $gen->create_user();
        $gen->enrol_user($teacherA->id, $courseA->id, 'editingteacher');   // role-shortname argument: VERIFY
        $gen->enrol_user($studentA->id, $courseA->id, 'student');
        $noteid = $DB->insert_record('local_coursenotes', (object) [
            'courseid' => $courseB->id, 'userid' => $teacherA->id,
            'note' => 'private', 'timecreated' => time(),
        ]);
        return [$courseA, $courseB, $teacherA, $studentA, $noteid];
    }

    public function test_teacher_of_other_course_cannot_view_note(): void {
        $this->resetAfterTest();
        [, , $teacherA, , $noteid] = $this->scenario();
        $this->setUser($teacherA);
        $this->expectException(required_capability_exception::class);
        access::require_can_view($noteid);       // the unit under test (see below)
    }

    public function test_student_in_same_course_cannot_view(): void {
        $this->resetAfterTest();
        [$courseA, $courseB, , $studentA] = $this->scenario();
        $this->setUser($studentA);
        // Note in course A for this check:
        global $DB;
        $id = $DB->insert_record('local_coursenotes', (object) [
            'courseid' => $courseA->id, 'userid' => 2, 'note' => 'x', 'timecreated' => time()]);
        $this->expectException(required_capability_exception::class);
        access::require_can_view($id);
    }

    public function test_teacher_in_same_course_can_view(): void {
        $this->resetAfterTest();
        [$courseA, , $teacherA] = $this->scenario();
        global $DB;
        $id = $DB->insert_record('local_coursenotes', (object) [
            'courseid' => $courseA->id, 'userid' => $teacherA->id, 'note' => 'x', 'timecreated' => time()]);
        $this->setUser($teacherA);
        access::require_can_view($id);           // must not throw
        $this->assertTrue(true);
    }
}
```

The unit under test, `classes/access.php`, centralizes the pipeline so pages and services share one tested implementation:

```php
<?php
namespace local_coursenotes;

final class access {
    /** @throws \core\exception\required_capability_exception */
    public static function require_can_view(int $noteid): \stdClass {
        global $DB;
        $note = $DB->get_record('local_coursenotes', ['id' => $noteid], '*', MUST_EXIST);
        $context = \context_course::instance($note->courseid);
        require_capability('local/coursenotes:view', $context);
        return $note;
    }
}
```

Test design notes: (1) Users are enrolled only in course A; the note is in course B: the capability exists in A but not in B, so denial proves the *context* is derived from the note. (2) A student in the right course is also denied: proves the capability, not mere enrolment, gates access. (3) A positive test prevents the failure mode "everything is denied, so all negative tests pass". (4) The tests use no admin: admin would pass every check (verified: `has_capability` is true for admins by default). (5) `setUser` simulates login (verified). Run after `php public/admin/tool/phpunit/cli/init.php` (verified path for 5.x) with `vendor/bin/phpunit local/coursenotes/tests/access_test.php`. Role-assignment variants (overrides, prohibits) can be created in tests with `assign_capability($capability, $permission, $roleid, $contextid, $overwrite)` and `role_assign($roleid, $userid, $contextid)` (signatures verified); the role id comes from `$DB->get_field('role', 'id', ['shortname' => 'editingteacher'])` (`get_field` signature VERIFY).

## 5. Production perspective

**Correctness.** Authorization is a function of (user, action, object). Tests must vary all three. Cache effects: capability checks are cached per request; changes in the same request in tests may need `accesslib_clear_all_caches_for_unit_testing()` (VERIFY name) or `reload_all_capabilities()`; `advanced_testcase` handles resets between tests.

**Maintainability.** One class that implements checks (`access::require_can_view`) beats copies of three function calls in ten files. Name capabilities by action (`:view`, `:add`, `:delete`, `:manageall`), not by role. Do not create a capability per button.

**Security.** Defense in depth: capability + sesskey + parameter typing + output escaping + prepared queries through `$DB`. Log denied attempts? Moodle logs events, not denials by default (VERIFY); for sensitive data, trigger a custom event on view/delete (lesson 3.5). Avoid information leaks in error messages (e.g., "note 7 belongs to course X").

**Performance.** `has_capability` per row in a loop is expensive; for lists, query only rows in contexts the user can access (e.g., load enrolled courses, filter by `courseid IN (...)` using `get_in_or_equal` (signature verified), and check once per course). Measure with the performance footer before optimizing; do not trust guesses.

**Operations.** Admins can change role definitions after you ship; a feature that works with archetype defaults can break or open up after a role change. Document each capability in the README with its risk and default archetypes.

**What a senior engineer does differently.** Writes the negative test first ("teacher of another course gets denied"), checks every entry point (pages, forms, AJAX, web services, CLI, tasks) rather than only the visible page, and searches the plugin for every place that reads the table to confirm each one is filtered.

**Beginner mistakes:** `require_login()` only; trusting a posted `courseid`; "hide the button" security; testing only as admin; forgetting to bump version after changing `access.php`; using `PARAM_RAW` to "make the error go away"; leaving `$doanything = false` after debugging.

**Diagnosing "permission denied" for a legitimate user.** (1) What context was checked? Print `$context->contextlevel` and id. (2) Role assignments: Site administration -> Users -> Permissions -> "Check permissions" for that user in that context (UI tool; name VERIFY). (3) Overrides along the path. (4) Prohibit anywhere? (5) Version bump done so the capability exists? (6) Is it `has_capability` true for the user in the DB but cache stale? purge caches.

A student without the capability requests `view.php?id=3`. What do they see? Name every defect.

**Lab B.** A test: "student cannot delete note". It creates a student, calls the delete code, and expects an exception. The test passes. The delete code has no capability check; it throws because `$PAGE->url` was not set in the test. What is wrong with the test and what would you add?

**Lab C.** `db/access.php` declares `'local/coursenotes:view'` with archetype `student => CAP_ALLOW`. A teacher later sets an override in course 5: role `student`, capability `local/coursenotes:view`, **Prohibit**. A site manager then assigns a student the `editingteacher` role in course 5 as well (they hold both roles). Can that user view notes in course 5?

**Lab D.** A delete link `delete.php?id=7&sesskey=...` checks capability and sesskey. The teacher's browser is tricked into loading an `<img src>` pointing to that link, using a sesskey copied from a screenshot shared in a support ticket. Does the attack succeed? Which two design flaws made it possible?

### Reveal (read after predicting)

- **Lab A.** The student sees "No access" and then, because there is no `die`/`throw`/`redirect`, the code falls through: `$OUTPUT->header()` called twice (a second call triggers a developer-visible error), and the note content is printed with `format_text` anyway. Defects: (1) missing stop after denial (use `require_capability`), (2) `require_login()` without the course, (3) `$PAGE` context/URL set in only one branch, (4) duplicate header, (5) output ordering and a `$PAGE` setup that exists in only one branch. *Procedure:* trace every code path that reaches the line printing protected data and ask "what stopped this?"
- **Lab B.** The test passes for the wrong reason: any exception satisfies a bare `expectException(\Exception::class)`. Assert the **specific** exception (`required_capability_exception`), assert the row still exists afterwards, and add a positive control (a teacher *can* delete). Mutation test: temporarily remove the capability check and confirm the test fails.
- **Lab C.** Expected answer: **no**. The docs state "Prohibit always wins" (verified): a Prohibit reached by any of the user's roles on the path to the context denies the capability, even though the `editingteacher` role would Allow it. Because role resolution is subtle, do not trust this reading alone: reproduce it in a PHPUnit test (create the override with `assign_capability(..., CAP_PROHIBIT, ...)`, assign both roles, assert `has_capability` is false) and compare with the UI "Check permissions" tool. Mark the claim VERIFY until your test confirms it on your version. *Diagnosis:* when a user is denied unexpectedly, look for a Prohibit anywhere on the path first.
- **Lab D.** The request is a GET; sesskey leaked via the screenshot (the docs warn about leakage through screenshots and Referer headers: verified). Flaws: state change on GET and the sesskey being exposed in a URL. Sesskey is per-session, so the attack works only while that session is alive, but the design should use POST (form) so the key is never in a URL. *Diagnosis:* search the code for `sesskey()` appended to URLs that change state.
