## 1. Engineering problem

Version 1 of the reading list works. Then:

- A tutor asks "who deleted the Chapter 3 link?" Nobody knows: nothing was logged.
- The marketing site wants to display counts; someone writes a script that queries your table directly and breaks when you rename a column.
- The nightly "remind students of unread items" feature was implemented by sending 4,000 emails inside the web request that saves an item; the teacher's browser times out and half the emails are sent twice when she retries.
- The list page does three queries per row. It is the slowest page on the course.
- Teachers upload PDFs into the note by pasting a pluginfile URL; students outside the course can open them.
- A student asks the DPO to export and delete everything the site holds on her. Your table has `userid`, and nobody told the DPO.

Each failure has a native Moodle mechanism: events for audit and decoupling, tasks for background work, external functions for a stable remote API, MUC for caching, the File API for attachments and the Privacy API for GDPR-style export and deletion. Misused, each creates its own failures (observer that throws and breaks the user's save; cache that serves stale permissions; task that is not idempotent; file served without checks; privacy provider that deletes the wrong context). This lesson teaches both uses and misuses.

## 2. Learning objectives

You can, without notes:

1. Define an event class, trigger it from the CRUD code, observe it in `db/events.php` from another component, and write a PHPUnit-style test that asserts the event was triggered with the right context and data.
2. Write a scheduled task with `db/tasks.php` and an adhoc task queued with custom data and duplicate checking, and make both idempotent and safe to retry.
3. Expose one function through `db/services.php` and an `external_api` class with validated parameters, a returns structure, `validate_context` and capability enforcement, and explain why `execute()` must call `validate_parameters` first.
4. Define a MUC definition in `db/caches.php`, add the required language string, read through the cache with a database fallback and invalidate it on every write path.
5. Store, list, serve and delete files through the File API with the correct six-key addressing, and implement a `local_readinglist_pluginfile` callback that checks login and capability before `send_stored_file`.
6. Implement a Privacy API provider (`get_metadata`, `get_contexts_for_userid`, `export_user_data`, `delete_data_for_all_users_in_context`, `delete_data_for_user`, userlist methods) and test export and deletion.
7. State at least five backward-compatibility rules for changing a published event, service or table, and apply them to a given change.

## 3. First-principles explanation

### 3.1 Events API

What: an event is an immutable record that something happened (class under `classes/event/`, extending `\core\event\base`). Observers registered in `db/events.php` are notified. Observers cannot change event data or stop dispatch (documented one-way channel).

Why: decouples producer from consumers (logging, notifications, cache invalidation, other plugins' reactions) and feeds the standard logstore, so audit and reports work without special code.

Class shape (names from the Events API documentation; the documentation page I could read is the archived docs.moodle.org/dev page, last edited 2021, and notes itself as stale, so treat the details as `VERIFY:` against a current core event such as `mod/page/classes/event/course_module_viewed.php` or `\core\event\course_created`):

```php
namespace local_readinglist\event;

defined('MOODLE_INTERNAL') || die();

class item_deleted extends \core\event\base {
    protected function init() {
        $this->data['crud'] = 'd';                         // c, r, u, d
        $this->data['edulevel'] = self::LEVEL_TEACHING;    // LEVEL_TEACHING, LEVEL_PARTICIPATING, LEVEL_OTHER
        $this->data['objecttable'] = 'local_readinglist_item';
    }

    public static function get_name() {
        return get_string('eventitemdeleted', 'local_readinglist');
    }

    public function get_description() {
        return "The user with id '$this->userid' deleted the reading list item with id '$this->objectid' "
             . "in the course with id '$this->courseid'.";
    }
}
```

Trigger:

```php
$event = \local_readinglist\event\item_deleted::create([
    'objectid' => $item->id,
    'context'  => \context_course::instance($item->courseid),
    'other'    => ['title' => $item->title],
]);
$event->add_record_snapshot('local_readinglist_item', $item);
$event->trigger();
```

Rules from the documentation: the class name encodes `object_action`; `objecttable` is required when `objectid` is used; the description should begin with the user id in quotes; `other` must be JSON-serialisable and small (it is stored in the log). `VERIFY:` current core also validates event data in an overridable `validate_data()` method and requires `get_url()`/`get_legacy_*` only where relevant: check an existing event.

Observers (`db/events.php`; the documented keys are `eventname`, `callback`, `includefile`, `priority`, `internal`):

```php
$observers = [
    [
        'eventname' => '\core\event\course_deleted',
        'callback'  => '\local_readinglist\observer::course_deleted',
    ],
];
```

```php
namespace local_readinglist;

class observer {
    public static function course_deleted(\core\event\course_deleted $event): void {
        global $DB;
        $DB->delete_records('local_readinglist_item', ['courseid' => $event->objectid]);
    }
}
```

`VERIFY:` an `observer` class under `classes/` named in the callback string, and the exact event object type hint. Documented behaviour you must design for: `internal` defaults to true, meaning the observer runs immediately and inside the producer's transaction; `internal => false` defers until after commit. An observer that throws can break the producer's operation; observers must be fast, defensive and, if they do heavy work, queue an adhoc task instead. Observers are cached: after adding or changing `db/events.php`, bump the version and purge caches. Also, `*` as `eventname` observes everything; avoid it, it taxes every request.

When to use events: audit, cross-plugin reaction, cache invalidation, data cleanup after deletion of a parent. When to avoid: needing a return value or ordering guarantees (events are one-way); making the producer's correctness depend on an observer.

Failure modes: observer assumes data the event did not include; infinite loops (observer triggers the event that triggers it); heavy work in the request path; renaming an event class (break for every observer in the ecosystem).

### 3.2 Tasks API

Documented: scheduled tasks extend `\core\task\scheduled_task` and run on a schedule an admin can override; adhoc tasks extend `\core\task\adhoc_task`, are queued with `\core\task\manager::queue_adhoc_task()`, carry JSON custom data (`set_custom_data()`/`get_custom_data()`), can run as a chosen user (`set_userid()`), and retry on failure with growing delay (starting at 1 minute, up to 24 hours; 12 attempts by default; override `retry_until_success()` to disable). Tasks only run as often as cron runs; blocking tasks were removed in 4.4 and legacy `cron.php`/`modname_cron()` were removed in 4.3. Task classes live in `classes/task/`, namespace `<component>\task`.

Scheduled task:

```php
namespace local_readinglist\task;

class send_reminders extends \core\task\scheduled_task {
    public function get_name() {
        return get_string('taskreminders', 'local_readinglist');
    }
    public function execute() {
        // Select candidates; queue one adhoc task per course; never do slow work here per user.
    }
}
```

`db/tasks.php` (documented keys: `classname`, `blocking`, `minute`, `hour`, `day`, `month`, `dayofweek`; `R` picks a random value; `blocking` is documented as `0` in the example and blocking support was removed in 4.4, so `VERIFY:` whether to omit it on 4.4+):

```php
$tasks = [
    [
        'classname' => 'local_readinglist\task\send_reminders',
        'minute' => 'R', 'hour' => '3', 'day' => '*', 'month' => '*', 'dayofweek' => '*',
    ],
];
```

Adhoc task with a factory method (documented recommendation):

```php
class notify_course extends \core\task\adhoc_task {
    public static function instance(int $courseid): self {
        $task = new self();
        $task->set_custom_data((object) ['courseid' => $courseid]);
        return $task;
    }
    public function execute() {
        $data = $this->get_custom_data();
        // Idempotent: skip items already notified (flag column or a log table).
    }
}
// Queueing, second argument true = do not duplicate an identical queued task:
\core\task\manager::queue_adhoc_task(notify_course::instance($courseid), true);
```

Per the 5.3 docs, `queue_adhoc_task` returns the id of the new or matching task since 5.3 and returned `false` for a match before 5.3: code that must run on 4.5 and 5.3 should not depend on the return value for the "duplicate" case.

Design rules (principles): tasks must be idempotent (retries and double execution will happen), must record progress in the database not in memory, must handle partial failure, must emit output with `mtrace()` for the cron log, and must never assume the user session context. After editing `db/tasks.php` bump the version (documented step). To run a task for testing use the admin CLI scripts `admin/cli/scheduled_task.php` and `admin/cli/adhoc_task.php` (`VERIFY:` flags with `--help` on your site; the pages I read pointed to docs.moodle.org for syntax, and the docs mention `--showdebugging`).

Failure modes: non-idempotent emails (double send on retry); a scheduled task doing per-user work serially (cron starvation: queue adhoc tasks); queueing from a loop without duplicate check (task flood); exception in `execute()` that is swallowed so retries never happen.

### 3.3 External functions and web services

What: a function callable by mobile app, AJAX (`ajax => true`) or token-authenticated clients, declared in `db/services.php`, implemented in a class extending `\core_external\external_api` (documented in the "writing a service" page for main/5.3).

```php
// db/services.php
$functions = [
    'local_readinglist_list_items' => [
        'classname'   => 'local_readinglist\external\list_items',
        'description' => 'Lists reading list items in a course.',
        'type'        => 'read',
        'ajax'        => true,
        'capabilities' => 'local/readinglist:view',
    ],
];
```

The documented keys: `classname`, `description`, `type` (`read`/`write`), `ajax`, `services` (e.g. `MOODLE_OFFICIAL_MOBILE_SERVICE`), `capabilities` (informational list; it does **not** replace the check in code). The older `methodname` and `classpath` (`externallib.php`) are documented as no longer recommended. Function names follow `{component}_{verb}_{noun}` (coding-style page).

```php
namespace local_readinglist\external;

use core_external\external_api;
use core_external\external_function_parameters;
use core_external\external_multiple_structure;
use core_external\external_single_structure;
use core_external\external_value;

class list_items extends external_api {
    public static function execute_parameters(): external_function_parameters {
        return new external_function_parameters([
            'courseid' => new external_value(PARAM_INT, 'Course id'),
        ]);
    }

    public static function execute(int $courseid): array {
        $params = self::validate_parameters(self::execute_parameters(), ['courseid' => $courseid]);
        $context = \context_course::instance($params['courseid']);
        self::validate_context($context);
        require_capability('local/readinglist:view', $context);

        $items = \local_readinglist\local\repository::get_for_course($params['courseid']);
        return array_map(fn($i) => [
            'id' => (int) $i->id,
            'title' => \core_external\util::format_string($i->title, $context),  // VERIFY: helper name in your version
            'url' => $i->url,
            'status' => $i->status,
        ], array_values($items));
    }

    public static function execute_returns(): external_multiple_structure {
        return new external_multiple_structure(new external_single_structure([
            'id' => new external_value(PARAM_INT, 'Item id'),
            'title' => new external_value(PARAM_TEXT, 'Title'),
            'url' => new external_value(PARAM_URL, 'Link'),
            'status' => new external_value(PARAM_ALPHANUMEXT, 'Status'),
        ]));
    }
}
```

The documented example uses the method names `execute_parameters`, `execute`, `execute_returns`, the `core_external\...` namespace, `self::validate_parameters`, `self::validate_context` and `require_capability`. The same page warns that `VALUE_OPTIONAL` cannot be used for top-level parameters and that the example page itself still contains a stale `get_context_instance()` call: use `context_course::instance()`. The `core_external\util::format_string` helper above is **not** verified; use `\format_string($title, true, ['context' => $context])` if unsure (`VERIFY:`).

Why validate parameters inside the function even though the framework declares them: `execute()` can also be called from PHP (other plugins, tests), and `validate_parameters` is what applies the cleaning to the declared types and rejects unknown keys. Why `validate_context`: it enforces login-state, maintenance mode, course visibility and enrolment rules for web-service users. Why still `require_capability`: `validate_context` is not authorisation for your action.

Writes: wrap multi-step writes in a delegated transaction (3.4 pattern, shown in the documented example); throw `invalid_parameter_exception` for bad input; use `type => 'write'`. Deprecation (documented 5.3 mechanism): add `public static function execute_is_deprecated(): bool { return true; }` and the PHPDoc `@deprecated since 5.3 MDL-XXXXX`; do not use the `\core\attribute\deprecated` attribute for external functions per that page.

Backward compatibility for services: a published function is a public API. Never rename it, change a parameter's type, make an optional parameter required, remove or retype a returned field. Add optional parameters and new returned fields instead; deprecate, then remove after a documented period. (Principle; the exact Moodle deprecation window policy is `VERIFY:` on moodledev.io, "Deprecation" policy page.)

Enabling a service for testing: site admin enables web services and creates a token (Site administration > Server > Web services). `VERIFY:` the current menu path for your version.

When to avoid: do not create a web service just to share data between two PHP plugins on the same site: call the PHP API or use events. A web service multiplies the attack surface.

### 3.4 Caching with MUC

Documented definition format (`db/caches.php`) and use:

```php
$definitions = [
    'courseitems' => [
        'mode' => cache_store::MODE_APPLICATION,
        'simplekeys' => true,
        'simpledata' => false,
        'staticacceleration' => true,
        'staticaccelerationsize' => 50,
        'invalidationevents' => ['local_readinglist_items_changed'],
    ],
];
```

Plus `$string['cachedef_courseitems'] = 'Reading list items per course';` in the language file, plus a version bump so Moodle reads the definitions. Use:

```php
$cache = \cache::make('local_readinglist', 'courseitems');
$items = $cache->get($courseid);
if ($items === false) {
    $items = array_values(\local_readinglist\local\repository::get_for_course($courseid));
    $cache->set($courseid, $items);
}
```

`get()` returns `false` on a miss (documented), so never cache a bare `false`. Invalidate on every write path: `$cache->delete($courseid)` or `\cache_helper::purge_by_event('local_readinglist_items_changed')` (documented; "invalidation events" are arbitrary strings, not Events API events). The docs recommend avoiding `ttl` in favour of event-based invalidation.

Modes: application (shared by all users), session (per session), request (one request). Security-critical rule: **never put per-user permission results in an application cache keyed without the user id**, and never cache capability decisions at all; capabilities have their own caching (3.3). Cache the *data*, check the *permission* on every request.

When to avoid: if you cannot name the event that makes the entry wrong, do not cache. If the query is cheap and indexed, do not cache. Measure first (3.6, Volume 4.4).

Failure modes: stale data after one write path forgets invalidation; cache stampede after purge; objects with closures or database handles stored in the cache; keys with illegal characters while `simplekeys` is true; tests that pass because the cache is warm.

### 3.5 File API

Documented model: a file is identified by `contextid`, `component`, `filearea`, `itemid`, `filepath` (starts and ends with `/`) and `filename`. Get the store with `get_file_storage()`. Create with `create_file_from_string($fileinfo, $content)`, `create_file_from_pathname`, `create_file_from_url`, `create_file_from_storedfile`. List with `get_area_files($contextid, $component, $filearea, $itemid)`; get one with `get_file(...)`. URL via `moodle_url::make_pluginfile_url(contextid, component, filearea, itemid, filepath, filename, forcedownload)`. `delete()` removes a file; to move between contexts, create from stored file then delete the original.

Serving: Moodle calls `<component>_pluginfile($course, $cm, $context, $filearea, $args, $forcedownload, array $options = [])` in your `lib.php`. It must return `false` when the file is not found and must call `send_stored_file()` on success. The documented skeleton checks context level and file area, calls `require_login($course, true, $cm)`, checks a capability, then looks the file up from `$args`. For a `local` plugin the context is your choice; we use the course context, so `$cm` is null and `$course` is supplied (`VERIFY:` how `$course` is derived for course-level contexts; check `lib/filelib.php` `file_pluginfile()` on your version).

```php
function local_readinglist_pluginfile($course, $cm, $context, string $filearea, array $args,
        bool $forcedownload, array $options = []) {
    if ($context->contextlevel != CONTEXT_COURSE || $filearea !== 'attachment') {
        return false;
    }
    require_login($course);
    require_capability('local/readinglist:view', $context);

    $itemid = (int) array_shift($args);
    $filename = array_pop($args);
    $filepath = $args ? '/' . implode('/', $args) . '/' : '/';

    // Object-level check: the item must exist and belong to this course.
    global $DB;
    if (!$DB->record_exists('local_readinglist_item', ['id' => $itemid, 'courseid' => $course->id])) {
        return false;
    }
    $file = get_file_storage()->get_file($context->id, 'local_readinglist', $filearea, $itemid, $filepath, $filename);
    if (!$file || $file->is_directory()) {
        return false;
    }
    send_stored_file($file, DAY_SECS, 0, $forcedownload, $options);
}
```

Uploading through forms uses `filemanager`/`filepicker` form elements and helper functions to move files from the user's draft area. The helper names (`file_prepare_standard_filemanager`, `file_postupdate_standard_filemanager`, `file_save_draft_area_files`) are what core uses but the page I fetched for the File API did not cover them; `VERIFY:` on moodledev.io "Using the File API in Moodle forms" before use.

Security principles: a pluginfile URL is guessable; the callback is the only gate. Always check the object, not just the context. Never serve files by path from the filesystem. Delete files when the owning record is deleted (`get_file_storage()->delete_area_files($contextid, $component, $filearea, $itemid)`, `VERIFY:` signature) and declare the files subsystem in the privacy provider.

### 3.6 Privacy API

Documented structure: `classes/privacy/provider.php`, namespace `<component>\privacy`.

If your plugin stores no personal data (no user-linked tables, no user preferences, no external links, no IP addresses) use `\core_privacy\local\metadata\null_provider` with `get_reason(): string` returning a language string key, e.g. `'privacy:metadata'`. Our plugin stores `userid`, so it must implement:

```php
namespace local_readinglist\privacy;

use core_privacy\local\metadata\collection;
use core_privacy\local\request\approved_contextlist;
use core_privacy\local\request\approved_userlist;
use core_privacy\local\request\contextlist;
use core_privacy\local\request\userlist;
use core_privacy\local\request\writer;

class provider implements
    \core_privacy\local\metadata\provider,
    \core_privacy\local\request\plugin\provider,
    \core_privacy\local\request\core_userlist_provider {

    public static function get_metadata(collection $collection): collection {
        $collection->add_database_table('local_readinglist_item', [
            'userid' => 'privacy:metadata:item:userid',
            'title' => 'privacy:metadata:item:title',
            'note' => 'privacy:metadata:item:note',
            'timecreated' => 'privacy:metadata:item:timecreated',
        ], 'privacy:metadata:item');
        $collection->add_subsystem_link('core_files', [], 'privacy:metadata:core_files');
        return $collection;
    }

    public static function get_contexts_for_userid(int $userid): contextlist {
        $contextlist = new contextlist();
        $sql = "SELECT ctx.id
                  FROM {context} ctx
                  JOIN {local_readinglist_item} i ON i.courseid = ctx.instanceid
                 WHERE ctx.contextlevel = :level AND i.userid = :userid";
        $contextlist->add_from_sql($sql, ['level' => CONTEXT_COURSE, 'userid' => $userid]);
        return $contextlist;
    }

    public static function get_users_in_context(userlist $userlist) {
        $context = $userlist->get_context();
        if ($context->contextlevel != CONTEXT_COURSE) {
            return;
        }
        $userlist->add_from_sql('userid',
            "SELECT userid FROM {local_readinglist_item} WHERE courseid = :courseid",
            ['courseid' => $context->instanceid]);
    }

    public static function export_user_data(approved_contextlist $contextlist) {
        global $DB;
        $userid = $contextlist->get_user()->id;
        foreach ($contextlist->get_contexts() as $context) {
            if ($context->contextlevel != CONTEXT_COURSE) {
                continue;
            }
            $rows = $DB->get_records('local_readinglist_item', ['courseid' => $context->instanceid, 'userid' => $userid]);
            if ($rows) {
                writer::with_context($context)->export_data(
                    [get_string('pluginname', 'local_readinglist')], (object) ['items' => array_values($rows)]);
            }
        }
    }

    public static function delete_data_for_all_users_in_context(\context $context) {
        global $DB;
        if ($context->contextlevel == CONTEXT_COURSE) {
            $DB->delete_records('local_readinglist_item', ['courseid' => $context->instanceid]);
        }
    }

    public static function delete_data_for_user(approved_contextlist $contextlist) {
        global $DB;
        $userid = $contextlist->get_user()->id;
        foreach ($contextlist->get_contexts() as $context) {
            if ($context->contextlevel == CONTEXT_COURSE) {
                $DB->delete_records('local_readinglist_item', ['courseid' => $context->instanceid, 'userid' => $userid]);
            }
        }
    }

    public static function delete_data_for_users(approved_userlist $userlist) {
        global $DB;
        $context = $userlist->get_context();
        if ($context->contextlevel != CONTEXT_COURSE) {
            return;
        }
        [$insql, $inparams] = $DB->get_in_or_equal($userlist->get_userids(), SQL_PARAMS_NAMED);
        $DB->delete_records_select('local_readinglist_item',
            "courseid = :courseid AND userid $insql", ['courseid' => $context->instanceid] + $inparams);
    }
}
```

The interface names, `add_database_table`, `add_subsystem_link`, `contextlist::add_from_sql`, `userlist::add_from_sql`, `writer::with_context`, `get_in_or_equal` and the method list come from the Privacy API page for main/5.3. Not from that page, so `VERIFY:` before use: exact `export_data` argument shapes, `delete_records_select` signature, and whether `get_contexts_for_userid` is declared with return type `contextlist` (the doc example uses it). Required language strings are in `lang/en`: `privacy:metadata`, `privacy:metadata:item`, one per field.

Behaviour you must design for: `delete_data_for_all_users_in_context` runs for expired contexts, so it must check context level and instance before deleting; deletion must be complete (files too); export must include only the requesting user's data, never other users' data in the same context; tests extend `core_privacy\tests\provider_testcase` (documented: `advanced_testcase` does not reset the content writer between tests).

Design judgement: is the *teacher's* note about a student personal data? Anything linked to an identifiable user is. The decision about retention and what counts is the organisation's, not yours; your job is to make the data findable, exportable and deletable and to ask the DPO when unclear.

### 3.7 Backward compatibility, collected

Principles (stable): published identifiers are contracts: event class names and their data fields, web service names, parameters and returns, capability names, language string keys that other plugins use, database column names used by reports, and file area names. Change by addition. Deprecate before removal. Never reuse a version number. Upgrade steps must migrate stored data (renamed events remain in the log). Dependencies are declared in `version.php`. Core APIs get deprecated on Moodle's schedule: read the release notes and `lib/upgrade.txt`-style notes (`VERIFY:` current location of upgrade notes in the 5.x tree, as repositories reorganised in 5.1 with `public/`) of each version you support, and test on each.

## 4. Worked example

Extend `local_readinglist` in this order, committing after each step.

Step 1: events. Create `item_created`, `item_updated`, `item_deleted` event classes. Trigger in `repository::save()` and `delete()`? Better in the page scripts or a service layer: the repository stays pure persistence, and the *use case* (edit.php, the web service) knows the context and user. Design choice: if two entry points (web page and web service) both mutate, move save/delete logic into a small `local_readinglist\local\service` class that both call, so the event is emitted in exactly one place. This is the simplest design that avoids drift; do not introduce more layers.

Step 2: observer `course_deleted` removing rows (principle: foreign keys in XMLDB are declarative only, so you clean up). Test it by deleting a course through `delete_course()` in a PHPUnit test (3.6).

Step 3: caching. Wrap `get_for_course()` (no search) in the `courseitems` cache. Invalidate in the service class on every create/update/delete and in the course-deleted observer. Write down the list of write paths in a code comment; if you add a fourth path and forget the invalidation, that comment is your review checklist.

Step 4: adhoc task. Add a nullable `reminded` timestamp to items via an upgrade step (3.4 pattern). The scheduled task `send_reminders` selects courses with unread items older than 7 days and queues `notify_course::instance($courseid)` with duplicate detection. The adhoc task messages each affected student once and sets `reminded`. Idempotency: the `WHERE reminded IS NULL` condition makes retries safe; set the flag per item inside the loop so a mid-run failure resumes correctly. Sending messages uses core's messaging API (`VERIFY:` `\core\message\message` and `message_send()`, plus a `db/messages.php` provider declaration, none of which were verified for this lesson; if you cannot verify them, log with `mtrace()` instead and mark the message sending as out of scope in your notes).

Step 5: web service. `local_readinglist_list_items` as in 3.3. Naive version: reading `$courseid` straight from the arguments and querying. Improved: `validate_parameters`, `validate_context`, `require_capability`, return structure typed. Test by calling `list_items::execute()` as a student, a teacher and a non-enrolled user (3.6), and by calling the HTTP endpoint with a token once by hand (`VERIFY:` REST endpoint path and parameters `wstoken`, `wsfunction`, `moodlewsrestformat` on docs.moodle.org Web service API).

Step 6: file attachments: add `filemanager` to the form, store in area `attachment`, itemid = item id, context = course context. Implement pluginfile callback as in 3.5; show attachments in the template via a list of URLs created by `make_pluginfile_url`. On delete, delete the area files.

Step 7: privacy provider as in 3.6, with a test that creates two users and three items, exports one user, deletes one user, and asserts the other user's data is intact.

Step 8: version bump, upgrade step for `reminded`, new lang strings (event names, task name, cache def, privacy strings). Run the upgrade on a dev site and purge caches.

## 5. Production perspective

Maintainability: one place emits each event; one place invalidates the cache; services call the same business class as pages. Naming follows frankenstyle.

Correctness: observers and tasks are idempotent; transactions around multi-table writes; event data minimal and stable.

Performance: observers run in the request path (unless `internal => false`): keep them under a few milliseconds or queue. MUC adds a hop; measure before and after (Volume 4.4 method), and do not claim a speedup you have not measured. Scheduled tasks that scan a whole table need an index matching their `WHERE`.

Security: services re-validate everything; capabilities checked in code; pluginfile is a security boundary; cache keys include anything that varies by user; privacy deletion deletes only the right user's rows.

Failure handling: tasks retry with backoff by design; log with `mtrace()`; decide what an unrecoverable failure does (`retry_until_success()` returning false). An observer failure should not break a user's save: wrap risky observer work in try/catch and log, or queue a task.

Testing: event observed via an event sink in PHPUnit (`$sink = $this->redirectEvents()`, `VERIFY:` method name in your version's `advanced_testcase`); tasks tested by calling `execute()` directly; privacy via `provider_testcase`; services via direct `execute()`.

Operations: after changing `db/events.php`, `db/tasks.php`, `db/caches.php`, `db/services.php`, bump `version.php` and run the upgrade. Forgetting that is the single most common "my change did nothing" bug in this lesson. Cron must run at least once a minute (documented recommendation) or tasks start late.

Senior habits: reading a similar core plugin's `db/*.php` files before writing yours; registering only observers you need; keeping the cache definition list tiny; writing the privacy provider *when you add the table*, not at the end; adding an ADR line for any public service.

Common mistakes with diagnosis: observer not firing (version not bumped or caches not purged; confirm the observer is registered by viewing the event list report or checking the event name's leading backslash); adhoc task never runs (cron not running, task queued to a different user, exception on every attempt: check the "Task logs" admin report); stale lists (missing invalidation: add `debugging()` temporarily around cache writes in a dev copy to see which path ran); pluginfile 404 (wrong filearea, itemid shifted from `$args`, or the callback returns `false` because the capability is missing); privacy tests failing in order (not extending `provider_testcase`).

## 6. Failure laboratory

Scenario: a developer ships this.

```php
// observer
public static function course_deleted(\core\event\course_deleted $event) {
    global $DB;
    $DB->delete_records('local_readinglist_item');          // forgot the condition
}

// adhoc task
public function execute() {
    foreach ($DB->get_records('local_readinglist_item') as $item) {
        email_to_user(...);                                  // for every item, every run
    }
}

// service
public static function execute($courseid) {
    return array_values($DB->get_records('local_readinglist_item', ['courseid' => $courseid]));
}

// cache
$cache->set($courseid, $items);   // on read; no invalidation on delete or update
```

Predict: (1) What data is lost, and when? (2) What happens when the task throws on the 400th email? (3) Which three security properties does the service lack, and what does the caller see for a non-enrolled user? (4) Teacher edits an item title; what does the student see, for how long? (5) Which of these four would a unit test catch easily, and which only a deliberate test?

### Reveal (read after predicting)

(1) The observer deletes every item on the site whenever any course is deleted. This is the "missing WHERE" class of defect; a test that creates two courses and deletes one catches it, a test with a single course does not. (2) With the default retry behaviour the task is retried after a delay and starts again from item 1: students 1-399 receive duplicates, repeatedly, up to the retry limit. Fix: a persisted per-item "sent" marker and a loop that updates it as it goes. (3) No `validate_parameters`, no `validate_context`, no `require_capability`: any authenticated token holder can read any course's items; the return structure is also undeclared, so extra fields leak (the framework would reject undeclared return fields when `execute_returns` is used; here it is missing). (4) The student sees the old title until the entry is evicted or purged; with no TTL and no invalidation that is indefinitely. (5) A unit test catches 1 and 3 easily; 2 requires a deliberate failure injection; 4 requires a test that reads the list, edits, and reads again.

Diagnosis procedure for "background feature misbehaves": (a) is it registered (version bumped, caches purged, listed in admin tasks or event observers)? (b) did it run (task logs, cron output)? (c) with what user and data (custom data, `set_userid`)? (d) did it run twice (duplicate detection, retries)? (e) is the side effect idempotent? (f) reproduce by calling the class method directly in a PHPUnit test with a controlled fixture, then add the missing assertion before fixing.

## 10. Engineering review

Checklist: every remote entry point validates parameters, context and capability; every write path emits one event and invalidates the cache; tasks are idempotent; tasks log with `mtrace()`; observers are short and defensive; pluginfile checks object and capability; privacy provider covers tables, files and preferences; all strings exist; `version.php` bumped for each `db/*.php` change; no event/service/capability renamed without deprecation; no debugging output; no core changes. Defend: why events in the service layer; why a task per course; what you do when an observer throws; why the `capabilities` key in `services.php` is not a substitute for `require_capability`.

## 11. Mastery gate

Pass = 80/100, no critical failure. Evidence: repository, tests output (or manual scripts), NOTES.md with VERIFY resolutions, contract table, diagram, 10-minute defence. Critical failures: a service function lacking `validate_parameters`, `validate_context` or capability enforcement; a pluginfile callback without access checks; a non-idempotent task that can duplicate side effects on retry; privacy deletion that can delete another user's or unrelated data; an observer that deletes without scoping; cache keyed without user/course where data depends on it; renaming a published identifier with no compatibility path; core modification. If failed: take one failing area, write the failing test first, fix, and explain in writing which documented mechanism you relied on; resubmit that area within 48 hours plus a new variant (e.g. a different table) to show transfer.
