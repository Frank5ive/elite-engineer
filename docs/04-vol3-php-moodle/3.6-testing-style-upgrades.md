## 1. Engineering problem

Your plugin is installed at a university. A new Moodle minor release arrives and an administrator upgrades on Friday. The upgrade fails halfway through your plugin's step because a column you add already exists on sites that ran an early alpha. The site is in maintenance mode all weekend. Separately:

- A reviewer finds 140 style violations, a missing `@package` docblock, and a string key that is not in alphabetical order, and asks you to fix them manually. Nobody wants to discuss the actual design.
- A change to `repository::get_for_course()` silently breaks the web service. No test exists. A student sees a teacher-only item in production.
- A teacher reports "the page is blank". The administrator has debugging off, the error log is not on your machine, and you do not know where Moodle writes errors.

Tests, automated checks, disciplined upgrade steps and an inspectable debugging setup convert these from weekend incidents into red CI builds on Tuesday afternoon. This lesson is also the readiness check for Capstone B: if you cannot do this lesson independently, the capstone will not be defensible.

## 2. Learning objectives

You can, without notes:

1. Initialise a PHPUnit environment for a Moodle dev site (`config.php` settings, init script, run a single test file), and write tests extending `advanced_testcase` that use `resetAfterTest`, data generators and `setUser`.
2. Write tests that verify a capability boundary (teacher can, student cannot, non-enrolled cannot), an event emission, an exception, a privacy export/delete, and an external function, with no test depending on order.
3. Write a plugin data generator (`tests/generator/lib.php`) and use it from a test.
4. Write one Behat scenario with generator steps for a teacher creating an item and a student seeing it, and explain when Behat is the wrong tool.
5. Run `moodle-plugin-ci` checks locally (or reproduce them with phpcs) and fix every reported violation without disabling a rule, and explain what each of phplint, phpcs, phpdoc, validate, savepoints, mustache, phpunit and behat checks.
6. Write an upgrade step that is safe on a partially upgraded site, bump versions correctly, test upgrade-from-previous in a scratch site, and state the backward-compatibility rules for a release.
7. Debug an unfamiliar Moodle failure using debug settings, the error log and an Xdebug step-through, and record the diagnosis in a report.
8. Complete a release checklist for a plugin and justify each item.

## 3. First-principles explanation

### 3.1 The test pyramid for Moodle plugins

```
          /\        Behat: browser-driven, slow, brittle; user-visible journeys only
         /  \
        /----\      PHPUnit with DB (advanced_testcase): the workhorse; real DB, real APIs
       /      \
      /--------\    PHPUnit basic_testcase: pure functions, no DB
```

Cost, in order: basic < advanced < Behat. Put each check at the cheapest level that can see the defect. A capability check is visible to PHPUnit; a rendered button inside a modal is visible to Behat. Measure runtime of your suite and keep Behat to a handful of journeys.

### 3.2 PHPUnit in Moodle

Documented facts (PHPUnit page and "Writing PHPUnit tests" page, main/5.3):

- PHPUnit is a Composer dependency, not part of Moodle: run `php composer.phar install` in the Moodle root (the PHPUnit page uses `php composer.phar install`; on 5.3 the dev dependencies come from `require-dev` in the root `composer.json`, which includes `moodle/moodle-testing`).
- Configure `config.php`: `$CFG->phpunit_prefix = 'phpu_';` and `$CFG->phpunit_dataroot = '/path/to/phpunit_dataroot';` with a dedicated directory. Optional `$CFG->phpunit_db*` settings can point to a separate database. The prefix must differ from the real prefix so that tests never touch production tables.
- Initialise: from the Moodle root, `php admin/tool/phpunit/cli/init.php` (on 5.1+ the script lives under `public/`: `php public/admin/tool/phpunit/cli/init.php`, as the PHPUnit docs show). Re-run it after upgrades, plugin install/uninstall, and when you add tests (new test files require a reinitialise so the phpunit config is regenerated). The docs require the PHP CLI on your path and the `en_AU.UTF-8` locale. The tool's `util.php` can manage an initialised environment without a full re-init (`--help` lists options).
- Run: from the Moodle root, `vendor/bin/phpunit path/to/file_test.php`, or filter with `--filter`, `--testsuite <component>_testsuite`, `--group`, or `-c` with a component's `phpunit.xml`.
- Test files: component's `tests/` directory; filename lowercase ending `_test.php`; class name equals the filename; one test class per file; the class namespace equals the component's namespace; extend `\advanced_testcase` (database, filesystem, globals) or `\basic_testcase` (pure unit tests).
- State: each test begins from a fresh installation state. Call `$this->resetAfterTest()` before the first data change, otherwise you get an "unexpected database modification" failure. Do **not** put `resetAfterTest` in a shared `setUp()` (documented as banned).
- Login: `$this->setUser($user)`, `$this->setAdminUser()`, `$this->setGuestUser()`, `$this->setUser(null)`. Only guest and admin exist at the start.
- Generators: `$this->getDataGenerator()->create_user()`, `create_course()`, `create_category()`, `enrol_user($userid, $courseid)`, `create_cohort()`, `create_group()`; plugin generators through `get_plugin_generator('component')`.
- Coverage attributes: on Moodle 5.0+ (PHPUnit 10+) use `#[\PHPUnit\Framework\Attributes\CoversClass(example::class)]`; on 4.5 and earlier use the `@covers` annotation with fully qualified names.
- Data providers may only define data, not create Moodle records, because they run before the database is reset; create the data inside the test.
- Messages and email: `preventResetByRollback()` then `redirectMessages()`; unset `noemailever` then `redirectEmails()`. Events: `redirectEvents()` (all of `preventResetByRollback()`, `redirectMessages()`, `redirectEvents()` exist in `lib/phpunit/classes/advanced_testcase.php`). Time: `mock_clock_with_frozen()`, `mock_clock_with_incrementing()` and `mock_clock_with_frozen_datetime()` exist there too.
- Privacy tests extend `core_privacy\tests\provider_testcase` (documented in the Privacy API page).

A first test for the repository:

```php
<?php
namespace local_readinglist\local;

defined('MOODLE_INTERNAL') || die();

/**
 * Tests for the repository.
 *
 * @package    local_readinglist
 */
#[\PHPUnit\Framework\Attributes\CoversClass(\local_readinglist\local\repository::class)]
final class repository_test extends \advanced_testcase {

    public function test_search_treats_percent_and_underscore_literally(): void {
        $this->resetAfterTest();
        $course = $this->getDataGenerator()->create_course();
        repository::save((object) ['courseid' => $course->id, 'userid' => 2, 'title' => '100%_done',
            'url' => 'https://example.org', 'status' => 'todo']);
        repository::save((object) ['courseid' => $course->id, 'userid' => 2, 'title' => '100 xdone',
            'url' => 'https://example.org', 'status' => 'todo']);

        $found = repository::get_for_course($course->id, '%_d');

        $this->assertCount(1, $found);
        $this->assertSame('100%_done', reset($found)->title);
    }

    public function test_get_throws_for_missing_item(): void {
        $this->resetAfterTest();
        $this->expectException(\dml_missing_record_exception::class);
        repository::get(999999);
    }
}
```

Notes: the `#[CoversClass]` attribute is the style core tests use on 5.x (e.g. `mod/forum/tests/generator_test.php`); on 4.5 (PHPUnit 9.6) use the `@covers` annotation instead, since attributes are ignored there. PHPUnit 11 still reads `@covers` but deprecates doc-block metadata; the test names state the behaviour; arrange, act, assert separated by blank lines (as in 1.4); `dml_missing_record_exception` is the documented `MUST_EXIST` outcome (3.4). In the first test we call `save()` which, in 3.5, was moved into the service class; update the call site accordingly or keep `save()` as persistence only.

Capability test:

```php
public function test_student_cannot_manage_but_can_view(): void {
    $this->resetAfterTest();
    $gen = $this->getDataGenerator();
    $course = $gen->create_course();
    $student = $gen->create_user();
    $teacher = $gen->create_user();
    $gen->enrol_user($student->id, $course->id, 'student');
    $gen->enrol_user($teacher->id, $course->id, 'editingteacher');
    $context = \context_course::instance($course->id);

    $this->assertTrue(has_capability('local/readinglist:view', $context, $student));
    $this->assertFalse(has_capability('local/readinglist:manage', $context, $student));
    $this->assertTrue(has_capability('local/readinglist:manage', $context, $teacher));
}
```

`enrol_user($userid, $courseid, $roleidorshortname)`: the third argument accepts a role shortname or id (`enrol_user($userid, $courseid, $roleidorshortname = null, $enrol = 'manual', ...)` in `lib/testing/generator/data_generator.php`). This test depends on the capability defaults in `db/access.php` (3.3), which is exactly the thing worth testing: change an `archetypes` entry and this test fails.

Event test (`redirectEvents()` returns the sink):

```php
$sink = $this->redirectEvents();
\local_readinglist\local\service::delete_item($itemid);
$events = $sink->get_events();
$sink->close();
$this->assertCount(1, $events);
$this->assertInstanceOf(\local_readinglist\event\item_deleted::class, $events[0]);
$this->assertEquals($itemid, $events[0]->objectid);
```

External function test: call `list_items::execute($course->id)` after `setUser($student)`, compare with `\core_external\external_api::clean_returnvalue(list_items::execute_returns(), $result)` (`clean_returnvalue(external_description $description, $response)` is a static method of `\core_external\external_api`), and test the denial with `$this->expectException(\required_capability_exception::class)` for the management function.

Privacy test: extend `provider_testcase`; create two users, items; use `provider::get_contexts_for_userid($user->id)`, then export with `approved_contextlist` and read the writer with `writer::with_context($context)`; then `delete_data_for_user` and assert counts. `provider_testcase` (namespace `core_privacy\tests`) has `export_all_data_for_user(int $userid, string $component)` and `export_context_data_for_user(int $userid, \context $context, string $component)` helpers.

Cache pitfalls in tests: caches may be warm; call `\cache_helper::purge_all()` (exists in `cache/classes/helper.php`) or use `\cache::make(...)->purge()` in setup of cache-sensitive tests. Test that the invalidation exists by reading, editing, reading again.

Time: tests that depend on `time()` are flaky; compare relative timestamps with a tolerance or inject time. Core provides clock mocking in `\advanced_testcase` (`mock_clock_with_frozen()` and siblings, checked in the 5.3 source), which works for code that uses the `\core\clock` service; code calling `time()` directly cannot be mocked, so inject or use the clock service.

Data generator for your plugin (`tests/generator/lib.php`, documented location; must extend `\component_generator_base`):

```php
class local_readinglist_generator extends \component_generator_base {
    public function create_item(array $record = []): \stdClass {
        global $USER;
        static $i = 0;
        $i++;
        $record = (object) ($record + [
            'courseid' => 0, 'userid' => $USER->id ?: 2, 'title' => "Item $i",
            'url' => "https://example.org/$i", 'note' => '', 'status' => 'todo',
        ]);
        $record->id = \local_readinglist\local\repository::save($record);
        return $record;
    }
}
```

Use: `$this->getDataGenerator()->get_plugin_generator('local_readinglist')->create_item(['courseid' => $c->id])`. The class-naming convention for plugin generators is `<component>_generator` in the file `tests/generator/lib.php`; Checked against core: `mod/forum/tests/generator/lib.php` declares `class mod_forum_generator extends testing_module_generator`; non-module plugins extend `component_generator_base`.

### 3.3 Behat at the level needed

Documented: Behat features are Given/When/Then scenarios in a component's `tests/behat/` folder; tests run against a separate Behat site configured with `$CFG->behat_wwwroot`, `$CFG->behat_prefix`, `$CFG->behat_dataroot`; setting `behat_wwwroot` also restricts tests to that URL, protecting production; initialise with `php admin/tool/behat/cli/init.php` (`php public/admin/tool/behat/cli/init.php` on 5.1+, mirroring PHPUnit), Behat itself via Composer; JavaScript scenarios need a browser driver such as Selenium; non-JS tests run faster.

Scenario skeleton (step wording checked against core: `I log in as "..."` is defined in `auth/tests/behat/behat_auth.php`, the `the following "users" exist:` generator steps are used throughout core features, and the page-resolver steps are in `lib/tests/behat/behat_navigation.php`):

```gherkin
@local @local_readinglist
Feature: Teachers manage a course reading list
  In order to guide students
  As a teacher
  I need to add reading items that students can see

  Background:
    Given the following "users" exist:
      | username | firstname | lastname | email                |
      | teacher1 | Terry     | Teacher  | teacher1@example.com |
      | student1 | Sam       | Student  | student1@example.com |
    And the following "courses" exist:
      | fullname | shortname |
      | Course 1 | C1        |
    And the following "course enrolments" exist:
      | user     | course | role           |
      | teacher1 | C1     | editingteacher |
      | student1 | C1     | student        |

  Scenario: Teacher adds an item and a student sees it
    Given I log in as "teacher1"
    And I am on the "C1" "Course" page   # resolver step: identifier, then type (type is matched case-insensitively)
    When I follow "Reading list"
    # ... fill the form and submit ...
    Then I should see "Clean Code"
    And I log out
    And I log in as "student1"
    # ... open the list ...
    Then I should see "Clean Code"
    And I should not see "Add item"
```

Rules: generate state with generator steps, not by clicking; one journey per scenario; no sleeps (Moodle steps wait); tag with the component. Decide Behat versus PHPUnit by asking "does a user-visible interaction (JS, layout, navigation) matter?" If not, PHPUnit. Behat failure artefacts (screenshots, HTML dumps) are configured in `config.php` (`$CFG->behat_faildump_path`, documented in `config-dist.php`). Do not write Behat tests that depend on the production database or theme.

### 3.4 Coding style and automated checks

The coding-style page (docs for main/5.3) says Moodle follows PSR-12 and PSR-1 unless stated otherwise: 4-space indent, opening braces on the same line, long PHP tags, no closing tag, LF endings, lines at most 132 characters (hard limit 180), `else if` rather than `elseif`, always braces, short array syntax, single-quoted strings unless interpolating, lowercase words with underscores for classes and functions, constants uppercase with component prefix, namespaces with the component as first level, classes under `classes/`, one class per file, explicit visibility, type hints and return types on all new code, `#[\Override]` on overriding methods, complete PHPDoc on every class, function, method and property, GPL file header with `@package`, `@copyright`, `@license`, `defined('MOODLE_INTERNAL') || die();` on non-class scripts with side effects, `moodle_exception` instead of `print_error()`, TODO comments carrying an MDL tracker reference, language strings complete with no leading/trailing whitespace.

Checking: moodle-plugin-ci (maintained by Moodle HQ) runs, per its documentation, PHPUnit, Behat, Moodle Code Checker (phpcs with the Moodle standard), Moodle PHPdoc check, Mustache linting, Grunt tasks, PHP Parallel Lint, PHP Mess Detector and PHP Copy/Paste Detector (deprecated). Local install per its docs: `composer create-project moodlehq/moodle-plugin-ci ../moodle-plugin-ci ^4` or the `.phar`. For GitHub Actions the project ships `gha.dist.yml` to copy into `.github/workflows/`. Travis CI support is deprecated as of 4.5.8 and slated for removal in 5.0.0. Command names below were checked against `docs/CLI.md` and `gha.dist.yml` of moodle-plugin-ci: `phplint`, `phpmd`, `phpcs`, `phpdoc`, `validate`, `savepoints`, `mustache`, `grunt`, `phpunit`, `behat` (plus `install`, `add-plugin`, `add-config`, `parallel`, `codefixer`/`phpcbf`; `codechecker` is the older name of `phpcs`; `phpcpd` was deprecated in 4.4.0 for removal in 5.0.0). The workflow file shipped as `gha.dist.yml` initialises with `composer create-project -n --no-dev --prefer-dist moodlehq/moodle-plugin-ci ci ^4` and runs `moodle-plugin-ci phpcs --max-warnings 0`; copy it, do not hand-write it.

| Check | What it catches | Typical cause of failure |
|---|---|---|
| lint (parallel lint) | PHP syntax errors, including on the oldest PHP the plugin supports | using PHP 8.2 syntax in a plugin claiming PHP 8.1 |
| phpmd | complexity, unused variables | god functions |
| phpcs (Moodle standard) | style rules above | missing docblock, wrong indent |
| phpdoc | missing/incorrect docblocks | undocumented method |
| validate | plugin structure and `version.php` | missing component, bad file |
| savepoints | missing `upgrade_plugin_savepoint` calls in upgrade steps | forgot the savepoint |
| mustache | template lint, missing docblock/example context | template without `Example context` |
| grunt | compiled JavaScript/CSS out of date | edited `src` but not `build` |
| phpunit / behat | behaviour | regression |

Run style before pushing; do not argue with the standard; never add `// phpcs:ignore` to hide a violation without an explicit justification comment and a reviewer agreeing. Fix violations by editing code. A style failure in CI is cheaper than a style comment in review. Check the standard's name and installation for plain phpcs usage in the PHPCS tool page of the developer docs (the PHPCS tool page names two standards in the `moodlehq/moodle-cs` package: `moodle`, the standard ruleset, and `moodle-extra`, which adds recommended best practices and is recommended for new code).

### 3.5 Upgrade steps and version bumps

Principles: a released version number is immutable; install.xml is the final schema; `upgrade.php` steps are incremental, guarded and each ends with a savepoint; steps are tested from every supported earlier version, not only from "last". Mechanics (verified in 3.4): `version.php` fields; `$dbman = $DB->get_manager();`, `field_exists`, `add_field`; `upgrade_plugin_savepoint(true, $version, 'local', 'readinglist')`. Savepoints let an interrupted upgrade resume.

Guarding: always check existence before adding (`field_exists`, `table_exists`, `index_exists`) so alpha/dev installs and retried upgrades do not fail. Data migration steps must be set-based and bounded in time: a single `UPDATE` with placeholders via `$DB->execute()` beats a PHP loop over a million rows. For truly long migrations queue an adhoc task and make the step only add the column.

Version scheme: `YYYYMMDDXX`; on a stable branch keep the date and increment `XX` (documented). `requires` and `supported` are compatibility declarations; set them from what you tested, not what you hope (`supported` is the lowest and highest inclusive branches, e.g. `[311, 400]`, documented since 3.9 on the `version.php` page). `incompatible` declares the first branch you do not support. `release` is the human string; choose semantic versioning and keep it consistent. `maturity` honest: do not mark `MATURITY_STABLE` without tests.

Core upgrade cadence: Moodle ships major versions every six months (4.5 LTS Oct 2024, 5.1 Oct 2025, 5.2 Apr 2026, 5.3 LTS Oct 2026 per the releases page). Support table from the same page: 4.5 LTS security until 4 Oct 2027; 5.1 security until 19 Apr 2027; 5.2 stable until 19 Apr 2027 then security to 4 Oct 2027; 5.3 LTS security to 1 Oct 2029. The page's intro text still says 4.5 is the most recent LTS and 5.3 the next, which is consistent with 5.3 being labelled LTS in the table once released (the 5.3.0 tag exists in the Moodle repository). Re-read https://moodledev.io/general/releases before quoting dates to a client. Decide which branches you support explicitly, test on each (CI matrix) and declare it in `supported`.

Backward compatibility checklist when releasing: identifiers published to others (events, services, capabilities, strings, DB columns, settings keys, file areas) unchanged or deprecated; database changes additive; a way to roll back (database backup is the administrator's responsibility, say so in the release notes; Moodle does not support downgrading a plugin version: a lower version number cannot be installed over a higher one: `plugin_manager` reports status `downgrade` and core throws `downgrade_exception` from `upgrade_plugin_savepoint` when the stored version is not lower); changelog entry; upgrade notes for administrators.

### 3.6 Debugging in an existing Moodle

Evidence-first procedure (extends Lesson 0.3): reproduce; read the error; localise; hypothesise; test; fix; add a regression test; log the failure.

Debug settings: Site administration > Development > Debugging sets `debug` (None, Minimal, Normal, Developer, which is `DEBUG_DEVELOPER`, defined as `E_ALL` in `lib/setuplib.php`) and `debugdisplay`. They can be forced in `config.php`:

```php
@error_reporting(E_ALL);
@ini_set('display_errors', '1');
$CFG->debug = (E_ALL);   // === DEBUG_DEVELOPER
$CFG->debugdisplay = 1;
```

These lines match the "development servers" section of `config-dist.php` on 5.3 (`E_ALL`, not the older `E_ALL | E_STRICT`); use them only on dev and staging, never in production because it discloses internals and paths. Other documented/conventional aids: `$CFG->debugsmtp` (only effective with developer debugging on; `config-dist.php`), the "Performance info" admin setting `perfdebug` (Site administration > Development > Debugging), error log location from your web server or PHP-FPM configuration (`error_log` in `php.ini`, or the web server log), and the admin "Task logs" and "Event list" reports. `debugging('message', DEBUG_DEVELOPER)` is the in-code API for developer-only notices; `mtrace()` for CLI/cron output; never `var_dump` in committed code.

Xdebug (php.net/xdebug docs; Xdebug 3 settings): `xdebug.mode=debug`, `xdebug.start_with_request=trigger` or `yes`, `xdebug.client_host`, `xdebug.client_port` (Xdebug 3 default 9003), IDE path mappings from the web root to your checkout. On 5.1+ the web server document root is `public/`, so map the web root to `<checkout>/public`, while CLI scripts such as `admin/cli/upgrade.php` live at the checkout root. For CLI (cron, tasks, upgrade scripts) set `XDEBUG_SESSION=1` or the trigger and run `php admin/cli/...`. Step through from the entry script, watch `$USER`, `$PAGE->context`, SQL parameters; do not leave Xdebug on in production (performance and security).

Reading an unfamiliar Moodle: `$CFG->wwwroot` URL to file via the plugin type's directory; use `grep -rn "function name"` over the tree; read the plugin's `lib.php` callbacks, `db/*.php` registrations, `classes/` and `tests/`. Use `git log -S`/`git blame` for history (0.2). Never "fix" core: report upstream or work around in a plugin.

Common errors and meaning: `Coding error detected, it must be fixed by a programmer: ...` is a developer error with the explanation in the message; `Exception - Call to undefined function ...` often a missing `require_once` or a function removed/renamed in a newer version (deprecation); `Invalid parameter value detected` is `validate_parameters` or `PARAM` cleaning rejecting; "Unexpected database modification" in tests means missing `resetAfterTest`; "cache definition not found" means a version bump or purge is missing.

### 3.7 Release checklist (summary, expanded in the project)

Version and metadata; style and static checks green; tests green on every supported Moodle/PHP/DB combination you claim; Behat journey green; upgrade from previous release and from the oldest supported release tested; strings complete; privacy provider current; capabilities documented; README, CHANGES, upgrade notes; tag in git matching `release`; (optional) submission to the Moodle plugins directory, which has its own requirements (`VERIFY:` current plugins-directory rules on moodle.org/plugins before promising anything to a client; not checked in this pass: those pages are not in the code or developer-docs repositories).

## 4. Worked example

Goal: prepare `local_readinglist` 2.0 for release as 2.0.1 (a bug fix) with tests and CI.

Step 1: dev site. Install Moodle 5.3 (or the target branch) from the official git repository on a throwaway database; configure PHPUnit settings and run the init script; run one core test (for instance a single small test file) to prove the environment works before touching your code. Common failure: the init script cannot find a locale; install `en_AU.UTF-8` (documented requirement).

Step 2: write tests top-down from the risks, not from the code: (1) capability matrix; (2) cross-course access denied (the IDOR from 3.4); (3) search literal `%`; (4) duplicate title behaviour; (5) events emitted once; (6) cache invalidation; (7) external function denial and success; (8) privacy export/delete isolation. Eight tests are enough to cover the contracts; resist writing a test per line.

Step 3: run each new test, break the code deliberately (remove the course check), confirm that the test goes red, restore. A test you have never seen fail is unproven. This is the most valuable habit in the lesson.

Step 4: run the style tools. Typical findings and fixes: missing docblocks (add meaningful ones, not "Constructor"), long lines (wrap at 132), `elseif` to `else if`, unsorted language strings (alphabetise), missing `@package`. Fix, do not suppress.

Step 5: Behat scenario. Write the Background with generator steps, one journey, run with a tag filter. Expect to spend time on step phrasing; read an existing core feature file for the exact steps.

Step 6: upgrade test. Take a database backup of a dev site with v1 installed, then install v2.0.1, observe the upgrade, then restore and run again via CLI to confirm repeatability. Also test the failure path: manually add the `reminded` column before upgrading and confirm the guarded step does not fail.

Step 7: CI. Copy `gha.dist.yml` (do not author it), set the matrix to the branches you support, push, and read the first red build line by line.

Step 8: release. Bump `version.php` (`2026110101`, release `2.0.1`), update CHANGES, tag `v2.0.1`. Create the debugging report for any production failure you simulated in the failure lab.

Naive versus improved: naive "test" calls the page in a browser and eyeballs it; improved asserts invariants in PHPUnit and only the user journey in Behat. Naive release edits an earlier upgrade step and re-uses the version; improved adds a new guarded step and a new version.

## 5. Production perspective

Maintainability: tests document contracts; generators keep tests short; CI is the single source of truth for "green". Keep the matrix small enough that people read failures.

Correctness: test across database engines you claim to support; the DB differences described in 3.4 (case sensitivity, empty string versus null) show up here first. Do not claim portability on one engine's evidence. For 5.3 the supported engines are PostgreSQL 17+, MySQL 8.4+, MariaDB 11.4+ and SQL Server 2019+ (release notes); include at least PostgreSQL and one MySQL-family engine.

Performance: PHPUnit init and Behat site setup are slow; use snapshots (`util.php --snapshot/--restore` documented) in CI to speed repeated runs. Keep tests independent so they can be run selectively. Never fabricate timing claims; time your suite and publish the number you measured.

Security: tests include negative cases (unauthorised access, hostile input). CI secrets never in repository. Debug settings never in production.

Failure handling: flaky tests are bugs; quarantine with an issue reference, do not retry blindly; time-dependent and cache-dependent tests are the usual culprits.

Operations: upgrade in maintenance mode with a backup; read upgrade notes; run `php admin/cli/upgrade.php` (at the Moodle root on 5.3; it is not under `public/`) on staging first. Provide an administrator-facing upgrade note listing schema changes.

Senior habits: write the failing test first for each bug; run style checks in a pre-push hook; read the Moodle release notes and deprecation notes for each version in the support matrix; keep PRs small enough that CI failures are attributable.

Beginner mistakes: tests that depend on previous tests; `resetAfterTest` forgotten; assertions on rendered HTML where an API result would do; a Behat scenario for every function; suppressing phpcs; editing an old upgrade step; testing only on the developer's favourite DB; leaving `debugdisplay` on in production; debugging by adding `echo` and forgetting to remove it.

## 6. Failure laboratory

Scenario: this test passes on your machine and fails randomly in CI.

```php
final class flaky_test extends \advanced_testcase {
    private static $courseid;

    public function setUp(): void {
        parent::setUp();
        $this->resetAfterTest();                 // flaw 1
    }

    public function test_a_create(): void {
        $c = $this->getDataGenerator()->create_course();
        self::$courseid = $c->id;                // flaw 2
        $this->assertNotEmpty(self::$courseid);
    }

    public function test_b_uses_course(): void {
        $items = \local_readinglist\local\repository::get_for_course(self::$courseid);   // flaw 3
        $this->assertEmpty($items);
    }

    public function test_c_cache(): void {
        $cache = \cache::make('local_readinglist', 'courseitems');
        $cache->set(1, ['stale']);
        $this->assertSame(['stale'], $cache->get(1));   // flaw 4: leaks into other tests
    }

    public function test_d_time(): void {
        $item = $this->make_item();
        $this->assertSame(time(), (int) $item->timecreated);   // flaw 5
    }
}
```

Predict: for each of flaws 1-5, what failure appears and under what condition? Also: this plugin's upgrade step does `$dbman->add_field($table, $field);` without checking; what happens on a site that previously ran an early alpha with the column already present, and why does CI on a clean install never see it?

### Reveal (read after predicting)

1: the documentation lists `resetAfterTest` in a shared `setUp()` as banned; it hides which test modified data and resets after tests that did not need it. Call it in the test that changes data. 2 and 3: test order dependency; `test_b` depends on state from `test_a`, but each test starts from a fresh installation state, so `self::$courseid` points to a course that no longer exists (or is `null` when `test_b` runs alone with `--filter`). Run it alone to expose it. 4: an application cache entry persists between tests unless purged; another test reading `courseitems` for id 1 sees `['stale']`. Purge in the test or setUp for cache-using tests. 5: `time()` differs between creation and assertion at second boundaries: flaky once in a few hundred runs; assert a range or use a clock mock (`mock_clock_with_frozen()`, exists in `advanced_testcase`). For the upgrade: `add_field` on an existing column raises a DDL exception and the upgrade stops mid-step; the savepoint is not reached, so the site is left needing a manual fix; fresh installs run install.xml only, so clean CI never exercises the upgrade path. The guard `if (!$dbman->field_exists(...))` fixes it, and an upgrade test from the previous release is the only thing that would have caught it.

Systematic diagnosis for a flaky or order-dependent test: run it alone; run it with `--filter` in reverse and random order; search for static state, caches, time, files, global config; bisect by removing tests from the class; add a deterministic fixture; add an assertion that would fail loudly if state leaked.

## 11. Mastery gate

Pass = 80/100, no critical failure. Evidence: repository, CI run links or logs, upgrade logs from both starting versions, red-then-green demonstrations, debugging report, release checklist, a 10-minute defence where the reviewer picks two tests and asks you to break and fix each live. Critical failures: tests that pass with the security check removed; style violations suppressed to pass; upgrade step that fails on a pre-existing column or lacks a savepoint; reuse of a released version number; debug settings left enabled in committed config; core modified; test suite order-dependent. If failed: remedial exercise, 48 hours: take the three weakest tests, rewrite each so it is deterministic and demonstrably red under a seeded defect, then redo the upgrade-from-previous test on a fresh snapshot and write what each failure taught you, citing the documentation.
