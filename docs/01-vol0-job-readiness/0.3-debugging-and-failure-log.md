## 1. Engineering problem

A Moodle site reports that "some users" see a wrong grade total, "sometimes". A FastAPI service returns 500 for one customer on Tuesdays. A test passes on your laptop and fails in CI one run in four.

What goes wrong when engineers handle these poorly:

- **Shotgun debugging.** Change three things, rerun, see green, ship. Nobody knows which change mattered, or whether anything did. The bug returns under a different name.
- **Confirmation bias.** You form a theory in the first five minutes and then read every log line as support for it. The evidence that would refute it is on the screen and unseen.
- **Fixing the symptom.** A `try/except` that swallows the error, a retry that hides a race, a `round()` that hides a representation problem.
- **No memory.** You solve the same class of problem three times in one year because nothing was written down.
- **Debugging in production** by guesswork, because no one can reproduce the problem locally.

This lesson gives you a loop (observe, hypothesise, predict, test, conclude), a set of techniques for the hard cases (stack traces, intermittent failures, minimal reproductions, bisection, logging), and a habit: the failure log, a nine-field record that turns each bug into reusable experience. The practice target is a 72-line program with five planted defects. You will find them with method, not luck.

---

## 2. Learning objectives

By the end you will be able to:

1. Apply the hypothesis loop to a failing program: state at least two competing hypotheses, a prediction that would distinguish them, run the experiment, and record the result.
2. Read a Python traceback (including chained exceptions) and a PHP/Moodle exception trace, and identify the frame where the defect lives, which is often not the last frame.
3. Reproduce an intermittent failure deterministically by identifying its source of nondeterminism (hash seed, test order, clock, concurrency, external state) and controlling it.
4. Reduce a failing input to a minimal reproduction in under 15 minutes, using manual halving, and keep that reproduction as a test.
5. Choose among bisection over history (`git bisect`), over input (halving), and over configuration, and apply each.
6. Add logging that would have made a given bug diagnosable without a debugger, without logging secrets or personal data.
7. Write a failure log entry with all nine fields for each defect you fix, including the hypotheses you rejected and the time lost.

## 3. First-principles explanation

### 3.1 Debugging is hypothesis testing

A bug is a difference between what you believe the program does and what it does. Every debugging action is an experiment that narrows that difference.

```
 observe -> hypothesise -> predict -> experiment -> conclude
 (exact     (a cause that   (if H is true,  (one change or   (H survives or is
  symptom)   explains ALL    X will happen)  one observation)  rejected; record it)
             observations)
```

1. **State the symptom precisely, with the expected value derived independently of the program.** "Order A-100 (3 x 19.99) prints 59.94; I expect 59.97" is a symptom; "the total is wrong" is not.
2. **Hold at least two hypotheses.** One theory is a conclusion in disguise. Choose the experiment that distinguishes them, not the one that confirms your favourite.
3. **Predict before you run**, so a result can surprise you. That is how you find out you were wrong.
4. **Change one thing at a time,** or only observe. Two simultaneous changes make the outcome unattributable.
5. **Prefer observation to modification:** print, log, inspect, then edit.
6. **A fix is a failing test that now passes plus an explanation of why the old behaviour occurred.** "It stopped happening" is not a fix.
7. **Narrow the search space:** work backwards along the data flow from the symptom to the first place where a value is wrong although its inputs are right.

Failure modes of the method: anchoring on the first hypothesis; fixing the first anomaly you notice (it may be unrelated); trusting a mental model over a measurement; heisenbugs, where observing (a print, a debugger pause) changes timing and hides the bug.

### 3.2 Reading stack traces

A Python traceback lists frames oldest first; the exception type and message are at the bottom. From the lesson app (`python3 shop.py orders.json`, Python 3.13, paths shortened):

```
Traceback (most recent call last):
  File "shop.py", line 72, in <module>
    raise SystemExit(main(sys.argv))
  File "shop.py", line 66, in main
    for line in summarise(fh.read()):
  File "shop.py", line 57, in summarise
    for order in load_orders(text):
  File "shop.py", line 52, in load_orders
    return [parse_order(r) for r in json.loads(text)]
  File "shop.py", line 47, in parse_order
    lines = [(l["sku"], int(l["qty"]), l["price"]) for l in record["lines"]]
KeyError: 'lines'
```

Read it: (1) **bottom first**: `KeyError: 'lines'` means a lookup with key `'lines'` failed (the message is the key, not the dictionary); (2) the **last frame in your code** raised; (3) the traceback says where, **not which data**: you must obtain `record` by logging, `pdb`, or reading the input; (4) work upward: the defect is often one or two frames above, in the caller that did not validate or the producer of bad data; (5) if the last frames are in a library (Starlette, SQLAlchemy, Moodle core), find the last frame in *your* code; your call into the library is more likely wrong than the library.

Chained exceptions: "The above exception was the direct cause of the following exception" means `raise X from Y`; "During handling of the above exception, another exception occurred" means an error inside an `except` block. Read the first (root cause) before the last. Python 3.11+ also prints `ExceptionGroup` as a tree (checked on 3.13: an `ExceptionGroup` traceback prints as a tree of sub-exceptions; `asyncio.TaskGroup` raises these).

FastAPI: an unhandled exception in an endpoint becomes a generic HTTP 500; the traceback is in the **server** log (first question: where do logs go? Lesson 0.1). `HTTPException` is a deliberate response, not a crash. PHP/Moodle: an uncaught `Exception` prints its message and, depending on `$CFG->debug`, a trace with the innermost call first (`#0 /path/file.php(120): function()`); `$CFG->debug` and `$CFG->debugdisplay` are the settings (they appear in `config-dist.php`); see moodledev.io for the level constants in your version. `debugging('message', DEBUG_DEVELOPER)` emits developer notices and `error_log()` writes to the PHP log. Debug display stays off on shared or production sites: traces reveal paths and sometimes data.

### 3.3 Minimal reproduction

A minimal reproduction (MRE) is the smallest input and environment that still fails. It focuses reasoning, can be attached to a ticket, and becomes the regression test. Procedure (manual delta debugging): confirm the failure and write the command; remove half the input (records, config lines, request fields); if it still fails keep the smaller version, otherwise restore and remove the other half; repeat until removing anything makes the failure disappear (a 10,000-record file takes about 14 halvings); then simplify values and replace configuration and network calls with literals. State it in one sentence: "A record with no `lines` key crashes `summarise` with KeyError." For the lesson app, `[{"id":"x"}]` is the MRE for the traceback above.

### 3.4 Intermittent failures

An intermittent failure is a deterministic bug with a hidden input. Find the input, then control it.

| Source | Why it varies | How to control it |
|---|---|---|
| Hash randomisation | Python randomises `str` hashes per process, so iteration order of a `set` of strings differs between runs | `PYTHONHASHSEED=0..N` in a loop; make the code independent of set order |
| Test order / shared state | Module-level state, mutable defaults, caches, leftover database rows | Run the test alone, then after its predecessors; reverse or randomise order if your runner supports it (pytest: the `pytest-randomly` plugin shuffles order, and `-p no:randomly` disables it; both checked) |
| Time | Midnight, month end, timezone, DST, "now" read twice | Inject the clock; test boundary values |
| Randomness | `random`, UUIDs, shuffles | Seed it; log the seed on failure |
| Concurrency | Races, lock ordering, cancellation | Many iterations and threads, deliberate delays at suspected points, timestamped logs with thread ids; reason about shared mutable state |
| External state | Network, files, environment, database | Stub or record and replay; log inputs and environment |

**Repeat and count.** Run the failing test across controlled values of the hidden input and record outcomes per value. "Failed in 4 of 6 seeds" is evidence; "failed once yesterday" is not.

**How many passes prove a fix?** If an unfixed defect fails with probability p per run, it passes k consecutive runs with probability `(1-p)^k`. For p = 1/3, five passes give `(2/3)^5 = 0.13`: weak. For 95% confidence you need `(1-p)^k <= 0.05`, i.e. `k >= ln(0.05)/ln(1-p)`; p = 1/3 needs 8 passes, p = 1/10 needs 29, p = 1/20 needs 59. So remove the nondeterminism and verify by forcing every enumerable value of the hidden input, rather than rerunning until green.

Time as a hidden input (runnable, Python 3.12):

```python
from datetime import datetime

def daily_key(prefix, clock=datetime.now):
    return f"{prefix}-{clock():%Y-%m-%d}"

def start_and_end(prefix, clock=datetime.now):
    return daily_key(prefix, clock), daily_key(prefix, clock)   # "now" read twice

ticks = iter([datetime(2026, 1, 1, 23, 59, 59, 999_000), datetime(2026, 1, 2, 0, 0, 0, 1_000)])
print(start_and_end("job", lambda: next(ticks)))   # ('job-2026-01-01', 'job-2026-01-02')
```

With the real clock the keys differ only around midnight, so the bug appears "occasionally at night"; with an injected clock it appears every time. Fix: read the clock once and pass the value down.

### 3.5 Bisection, four ways

The idea is the same each time: find a predicate that splits the space into "still correct" and "already wrong", and apply it repeatedly. Over **history**: `git bisect run` (Lesson 0.2). Over **input**: halve it (3.3). Over **configuration or environment**: move setting groups from the working environment to the failing one until behaviour flips (`diff` of `env | sort` from both helps). Over a **code path**: check a known-good invariant at the midpoint of the data flow and recurse into the half where it first fails. The skill is choosing the predicate.

### 3.6 Logging for diagnosis

The standard library `logging` separates what happened (a log call with a level) from where it goes (handlers and formatters, configured once at the application entry point). Modules use `log = logging.getLogger(__name__)` and never configure handlers.

- **Levels:** DEBUG developer detail; INFO normal milestones; WARNING unexpected but handled; ERROR a failed operation; CRITICAL process-level failure. `log.exception("...")` inside an `except` block adds the traceback.
- **Pass values as arguments**, `log.info("loaded %d orders from %s", n, path)`; formatting is skipped when the level is disabled.
- **Log what makes a bug diagnosable:** the unit-of-work identifier (order id, request id), decisions at branches that matter, counts in and out, boundary inputs as sizes and identifiers rather than whole payloads. "bad record at index 2, id=A-102, keys=['id','tags']" turns the KeyError into a one-line diagnosis.
- **Never log** passwords, tokens, keys, full personal data (names with grades, emails), or payment details. In Moodle the privacy implications are real (follow your organisation's policy).
- **Correlation:** a per-request id attached to every log line lets you follow a request across components; how your team does it is a convention to discover.
- **Cost:** logging in hot loops can dominate runtime; measure (Lesson 4.4).

`breakpoint()` (Python 3.7+) opens `pdb` at that line; `python -m pdb script.py`; `pytest --pdb` stops at failures (the `--pdb` option is in `pytest --help`, checked on pytest 9.1). Debuggers are best for state you do not yet know to ask about; logs are best for production, races, and history. Use both.

### 3.7 The failure log

A failure log is a personal (or team) record of bugs you hit, written when you resolve them. It is how experience compounds: after twenty entries you recognise patterns ("another mutable default argument"), and you can answer interview and incident questions with specifics. It is blameless by design: it records mechanisms, not culprits, including your own wrong hypotheses.

**The nine fields:**

| # | Field | What to write |
|---|---|---|
| 1 | Symptom | Exact observable behaviour with command and output; no interpretation |
| 2 | Expectation | What should have happened and how you know (spec, derivation) |
| 3 | Evidence | Facts: outputs, traceback, MRE, logs, measurements |
| 4 | Hypotheses | Each theory with its experiment and result (rejected/confirmed) |
| 5 | Root cause | The mechanism in one or two sentences: why, not where |
| 6 | Fix | The minimal change and the regression test that proves it |
| 7 | How detected | Who or what found it, and how it escaped earlier |
| 8 | Prevention | A proportionate change that makes the class of bug harder (test, type, lint rule, convention, monitoring) |
| 9 | Time lost | Actual time and which step consumed it |

Template (one section per entry in `FAILURE_LOG.md`):

```
## FL-<n> <title>   (date, lesson)
1. Symptom:   2. Expectation:   3. Evidence:   4. Hypotheses (H -> experiment -> result):
5. Root cause:   6. Fix (+ test):   7. Detected / escaped:   8. Prevention:   9. Time lost:
```

Short entry (from Lesson 0.1):

```
## FL-1 Missing API_TOKEN breaks tests locally   (day one)
1. `make test` -> KeyError: 'API_TOKEN' at app/deps.py:5 in 3 tests.
2. All 6 tests pass, as in CI.
3. Traceback; ci.yml sets API_TOKEN: test-token; README silent.
4. H1 broken install -> `pip check` clean -> rejected. H2 variable unset locally -> `env | grep API` empty -> confirmed.
5. Code reads os.environ["API_TOKEN"] (required, no default); CI supplies it, my shell does not; undocumented.
6. Run with API_TOKEN=test-token; README line proposed in a separate PR after asking.
7. Found by running the baseline before changing code; escaped because CI hides the gap.
8. README line; clearer startup error (proposed to the team, not imposed).
9. 12 minutes, mostly reading wrong places before checking CI.
```

## 4. Worked example

The lesson application is `shop.py`. It summarises orders from a JSON file. **It is deliberately broken**: it contains five defects. Do not read the solutions file before your own attempt. The worked example below demonstrates the method on the first symptom using only information you can get by running the program, and stops before revealing the defect list.

Save as `shop.py`:

```python
"""shop.py - tiny order summariser. DELIBERATELY BROKEN (Lesson 0.3). Python 3.12+."""
from __future__ import annotations

import json
import logging
import sys
from dataclasses import dataclass, field

log = logging.getLogger("shop")

NOTES: dict[str, list[str]] = {}


@dataclass
class Order:
    order_id: str
    lines: list[tuple[str, int, str]]  # (sku, quantity, unit price as decimal string)
    tags: set[str] = field(default_factory=set)


def parse_price_cents(price: str) -> int:
    return int(float(price) * 100)


def order_total_cents(order: Order) -> int:
    return sum(qty * parse_price_cents(price) for _sku, qty, price in order.lines)


def primary_tag(order: Order) -> str:
    """The tag shown first on the packing slip."""
    return next(iter(order.tags), "none")


def add_note(order_id: str, note: str, notes: list[str] = []) -> list[str]:
    notes.append(f"{order_id}: {note}")
    NOTES[order_id] = notes
    return notes


def page(items: list, page_number: int, size: int) -> list:
    """Return the 1-based page_number-th page of items."""
    start = page_number * size
    return items[start : start + size]


def parse_order(record: dict) -> Order:
    lines = [(l["sku"], int(l["qty"]), l["price"]) for l in record["lines"]]
    return Order(record["id"], lines, set(record.get("tags", [])))


def load_orders(text: str) -> list[Order]:
    return [parse_order(r) for r in json.loads(text)]


def summarise(text: str) -> list[str]:
    out = []
    for order in load_orders(text):
        total = order_total_cents(order)
        out.append(f"{order.order_id} {total / 100:.2f} [{primary_tag(order)}]")
    return out


def main(argv: list[str]) -> int:
    logging.basicConfig(level=logging.INFO)
    with open(argv[1], encoding="utf-8") as fh:
        for line in summarise(fh.read()):
            print(line)
    return 0


if __name__ == "__main__":
    raise SystemExit(main(sys.argv))
```

Save as `test_shop.py`:

```python
import json
import unittest

import shop


class ShopTests(unittest.TestCase):
    def test_price_parsing(self):
        self.assertEqual(shop.parse_price_cents("19.99"), 1999)

    def test_total(self):
        o = shop.Order("X", [("pen", 3, "19.99"), ("ink", 1, "0.29")])
        self.assertEqual(shop.order_total_cents(o), 6026)

    def test_primary_tag_is_alphabetical_first(self):
        o = shop.Order("X", [], {"priority", "gift", "fragile"})
        self.assertEqual(shop.primary_tag(o), "fragile")

    def test_notes_are_per_order_first(self):
        self.assertEqual(shop.add_note("A", "call customer"), ["A: call customer"])

    def test_notes_are_per_order_second(self):
        self.assertEqual(shop.add_note("B", "leave at door"), ["B: leave at door"])

    def test_page_one_is_first_items(self):
        self.assertEqual(shop.page(list(range(10)), 1, 3), [0, 1, 2])

    def test_summarise_single_order(self):
        text = json.dumps([{"id": "A", "lines": [{"sku": "s", "qty": 1, "price": "1.00"}]}])
        self.assertEqual(shop.summarise(text), ["A 1.00 [none]"])


if __name__ == "__main__":
    unittest.main()
```

[
  {"id": "A-100", "lines": [{"sku": "pen", "qty": 3, "price": "19.99"}], "tags": ["priority", "gift", "fragile"]},
  {"id": "A-101", "lines": [{"sku": "ink", "qty": 1, "price": "0.29"}], "tags": ["gift"]},

### Step 0: Establish the baseline (Lesson 0.1)

```
python3 -m unittest -v 2>&1 | tail -20
```

Record: which tests fail, which pass. Run it twice, then run three times with `PYTHONHASHSEED=1`, `2`, `3`. Do the results differ between runs? (Predict first: how many tests do you expect to differ across seeds, and which?) The tests themselves may be wrong; tests are evidence, not authority. For each failing test, read the assertion and ask whether the expectation is right.

### Step 1: One symptom, full loop

Symptom: `test_price_parsing` fails. Write the observation exactly: `parse_price_cents("19.99")` returns a value that is not 1999. Find the value without editing the program:

```
python3 -c "import shop; print(shop.parse_price_cents('19.99'), repr(float('19.99')*100))"
```

Hypotheses:

- H1: the conversion goes through binary floating point; `19.99` is not exactly representable, `19.99*100` is slightly below 1999, and `int()` truncates toward zero.
- H2: the string has unexpected characters or the function is called with a different argument than the test passes.

Predictions: H1 predicts the printed float is just below 1999 (like `1998.9999999999998`) and the int is 1998. H2 predicts the float would not even be near 1999. Run the experiment; your output decides. Then test H1's wider prediction, which distinguishes it from "bad arithmetic only for 19.99": it predicts other prices also truncate down (try `0.29`, `0.58`, `1.15`, and measure rather than assuming which ones fail).

Conclude, but do not stop at the symptom: the root cause is a design problem (money handled as binary floating point then truncated), not a one-off bad number. A patch like `round(float(price) * 100)` makes today's values pass, but still uses binary floats for decimal quantities; the exact approach is to parse the decimal string without floats. Choosing between them is a judgement about the stated requirements (Lesson 0.4: ask what precision prices have). Record this in a failure log entry now, in the nine fields.

### Naive vs systematic

| Naive | Systematic |
|---|---|
| Change `int` to `round`, tests pass, move on | Ask why 19.99 fails, measure other prices, identify float truncation, decide the fix on requirements |
| Rerun until the flaky test passes | Loop over hash seeds, count failures, find the unordered `set` |
| "Works on my machine" | Record environment; control the hidden input |

### Step 2: Method for the rest

For each remaining failing test: baseline, exact symptom, two hypotheses, prediction, experiment, conclusion. Three more behaviours need special techniques:

1. A test that passes alone and fails in the suite: use test selection to find the interaction (`python3 -m unittest test_shop.ShopTests.test_notes_are_per_order_second` versus the full class), then look for state that survives between tests (module-level objects, default arguments).
2. A test that passes under some `PYTHONHASHSEED` values and fails under others: write the loop, count, then ask what in the failing function depends on hash order.
3. A crash on the command line (`python3 shop.py orders.json`): read the traceback bottom-up as in 3.2, find the data that triggered it, write the minimal reproduction by halving `orders.json`, and then decide what *correct behaviour* is for a malformed record. That is a requirements question, not a debugging question; write down your choice and the alternative you rejected.

A seed-sweep helper (prints one line per seed; count the outcomes yourself and keep the raw list):

```bash
for seed in $(seq 0 19); do
  if PYTHONHASHSEED=$seed python3 -m unittest test_shop.ShopTests.test_primary_tag_is_alphabetical_first >/dev/null 2>&1
  then echo "seed $seed: pass"; else echo "seed $seed: FAIL"; fi
done
```

## 5. Production perspective

- **Correctness.** Every fix ships with a regression test that fails before and passes after. For intermittent bugs the test must force the hidden input (the clock value, the seed, the order) so it fails every time without the fix.
- **Observability.** Production bugs are diagnosed from what you logged before they happened. Decide what you would need at 03:00 with no debugger: the identifier, the branch taken, counts, and the exception with traceback. Alerts should fire on symptoms users feel; logs explain them. (Operations tooling is Lesson 2.7.)
- **Security.** Logs are an attack surface and a privacy liability. Never log secrets; truncate or hash identifiers where policy requires; keep debug display off in production (Moodle: `$CFG->debugdisplay`, present in `config-dist.php`). A traceback shown to end users leaks paths and structure.
- **Failure handling.** Do not catch broad exceptions to make a symptom disappear. If you catch, either handle (with a defined behaviour), enrich and re-raise (`raise NewError(...) from exc`), or log with traceback and fail the unit of work explicitly. A swallowed exception is a bug with its evidence deleted.
- **Team practice.** Share minimal reproductions in tickets (Lesson 0.4). Treat "can't reproduce" as a request for more evidence on both sides, not as a verdict.

**Senior habits:** write the expected value before running anything; keep a running list of hypotheses; reduce the problem before reading deeply; bisect early; distrust a fix that was not preceded by a reproduction; check whether the same defect pattern exists elsewhere (`grep -rn "=\[\]"` for mutable defaults) and report it instead of silently refactoring; end by updating the failure log and, proportionately, adding a guard the team agrees to.

| Beginner mistake | Diagnosis |
|---|---|
| Editing before reproducing | Write the failing command first |
| Reading the traceback top-down | Start at the last line, then the last frame in your code |
| First plausible theory only | Write a contradicting hypothesis and the splitting experiment |
| Rerun until green | Count outcomes across controlled values of the hidden input |
| Print debugging that hides the bug | Timestamps, lower overhead, reason from ordering |
| Swallowing exceptions | Search for bare `except:` and `except Exception: pass` near the symptom |
| Editing a test to pass | Find the spec statement that makes the old assertion wrong, or do not edit |

## 6. Failure laboratory

Scenario. Your teammate reports: "`test_primary_tag_is_alphabetical_first` failed in CI, so I reran it three times locally and it passed all three, so it is a CI flake; I added `@unittest.skipIf(os.environ.get('CI'), 'flaky')` and merged." Assume `Order.tags` is a `set` of three strings, and that the first element returned by iterating it depends on the process's hash seed.

**Predict** (write answers down before reading on): (1) If the true failure probability per run is 2/3 (a rough guess from seeds 2, 3, 5, 6 failing and 1, 4 passing in a six-seed sample on one machine, not a measurement), what is the chance three local reruns all pass by luck? (2) What does CI have that the laptop lacks, relevant to this test? (3) What is wrong with the chosen fix beyond the probability? (4) Which command would have produced a deterministic local failure?

### Reveal (read after predicting)

1. Pass probability is 1/3 per run, so three passes have probability (1/3)^3 = 1/27, about 3.7%. The estimate is itself shaky (six seeds), which is the point: if the real failure probability were 1/3, three passes would be (2/3)^3 = 30% likely. The teammate's observation cannot distinguish the two, so reruns are the wrong instrument; controlled seeds are the right one.
2. Nothing. Hash randomisation applies to every process unless `PYTHONHASHSEED` is set, so the laptop fails at the same rate (check `env | grep PYTHONHASHSEED`). "CI differs" was a hypothesis, never tested.
3. The fix leaves the defect live in production code (the packing slip prints a random tag) and removes the test's protection in CI. The test found a real bug and was treated as the problem; "flaky" was concluded, not demonstrated.
4. `for s in $(seq 0 19); do PYTHONHASHSEED=$s python3 -m unittest test_shop.ShopTests.test_primary_tag_is_alphabetical_first >/dev/null 2>&1 || echo "seed $s fails"; done` lists failing seeds; any one of them reproduces on demand (which seeds fail depends on the Python version, so measure).

Diagnosis procedure for "flaky": never conclude it from reruns; enumerate hidden inputs (3.4); control one at a time and count outcomes; find the value that makes failure deterministic; find the code that depends on it; fix the code, or fix the expectation with a stated requirement; verify across every enumerable value.

## 7. Retrieval practice

Closed-book; answers in the solutions file.

1. Why write the expected value before running the program? Give a concrete way it protects you.
2. In a Python traceback, which line do you read first, and which frame usually holds the defect?
3. How do "direct cause" and "during handling" chained-exception messages differ?
4. `def f(x, acc=[]): acc.append(x); return acc`. What do `f(1)` then `f(2)` return in one process, and why?
5. `s = {"b", "a", "c"}; print(next(iter(s)))` in three separate processes: guaranteed the same? What controls it?
6. A test fails in the full suite but passes alone. Give three causes with one experiment each.
7. A defect fails a test with probability 1/10 per run. How many consecutive passes give about 95% confidence a fix worked? Show the calculation.

## 8. Independent implementation challenge

**Mode A.** Time box: 60 minutes. Write `repro_tools.py` (stdlib only) with unittest tests:

1. `seed_sweep(test_id: str, seeds: range, cwd: Path, timeout: float = 30.0) -> dict[int, str]`: runs `python3 -m unittest <test_id>` as a subprocess per `PYTHONHASHSEED` (set in the child's environment only; never mutate `os.environ`), using `subprocess.run` with a list of arguments (no shell). The value is `"pass"`, `"fail"`, or `"timeout"`; a timeout is a distinct third outcome.
2. `halve(items: list, fails: Callable[[list], bool]) -> list`: given `fails(items)` true, return a smaller list for which it is still true, trying halves first, then dropping single elements. Deterministic; never returns a list for which `fails` is false; state your worst-case call-count bound. Document the behaviour for an empty list.

Tests: a toy predicate ("contains a dict without key `'lines'`"); a predicate needing two elements together (so single removal alone cannot minimise it); a timeout case; the shop test via a generated test file in a temp directory. Done when tests pass and you can explain why `halve` yields a locally minimal result, not necessarily the smallest.

Checklist: each root cause is stated as a mechanism ("float truncation toward zero of a non-exact binary value"), not a location; every "fails before" claim was run against the original code; regression tests assert the spec, not the implementation; seed sweeps cover at least 50 seeds before and after; no exception swallowed; messages carry the order id and no payloads; `diff -u` against the original shows no unrelated change; no test weakened.

## 11. Mastery gate

Pass = 80/100 and no critical failure. Critical failures: (1) an intermittent defect declared fixed without a controlled sweep; (2) a regression test that passes against the original code; (3) a swallowed exception or weakened assertion used to get green; (4) a log entry with no hypotheses, or a root cause given as a line number; (5) AI or web search used in the diagnosis phase for these bugs.

Evidence: the repository with before/after sweeps; five log entries; the report; a 20-minute live defence on a new broken 40-line program (different defects, same classes) applying the loop aloud: symptom, two hypotheses, predictions, experiments, conclusion.

If failed: a fresh small program with three planted defects (one nondeterministic, one state leak, one data-dependent crash); 90 minutes, notes allowed; deliver a log entry, minimal reproduction, and fix test for each. Repeat with new programs until two of three are root-caused on the first attempt.
