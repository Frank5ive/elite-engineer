## 1. Engineering problem

Wednesday of week one. You have two days of work on a branch in 11 commits titled "wip", "fix", "fix2", one of which accidentally includes a 3 MB log file. A colleague merged into `main` an hour ago and touched the same function as you. You run `git pull`, an editor opens for a merge commit you did not intend, 14 files are in conflict, and you run `git reset --hard origin/main` to "start clean". Two days of uncommitted edits in one file vanish.

Poor Git handling fails in specific, expensive ways: lost work (discarding commands used without knowing which state they destroy); unreviewable pull requests (reformatting and "wip" commits make a 60-line fix look like 900 lines, so reviewers skim and defects pass); broken shared history (force-pushing a branch others built on, committing secrets); slow diagnosis (no `bisect`, `log -S`, or `blame`, so a regression costs a day instead of ten minutes); and fear, which leads to avoiding experiments. The skill is a correct mental model of what Git stores and which command moves which pointer, so every mistake is recoverable and every command predictable.

## 3. First-principles explanation

### 3.1 What Git stores

Git is a content-addressed object database plus a set of movable pointers.

- A **blob** is file content. A **tree** is a directory listing of blobs and trees. A **commit** points to one tree, to zero or more parent commits, and carries an author, a date, and a message. Each object is named by a hash of its content, so a commit's identity depends on its entire ancestry: changing any ancestor yields different hashes for every descendant. This is why rebasing "rewrites history": it creates new commits with new hashes.
- A **branch** is a name pointing at a commit; making a commit moves the current branch's pointer forward. `HEAD` says which branch (or, when detached, which commit) you are on.
- A **tag** is a name that normally never moves.
- The **reflog** is a local, per-reference log of where each pointer used to point. It is not pushed. It is what makes most mistakes reversible.

```
 working tree  --git add-->  index (staging)  --git commit-->  repository (commits)
      ^                           |                                  |
      +------ git restore --------+<------ git restore --staged -----+
      +-------------- git switch / checkout <-- (moves HEAD, updates both) --------+
```

Three areas, hence three kinds of diff:

| Command | Compares |
|---|---|
| `git diff` | working tree vs index (unstaged changes) |
| `git diff --staged` (alias `--cached`) | index vs HEAD (what the next commit will contain) |
| `git diff HEAD` | working tree vs HEAD (everything uncommitted, to tracked files) |
| `git diff A..B` | tree at A vs tree at B |
| `git diff A...B` | merge-base of A and B vs B (what B added since diverging; this is what a PR shows) |

Untracked files appear in none of these; `git status` lists them.

### 3.2 Staging and commits

The index exists so that you can commit part of your work. `git add -p` walks through hunks (`y` stage, `n` skip, `s` split, `e` edit). Use it to turn a mixed working tree into separate logical commits. Always check `git diff --staged` before committing: it is the commit you are about to make.

An **atomic commit** has one purpose, builds and passes tests on its own, and can be reverted without side effects. Why it matters in production: `git revert`, `git bisect`, `git blame`, and code review all operate on commits. A commit containing a feature, a reformat, and a dependency bump cannot be reverted for just one of them.

Messages: a short imperative subject (commonly kept under about 50-72 characters), a blank line, and a body that says what and why, not how (the diff shows how). `Conventional Commits` prefixes (`fix:`, `feat:`) are a convention, used only if the team uses it. **Discover the local style before writing your first message:** `git log --oneline -30` and `git log -5` (full messages), and check for `CONTRIBUTING`, a commit template (`git config commit.template`), or commit hooks (`.git/hooks`, `.pre-commit-config.yaml`).

### 3.3 Branching and integrating: merge vs rebase

Two lines have diverged. There are three ways to combine them.

```
before:        A---B---C   main            after merge:    A---B---C-------M   main
                    \                                           \         /
                     D---E feature                               D---E---+

                                           after rebase:   A---B---C---D'---E'   feature (new hashes)
```

| | Merge | Rebase | Squash-merge |
|---|---|---|---|
| Effect | New commit with two parents; history preserved | Replays your commits onto a new base; new hashes | Collapses the branch into one new commit on the target |
| History shape | Non-linear, honest | Linear, rewritten | Linear, one commit per PR |
| Conflicts | Resolved once | May recur per commit replayed | Resolved once (at merge time) |
| Risk | Noisy history | Rewrites commits: dangerous if others built on them | Loses internal commit granularity |

Rules that hold regardless of preference:

- **Do not rewrite history that others have based work on.** Rebase your own unshared or personal branches; do not rebase `main` or a branch a colleague has checked out.
- After rebasing a branch you have already pushed, the remote rejects a normal push. Use `git push --force-with-lease`, which refuses if the remote has commits you have not seen, rather than `--force`, which overwrites blindly. Even this is only appropriate on your own branch.
- Which strategy the team uses (merge commits, squash, rebase-and-merge) is a repository setting and a team decision. Ask; do not guess. Opinion: for personal feature branches, rebasing onto the latest `main` before opening the PR keeps the PR diff clean; but if the team squash-merges, the internal history of your branch is discarded anyway and tidying commits matters less than a clear PR description.

### 3.4 Conflicts

A conflict occurs when two changes touch the same lines (or one deletes what the other edits) and Git cannot decide. Git marks the file:

```
<<<<<<< HEAD
timeout = 45
=======
timeout = 60
>>>>>>> cf68175 (feat: raise timeout to 60)
```

The labels are the trap. In a **merge**, `HEAD`/ours is the branch you are on and theirs is the branch being merged in. In a **rebase**, Git is replaying your commits onto the target, so `HEAD`/ours is the *target* (the upstream you are rebasing onto) and theirs is *your own commit being replayed*. The meaning inverts. Resolve by understanding the intent of both changes, not by picking a side.

Procedure:

1. `git status` shows `both modified` (UU) files; `git diff` shows the conflict hunks.
2. Read `git log --merge -p -- <file>` (or `git log main..feature -- <file>`) to learn what each side was trying to do.
3. Edit the file to the correct final content; remove all markers (`grep -n '<<<<<<<\|>>>>>>>' file`).
4. `git add <file>`; then `git merge --continue` or `git rebase --continue`.
5. **Run the tests.** A textually clean merge can still be semantically wrong, and a hand-resolved conflict can be wrong while the file looks tidy.
6. To bail out at any time: `git merge --abort` or `git rebase --abort` returns you to the state before you started.

Setting `git config merge.conflictStyle zdiff3` (Git 2.35+; use `diff3` on older versions; an unknown value is rejected with `unknown style`, checked) additionally shows the common ancestor in the markers, which often makes the intent obvious. It changes your own configuration only, so it is safe even on a team repository.

### 3.5 Searching history

`git blame -L 40,60 -w file` (who last touched these lines; `-w` ignores whitespace; the last touch is often a reformat, so read the commit, do not judge a person); `git log -S"retries" --oneline -- path` (pickaxe: commits that changed the count of an occurrence); `git log -G"timeout\s*=" --oneline` (regex); `git log --follow -p -- file` (through renames); `git log --oneline main..HEAD` (on my branch, not on main); `git reflog` (where my pointers have been).

### 3.6 Bisect

When you know a good commit and a bad commit, binary search finds the first bad one in about log2(N) steps (1,000 commits take about 10 steps).

```
git bisect start
git bisect bad                 # current commit is bad
git bisect good <hash-or-tag>  # a known good commit
# Git checks out the midpoint; test it, then mark: git bisect good | bad | skip
git bisect reset               # when done: return to where you started
```

Automate with a check script: `git bisect run ./check.sh`. Exit code 0 means good; 1-127 except 125 means bad; 125 means "cannot test this commit, skip it" (for example it does not build); an exit code above 127 aborts the bisection. Requirements for trustworthy results: the check must be deterministic, must test the symptom and nothing else, and must not live inside the tracked tree where bisect will overwrite or remove it (copy it outside the repository). Bisect fails when the test is flaky (Lesson 0.3), when the history has many unbuildable commits (use skip), or when two independent bugs exist.

### 3.7 Recovery

The recovery model: **committed work is recoverable; unstaged work is not.**

| State when you run a destructive command | Recoverable? | How |
|---|---|---|
| Committed (any branch, even deleted, even after reset) | Yes, typically for weeks | `git reflog`, then `git branch rescue <hash>` |
| Staged (`git add` done) but not committed | Usually | Blob remains as a dangling object: `git fsck --lost-found` (not guaranteed after `git gc`) |
| Modified but never staged or committed | **No** | Gone. Git never saw it |
| Untracked files | Not touched by `reset --hard`; **deleted** by `git clean` | n/a |

The reflog keeps entries for a limited time (defaults are about 90 days for reachable entries and 30 days for unreachable ones; `gc.reflogExpire` is 90 days and `gc.reflogExpireUnreachable` is 30 days per `git help gc`, checked on 2.47.3). It is local: a fresh clone has none of your history of mistakes.

Common recoveries:

| Mistake | Fix |
|---|---|
| Last commit message wrong or file forgotten, not yet pushed | `git commit --amend` |
| Committed to `main` by mistake, not pushed | `git branch feature` (keep the commits), then `git reset --hard origin/main` (while on `main`; check `git status` is clean first) |
| Undo last commit, keep the changes | `git reset --soft HEAD~1` (keeps staged); `git reset HEAD~1` (mixed, keeps unstaged) |
| Wrong `reset --hard` | `git reflog`, then `git reset --hard 'HEAD@{1}'` or `git branch rescue <hash>` |
| Deleted branch | `git reflog`, then `git branch name <hash>` |
| Detached HEAD with work you want | `git switch -c new-branch` |
| Bad commit already pushed and shared | `git revert <hash>` (new commit that undoes it; safe for shared history). For a merge commit: `git revert -m 1 <merge-hash>` (`-m 1` keeps the first parent, usually the target branch) |
| Staged the wrong file | `git restore --staged file` |
| Discard unstaged edits to one file (destructive) | `git restore file` |
| Committed a secret | Treat as compromised: rotate it first. Removing it from history (a rewrite plus force-push, or specialised tools) is secondary, needs team coordination, and does not undo anyone who already fetched it. Escalate per team policy |

### 3.8 Stash

`git stash push -m "msg"` shelves tracked changes (`-u` adds untracked); `git stash pop` applies and drops, `git stash apply` keeps. Stashes are easy to forget; for anything you keep over a day, prefer a WIP commit on a branch.

### 3.9 Pull request hygiene

A pull request is a unit of review. A reviewer should be able to say "yes" or ask a precise question within minutes. That requires:

- **One purpose.** If the title needs "and", consider two PRs.
- **Small.** Review quality drops as size grows; as a rule of thumb (opinion, not measurement), aim for a diff a reviewer can read in under 30 minutes, and agree on the team's norm.
- **No noise.** No reformatting of untouched lines, no editor config files, no `.env`, no logs, no compiled artefacts. Check with `git diff --stat main...HEAD` and `git status` before pushing; open the diff in the PR interface and read it as the reviewer will.
- **Green.** Run the project's checks locally (the commands you found in Lesson 0.1).
- **Commits that tell a story, or a clear squash.** Use `git commit --fixup <hash>` then `git rebase -i --autosquash <base>` to fold corrections into the commit they belong to.
- **Description.** What, why, how verified, what to look at, risks. Template and rubric in Lesson 0.4.
- **Convention first.** Branch names, PR title format, linked ticket ids, required reviewers, and draft-PR etiquette are team decisions. Discover by reading the last five merged PRs and `CONTRIBUTING`; ask once if unclear.

### 3.10 Failure modes

Rebasing a shared branch; `pull` creating accidental merges (`git fetch` and inspect first, or `git pull --rebase`; the default is a team and personal choice); committing generated files; `git add .` staging things you did not intend (prefer `git add -p` or explicit paths, and read `git status`); long-lived branches that diverge until merging hurts; treating `--force` as normal.

## 4. Worked example

Everything happens in a scratch repository. Never practise destructive commands in a work repository. Set a safe environment first (so a typo cannot touch your real configuration or repositories):

```
export LAB=$HOME/git-lab && mkdir -p $LAB && cd $LAB
```

### Lab 0: build the scratch repository (script tested with Git 2.47.3)

Save as `mk_lab.sh`. It creates 12 commits in which commit 7 silently breaks `check.sh`.

```bash
#!/usr/bin/env bash
# Builds $LAB/scratch with 12 commits; commit 7 silently breaks check.sh.
set -euo pipefail
LAB="${1:-$HOME/git-lab}"
rm -rf "$LAB/scratch" && mkdir -p "$LAB/scratch" && cd "$LAB/scratch"
git init -q -b main
git config user.name "Lab User" && git config user.email "lab@example.invalid"
cat > calc.sh <<'EOS'
#!/usr/bin/env bash
# usage: calc.sh a b  -> prints a+b
echo $(( $1 + $2 ))
EOS
cat > check.sh <<'EOS'
#!/usr/bin/env bash
# exit 0 = good, 1 = bad
[ "$(bash ./calc.sh 2 3)" = "5" ]
EOS
chmod +x calc.sh check.sh
git add . && git commit -q -m "feat: add calc.sh and check.sh"
for i in 2 3 4 5 6; do echo "# change $i" >> calc.sh; git commit -qam "chore: touch calc ($i)"; done
sed -i 's/\$1 + \$2/$1 - $2/' calc.sh
git commit -qam "refactor: simplify arithmetic expression"
for i in 8 9 10 11 12; do echo "# change $i" >> calc.sh; git commit -qam "chore: touch calc ($i)"; done
git log --oneline | cat
```

The `rm -rf` targets only `$LAB/scratch`; read any script that deletes before you run it.

### Lab 1: states, diffs, partial staging

```
cd $LAB/scratch
echo "echo done" >> calc.sh          # edit 1
echo "# TODO later" >> check.sh      # edit 2 (unrelated)
git status -s ; git diff ; git diff --staged
git add -p calc.sh                   # stage hunk, check diff --staged, commit
git diff --staged
git commit -m "feat: print done after calculation"
git restore check.sh                 # discards edit 2 (unstaged work is not recoverable)
```

Observe after each command which of `git diff`, `git diff --staged`, `git diff HEAD` is non-empty and why. Predict first; then check.

### Lab 2: a conflict, by rebase (tested)

```
mkdir $LAB/conflict && cd $LAB/conflict && git init -q -b main
git config user.name L && git config user.email l@example.invalid
printf 'timeout = 30\nretries = 3\nmode = fast\n' > settings.ini && git add . && git commit -qm "base"
git switch -c feature/timeout
sed -i 's/timeout = 30/timeout = 60/' settings.ini && git commit -qam "feat: raise timeout to 60"
git switch main
sed -i 's/timeout = 30/timeout = 45/' settings.ini && git commit -qam "fix: set timeout to 45"
git switch feature/timeout
git rebase main                       # stops with a conflict
git status -sb ; cat settings.ini     # note: HEAD side shows 45 (main), the replayed commit shows 60
```

Decide the correct value by reading both commit messages (a real engineer would ask the author of the 45 change). Suppose 60 is intended; write the final file, then:

```
git add settings.ini && git rebase --continue    # an editor may open; accept the message
git log --oneline --graph --all
```

Reasoning for each step: `rebase` replays "raise timeout to 60" on top of main's new commit; Git cannot apply it cleanly because the line it expected (`timeout = 30`) no longer exists; the marker's `HEAD` side is main's version because during a rebase the checked-out state is the target being built on. Repeat the whole lab with `git merge main` instead of rebase and note that the labels now mean the opposite.

### Lab 3: recovery drill (tested)

```
mkdir $LAB/rescue && cd $LAB/rescue && git init -q -b main
git config user.name L && git config user.email l@example.invalid
echo a > a.txt && echo b > b.txt && git add . && git commit -qm base
git switch -c feature
echo a2 >> a.txt && git commit -qam "feat 1"
echo a3 >> a.txt && git commit -qam "feat 2"
echo b2 >> b.txt && git add b.txt        # staged, never committed
echo c > untracked.txt                    # untracked
echo a4 >> a.txt                          # modified, unstaged
git reset --hard main                     # the "start clean" mistake
```

Predict: which of "feat 1", "feat 2", the `b2` line, `untracked.txt`, the `a4` line survive? Then check: `ls`, `git status -s`, `git reflog`, `git fsck --lost-found`. Recover the commits with `git branch rescue 'HEAD@{1}'` and inspect `git log --oneline rescue`. Outcome when I ran it: both commits recovered via reflog; `untracked.txt` untouched; the staged `b2` line survives only as a dangling blob (`git fsck --lost-found` lists it; `git show <blob-hash>` prints `b` and `b2`); the `a4` line is gone for good.

### Lab 4: bisect (tested)

```
cd $LAB/scratch
cp check.sh /tmp/check_outside.sh     # keep the oracle outside the tracked tree, which bisect rewrites
git bisect start HEAD $(git rev-list --max-parents=0 HEAD)    # bad = HEAD, good = root commit
git bisect run bash /tmp/check_outside.sh
git bisect reset
```

The check script runs `bash ./calc.sh 2 3` in the current directory, which bisect has checked out at each step. The run ends with "bisect found first bad commit" and shows "refactor: simplify arithmetic expression" (the 7th commit) after about 4 steps instead of 11. Naive alternative: test each commit by hand, linear in history length. Improvement: logarithmic, scripted, and therefore repeatable and attachable to a bug report.

### Lab 5: tidy a branch with autosquash (tested)

```
cd $LAB/scratch && git switch -c tidy main
echo x > a.txt && git add a.txt && git commit -qm "feat: a"
echo y >> a.txt && git commit -qam "temp"
git commit --amend -qm "fixup! feat: a"            # in real use: git commit --fixup <hash> writes this message for you
GIT_SEQUENCE_EDITOR=true git rebase -q -i --autosquash main
git log --oneline | head -3                         # the fixup is folded into "feat: a"
```

`--autosquash` reorders and folds commits whose subject starts with `fixup!` into their target. `GIT_SEQUENCE_EDITOR=true` accepts the generated todo list non-interactively for the lab; normally the editor opens so you can review it.

## 5. Production perspective

- **Correctness:** run tests after every conflict resolution and rebase; a clean rebase can still break behaviour because the base changed.
- **Security:** check `git diff --staged` for secrets and `.env` before every commit. If a secret reaches a remote, rotating it is the fix and history editing is cleanup. Do not commit data dumps (a Moodle database dump contains personal data).
- **Failure handling:** before any destructive command, `git status` and `git stash list`; when unsure, `git branch backup-$(date +%Y%m%d-%H%M)`. A branch costs nothing.
- **Operations:** tags and release branches may drive deployment; never move or delete them. Protected branches reject force-pushes. `ASSUMPTION:` your team uses pull requests; if it uses patches or trunk commits, the local mechanics are the same.
- **Testing:** bisect makes a regression test the search oracle.

**Senior habits:** backup branch before risk; `git status` before and after each command; commit early locally and tidy later; small PRs; `--force-with-lease` only on own branch; read `git log` and recent merged PRs before writing a message; ask the author when conflict intent is unclear; never `git add .` unread.

| Mistake | Diagnosis and fix |
|---|---|
| Working on `main` | `git branch --show-current`; branch, then repair `main` (3.7) |
| `git add .` pulled in junk | `git diff --stat main...HEAD`; `git restore --staged <file>` |
| Conflict markers committed | `git grep -n '^<<<<<<<'` before committing |
| Pull made a merge commit | `git reflog`; `git reset --hard 'HEAD@{1}'` if nothing else happened since |
| Detached HEAD | `git switch -c name` to keep work, else `git switch -` |
| Rebase "ate" a commit | `git reflog`; the old tip is still there |

## 6. Failure laboratory

Scenario (this is Lab 3 in disguise, with a twist). A colleague tells you: "Don't worry, Git never loses anything. I ran `git reset --hard origin/main` and recovered everything from the reflog." Before they ran it, their state was: two local commits on `feature` not pushed; one file with unsaved-to-Git edits that they had staged with `git add`; another file edited but never staged; and a new untracked file. They ran the reset, then `git clean -fd` "to tidy up".

**Predict** for each of the five items (two commits, staged edit, unstaged edit, untracked file): is it recoverable, and how? Write your answers before reading on.

### Reveal (read after predicting)

- Two commits: recoverable through the reflog (`git reflog`, then `git branch rescue <hash>`), as long as they are within the reflog expiry window and nobody ran `git gc --prune=now`.
- Staged edit: probably recoverable as a dangling blob (`git fsck --lost-found`; look for the content with `git show <hash>`), though not through the reflog, since it was never in a commit. Not guaranteed after garbage collection.
- Unstaged edit: gone. The colleague's claim "Git never loses anything" is false for this state.
- Untracked file: `reset --hard` leaves untracked files alone, but `git clean -fd` deletes them, and they were never in Git, so they are gone (OS-level undelete is outside Git).

Diagnosis procedure when you think something is lost:
1. **Stop.** Do not run `git gc`, `git clean`, or more resets.
2. `git reflog` (HEAD) and `git reflog show <branch>`: find the last good commit.
3. `git branch rescue <hash>` to pin it, then inspect with `git log` and `git diff`.
4. For content never committed: `git fsck --lost-found`; inspect dangling commits and blobs with `git show`.
5. Check non-Git sources: editor local history/swap files, IDE local history, backups.
6. Record the failure (Lesson 0.3's log) with the state table above.

The general rule to carry: reflog protects *commits*. Frequent local WIP commits are the cheapest insurance, because you can squash them later.

| 2. Context | Your first week will include a Git mistake, yours or a colleague's. A tested runbook makes it a ten-minute event. Team conventions are unknown, so the project makes you discover them in a real or public repository. |
| 3. Requirements | (a) 8 scripts `drills/drillN-<name>.sh`, each creating the broken state in a fresh scratch repo: wrong-branch commit; `reset --hard` of two commits; deleted branch; bad merge needing `revert -m 1`; detached HEAD with new commits; rebase gone wrong; secret committed locally (not pushed); `git add .` of an unwanted file. (b) `RUNBOOK.md`: per drill, symptoms, diagnosis, recovery, verification command, what is NOT recoverable, when to escalate. (c) `cleanup.sh` generating a messy branch (8+ commits, one formatting-only change, one accidentally committed log file) and a clean branch of 3-4 logical commits. (d) `CONVENTIONS.md`: commit, branch, and PR conventions discovered in one real repository, each with evidence (log lines, CONTRIBUTING text). |
| 4. Constraints | Scratch repositories only. Scripts are idempotent, use `set -euo pipefail`, set a local `user.name`/`user.email` with an `example.invalid` address, never touch global Git config, and `rm -rf` only a path they created. |
| 5. Acceptance criteria | Each drill ends by printing the broken state; following only the runbook restores it and the verification command exits 0. `git diff --exit-code messy clean` is empty; `git log --oneline main..clean` shows 3-4 commits that each build; the log file and formatting noise are absent or isolated in their own justified commit. |
| 6. Edge cases | Branch names with slashes; file names with spaces; a rebase that conflicts on the second of three commits; a stash present during recovery; expired reflog (what then?); the bad state already pushed (revert, not reset). |
| 7. Quality requirements | Every runbook command is copy-pasteable and was run by you; every destructive command is preceded by a safety branch or `git status` check; no GUI steps. |
| 8. Deliverables | `drills/*.sh`, `RUNBOOK.md`, `CONVENTIONS.md`, `cleanup.sh`, a transcript of one drill from break to verified recovery, a failure log entry (Lesson 0.3). |
| 9. Difficulty | Intermediate. |
| 10. Estimated effort | 6-9 hours including debugging the scripts (idempotence and quoting take longer than expected). |
| 11. Progressive hints | L1: perform the recovery by hand once, then script the break. L2: write each drill's verification first (for example `git rev-parse feature` equals a saved hash). L3: for cleanup, `git reset --soft main` then `git add -p` per logical commit is an alternative to interactive rebase; compare what each preserves. L4: prove equal trees with `git diff --exit-code messy clean` or compare `git rev-parse messy^{tree} clean^{tree}`. |
| 12. Evaluation rubric (100) | Drills reproduce states and are idempotent 20; runbook accuracy (a reviewer follows it blind) 25; honesty about unrecoverable states 10; cleanup with proven identical tree and logical commits 20; conventions discovery with evidence 10; script safety 10; commit message quality 5. |
| 13. Extension challenge | A drill for `git rebase --onto` (branch created from the wrong base), and one for a dropped stash (`git fsck --unreachable --no-reflogs` lists the dropped stash commit among unreachable commits; `git stash apply <hash>` restores it; checked on Git 2.47.3). |
| 14. Reflection questions | Which drill exposed a wrong mental model? Which recovery depended on a time window? What workflow change makes the mistake less likely? What is the team's merge strategy and how did it change how you tidy commits? |

## 10. Engineering review

Checklist: every destructive command has a safety net; every "recoverable" claim was demonstrated, not assumed; scripts never reach outside the lab directory (run one from a different working directory and from a path with a space); commit messages explain why; the cleaned branch builds at each commit (`git rebase -x "./check.sh" main` runs a command after each replayed commit; checked on Git 2.47.3: the rebase succeeded when the command exited 0); the runbook names the tested Git version; no secrets in fixtures.

Explain your decisions: rebase or soft-reset for the cleanup, and what changes if the team squash-merges; why `--force-with-lease`; which drill a stressed colleague would most likely get wrong, and how you would simplify it; what you chose not to automate.

## 11. Mastery gate

Pass = 80/100 and no critical failure. Critical failures: (1) a script that can delete or modify anything outside its scratch directory; (2) a runbook step that fails when followed or silently loses work; (3) claiming an unrecoverable state (unstaged edits) is recoverable; (4) force-pushing or rewriting shared history anywhere in the transcript; (5) a cleaned branch whose tree differs without an explicit justification.

Evidence: scripts, transcripts, and a live 15-minute demonstration: given a scratch repository in an unknown broken state, diagnose and recover it, narrating the reflog evidence.

If failed: a reviewer produces three broken states you have not seen (a lost stash, a rebase that dropped a commit, a wrongly reverted merge). You get 30 minutes with notes, must recover all three, and write a one-line runbook entry for each. Repeat with new states.
