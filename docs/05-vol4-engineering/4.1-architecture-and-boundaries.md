## 1. Engineering problem

You join a team that owns a FastAPI service issuing course-completion certificates. File `certificates.py` is 1,400 lines: HTTP handlers, SQLAlchemy queries, a `requests` call to the Moodle web service, PDF generation, and the rule "issue only if all mandatory activities are complete and the course is not archived". The nightly batch job re-implements that rule and forgets the archived check.

Three things go wrong, and this lesson exists to prevent them.

1. **Change amplification.** "Allow archived-course certificates with an admin override" means editing the handler, the batch job, two queries and a response parser. A one-line business change costs a week.
2. **Untestable core.** Testing the rule needs a database and a mocked `requests`; tests take minutes, people stop running them, and the batch bug survives.
3. **Blast radius.** When Moodle is slow, every handler hangs, including the health check, because they share a pool and a client with no timeout (4.3 covers the reliability half).

Architecture is the set of decisions that are expensive to change. You will learn to separate the expensive decisions (database, framework, remote system) from the valuable ones (business rules), to recognize when that separation is worth its cost, and to record why. You will also learn to refuse layers a 300-line service does not need.

## 2. Learning objectives

By the end of this lesson you can:

1. Given a module, identify its responsibilities and rate its cohesion and its efferent/afferent coupling, naming the specific imports or call sites that justify your rating.
2. Refactor a class hierarchy that uses inheritance for code reuse into composition with an injected collaborator, and write a test that fails on the inheritance version and passes on the composed version.
3. Design a port (Protocol in Python, interface in PHP) owned by the consumer, write two adapters (in-memory and one real-shaped), and show with a test that the domain code runs with neither a database nor a network.
4. Model a small domain with at least one entity, one value object, and one aggregate root whose invariants cannot be violated through its public API, and write tests that attempt to violate each invariant.
5. Write an automated architecture fitness test (import-direction check) that fails when a forbidden dependency is introduced.
6. Evolve an event/message schema across two versions without breaking old producers or consumers, and demonstrate it with tests using stored v1 payloads.
7. Write an ADR that states context, options considered, decision, and consequences, including the costs you are knowingly accepting; and name two situations where a given pattern is ceremony and should not be used.

## 3. First-principles explanation

### 3.1 Cohesion and coupling

**Cohesion**: how strongly the parts of a module belong together (change for the same reason, use the same data, serve one purpose). **Coupling**: how much one module must know about another to function. Aim for high cohesion inside boundaries and low, explicit, narrow coupling across them. Why: the cost of change is dominated by how many places must change together and how much you must hold in your head.

Heuristics (none is a law):

- **Afferent coupling (Ca)**: how many modules depend on me. High Ca means I am hard to change; fine for a small stable `Money` type, dangerous for a 1,400-line grab bag.
- **Efferent coupling (Ce)**: how many modules I depend on. High Ce means I break often.
- **Change coupling**: files that always change together in git history, whatever the import graph says. `git log --name-only` plus co-occurrence counting finds hidden coupling; use it as evidence in design discussions.
- **Kinds of coupling, weak to strong**: data, interface, temporal (A before B), shared mutable state, shared database table, knowledge of internals. A shared table between two services is the most underestimated because no compiler or import checker sees it.

Low cohesion looks like: a module named `utils`/`helpers`/`manager`; a class whose methods split into groups touching disjoint fields; a function whose docstring needs "and".

### 3.2 Separation of concerns

Separate things that change for different reasons and at different rates: policy (business rules) from mechanism (HTTP, SQL, PDF, remote calls).

```
HTTP request -> [transport: parse/validate shape] -> [application: orchestrate use case]
             -> [domain: rules and invariants]    -> [infrastructure: DB, remote APIs]
```

This is not the same as folders by technical type (`controllers/`, `services/`, `models/`), which yields high coupling across folders for every feature and low cohesion within each. Slice by capability first (`certificates/`, `enrolment/`), by role second.

### 3.3 Composition over inheritance

Inheritance couples a subclass to the parent's *implementation*, including which of its methods call which. In the "fragile base class" problem the parent changes an internal call pattern and the child silently breaks (section 6 shows it). Composition holds a collaborator behind an interface and delegates, so the coupling is to the public contract only.

Inheritance is legitimate for genuine Liskov-safe subtyping, for classes designed for extension with documented hooks (framework base classes; exceptions), and when you override less than you inherit. Avoid it when the motive is "reuse some code". Alternatives: a function, a collaborator object, a wrapper/decorator, a strategy argument.

Moodle note: many plugin types require extending framework classes (`moodleform`, `\core\event\base`, `\core\task\scheduled_task`; see 3.2, 3.4, 3.5). That is inheritance by framework design. Keep business logic in plain classes they call; the subclass becomes a thin adapter.

### 3.4 SOLID, and its limits

SOLID is five heuristics, not laws.

- **SRP** (one reason to change, i.e. one stakeholder driving change): splits the "HTTP + SQL + rule" file. Oversold as "one method per class", which gives 40 tiny classes to open for one flow.
- **OCP** (extend without editing): good at *proven* axes of variation. Oversold as pre-built extension points; edit the code the first time, abstract on the second or third real variant.
- **LSP** (a subtype honors the parent's contract: preconditions not stronger, postconditions not weaker): applies to Protocol/interface implementations too. Operational test: one contract test suite that every implementation passes.
- **ISP** (do not depend on methods you do not use): narrow ports (`OrderRepository`, not `Database`). Oversold as one-method interfaces everywhere.
- **DIP** (policy must not depend on detail; the abstraction is owned by the policy side): the core of ports and adapters. Oversold as an interface in front of every class "for testability" when a plain function or fake would do.

In backend code SRP and DIP carry most of the weight; LSP is your test for whether an abstraction is any good.

### 3.5 Dependency inversion: ports and adapters

Without inversion, source dependencies follow control flow (`use case -> SQLAlchemy, requests`). With it, the use case declares what it needs in its own vocabulary and infrastructure implements it:

```
   application/domain --owns--> port: OrderRepository <--implements-- SqlAlchemyOrders (adapter)
                                                      <--implements-- InMemoryOrders  (adapter, tests)
```

Source dependency points toward the domain; runtime control still points outward. In Python a `typing.Protocol` gives structural typing (adapters need not import the port); in PHP use `interface`/`implements`. It buys millisecond domain tests and replaceable infrastructure. It costs files, indirection, and the risk that the port is shaped like the first adapter (a leaky abstraction, e.g. a repository taking a `session`). Design the port from what the use case needs, never from what the library offers.

### 3.6 Architectural styles as trade-offs

- **Layered**: simple, well understood, a good default for CRUD-dominant systems. Fails when the domain layer depends on the data layer (ORM models everywhere), so layers are only folders, or when layers just pass calls through.
- **Modular monolith**: one deployable, modules with small public APIs, no importing of each other's internals, ideally each owning its tables. Most of the ownership benefit of services with none of the distributed-systems cost. Fails when boundaries exist only by convention; mitigate with a fitness test (section 4, Part E).
- **Ports and adapters / clean architecture**: DIP applied systematically. Worth it for non-trivial, long-lived rules or volatile, slow-to-test externals. Ceremony for a thin pass-through to one table.
- **Microservices**: independent deployability bought with network failure, eventual consistency, versioned remote contracts and per-service operations. Justified by many teams needing independent release or very different scaling needs, not by code size. A team of one to five owning one product should normally begin as a modular monolith (strong practitioner consensus; an opinion, so state it as such in ADRs).

### 3.7 Domain-driven design fundamentals

- **Entity**: defined by identity that persists through change (`Order` with `id`).
- **Value object**: defined by its attributes, immutable, validated in the constructor (`Money`, `EmailAddress`). Python `@dataclass(frozen=True)`; PHP 8.2 `final class` with `readonly` properties.
- **Aggregate**: a cluster treated as one consistency unit with one **root** through which all changes pass; the root enforces invariants that span the cluster. Rules of thumb: reference other aggregates by id, one aggregate per transaction, keep them small. Boundaries come from invariants that must hold *immediately*, not from foreign keys.
- **Repository**: a collection-like port for loading and saving aggregates.
- **Domain event**: an immutable past-tense fact (`OrderClosed`).
- **Bounded context**: a boundary within which one model and vocabulary is consistent. "Course" means a catalogue entry to marketing, a Moodle `course` row with contexts and enrolments to the LMS, and a billable product to finance. One `Course` class serving all three becomes a god object. Each context gets its own model and a translation at the border (an **anti-corruption layer**: an adapter converting the other model into yours).

DDD is ceremony for CRUD screens, reports and glue code. Entities with no rules are records; do not wrap a table in an "aggregate" to feel disciplined.

### 3.8 Event-driven basics and their costs

Producers publish facts; consumers react without the producer knowing them. Moodle's events system (3.5) is an in-process example. Benefit: code-level decoupling and easy addition of reactions. Costs, routinely under-counted:

- **Hidden control flow**: "what happens when an order closes?" is no longer answerable from one function.
- **Eventual consistency**: readers may see old state.
- **At-least-once delivery** in most real brokers, so consumers must be idempotent (2.6); "exactly once" in practice means idempotent consumers plus deduplication.
- **Dual write**: "save to DB, then publish" can fail between the steps. The standard fix is the **transactional outbox**: write the event to an `outbox` table in the same transaction as the state change; a relay publishes it later. The `notifier.order_closed` call in section 4 is exactly this hazard.
- **Ordering**: at best per key/partition; tolerate duplicates and reordering.

Do not use events for a synchronous command that needs an answer ("charge this card"); that gives all the costs and none of the decoupling.

### 3.9 Schema evolution

Anything crossing a boundary and outliving a deploy (queue JSON, stored events, public APIs, a column another module reads) is a contract, and old and new versions coexist. Compatible: add an optional field with a default; add a new event type. Incompatible: remove/rename a field, change type or meaning, make optional required, tighten validation. Techniques: tolerant reader (ignore unknown, default missing); expand/contract (add, dual-write, migrate readers, remove later; same for DB columns, see 2.4); version field plus upcasting; never change a field's meaning (add a new field). Pydantic v2 ignores extra fields by default, while `extra='forbid'` makes a strict reader that breaks on additive changes; choose per boundary (VERIFY in the Pydantic docs for your version).

### 3.10 Failure boundaries

A failure boundary contains a dependency's failure: timeouts, bulkheads (separate pools so one slow dependency cannot exhaust shared resources), circuit breakers, degraded fallbacks (4.3). For each outbound call ask: what is the timeout, which endpoints share its resources, what does the user see when it is down? A port is the natural place for the policy: the adapter owns the timeout and translates `Timeout` into a domain `RemoteUnavailable`.

### 3.11 ADRs and when patterns are ceremony

An **Architecture Decision Record** is a one-page record of one decision: **Context**, **Options** (at least two real ones, including "do nothing"), **Decision**, **Consequences** (including negative ones and what would trigger revisiting). Immutable once accepted; a later ADR supersedes it. It lets the next engineer tell a deliberate trade-off from an accident.

A pattern is ceremony when its cost is paid and its benefit never collected. Tests: can you name the second implementation or the specific test it enables? Does the layer only forward calls? Must a newcomer open more than three files to follow one request? Does it contradict team convention (follow it unless you can win the argument with evidence)?

## 4. Worked example

Scenario: close an order and notify. We build it in three parts, with the naive version first.

### Part A. Naive version

```python
# naive.py -- everything in one place (do not copy)
import sqlite3, requests

def close_order(order_id: str) -> float:
    db = sqlite3.connect("shop.db")
    rows = db.execute("SELECT qty, price FROM lines WHERE order_id=?", (order_id,)).fetchall()
    if not rows:
        raise ValueError("cannot close empty order")
    total = sum(q * p for q, p in rows)          # floats for money
    db.execute("UPDATE orders SET closed=1 WHERE id=?", (order_id,))
    db.commit()
    requests.post("https://notify.example/api", json={"order": order_id, "total": total})
    return total
```

Problems: the rule is untestable without SQLite and a network; money is `float`; the notification can fail after commit (dual write); `requests.post` has no timeout; a second consumer means editing this function.

### Part B. Domain, ports, adapters (Python 3.12+; run and verified)

```python
from __future__ import annotations
from dataclasses import dataclass, field
from typing import Protocol
from decimal import Decimal


@dataclass(frozen=True)
class Money:
    amount: Decimal
    currency: str

    def __post_init__(self) -> None:
        if len(self.currency) != 3:
            raise ValueError("currency must be a 3-letter code")

    def __add__(self, other: Money) -> Money:
        if other.currency != self.currency:
            raise ValueError("currency mismatch")
        return Money(self.amount + other.amount, self.currency)


class OrderClosed(Exception):
    pass


@dataclass
class Order:
    """Aggregate root. All changes to lines go through this class."""
    id: str
    currency: str
    _lines: list[tuple[str, int, Money]] = field(default_factory=list)
    _closed: bool = False
    MAX_LINES = 3

    def add_line(self, sku: str, qty: int, unit_price: Money) -> None:
        if self._closed:
            raise OrderClosed(self.id)
        if qty <= 0:
            raise ValueError("qty must be positive")
        if unit_price.currency != self.currency:
            raise ValueError("currency mismatch")
        if len(self._lines) >= self.MAX_LINES:
            raise ValueError("too many lines")
        self._lines.append((sku, qty, unit_price))

    def total(self) -> Money:
        total = Money(Decimal(0), self.currency)
        for _, qty, price in self._lines:
            total = total + Money(price.amount * qty, price.currency)
        return total

    def close(self) -> None:
        if not self._lines:
            raise ValueError("cannot close empty order")
        self._closed = True


# Ports: owned by the application layer, expressed in domain terms.
class OrderRepository(Protocol):
    def get(self, order_id: str) -> Order: ...
    def save(self, order: Order) -> None: ...


class Notifier(Protocol):
    def order_closed(self, order_id: str, total: Money) -> None: ...


# Adapters
class InMemoryOrders:
    def __init__(self) -> None:
        self._rows: dict[str, Order] = {}

    def get(self, order_id: str) -> Order:
        return self._rows[order_id]

    def save(self, order: Order) -> None:
        self._rows[order.id] = order


class RecordingNotifier:
    def __init__(self) -> None:
        self.sent: list[tuple[str, Money]] = []

    def order_closed(self, order_id: str, total: Money) -> None:
        self.sent.append((order_id, total))


# Application service: orchestration only, no business rules, no SQL, no HTTP.
class CloseOrder:
    def __init__(self, orders: OrderRepository, notifier: Notifier) -> None:
        self._orders = orders
        self._notifier = notifier

    def __call__(self, order_id: str) -> Money:
        order = self._orders.get(order_id)
        order.close()
        self._orders.save(order)
        total = order.total()
        self._notifier.order_closed(order_id, total)  # dual-write hazard: see 3.8
        return total


if __name__ == "__main__":
    repo, notifier = InMemoryOrders(), RecordingNotifier()
    o = Order("o1", "USD")
    o.add_line("A", 2, Money(Decimal("2.50"), "USD"))
    repo.save(o)
    assert CloseOrder(repo, notifier)("o1") == Money(Decimal("5.00"), "USD")
    assert notifier.sent == [("o1", Money(Decimal("5.00"), "USD"))]
```

Design choices:

- `Money` is a frozen value object using `Decimal` (float money accumulates representation error; see 6.2); its constructor validates, so an invalid one never exists.
- `Order` is the aggregate root; invariants (positive quantity, same currency, line limit, no mutation after close, no empty close) sit in one place, testable without I/O. Python's underscore is convention only, a weaker guarantee than PHP `private`.
- Ports are `Protocol`s next to the use case and speak `Order` and `Money`, not rows or HTTP.
- `CloseOrder` holds no rules: load, call, save, notify. An `if` about business state here belongs in the aggregate.
- Versus naive: rule tested in microseconds; money exact; notification behind a port that owns timeout and retry policy; a second consumer is a second `Notifier`. Cost: five new types and an indirection. For a monthly one-off script the naive version is the correct choice.

Real adapters: `SqlAlchemyOrders` with explicit row-to-`Order` conversion functions (so the domain class never imports SQLAlchemy; VERIFY imperative-mapping details in the SQLAlchemy 2.x docs before choosing it over a separate persistence model) and `HttpNotifier` with an explicit timeout translating `httpx.TimeoutException` to a domain `NotifyUnavailable`.

### Part C. Schema evolution with an upcaster (verified)

```python
import json

def upcast(event: dict) -> dict:
    e = dict(event)
    if e.get("version", 1) == 1:
        # v1: float dollars 'total'; v2: integer 'total_minor' + 'currency'
        e["total_minor"] = round(e.pop("total") * 100)
        e["currency"] = "USD"      # lossy assumption: record it in an ADR
        e["version"] = 2
    return e

def handle(raw: str) -> int:
    return upcast(json.loads(raw))["total_minor"]   # unknown fields ignored

assert handle('{"type":"order_closed","total":12.5}') == 1250
assert handle('{"type":"order_closed","version":2,"total_minor":99,"currency":"USD","new_field":1}') == 99
```

Test with *literal stored payloads*, not objects built by current code; that is how accidental breaking changes are caught.

### Part D. PHP 8.2 equivalent (verified)

```php
<?php
declare(strict_types=1);
final class Money {
    public function __construct(public readonly int $minor, public readonly string $currency) {
        if (strlen($currency) !== 3) { throw new InvalidArgumentException('currency'); }
    }
    public function add(Money $o): Money {
        if ($o->currency !== $this->currency) { throw new InvalidArgumentException('mismatch'); }
        return new Money($this->minor + $o->minor, $this->currency);
    }
}
interface ReceiptSender { public function send(string $userId, string $text): void; } // port
final class CheckoutService {                                  // composition via constructor
    public function __construct(private ReceiptSender $sender) {}
    public function checkout(string $userId, Money $a, Money $b): Money {
        $total = $a->add($b);
        $this->sender->send($userId, "Paid {$total->minor} {$total->currency}");
        return $total;
    }
}
```

Mutating `$money->minor` raises `Error: Cannot modify readonly property Money::$minor`. PHP `private` is enforced, unlike Python's underscore convention. Money uses integer minor units (the usual PHP approach). In Moodle, place such classes under the plugin's `classes/` directory so they autoload by namespace (3.2), keep `lib.php` thin, and wrap the global `$DB` in an adapter implementing your repository interface rather than calling `$DB` inside rules.

### Part E. An architecture fitness test (verified)

```python
import ast, pathlib

FORBIDDEN = {"sqlalchemy", "fastapi", "requests", "httpx"}

def violations(domain_dir: pathlib.Path) -> list[str]:
    bad = []
    for f in domain_dir.rglob("*.py"):
        for node in ast.walk(ast.parse(f.read_text())):
            names = ([a.name for a in node.names] if isinstance(node, ast.Import)
                     else [node.module] if isinstance(node, ast.ImportFrom) and node.module else [])
            bad += [f"{f.name}: imports {n}" for n in names if n.split(".")[0] in FORBIDDEN]
    return bad
```

CI asserts `violations(Path("src/shop/domain")) == []`. An unenforced boundary decays. Limit: dynamic imports are invisible. For richer rules see import-linter (VERIFY current status and config) or, for PHP, PHPStan/Deptrac (VERIFY); new dependencies need team agreement.

## 5. Production perspective

- **Maintainability.** Symptoms of bad boundaries: PRs touching many unrelated files, ripple bugs, files nobody dares touch. `git log --format= --name-only -- path | sort | uniq -c | sort -rn | head` finds hot files; co-change counts find coupling.
- **Correctness.** Each invariant lives in one place. Duplicate rules (section 1's batch job) are bugs waiting; the cure is one domain function with one test.
- **Failure handling.** Adapters translate low-level exceptions and own timeouts (4.3); the domain never sees `ConnectionError`.
- **Testing.** Domain: plain unit tests. Adapters: integration tests or a contract test shared by all adapters of a port (4.2). Wiring: in-memory adapters.
- **Operations.** One deployable is cheaper to run; each service adds a pipeline, dashboards and on-call load. In-process boundaries cost nothing at runtime.

**What a senior engineer does differently.** Starts from change axes ("what will likely change? what is expensive to change?"). Defers cheap-to-reverse decisions and writes ADRs for expensive ones (database, public API, message format, tenant model). Reads the existing architecture for its intent and extends it consistently rather than adding a second style. Moves one seam at a time (4.2), never a rewrite. States the *cost* of a pattern in the PR description.

**Common beginner mistakes and diagnosis.**

- ORM model used as domain model and API schema: one class imported by routers, queries and rules. grep for it across layers.
- Interface for everything: each `Foo` has one `FooImpl` nobody substituted. List one-implementation interfaces without a test double.
- Anemic domain: repeated `if order.status == ...` across services. Search for the repeated checks.
- Shared database between "services", or services that must deploy together: compare connection strings; count PRs spanning two repos.
- Event used as disguised RPC: producer waits for a reply event. Look for correlation ids and timeouts around publish.
- God `utils`: many importers, no single topic.

## 6. Failure laboratory

A teammate wants a counting collection and writes this. Read it, then **predict** what the final line prints before running anything.

```python
class Counter:
    def __init__(self): self.items = []
    def add(self, x): self.items.append(x)
    def add_all(self, xs):
        for x in xs: self.add(x)

class CountingList(Counter):
    def __init__(self): super().__init__(); self.added = 0
    def add(self, x): self.added += 1; super().add(x)
    def add_all(self, xs): self.added += len(xs); super().add_all(xs)

c = CountingList(); c.add_all([1, 2, 3])
print("inheritance counted:", c.added, "(expected 3)")
```

Write down: the number printed, which methods run in which order, and the one-sentence reason.

### Reveal (read after predicting)

It prints `inheritance counted: 6 (expected 3)` (verified by running).

Trace: `CountingList.add_all` adds 3 to `added`, then calls `Counter.add_all`, which loops and calls `self.add(x)`. Because `self` is a `CountingList`, `self.add` dispatches to the override, which adds 1 each time: 3 + 3 = 6.

Root cause: the subclass depends on an undocumented implementation detail of the parent (that `add_all` is implemented by calling `add`). If the parent were later optimized to `self.items.extend(xs)`, the result would silently change to 3. The bug is in the *design* (inheritance for reuse), not in either class alone.

Systematic diagnosis procedure for "inherited class behaves strangely":
1. Print or log the method resolution order: `CountingList.__mro__`.
2. For each overridden method, read the parent's version and list every `self.` call it makes.
3. Draw the call graph including overrides; look for re-entry.
4. Ask whether the parent documents those calls as part of its contract. If not, the child is coupled to an implementation detail.
5. Fix: remove the inheritance relationship or make the hook contract explicit.

The composed version (`Counting` wrapping a `Collection`, delegating `add` and `add_all`) prints `composition counted: 3` (verified). It converts the iterable to a list before counting, because a one-shot generator would break `len(xs)`; composition confines the thinking to the public contract, it does not remove it.

## 8. Independent implementation challenge

**8.1 (Mode A, 45-60 min). Composition refactor with a failing test.** Given a class `Notifier` with methods `send(msg)` and `send_many(msgs)` (the latter calls `send` in a loop), write `RateLimitedNotifier` first as a subclass, and a test that exposes the double-counting/double-delay defect. Then rewrite it by composition. Both versions go in one file; the test must fail on the first and pass on the second. Constraints: no libraries beyond the standard library and pytest; time is injected (a callable `now() -> float`), never `time.sleep` in tests.

**8.2 (Mode A, 60-90 min). Aggregate with invariants.** Model `Enrolment` for a course with: a `Course` capacity (value object `Capacity` that rejects values < 1), enrolment states `pending`, `active`, `withdrawn` with allowed transitions only `pending->active`, `active->withdrawn`, `pending->withdrawn`; at most `capacity` active enrolments per course in one `CourseRoster` aggregate; a learner cannot hold two non-withdrawn entries for the same course. Write at least 12 tests, at least half of which try to *violate* an invariant through the public API. Show that a 13th "test" that mutates private state is the only way to break an invariant, and state in a comment why that is acceptable. ## 10. Engineering review

Checklist: every invariant has a test that tries to violate it through the public API; no rule is duplicated outside the domain; a request is traceable in at most three files; domain names, not technology names, inside domain/application; each adapter tested against its real counterpart or a shared contract test; concurrency, partial failure, malformed upstream data and empty overrides covered; upstream response validated before building domain objects, no secrets in code, override records who did it (4.3); every outbound call has a timeout and the outbox backlog is observable; no field changed meaning; no unapproved dependency.

Explain in 3-5 sentences each: which invariant forced your aggregate boundary; which port you shaped from the library in hindsight; what you could delete without losing a requirement; what would make you merge `Billing` back or split further; what the mid-way change revealed about your boundaries.

## 11. Mastery gate

Pass = at least 80/100 on the rubric, no critical failure, with evidence: test output; the fitness test failing on a deliberately introduced violation; three ADRs; `CHANGES-midway.md`; a written defense of the Section 10 prompts produced without the lesson (Mode A).

Critical failures: domain imports a web framework, ORM or HTTP client; uniqueness enforced only in application code; event published outside the transaction with no outbox while the report claims safety; a test claimed to cover a rule still passes when the rule is deleted (demonstrate by deleting it); an unverified fact or number asserted without VERIFY.

If failed, remedial exercise on the weakest area only: aggregates, redo 8.2 for library loans (member, copy, loan limit) with 12 violation tests; outbox, implement only outbox, relay and crash-simulation test against SQLite; ADRs, write three ADRs for decisions already present in a codebase you work on and have a peer find a missing alternative in each.
