## 1. Engineering problem

Your first ticket: "fix the grading label bug" in a 600-line PHP class `LegacyGrader` with no tests, a call to `date('n')` buried in the middle, two global reads, and a comment saying `// don't touch, breaks reports`. If you fix the bug and a downstream report changes, you will be blamed for a change you could not have predicted. If you refuse to touch it, the bug stays.

Meanwhile on your own team, test suites fail in three characteristic ways: a suite with 95% coverage that misses a boundary bug; a suite so slow and flaky that CI is re-run until green and its failures are ignored; and a suite of mock-heavy tests that break on every refactor yet find nothing. And code review fails in two: rubber-stamped approvals, and nit-picking style while a missing authorization check ships.

This lesson gives you a strategy for deciding what to test and at what level, a method for gaining safe footing in untested code (characterization tests and seams), a review checklist usable on both sides of a pull request, and a way to decide which debt deserves attention.

## 2. Learning objectives

By the end you can:

1. Given a feature, choose test levels (unit, integration, contract, end-to-end) and justify each choice by what failure it detects and what it costs to run and maintain.
2. Write a characterization test suite for an unfamiliar function that pins its current behavior including boundaries and surprising cases, without first "fixing" anything.
3. Introduce a seam in legacy Python and PHP code (parameterization or extract-and-override) that makes a hidden dependency controllable, with the characterization suite green before and after.
4. Write property-based tests with Hypothesis that state invariants, and explain what a shrunk counterexample tells you.
5. Demonstrate with a hand-built or tool-based mutation check that a suite with full line coverage can still miss a defect, and strengthen the suite so the mutant is killed.
6. Diagnose and fix a flaky test by identifying its nondeterminism source (time, ordering, shared state, concurrency, network) and removing it rather than retrying.
7. Review a diff using a written checklist, producing comments classified as blocking, suggestion, or question, each with a reason; and respond to review comments with technical verification rather than reflex agreement.
8. Triage a list of tech-debt items by impact, change frequency and risk, and produce a ranked plan with explicit "do not fix" entries.

## 3. First-principles explanation

### 3.1 What tests are for

A test is an executable claim about behavior, valuable in proportion to (a) the probability it fails when something real breaks and (b) how cheaply it can be run and understood. Tests serve three distinct purposes that are often confused:

- **Design feedback** (tests written first or alongside): hard-to-test code is usually too coupled (4.1).
- **Regression protection**: today's behavior stays true tomorrow.
- **Specification**: a named test is documentation that cannot silently go stale.

Cost side: runtime, maintenance when behavior legitimately changes, and false confidence. The target is not "more tests" but *the cheapest set that makes you willing to change the code*.

### 3.2 The test pyramid as a trade-off

```
        /\        end-to-end: few, slow, realistic, brittle, wide failure radius
       /  \       
      /----\      integration / contract: moderate; real boundaries (DB, HTTP schema)
     /      \
    /--------\    unit: many, fast, precise failure location, may miss wiring bugs
```

Why the shape: failure *localization* and *speed* fall as you go up, while *realism* rises. Unit tests tell you which function broke in milliseconds; end-to-end tests tell you the product is broken in minutes, without saying where. The pyramid is a heuristic about cost, not a rule: a CRUD-heavy service whose logic lives in SQL may be better served by a "trophy" shape with more integration tests against a real database, because mocking the database removes exactly the thing most likely to be wrong. A numerical library is nearly all unit and property tests. Choose the shape from where your bugs live.

Definitions used here:

- **Unit**: exercises one behavior in-process, no real I/O, deterministic. "Unit" is about isolation and speed, not about "one class".
- **Integration**: exercises your code with a real collaborator across a boundary (your repository against a real database; your HTTP client against a local test server).
- **Contract**: verifies that two sides agree on an interface. *Consumer-driven contract* tests record what a consumer expects and verify the provider meets it. A simpler form (used in 4.1): one test suite parameterized over every adapter of a port (section 4, Part C).
- **End-to-end (E2E)**: drives the deployed system via its real entry point (browser, public API). Moodle's Behat tests (3.6) are E2E.

### 3.3 Test behavior and invariants, not coverage

Line coverage tells you which lines ran, not whether anything was *checked*. A test with no assertions gives 100% coverage. Coverage is useful in one direction only: low coverage reliably identifies untested code. High coverage proves little. Mutation testing (3.6) measures whether tests would notice a change.

Prefer assertions about observable behavior and about **invariants**: properties that hold for all valid inputs (a sorted list is ordered and a permutation of the input; encode then decode returns the input; balance never goes negative; an idempotent endpoint called twice leaves the same state). Tests coupled to implementation (asserting which private method ran, or exact call order on mocks) break when you refactor even though behavior is unchanged: they tax refactoring, which is the opposite of their purpose.

### 3.4 Property-based testing

Instead of hand-picking examples, state a property and let a generator produce many inputs; on failure, the tool **shrinks** the input to a minimal counterexample. Python: Hypothesis. PHP options exist (Eris, `giorgiosironi/eris`, was still receiving releases on Packagist when checked; confirm it fits your PHPUnit version, or write a seeded random loop by hand).

```python
# test_prop.py -- needs: pip install hypothesis   (verified: 3 passed)
from hypothesis import given, strategies as st

def normalize_ws(s: str) -> str:
    return " ".join(s.split())

@given(st.text())
def test_idempotent(s):
    assert normalize_ws(normalize_ws(s)) == normalize_ws(s)

@given(st.text())
def test_no_double_spaces_or_edges(s):
    out = normalize_ws(s)
    assert "  " not in out and out == out.strip()

def sorted_unique(xs): return sorted(set(xs))

@given(st.lists(st.integers()))
def test_sorted_unique_properties(xs):
    out = sorted_unique(xs)
    assert out == sorted(out)
    assert len(out) == len(set(out))
    assert set(out) == set(xs)
```

Good property sources: round-trips, idempotence, commutativity, "same result as a slow obvious implementation" (a **model** or **oracle**), and "output satisfies the invariant". Hypothesis stores failing examples in a local database so they re-run next time (checked on Hypothesis 6.x: failures are saved under `.hypothesis/examples` in the working directory by default, and the saved example is replayed first on the next run). Limits: you must define a correct property (a wrong property is a wrong test), generators for domain objects take effort, and properties cannot replace a few well-chosen examples that document intent.

### 3.5 Test doubles

Terms (after Meszaros; usage varies by community, so define them in your team):

- **Dummy**: passed but never used. **Stub**: returns canned answers. **Fake**: a working lightweight implementation (in-memory repository). **Spy**: records calls. **Mock**: pre-programmed with expectations about calls, fails if they are not met.

Prefer **fakes** and **state-based assertions** where possible: they survive refactoring because they assert outcomes. Use mocks for interactions that *are* the behavior (an email must be sent; a payment API must be called with this idempotency key) and for boundaries you cannot fake cheaply. Hazards: mocking what you do not own (you encode your assumption of the library's behavior, not the library's behavior), over-specified call order, and mocks that accept any call (use `Mock(spec=Class)` / `create_autospec` in Python so typos fail; verified below).

```python
# Python 3.12 (verified)
from unittest.mock import Mock
class Mailer:
    def send(self, to, body): raise NotImplementedError
def welcome(users, mailer):
    for u in users:
        if u["active"]: mailer.send(u["email"], f"Hi {u['name']}")

class FakeMailer(Mailer):
    def __init__(self): self.outbox = []
    def send(self, to, body): self.outbox.append((to, body))

f = FakeMailer()
welcome([{"name": "A", "email": "a@x", "active": True}, {"name": "B", "email": "b@x", "active": False}], f)
assert f.outbox == [("a@x", "Hi A")]          # state-based: survives batching the sends

m = Mock(spec=Mailer)
welcome([{"name": "A", "email": "a@x", "active": True}], m)
m.send.assert_called_once_with("a@x", "Hi A")  # interaction-based: breaks if you batch
try: m.sendd("x")
except AttributeError: print("spec catches typos: ok")
```

### 3.6 Mutation testing, introduced

Mutation testing makes small automated changes ("mutants": `>=` to `>`, `+` to `-`, delete a statement) to the code and reruns the suite. A mutant that passes (**survives**) shows a behavior no test pins down. The **mutation score** is killed/total (excluding equivalent mutants, which change nothing observable and are an undecidable nuisance). It is expensive (suite run per mutant), so apply it to critical modules, not the whole repo. Python tools exist (mutmut and cosmic-ray both had recent PyPI releases when checked); PHP has Infection (infection.github.io, current releases on Packagist). Section 6 does it by hand with `ast`, which is enough to understand the idea.

### 3.7 Flaky tests

A flaky test passes and fails on the same code. Causes, by frequency: **time** (real clocks, sleeps, timezones, month/day boundaries), **ordering/shared state** (tests depend on run order, leaked globals, shared DB rows, cached singletons), **concurrency** (races, unawaited tasks), **network/external services**, **randomness without a seed**, **resource limits** (ports in use, slow CI). Reruns hide the problem and teach the team to ignore red. The method: reproduce (loop the test, randomize order, run in isolation, run under CPU load), find the nondeterminism source, remove it (inject a clock, isolate state per test, await completion deterministically, seed randomness and print the seed), and only quarantine as a last resort with an owner and a date. A deterministic clock:

```python
# Python 3.12 (verified)
import datetime

class Session:
    def __init__(self, now, ttl=datetime.timedelta(minutes=30)):
        self._now, self._ttl, self._start = now, ttl, now()
    def expired(self) -> bool:
        return self._now() - self._start >= self._ttl

class FakeClock:
    def __init__(self): self.t = datetime.datetime(2025, 1, 1)
    def __call__(self): return self.t
    def advance(self, **kw): self.t += datetime.timedelta(**kw)

clock = FakeClock(); s = Session(clock)
clock.advance(minutes=29, seconds=59); assert not s.expired()
clock.advance(seconds=1);              assert s.expired()
```

The flaky alternative (`time.sleep(0.05)` against a 50 ms TTL) races the scheduler, and it also makes the suite slow.

### 3.8 Code review

Review has four jobs: catch defects, spread knowledge, keep the design coherent, and keep the codebase consistent. It has a cost (latency); the best lever is small PRs with a clear description (0.4).

**As author:** self-review the diff first; state what and why, what you tested, what you did *not* test, and where you want attention; keep the change to one purpose; run the checks before requesting review; explain trade-offs in the PR rather than defending them in comments.

**As reviewer, in priority order:**

1. **Correctness and requirements**: does it do what the ticket says; boundary and error cases; concurrency; idempotency.
2. **Security**: authorization on every new path, input validation, injection and output encoding, secrets, logging of sensitive data (4.3).
3. **Data and migrations**: reversible, safe on large tables, backward compatible with old code during rollout (2.4).
4. **Tests**: do they fail without the change? Do they test behavior? Edge cases present?
5. **Design**: boundaries respected (4.1), dependency direction, naming, complexity.
6. **Operability**: logs, metrics, timeouts, failure behavior, config.
7. **Style**: last, and preferably by automated formatters and linters.

Comment hygiene: label each comment **blocking** (must change), **suggestion** (take it or explain), **question** (I do not understand; not a demand), or **nit** (optional). Explain *why*, point to evidence, propose an alternative when blocking. Review the code, not the person. Approve when the code improves the codebase and is safe, not when it matches how you would have written it.

**Receiving review:** treat each comment as a claim to verify. Reproduce the reported issue; check the suggested change against the code and tests before applying; if you disagree, answer with evidence and a question, not with a grudging "done". Equally, do not implement a suggestion you do not understand: ask. Performative agreement is how wrong changes get merged.

Checklist usable in both roles:

```
[ ] Purpose clear; PR small enough to review in 30 minutes
[ ] Behavior matches the requirement; edge cases (empty, zero, max, duplicate, unicode, timezone)
[ ] Failure modes: timeouts, partial failure, retries safe/idempotent
[ ] AuthN/Z on every new entry point; least privilege; no secrets or PII in logs
[ ] Inputs validated; queries parameterized; outputs encoded
[ ] Tests fail without the change; assert behavior; no sleeps; no order dependence
[ ] DB changes safe to deploy (old and new code run together briefly); rollback story
[ ] Dependency direction and naming consistent with the codebase
[ ] Observability: can we tell if this is broken in production?
[ ] No unrelated changes; no dead code; docs/changelog if user-visible
```

### 3.9 Characterization tests

Legacy code is, in Michael Feathers' working definition, code without tests. You cannot refactor safely without tests, and you cannot write correct tests for behavior you do not understand. The way out: a **characterization test** pins what the code *does*, not what it *should* do. Procedure: (1) call the code in a test harness with a chosen input; (2) assert something you know is wrong, run it, and let the failure message tell you the actual value; (3) change the assertion to the actual value; (4) repeat for boundaries (zero, one, limit, limit+1, negative, empty, unknown key), for each branch, and for each surprising case you discover. Record surprising behavior as pinned facts; do not fix it in this step. Separating "pin" from "fix" is the discipline: fixing while characterizing means you no longer know whether a change in output is yours or the original's.

Bugs you pin are still bugs: mark them (`# pinned: probably a bug, ticket NNN`) so the behavior change later is a deliberate, reviewed commit with a test change.

### 3.10 Seams and safe refactoring (Feathers-style)

A **seam** is a place where you can alter behavior without editing the code at that place. Legacy code is hard to test because of hidden dependencies (clock, globals, singletons, database, filesystem, network) that you cannot substitute. Techniques, smallest first:

- **Parameterize**: add an optional argument defaulting to the old behavior (`today=datetime.date.today`). Production callers are unchanged.
- **Extract and override call** (OO languages): move the hidden call into a method, override it in a test subclass (the PHP example in section 4).
- **Wrap / adapter**: wrap a static or global in a small class and inject it.
- **Link or module-level seam**: replace a module attribute in the test (`monkeypatch.setattr`), acceptable as a scaffold, but a brittle one.

Refactoring loop: pin behavior (green) -> make one small structural change -> run tests (green) -> commit. Never mix a refactor with a behavior change in one commit. Prefer the **strangler** approach to replacement: route calls through a new implementation incrementally while the old one remains, compare outputs on real inputs ("shadow" or dual-run, logging differences, in a way that has no side effects), and delete the old path last. A rewrite from scratch discards the accumulated bug fixes encoded in the old code; do it only with explicit agreement and with the characterization suite as the acceptance test.

Moodle-specific caution: core code and the global `$DB`, `$CFG`, `$USER`, `$PAGE` make unit testing hard; Moodle's PHPUnit setup provides database reset between tests (`resetAfterTest()`, defined in Moodle's `advanced_testcase.php`; checked in core source, signature `resetAfterTest($reset = true)`) so many plugin tests are integration-style by design. Do not refactor *core*; wrap your plugin's use of globals behind your own small classes (4.1).

### 3.11 Tech-debt triage

Technical debt is the gap between the code's current state and the state in which the next change would be cheap and safe. Not all of it matters. Score each item on:

- **Interest**: how much does it slow or endanger work now (cost per change times change frequency; use `git log` to find the files changed most often)?
- **Risk**: what is the blast radius if it fails (security, data loss, money)?
- **Fix cost**: effort and the risk of the fix.
- **Dependency**: does it block something valued?

Rank by (interest + risk) against cost. Hot, risky, cheap items first. Debt in code nobody changes has zero interest: leave it, and write that decision down ("do not fix: stable, untouched for 2 years, no incidents"). Fix as you go (the boy-scout rule, limited to the code you are already changing and covered by tests) rather than in a big-bang "refactoring sprint" that stops delivery and ships risk. Categories help conversation: deliberate/inadvertent, prudent/reckless; code, test, build, dependency, documentation, architecture.

## 4. Worked example

### Part A. Characterize, then create a seam (Python, verified)

Legacy function with a hidden clock:

```python
# legacy.py
import datetime
RATES = {"MW": 5.0, "ZA": 8.0}

def shipping_cost(country, weight_kg, express=False):
    c = RATES.get(country, 12.0)
    if weight_kg > 10:
        c = c + (weight_kg - 10) * 0.5
    if express:
        c = c * 2
    if datetime.date.today().month == 12:      # hidden dependency: the clock
        c = c * 1.1
    return round(c, 2)
```

Step 1, a scaffold seam (monkeypatching the date class) so tests are deterministic; the table of observed values came from running the code, not from reasoning:

```python
# test_char.py (verified: 1 passed)
import datetime, legacy

class FixedDate(datetime.date):
    @classmethod
    def today(cls): return cls(2025, 6, 15)

def test_characterize(monkeypatch):
    monkeypatch.setattr(legacy.datetime, "date", FixedDate)
    observed = {
        ("MW", 1, False): 5.0,
        ("ZA", 1, False): 8.0,
        ("XX", 1, False): 12.0,
        ("MW", 20, False): 10.0,
        ("MW", 20, True): 20.0,
        ("MW", 10, False): 5.0,   # boundary: exactly 10 is NOT surcharged
        ("MW", 0, False): 5.0,    # zero weight accepted: surprising, now pinned
    }
    for args, expected in observed.items():
        assert legacy.shipping_cost(*args) == expected, args
```

Step 2, replace the scaffold with a real seam by parameterizing; the signature remains compatible with existing callers, and the same characterization expectations apply (verified):

```python
# refactored.py
import datetime
from typing import Callable
RATES = {"MW": 5.0, "ZA": 8.0}

def shipping_cost(country, weight_kg, express=False, *, today: Callable[[], datetime.date] = datetime.date.today):
    c = RATES.get(country, 12.0)
    if weight_kg > 10:
        c += (weight_kg - 10) * 0.5
    if express:
        c *= 2
    if today().month == 12:
        c *= 1.1
    return round(c, 2)
```

Now the December rule is directly testable (`today=lambda: datetime.date(2025, 12, 1)` gives 5.5 for `("MW", 1)`; verified). Reasoning for each choice: a keyword-only defaulted parameter changes no call site; `Callable` rather than a `date` value so the default evaluates at call time (a default of `datetime.date.today()` would freeze at import time, a classic bug; see 1.1 on default-argument evaluation). Next steps (separate commits): extract the surcharge rules into named functions; only then discuss whether `weight_kg == 0` should be rejected, as a behavior change with a test change.

### Part B. PHP seam by extract-and-override (verified, PHP 8.2+)

```php
<?php
declare(strict_types=1);

class LegacyGrader {
    public function label(int $score): string {
        $month = $this->currentMonth();         // seam: was (int) date('n') inline
        $pass = $month === 12 ? 45 : 50;        // undocumented end-of-year rule
        return $score >= $pass ? 'pass' : 'fail';
    }
    protected function currentMonth(): int { return (int) date('n'); }
}

final class GraderInMonth extends LegacyGrader {   // test-only subclass
    public function __construct(private int $m) {}
    protected function currentMonth(): int { return $this->m; }
}

assert((new GraderInMonth(6))->label(50) === 'pass');
assert((new GraderInMonth(6))->label(49) === 'fail');
assert((new GraderInMonth(12))->label(45) === 'pass');
assert((new GraderInMonth(12))->label(44) === 'fail');
```

This is inheritance used *for testing*, which section 3 of 4.1 told you to distrust; here it is a deliberate, temporary scaffold with a clear exit: once tests exist, inject a `Clock` interface and delete the subclass. In Moodle's PHPUnit, the equivalent is to use the framework's clock facilities if your version has them (core source has `\core\clock` and `advanced_testcase::mock_clock_with_frozen()` / `mock_clock_with_incrementing()`; they are absent from older releases, so check your version) or to inject a small clock class.

### Part C. A contract test over two adapters (verified, pytest)

```python
import sqlite3, pytest

class MemKV:
    def __init__(self): self.d = {}
    def put(self, k: str, v: str) -> None: self.d[k] = v
    def get(self, k: str) -> str: return self.d[k]          # KeyError if missing

class SqlKV:
    def __init__(self):
        self.c = sqlite3.connect(":memory:")
        self.c.execute("CREATE TABLE kv (k TEXT PRIMARY KEY, v TEXT)")
    def put(self, k, v):
        self.c.execute("INSERT OR REPLACE INTO kv VALUES (?,?)", (k, v))
    def get(self, k):
        r = self.c.execute("SELECT v FROM kv WHERE k=?", (k,)).fetchone()
        if r is None: raise KeyError(k)
        return r[0]

@pytest.fixture(params=[MemKV, SqlKV])
def kv(request): return request.param()

def test_roundtrip(kv):
    kv.put("a", "1"); assert kv.get("a") == "1"
def test_overwrite(kv):
    kv.put("a", "1"); kv.put("a", "2"); assert kv.get("a") == "2"
def test_missing_raises_keyerror(kv):
    with pytest.raises(KeyError): kv.get("nope")
```

One suite, every implementation: this is Liskov Substitution made executable (4.1). The fake used by fast tests is trusted only because it passes the same contract as the real adapter.

## 5. Production perspective

- **Maintainability**: delete tests that assert implementation details and obsolete behavior; a test that must be edited on every refactor is a liability.
- **Correctness**: for each bug fix, write the failing test first, see it fail for the right reason, then fix. The test is the permanent record.
- **Performance of the suite**: keep the commit-gate suite fast (minutes at most); slow tests move to a nightly job. A suite people do not run does not exist.
- **CI hygiene**: no retries to hide flakes; track flaky tests with an owner; fail the build on new warnings if the team agrees.
- **Security**: tests for authorization are first-class (a "forbidden" case for every protected path), see 4.3.
- **Operations**: test the migrations and the rollback path, not only the happy path.

**What a senior engineer does differently.** Writes the characterization suite *before* touching legacy code and says so in the PR. Asks "what would have to be true for this change to be wrong?" and writes that test. Reviews the tests first: they show intent and expose gaps. Keeps refactor commits separate from behavior commits so review and `git bisect` (0.2) stay useful. Treats a flaky test as a production bug in the test system. Writes "do not fix" entries in debt triage.

**Common beginner mistakes and diagnosis.**

- Mocking everything: tests pass but integration fails. Diagnosis: count mocks per test; if the SUT's collaborators are all mocks, the test checks your assumptions only. Add one integration test through the real boundary.
- Asserting on `mock.assert_called` ordering for pure logic: refactor breaks it. Prefer outputs.
- Coverage chasing: tests with no assertions. Diagnosis: delete a rule and see whether any test fails.
- Shared fixtures that grow: every test depends on a 200-line setup. Diagnosis: a failure in one test cascades; shrink to per-test builders.
- Fixing while pinning: output changed and nobody knows why. Diagnosis: diff the characterization table in version control.
- Review by style: 30 comments on naming, none on authorization. Diagnosis: check against the review checklist order.
- Test order dependence: passes alone, fails in the suite. Diagnosis: run with randomized order (pytest-randomly, checked: it shuffles by default, prints the seed, `--randomly-seed=N` replays an order, `-p no:randomly` disables it) and bisect the order.

## 6. Failure laboratory

A teammate reports 100% line and branch coverage for this function and says it is "fully tested".

```python
def can_vote(age: int) -> bool:
    return age >= 18

def tests(fn) -> bool:
    try:
        assert fn(30) is True
        assert fn(5) is False
        return True
    except AssertionError:
        return False
```

Before running anything, predict: (a) if a developer "optimizes" `>=` to `>`, do the tests pass? (b) What is the real-world consequence? (c) Name the technique that detects this and write the minimum extra assertions that close the gap.

### Reveal (read after predicting)

(a) Yes, they pass. Verified with a hand-built mutation script using `ast.NodeTransformer` that flips `GtE` to `Gt`:

```python
import ast
SRC = '''
def can_vote(age: int) -> bool:
    return age >= 18
'''
class FlipGe(ast.NodeTransformer):
    def visit_Compare(self, node):
        if isinstance(node.ops[0], ast.GtE): node.ops[0] = ast.Gt()
        return node
def build(tree):
    ns = {}; exec(compile(ast.fix_missing_locations(tree), "<m>", "exec"), ns); return ns["can_vote"]
orig = build(ast.parse(SRC)); mutant = build(FlipGe().visit(ast.parse(SRC)))
# tests(orig) -> True ; tests(mutant) -> True  (mutant SURVIVES)
# tests_better = tests + fn(18) is True + fn(17) is False  -> mutant is killed
```

Output observed: original passes True, mutant passes True (survived), mutant fails the improved suite.

(b) Every 18-year-old is refused: an off-by-one at the exact boundary, where real bugs concentrate.

(c) Mutation testing. Close it with boundary tests: `fn(18) is True` and `fn(17) is False`. A property-based test alone would catch it only if the generator hits 17/18 (Hypothesis biases toward boundary-like values but does not guarantee it; do not rely on this), which is why you also write explicit boundary examples.

Systematic diagnosis when coverage is high but a bug escaped: (1) reproduce the bug as a failing test; (2) ask which line of the suite *should* have caught it; (3) apply the "delete the rule" test: remove or mutate the relevant line and see whether anything fails; (4) classify the gap (missing boundary, missing assertion, over-mocked collaborator, wrong level); (5) add the test at the cheapest level that catches it.

## 7. Retrieval practice

Answers are in the solutions file.

1. Explain what failure each of unit, integration, contract and E2E tests is best at detecting, and one cost of each.
2. A service's logic lives mostly in SQL queries. Argue for or against a pyramid-shaped suite for it.
3. Why can 100% line coverage coexist with an off-by-one in production? What measures that gap?

## 10. Engineering review

Self-review checklist:

- Correctness: the characterization table was produced by running the code, not by reasoning; no pinned case was edited to make a refactor pass.
- Readability: test names state behavior; helper builders are small.
- Tests: deleting any single rule makes at least one test fail (check the three most important rules explicitly); no test depends on order or time.
- Edge cases: boundaries enumerated for every threshold.
- Security: the legacy code's injection or authorization issues are recorded in `DEBT.md` with risk ratings, not silently left.
- Refactoring discipline: each commit does one thing; a reviewer can follow it mechanically.
- Honesty: unpinned areas are listed.

Explain in writing: why you chose each seam technique; which test you trust least and why; one case where a mock would have been wrong and a fake right (or the reverse); which debt item you would fix next and what evidence ranks it first.

## 11. Mastery gate

Pass = at least 80/100 on the rubric, no critical failure.

Critical failures:

- Behavior changed inside a "pure refactor" commit without a corresponding test change.
- A characterization expectation was derived by reading the code instead of running it, and is wrong.
- Retries, sleeps, or quarantining used to make a flaky test pass.
- Mutation or coverage numbers reported that were not measured.
- Review comments that are all style and none on correctness/security in the review exercise 8.3 (the missing authorization and SQL injection must be found).

Evidence required: commit history or step log; test output (including 20 consecutive passes and randomized-order run); mutation results table; the review; `DEBT.md`; plus a closed-book (Mode A) re-derivation: given a fresh 40-line legacy function, produce a 10-case characterization suite and one seam in 45 minutes.

If failed: remedial exercise: repeat 8.1 on a different function (a 40-line tax calculator with a clock dependency) in Mode A, with one peer-injected regression you must catch; for review failures, review three real pull requests in an open-source repository you use (read only) and compare your comments against the checklist.
