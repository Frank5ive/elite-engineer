## 1. Engineering problem

"The course dashboard is slow." Three engineers respond. One adds a cache. One rewrites a loop in a "faster" style. One upgrades the database instance. A week later the dashboard is still slow for some users, the cache serves stale grades to teachers, and nobody can say which change helped, because nobody recorded how slow it was before, for whom, or on what.

Performance work fails in predictable ways: optimizing the wrong thing (the loop was 2% of the time; the real cost was 300 database queries); measuring wrongly (a cached result benchmarked as if it were computation, a single run on a noisy laptop, an average hiding a terrible tail); and "fixes" with hidden costs (complexity, staleness, memory) that exceed their benefit. The cure is a scientific loop: **baseline, hypothesis, measurement, result**, repeated, with a stop condition tied to a requirement.

## 2. Learning objectives

By the end you can:

1. Define a performance requirement as a measurable statement (metric, percentile, load, environment, threshold) and derive a baseline for an existing function or endpoint using a harness with warmup, repeated samples and a reported spread.
2. Profile a Python program with `cProfile` (and describe `py-spy` usage), identify the dominant cost from the profile, and show the profile before and after a change.
3. Read a database query plan (`EXPLAIN` / `EXPLAIN QUERY PLAN`), explain scan versus index search, and demonstrate a plan change from an index without claiming a speedup you have not measured.
4. Distinguish algorithmic complexity from constant factors by counting operations (not timing) and by measuring the crossover for your own data sizes.
5. Compute latency percentiles correctly, explain why averages and averages-of-percentiles mislead, and explain coordinated omission in load testing.
6. Design a benchmark that controls for warmup, caching, noise and dead-code effects, and write a regression check with a noise-aware threshold, tested on synthetic data.
7. Evaluate a caching proposal on hit rate, staleness, invalidation, memory and stampede risk, and test its behavior with an injected clock.
8. Write a report in which each optimization has baseline, hypothesis, method and result, and in which a negative result (the hypothesis was wrong) is recorded honestly.

## 3. First-principles explanation

### 3.1 The method: baseline, hypothesis, measurement, result

Performance is an empirical property of a program, a workload and an environment together. Change any of the three and the answer changes. So:

1. **Requirement.** What must be true? "p95 of `GET /dashboard` under 400 ms at 50 concurrent users on the staging environment with the 10,000-learner dataset." A requirement without a metric, percentile, load and environment is a wish. If there is no requirement, the right first output is a question to the stakeholder.
2. **Baseline.** Measure current behavior with the method you will reuse later. Record the commit hash, data size, hardware/VM, software versions, configuration, concurrency, number of samples and spread. A baseline you cannot reproduce is not a baseline.
3. **Locate the cost.** Profile or trace; do not guess. Typical result: one or two places dominate (the 80/20 shape is common, not guaranteed).
4. **Hypothesis.** A falsifiable statement: "Rendering the dashboard issues one query per course (N+1); replacing it with one joined query will reduce query count from about 1+N to 2 and reduce p95 by at least 30%." State the *predicted mechanism* and the *expected effect*.
5. **Change one thing.** Otherwise you cannot attribute the effect.
6. **Re-measure** with the identical method and report before/after with spread. Check correctness first (same outputs: use the characterization approach from 4.2).
7. **Decide.** Did it meet the requirement? Is the gain worth the complexity? If the hypothesis failed, record it, revert, and form a new one. Stop when the requirement is met; further optimization is a cost, not a virtue.

Amdahl's law bounds the payoff: if a part accounts for fraction `f` of total time and you speed it up by factor `s`, overall speedup is `1 / ((1 - f) + f / s)`. Eliminating 100% of a part that is 2% of runtime gains about 2%. This is why profiling precedes optimizing.

### 3.2 Profiling before optimizing

A **profiler** attributes cost to code. Two families: **deterministic/instrumenting** (hooks every call; accurate counts, adds overhead that distorts short functions) and **sampling** (periodically records the stack; low overhead, statistical, can profile a running process).

**Python `cProfile`** (stdlib, deterministic). Run as `python -m cProfile -o out.prof script.py` or programmatically. Read with `pstats`: `sort_stats("cumulative")` shows inclusive time (where time is spent including callees), `"tottime"` shows time inside the function itself. Columns: `ncalls`, `tottime`, `percall`, `cumtime`, `percall`, `filename:lineno(function)`. Overhead inflates functions that are called very many times, so confirm the winner with a plain timing harness.

```python
# Python 3.12 (verified; we check behavior equality first, and do not quote timings)
import cProfile, pstats, io
def normalize(s): return s.strip().lower()

def dedupe_slow(names):
    out = []
    for n in names:
        if normalize(n) not in [normalize(x) for x in out]:   # rebuilds a list every iteration
            out.append(n)
    return out

def dedupe_fast(names):
    seen, out = set(), []
    for n in names:
        k = normalize(n)
        if k not in seen:
            seen.add(k); out.append(n)
    return out

names = [f"User{i % 300} " for i in range(2000)]
assert dedupe_slow(names) == dedupe_fast(names)           # same behavior before comparing speed
pr = cProfile.Profile(); pr.enable(); dedupe_slow(names); pr.disable()
pstats.Stats(pr).sort_stats("cumulative").print_stats(4)
```

On the verified run the profile shows `normalize` called 556,850 times for 2,000 inputs (a deterministic count that follows from the algorithm), almost all inside the list comprehension; the profile makes the quadratic recomputation obvious without any timing claim from this lesson. Your absolute times will differ; run it and read your own.

**`py-spy`** (sampling, external): attaches to a running Python process without code changes. Typical commands: `py-spy top --pid <PID>` (live view), `py-spy record -o profile.svg --pid <PID>` (flame graph), `py-spy dump --pid <PID>` (current stacks, useful for hangs). May require elevated ptrace permissions, especially in containers. Checked against py-spy's `--help` (installed from PyPI): subcommands are `record`, `top` and `dump`; `record` takes `-p/--pid`, `-o/--output` and `-f/--format` (default flamegraph, SVG). Prefer it for production-like processes where instrumentation overhead or code changes are unacceptable. For async code, remember that a profiler sees the event loop; tested with `py-spy dump` on a process running one busy coroutine and two sleeping ones: only the running coroutine appears in the stack; suspended coroutines are invisible, so a sampling profiler cannot show what your awaiting tasks are waiting on.

**Flame graphs**: x-axis is proportion of samples (not time order), y-axis is stack depth; wide boxes are where time goes; look for wide plateaus at the top.

**PHP profiling options (checked against xdebug.org, the Moodle core source and GitHub project pages; confirm for your PHP/Moodle versions):**

- **Xdebug profiler**: `xdebug.mode=profile` writes cachegrind-format files viewable in KCachegrind/QCachegrind or webgrind; deterministic with significant overhead; do not leave on in production.
- **XHProf / Tideways** extensions: lightweight instrumenting profilers designed to be lower overhead. Moodle core has admin-level profiling integration: the settings page `profiling` (Site administration > Development > Profiling) is hidden unless one of the PHP extensions `tideways_xhprof`, `tideways` or `xhprof` is loaded (checked in `admin/settings/development.php`); its settings include enable, included/excluded URLs and a random-sampling frequency. Note that the `tideways/php-xhprof-extension` GitHub repository was archived in 2023, so check which extension build your PHP version can actually use.
- **SPX** (a simple profiling extension) and **Blackfire** (commercial service): other options (SPX is GPL-3.0 and actively maintained on GitHub when checked; Blackfire is a paid service with a free tier you should confirm yourself).
- Moodle also provides performance-oriented debug facilities such as the performance info footer and DB query counts (Site administration > Development > Debugging, the "Performance info" checkbox, stored as `$CFG->perfdebug`; checked in core source: ticking it prints performance info in the footer; the DB layer exposes `$DB->perf_get_reads()` and `$DB->perf_get_queries()`). For Moodle, query count and cache behavior are often the first-order explanation (MUC: the Moodle Universal Cache, present since Moodle 2.4 per the `@since` tags in core).

**Database profiling.** Application profilers show time waiting on the DB as one opaque cost; to look inside use the database: slow query log or `pg_stat_statements` (PostgreSQL; checked in the docs: add it to `shared_preload_libraries`, restart, then `CREATE EXTENSION pg_stat_statements` in the database), `EXPLAIN`, and `EXPLAIN (ANALYZE, BUFFERS)` (PostgreSQL; ANALYZE *executes* the query, so do not run it on destructive statements without a transaction you roll back). Count queries per request first: N+1 patterns show up as query counts that scale with data size.

### 3.3 Reading a query plan

`EXPLAIN` shows the plan the optimizer chose: scans (read all rows) versus index searches, join order and method, sort steps, estimated row counts. Check: estimated versus actual rows (large gaps indicate stale statistics), whether a filter column is indexed (and whether the index's column order matches the query; a composite index `(user_id, course_id)` serves `WHERE user_id = ? AND course_id = ?` and `WHERE user_id = ?`, but not `WHERE course_id = ?` alone, as a general rule of B-tree indexes), whether a function applied to a column (`LOWER(email) = ...`) defeats the index, and whether `LIMIT` with `ORDER BY` can use an index. Indexes cost write time and space; add them for measured read paths (2.3).

```python
# Python 3.12, SQLite 3.46 on the verified run (plan text is version-dependent)
import sqlite3
db = sqlite3.connect(":memory:")
db.execute("CREATE TABLE grades (id INTEGER PRIMARY KEY, user_id INT, course_id INT, value REAL)")
db.executemany("INSERT INTO grades (user_id, course_id, value) VALUES (?,?,?)",
               [(i % 500, i % 40, float(i % 100)) for i in range(20000)])
q = "SELECT value FROM grades WHERE user_id = ? AND course_id = ?"
def plan(): return [r[3] for r in db.execute("EXPLAIN QUERY PLAN " + q, (7, 3))]
print("before:", plan())   # ['SCAN grades']
db.execute("CREATE INDEX idx_grades_user_course ON grades (user_id, course_id)")
print("after: ", plan())   # ['SEARCH grades USING INDEX idx_grades_user_course (user_id=? AND course_id=?)']
```

The plan change (scan to index search) is a verified, deterministic fact. Whether it makes your endpoint faster is a *hypothesis* to be measured; small tables may be faster to scan, and PostgreSQL's planner may legitimately choose a sequential scan when a large fraction of rows match.

### 3.4 Algorithmic complexity versus constant factors

Big-O describes how cost grows with input size `n`; it ignores constants. Both matter, in different regimes. An `O(n^2)` algorithm with `n = 20` is irrelevant; an `O(n)` algorithm with a 1,000-times-larger constant can lose to `O(n log n)` until `n` is huge. Decide by your actual `n` (and its growth), not by textbook ideals. Python-specific constant factors: interpreter overhead per bytecode, allocation, attribute lookups, and calls to C-implemented builtins (which are fast per element) versus Python-level loops.

Count operations to make complexity observable without timing noise:

```python
# Python 3.12 (verified)
class Key:
    cmps = 0
    def __init__(self, v): self.v = v
    def __eq__(self, o): Key.cmps += 1; return self.v == o.v
    def __hash__(self): return hash(self.v)

def count_list(n):
    items = [Key(i) for i in range(n)]; Key.cmps = 0
    for i in range(n): Key(i) in items
    return Key.cmps
def count_set(n):
    items = {Key(i) for i in range(n)}; Key.cmps = 0
    for i in range(n): Key(i) in items
    return Key.cmps
# n=100,200,400 -> list: 5050, 20100, 80200 (= n(n+1)/2, quadratic); set: 100, 200, 400 (linear)
```

The equality-call counts are exact and reproducible: list membership does quadratic total work (doubling `n` quadruples it), the set does linear. This establishes the *growth*; whether it is worth changing at your `n` requires a timing measurement at your sizes. Typical wins in application code are not exotic: remove repeated work in loops, avoid N+1 queries, batch I/O, stream instead of materializing, choose a better data structure, and avoid doing work at all (pagination, filtering in the database).

### 3.5 Latency, percentiles and the tail

Latency distributions are skewed with a long right tail; the mean is dominated by it and describes nobody's experience. Report **percentiles** (p50, p95, p99, max) and the sample count. A user who loads a page making 10 backend calls experiences the *worst* of them often: if each call is slow 1% of the time, a request is hit by at least one slow call about `1 - 0.99^10` (roughly 10%) of the time (arithmetic assuming independence).

Computation. Nearest-rank percentile: sort the `n` samples; the p-th percentile is the value at index `ceil(p/100 * n) - 1` (0-based). Other definitions interpolate; state which you use. Do not average percentiles across servers or intervals: the p99 of a union is not the mean of the p99s. Keep histograms (fixed buckets) or the raw samples and compute from those.

```python
# Python 3.12 (verified)
import math, statistics
def percentile_nearest_rank(xs, p):
    if not xs: raise ValueError("empty")
    if not 0 < p <= 100: raise ValueError("p in (0,100]")
    s = sorted(xs)
    return s[math.ceil(p / 100 * len(s)) - 1]

data = list(range(1, 101))
assert [percentile_nearest_rank(data, p) for p in (50, 95, 99, 100)] == [50, 95, 99, 100]
lat = [10.0] * 99 + [5000.0]                         # synthetic, hand-constructed
assert statistics.mean(lat) == 59.9                  # the mean describes no request
assert percentile_nearest_rank(lat, 99) == 10.0 and percentile_nearest_rank(lat, 100) == 5000.0
a = [1.0] * 100; b = [1.0] * 98 + [100.0, 100.0]
assert percentile_nearest_rank(a + b, 99) == 1.0     # union p99 is not mean(p99_a, p99_b) = 50.5
```

Note the last line: with a tiny sample, a "p99" is determined by one or two points. Percentiles need enough samples: for p99 you want at least several hundred, for p99.9 several thousand (rule of thumb, not a theorem).

### 3.6 Measurement noise and benchmark design

Sources of noise: other processes, CPU frequency scaling and thermal throttling, shared cloud hosts, garbage collection and allocator state, JIT or warmup (OS file cache, DB buffer cache, import costs, Python's specializing adaptive interpreter, introduced by PEP 659 in 3.11, which warms up as code runs), network jitter, and test-order effects. Controls:

- **Warmup**, then discard those samples (and *also* report a cold-start measurement separately if cold start matters to users).
- **Many repeats**; report median and a spread measure (min/max, interquartile range, or median absolute deviation). The **minimum** is a good estimate of the noise-free cost for CPU-bound microbenchmarks (noise only adds time), but not for latency distributions, which you describe with percentiles.
- **Same environment before and after**; interleave A/B runs (A B A B) so drift affects both.
- **Isolate**: close other work, pin CPU if you can, fixed data and seeds, `time.perf_counter` for intervals (monotonic, high resolution; not `time.time`).
- **Defeat dead-code and caching illusions**: use results; vary inputs; make sure you measure computation and not a cache hit. Section 6 shows the classic trap.
- **Realistic data and workload**: production-like row counts, skew, and access mix; a benchmark on 100 rows predicts nothing about 10 million.
- **Statistical care**: with few samples, differences under the noise floor mean nothing. A significance test or bootstrap helps (choose the method before looking at the data; for a first cut, the rule below is a defensible heuristic).

```python
# Python 3.12 (verified): harness and a noise-aware regression rule, tested on SYNTHETIC samples
import statistics, time
def bench(fn, *, warmup=3, repeats=15, inner=1):
    for _ in range(warmup): fn()
    out = []
    for _ in range(repeats):
        t0 = time.perf_counter()
        for _ in range(inner): fn()
        out.append((time.perf_counter() - t0) / inner)
    return out

def regressed(base, new, *, min_ratio=1.10, k=3.0):
    """Flag only if the new median is >10% above baseline AND more than k*MAD above it."""
    mb, mn = statistics.median(base), statistics.median(new)
    mad = statistics.median(abs(x - mb) for x in base) or 1e-12
    return mn > mb * min_ratio and (mn - mb) > k * mad
```

Tested with seeded synthetic samples (`random.Random(42)`, `1.00 + gauss(0, 0.02)` for baseline and an unchanged run, `1.25 + gauss(0, 0.02)` for a slowed run): `regressed(base, same)` is False and `regressed(base, slow)` is True. These are constructed data for checking the *logic of the rule*, not measurements of anything. Thresholds (10%, 3 MAD) are starting points you must tune against the observed noise of your CI environment.

### 3.7 Load testing

A load test applies a controlled workload to a deployed system to find capacity, latency under load, and breaking behavior. Types: **load** (expected peak), **stress** (beyond capacity to see how it fails), **soak** (hours, to find leaks), **spike**. Design: realistic request mix and data, ramp-up, steady state long enough to be stable, then read the steady-state window only; separate load generator from system under test and watch the generator's own CPU (a saturated generator under-reports load).

**Open versus closed models.** A *closed* generator (N users, each waits for a response before the next request) slows down when the server slows, which masks the problem; an *open* generator (requests arrive at a fixed rate regardless) reflects real traffic. **Coordinated omission**: if the generator waits for slow responses before sending the next measured request, it omits the requests that *would have* been delayed, so reported tail latency is far too optimistic. Prefer tools and settings that measure from intended send time. Checked: k6's docs name this problem and recommend the arrival-rate executors (`constant-arrival-rate`, `ramping-arrival-rate`, open model) over VU-based ones; wrk2's README explains how it corrects for coordinated omission (plain `wrk` does not). Locust's documentation I could fetch did not discuss it, and its default user-based model is closed, so treat its tail latencies as suspect unless you confirm how your version schedules requests (still open: I searched Locust's stable docs for "coordinated omission" and found no mention).

**Little's law**: `L = lambda * W` (average number in the system = arrival rate times average time in system). If requests arrive at 100/s and each takes 0.5 s on average, about 50 are in flight at once; with a worker pool of 20, the queue grows without bound. Use it to size pools and sanity-check test results. (Values here are illustrative arithmetic.)

Tools (projects verified live on GitHub or their sites; check versions and features yourself): `wrk`/`wrk2`, `k6`, `locust`, `hey`, `ab` (limited), JMeter. Use throwaway environments you own; never aim a load test at a system you do not own.

### 3.8 Caching trade-offs

A cache trades **staleness and complexity** for **speed and reduced load**. Before adding one: confirm with a profile that the cached work is the bottleneck; estimate hit rate (a cache with a 10% hit rate is mostly overhead); define the **staleness the product can tolerate**; decide the **key** (everything that affects the value: user, locale, permissions!), **invalidation** (TTL, explicit invalidation on write, versioned keys), **eviction** (LRU, size bound), and **stampede protection** (many concurrent misses recomputing the same value: request coalescing/locking, jittered TTLs, serve-stale-while-revalidate). Hazards: caching per-user data under a shared key (a security bug: 4.3), unbounded memory growth, caching errors, and cache warming dependence at startup. "There are two hard things: cache invalidation, naming things" is a joke with a cost. Moodle's MUC provides application, session and request caches with definitions in `db/caches.php` (checked in core: `lib/db/caches.php` and `cache/README.md`; the mode is `application`, `session` or `request`); use it rather than ad hoc static arrays, and ensure keys include context and user dimensions where results depend on them.

```python
# Python 3.12 (verified): staleness is a designed behavior; the clock is injected
class TTLCache:
    def __init__(self, ttl, now): self.ttl, self.now, self.d = ttl, now, {}
    def get_or_load(self, key, loader):
        hit = self.d.get(key)
        if hit and self.now() - hit[1] < self.ttl: return hit[0], "hit"
        v = loader(key); self.d[key] = (v, self.now()); return v, "miss"
    def invalidate(self, key): self.d.pop(key, None)
# Tested: miss then hit; after the source changes the cache STILL returns the old value (stale)
# until the TTL elapses or invalidate() is called, then reloads.
```

Memoization (`functools.lru_cache`) is a cache too: same trade-offs, and it is process-local, which in a multi-worker deployment means N independent caches with N different staleness states.

### 3.9 Regression detection

Performance regresses silently. Defenses: **benchmarks in CI** on stable hardware with the noise-aware rule above, run nightly rather than per commit if they are slow; **budgets on cheap deterministic proxies** (query count per endpoint, allocations, operation counts) enforced as ordinary tests, because they are immune to machine noise (for example, "the dashboard issues at most 5 queries", asserted by counting statements through a SQLAlchemy event hook or Moodle's DB read counters, `$DB->perf_get_reads()`; SQLAlchemy's `before_cursor_execute` engine event, tested on SQLAlchemy 2.x, fires once per statement); **production SLO monitoring** with percentile metrics and alerts on burn rate; **bisecting** a regression with `git bisect run` over a benchmark script (0.2) once you have a reliable pass/fail criterion; and **change annotations** on dashboards (deploy markers). A regression test that flakes teaches people to ignore it: tune thresholds to the measured noise and fail only on clear effects.

## 4. Worked example

**Scenario.** `GET /dashboard` (FastAPI) lists a teacher's courses with the number of learners and the average grade per course. Complaint: slow for teachers with many courses. The numbers in this walk-through are placeholders you will replace with your own measurements (written as `<measured>`); the example demonstrates the structure of the work.

**Step 0, requirement.** "p95 under 400 ms at 20 concurrent teachers with 60 courses each and 500 learners per course, on the staging VM" (threshold is an example; get the real one from the stakeholder).

**Step 1, baseline.** Build the dataset with a seeded generator; start the app; send 300 warmup requests then 2,000 measured requests at fixed concurrency from a separate machine or process; record p50/p95/p99, request count, error count; record commit hash, VM size, Python/FastAPI/DB versions, `<measured>` results. Record the **query count per request** from the database log or a counting hook.

**Step 2, locate.** Query count per request is `<measured>`; if it is about `1 + 60 * 2`, the profile of time will show the DB driver and ORM dominating, and `EXPLAIN` on the per-course queries will show whether they scan. Naive code (shape only):

```python
def dashboard(teacher_id, db):
    out = []
    for c in db.scalars(select(Course).where(Course.teacher_id == teacher_id)):   # 1 query
        n = db.scalar(select(func.count()).where(Enrolment.course_id == c.id))    # N queries
        avg = db.scalar(select(func.avg(Grade.value)).where(Grade.course_id == c.id))  # N more
        out.append({"course": c.name, "learners": n, "avg": avg})
    return out
```

**Step 3, hypothesis (written before changing anything).** "The cost is the `2N + 1` sequential queries, each paying a round trip and, if `grades.course_id` is unindexed, a table scan. Replacing them with one grouped query and adding an index on `grades(course_id)` will cut query count to 1-2 and reduce p95 by at least 50%. If the plan shows index use already and p95 does not fall, the hypothesis is wrong and the cost is elsewhere (serialization, auth)."

**Step 4, change one thing at a time.** (a) Check correctness harness: a test comparing old and new outputs over the seeded dataset (4.2). (b) Replace with `GROUP BY` queries (SQLAlchemy 2.x `select(...).group_by(...)`; assemble with your models). Re-measure. (c) Only then add the index; re-measure; compare `EXPLAIN` before/after. Two separate measurements, so you can attribute each effect.

**Step 5, results table.** Columns: change, query count, p50, p95, p99, samples, errors, notes (`<measured>` for every number). Include a row for any change that did **not** help.

**Step 6, decide.** If the requirement is met, stop. Consider caching only if the requirement is still unmet and the profile shows the grouped query itself dominating; then follow section 3.8's checklist.

**PHP/Moodle variant.** Same loop: baseline with Moodle's performance info and DB query counts for the page; locate with an Xdebug/XHProf-style profile on a development site (Xdebug or an XHProf-style extension, as above); typical hypotheses are per-row `$DB->get_record` calls inside loops (replace with one `get_records_sql` using `IN` via `$DB->get_in_or_equal`), repeated capability checks (cache within the request), and uncached expensive computations (use MUC). Checked in core source: `$DB->get_in_or_equal($items, $type = SQL_PARAMS_QM, $prefix = 'param', $equal = true, $onemptyitems = false)` returns `[$sql, $params]`, and an empty array throws unless `$onemptyitems` is set; confirm both for your version.

## 5. Production perspective

- **Maintainability**: an optimization that makes code unreadable must pay for itself in a measured, requirement-relevant way; comment the measurement ("see docs/perf/2025-03-dashboard.md") next to the odd code.
- **Correctness**: optimizations are behavior changes in risk terms; keep the old implementation as an oracle in tests for a period (property: new equals old on generated inputs, 4.2).
- **Performance** (of the tooling): profilers perturb; confirm with a plain timer.
- **Security**: caches and shared keys are access-control hazards (4.3); verbose profiling data may contain user data.
- **Failure handling**: caching can hide a dependency outage (good: degradation) or keep serving wrong data (bad); define it (4.3).
- **Observability**: percentile latency histograms per endpoint, query counts, cache hit rates, pool saturation, queue depth, GC/memory; compare before/after deploys.
- **Operations**: capacity plan from Little's law and measured service times; load test before a known peak (term start, exam day); keep a runbook for degrading features under load.

**What a senior engineer does differently.** Asks for the requirement and the measured baseline before touching code. Counts queries before profiling CPU. Writes the hypothesis down and predicts the number. Distrusts any speedup that is too good (check caching, dead code, different data). Reports percentiles with sample counts and environment. Removes work instead of making it faster. Leaves a regression guard (a query-count test) behind.

**Common beginner mistakes and diagnosis.**

- Optimizing without profiling. Diagnose: ask "what share of total time does this code account for?" (Amdahl).
- Benchmarking once, on a laptop with other things running. Diagnose: repeat 15 times; look at spread.
- Measuring a warm cache and calling it computation, or measuring a cold one and calling it steady state. Diagnose: instrument the underlying call count.
- Averages. Diagnose: ask for p95/p99 and the count.
- Different data/environment before and after. Diagnose: compare the recorded environment line.
- Micro-optimizing Python loops while 200 queries run. Diagnose: query counts.
- Adding indexes everywhere. Diagnose: write cost and plan; check unused indexes in database statistics (PostgreSQL: `pg_stat_user_indexes.idx_scan`, checked in the docs).
- Believing `EXPLAIN` alone proves speed. It shows intent, not time (use `ANALYZE` variants for actuals).

## 6. Failure laboratory

A teammate benchmarks a function and reports "15 samples, great consistency, and it's extremely fast". The function is decorated with `lru_cache`. Predict, before running: how many times does the function *body* execute across the warmup plus the 15 timed samples, and what does the benchmark actually measure?

```python
import time
from functools import lru_cache

body_calls = 0
@lru_cache(maxsize=None)
def expensive(n: int) -> int:
    global body_calls
    body_calls += 1
    return sum(i * i for i in range(n))

def bench(fn, warmup=3, repeats=15):
    for _ in range(warmup): fn()
    out = []
    for _ in range(repeats):
        t0 = time.perf_counter(); fn(); out.append(time.perf_counter() - t0)
    return out

samples = bench(lambda: expensive(100_000))
print("samples:", len(samples), "| body executed:", body_calls)
```

### Reveal (read after predicting)

The body executes exactly **once** (verified output: `samples: 15 | body executed: 1`), during the first warmup call. All 18 calls after that, including all 15 timed ones, are cache lookups. The benchmark measures the cost of an `lru_cache` hit (tens of nanoseconds to hundreds, platform dependent; measure it if you care), not the function. The "great consistency" is the consistency of a trivial operation.

Systematic diagnosis for suspiciously good benchmark results:
1. Count the work: add a counter or use `cache_info()`; compare `hits`/`misses`.
2. Vary the input across samples (or call `expensive.cache_clear()` per sample if you intend to measure cold cost) and decide explicitly which scenario you are measuring (cold, warm, mixed with a realistic hit rate).
3. Check that results are used (dead-code elimination is rarer in CPython than in compiled languages, but caches, branch shortcuts and skipped I/O occur).
4. Compare the order of magnitude to a back-of-envelope estimate (operations times plausible cost per operation); a result off by orders of magnitude is a measurement bug until proven otherwise.
5. Re-run in an A/B interleaved fashion with the suspect removed.

The same logic applies to a database buffer-cache or an HTTP cache in front of a load test: record which cache state you measured.

## 10. Engineering review

Self-review checklist: the requirement has metric, percentile, load and environment; the baseline is reproducible by one command; the harness was tested; warmup and repeats are reported; spreads and sample counts accompany every number; every claim of "faster" is backed by before/after with identical method and data; correctness equivalence tested; each optimization has a hypothesis recorded earlier in the history; failed hypotheses are in the report; the cache has a stated staleness bound, key design including user/context, and an invalidation test; the guard tests are deterministic (query counts) where possible; no secrets or personal data in profiling output; the environment fingerprint is saved.

Explain in writing: why you stopped where you did; which measurement you do not trust and what you would do to improve it; what you would measure first in production; what the largest remaining cost is and why you left it.

## 11. Mastery gate

Pass = at least 80/100 on the rubric, no critical failure, with evidence: raw result files, environment fingerprints, harness tests, hypothesis log with timestamps in version control, the guard failing and passing, and a closed-book (Mode A) exercise: given an unfamiliar 50-line function and a dataset generator, produce within 60 minutes a baseline method, a profile-based hypothesis, one verified change, and an honest result including spread.

Critical failures:
- Any performance number that was not measured by you (or lacks environment and method).
- An optimization claimed without a before/after under identical conditions.
- A benchmark that measures a cache or dead code unknowingly (demonstrated by your own counters).
- Behavior changed by an optimization (outputs differ) without being reported.
- A cache without a stated staleness bound, or a shared cache key for user-specific data.
- Averages reported as latency without percentiles.
- Load testing any system you do not own.

If failed, remedial exercise: pick 8.2 and redo it with a different function pair, adding an A/B interleaved harness and a written explanation of the noise floor, reviewed by a peer who tries to break your measurement; for percentile errors, redo 8.1 with a peer-supplied adversarial dataset.
