## 1. Engineering problem

A teammate ships a checkout change. The test suite is green. In production, customers are charged twice. Investigation: the test patched `shop.gateway.charge`, but the code under test had done `from shop.gateway import charge`, so the patch never applied; the test called a hand-made `Mock` whose return value nobody checked, and `assert_called_once` (without parentheses) asserted nothing. Separately, another test fails once a week because it compares `datetime.now()` to a string, and a third passes only when run after the one that creates a file in the working directory.

Tests that cannot fail, tests that fail randomly, and tests coupled by hidden state are worse than no tests: they train the team to ignore red builds. This lesson is about writing tests that fail for the right reason, deterministically, and about the discipline of putting a net under code you did not write before touching it.

## 2. Learning objectives

After this lesson, closed-book, you can:

1. Write pytest tests with plain `assert`, `pytest.raises(..., match=...)` and `@pytest.mark.parametrize` (with readable ids) for a function with six or more behaviors.
2. Build fixtures at the correct scope, with teardown via `yield`, using `tmp_path` and `monkeypatch`, and explain why each test leaves no residue.
3. Explain "patch where it is used" and demonstrate the failure of patching where it is defined; use `autospec` to catch wrong signatures.
4. Distinguish dummy, stub, spy, mock and fake, and replace a mock-heavy test with a fake behind a `Protocol`.
5. Make a time- and randomness-dependent function deterministic by injection rather than patching.
6. Write a property-based test with Hypothesis, interpret a falsifying example, and say when a property test is the wrong tool.
7. Write characterization tests that pin down the current behavior of an untested function, including behavior you believe is wrong, before refactoring.

## 3. First-principles explanation

### 3.1 What a test is for

A test is an executable claim: given this setup and action, this observable outcome follows. A good test has one reason to fail, needs no network, real time or ordering assumptions, and asserts on behavior visible through the public interface, not on call choreography (unless the interaction is the behavior, for example "the gateway was not called"). Structure: Arrange, Act, Assert; name for behavior.

### 3.2 pytest essentials

pytest collects `test_*.py` files and `test_*` functions, runs them, and rewrites `assert` statements so a failure shows the compared values (assertion introspection). No base class needed.

```python
# test_pricing.py (the function under test is in the Section 4 package)
import pytest
from shop.pricing import apply_discount

@pytest.mark.parametrize(
    "total, code, expected",
    [(1000, None, 1000), (1000, "SAVE10", 900), (1000, "save10", 900),
     (1000, "HALF", 500), (1000, "BOGUS", 1000), (1, "HALF", 1), (0, "HALF", 0)],
    ids=["no-code", "save10", "case-insensitive", "half", "unknown", "rounds-down-discount", "zero"],
)
def test_apply_discount(total, code, expected):
    assert apply_discount(total, code) == expected

def test_negative_total_rejected():
    with pytest.raises(ValueError, match="negative"):
        apply_discount(-1, None)
```

- `parametrize` generates one test per row; failures name the row. Use `ids=` when the values are not self-describing. Do not use it to hide complex branching inside the test body.
- `pytest.raises(E, match=regex)` checks type and message; always assert on the narrowest type. Inspect `excinfo.value` for attributes (Lesson 1.2's `__cause__`).
- Useful flags: `-x`, `-k expr`, `-q`, `-ra`, `--lf`, `-s`, `--tb=short`, `--pdb` (all listed by `pytest --help` on pytest 9.1, checked).
- Markers: `@pytest.mark.skip`, `skipif`, `xfail(strict=True)`. An `xfail(strict=True)` documents a known bug and turns red when someone fixes it, prompting removal of the marker. Unexplained skips rot.
- Configuration lives in `pyproject.toml` under `[tool.pytest.ini_options]` (`testpaths`, `pythonpath`, `addopts`). Register custom markers there to catch typos.

### 3.3 Fixtures

A fixture is a function providing a test dependency, requested **by naming it as a parameter**. pytest resolves the graph, creates each fixture, injects it, and tears down in reverse order. Fixtures can depend on other fixtures. Shared fixtures live in `conftest.py`, found automatically by directory.

```python
import pytest

@pytest.fixture
def db_conn():
    conn = open_connection()      # setup
    yield conn                    # the test runs here
    conn.close()                  # teardown: runs even if the test failed
```

**Scope** controls how often the fixture is built: `function` (default; fresh per test), `class`, `module`, `package`, `session`. Wider scope saves time and costs isolation. Rule: default to function scope; widen only for expensive, **immutable or reset-able** resources (a database schema created once, with each test rolling back its own transaction). A mutable object at session scope is a test-order dependency (Lesson 1.1's shared mutable state, now in your test suite).

Related built-ins:

- `tmp_path` (a fresh `pathlib.Path` directory per test), `tmp_path_factory` for wider scopes.
- `monkeypatch`: `setattr`, `delattr`, `setenv`, `delenv`, `chdir`, `setitem`; everything is **undone automatically** at test end.
- `capsys`/`capfd` capture output; `caplog` captures log records (Lesson 1.3).

```python
import os

def test_tmp_path_and_env(tmp_path, monkeypatch):
    f = tmp_path / "name.txt"
    f.write_text("  ann \n", encoding="utf-8")
    monkeypatch.setenv("APP_NAME", "x")
    assert os.environ["APP_NAME"] == "x"

def test_env_restored_after_previous_test():
    assert "APP_NAME" not in os.environ        # monkeypatch undid it
```

Autouse fixtures apply to every test in scope: reserve them for global safety nets (for example failing any network connection).

### 3.4 Test doubles

Terms (after Meszaros; vocabulary conventions vary, so define yours in the team's docs):

| Double | What it does | Use when |
|---|---|---|
| Dummy | Passed but never used | A required parameter is irrelevant |
| Stub | Returns canned answers | You need to steer the code down a path |
| Spy | Records calls for later assertions | The call itself is the behavior |
| Mock | Pre-programmed with expectations that fail the test if not met (`unittest.mock.Mock` is often used as stub/spy; mock-as-expectation is one style) | Verifying an outgoing interaction |
| **Fake** | A working lightweight implementation (in-memory repository, fake gateway with state) | Behavior matters over multiple calls; you want tests that read like usage |

Prefer **fakes over mocks** for collaborators your code uses substantively: a fake gateway that records charges and can be told to decline a user lets tests assert on outcomes (`gateway.charges == [...]`, status `declined`) rather than on call choreography. The fake must be kept honest: type it against the same `Protocol` as the real thing (Lesson 1.3), and for important seams run a small **contract test** suite against both fake and real (in an integration environment) so they cannot drift.

Prefer mocks/spies for pure outgoing side effects with no state to query (send email, publish event), and for failure injection that is awkward to script in a fake. Over-mocking produces tests coupled to implementation: a harmless refactor turns them red, while real bugs stay green.

### 3.5 `unittest.mock` and its pitfalls

`unittest.mock.Mock`/`MagicMock` create objects that accept any call and attribute access and record them. `mock.patch("pkg.module.name")` replaces `name` in that module's namespace for the duration of a `with` block or decorated test.

**Patch where it is looked up, not where it is defined.** `from shop.gateway import charge` copies a reference into `shop.orders_naive`'s namespace at import time. Replacing `shop.gateway.charge` afterwards changes the original namespace only; `orders_naive.charge` still points at the real function. The lookup site is the one to patch: `mock.patch("shop.orders_naive.charge")`. (Equivalently, the import binds a name, exactly the aliasing model of Lesson 1.1.)

Pitfall list, each verified in Section 4.3's tests:

1. **Wrong patch target**: the patch silently does nothing, and the real code runs.
2. **No spec**: a bare `Mock` accepts any call signature, so tests keep passing after the real function's signature changes. Use `autospec=True` (or `create_autospec`, or `spec=`) so calls are checked against the real signature.
3. **Assertion typos**: attribute access like `m.assert_called_once` (no call parentheses) asserts nothing. A non-`unsafe` Mock raises `AttributeError` for attribute names starting with `assert`, `assret`, `asert`, `aseert` or `assrt` (since Python 3.5, per the `unittest.mock` docs: before 3.5 such typos silently passed), and since Python 3.12 also for names like `called_once_with`, `called_with`, `not_called` that look like an assertion missing the `assert_` prefix (gh-100690). Both were checked on 3.13.5. A missing `()` is still silent, and other misspelled attributes of a plain Mock (for example `m.charge.caled_once_with`) are accepted, so rely on `spec`/`autospec` and real assertions rather than on this guard. Prefer `assert_called_once_with(...)` and consider a linter.
4. **Mutable argument capture**: mocks store references to arguments, so later mutation changes what the mock "remembers" (Lesson 1.1 again).
5. **Patching what you own**: if you have to patch internals of your own module to test it, the design needs a seam (a parameter or a Protocol), not a deeper patch.
6. **Leaking patches**: use the context manager, decorator, or pytest's `monkeypatch`; never start a patcher without stopping it.

`monkeypatch` and `mock.patch` do the same job at different levels of abstraction; use `monkeypatch` for environment, cwd and simple attribute replacement, `mock.patch(..., autospec=True)` when you need call recording with signature checking.

### 3.6 Deterministic tests: time, randomness, order, environment

Sources of nondeterminism and the remedy for each:

| Source | Remedy |
|---|---|
| Current time | Inject a `Clock` (Lessons 1.1, 1.3); never `sleep` in tests. Time-travel libraries such as freezegun exist (third-party; check maintenance and compatibility before adopting); injection is the dependency-free default |
| Randomness | Inject a `random.Random(seed)` or an id factory, assert on properties when exact values are irrelevant |
| Test order | No shared mutable state; function-scoped fixtures; run the suite in random or reverse order periodically (a plugin such as pytest-randomly exists and works, checked; get team agreement before adding a dependency to a team repo) |
| Environment variables, cwd | `monkeypatch` |
| Files | `tmp_path` |
| Network | Fakes; an autouse fixture that blocks sockets as a safety net |
| Concurrency | Test the logic single-threaded; test synchronization separately with deterministic coordination (events, barriers), not sleeps |
| Dict/set ordering | Dicts are insertion-ordered; sets are not ordered meaningfully: compare as sets or sort |

A flaky test is a bug report about the test or the code. Diagnose; do not "rerun until green".

### 3.7 Property-based testing (Hypothesis, introduction)

Instead of choosing examples, state a **property** that must hold for all inputs of a described kind, and let the library generate many inputs, then **shrink** a failing one to a minimal counterexample.

```python
from hypothesis import given, strategies as st
from shop.pricing import apply_discount

@given(st.integers(min_value=0, max_value=10**9), st.sampled_from([None, "SAVE10", "HALF", "x"]))
def test_discount_never_increases_and_never_negative(total, code):
    out = apply_discount(total, code)
    assert 0 <= out <= total

@given(st.lists(st.integers()))
def test_dedupe_idempotent_and_preserves_membership(xs):
    once = list(dict.fromkeys(xs))
    assert list(dict.fromkeys(once)) == once
    assert set(once) == set(xs) and len(once) == len(set(xs))
```

Both pass locally. Now a deliberately weak function:

```python
from hypothesis import given, strategies as st

def clamp(x, lo, hi):
    return max(lo, min(x, hi))

@given(st.integers(), st.integers(), st.integers())
def test_clamp(x, lo, hi):
    assert lo <= clamp(x, lo, hi) <= hi
```

This **fails** (run locally): Hypothesis finds an input where `lo > hi`, a precondition the example-based test author never considered. The fix is a decision, not a patch: either the function must raise `ValueError` when `lo > hi` (and the property then assumes `lo <= hi` through `hypothesis.assume` or a constrained strategy), or the contract allows it and the property changes. This is the value: it forces the contract to be stated.

Patterns: round trip, idempotence, invariants (sorted, length preserved), oracle, "does not crash". Limits: hard for I/O-heavy code; inputs must be constrained; keep failing examples as ordinary tests via `@example(...)`. Property tests complement example tests.

### 3.8 Characterization tests for legacy code

When code has no tests and you must change it (Lesson 4.2 covers refactoring strategy), first **pin its current behavior**: call it with representative and awkward inputs, record what it actually returns (including results you think are bugs), and assert exactly that. The tests do not say the behavior is right; they say it is *unchanged*. Procedure:

1. Find a seam: a function boundary where you can call the code without the whole system. If none exists, the smallest behavior-preserving change to create one (extract a parameter) comes first, done carefully and by hand.
2. Write a test with an assertion you expect to fail (`assert result == None`), run it, read the real value, replace the assertion with the observed value.
3. Cover branches: run coverage (`pytest --cov` needs the pytest-cov plugin, checked: `--cov=pkg --cov-branch` worked) and add inputs until the branches you intend to change are exercised.
4. Mark surprising behavior with a comment (`# CURRENT behavior, believed wrong, ticket #...`). Do not fix it in the same change as the refactor.
5. Refactor in small steps, running the tests after each. Then, separately, change behavior on purpose and update the tests, in a distinct commit.

A characterization suite is scaffolding, not a specification.

## 4. Worked example: testing a checkout

### 4.1 Naive code and the test you should not write

`orders_naive.py`:

```python
# src/shop/orders_naive.py
import datetime
import random

from shop.gateway import charge, PaymentDeclined


def checkout(user: str, total_cents: int) -> dict:
    order_id = f"ord-{random.randint(1000, 9999)}"
    placed = datetime.datetime.now().isoformat()
    try:
        receipt = charge(user, total_cents)
    except PaymentDeclined:
        return {"id": order_id, "status": "declined", "placed": placed}
    return {"id": order_id, "status": "paid", "receipt": receipt, "placed": placed}
```

Problems for testing: `random` and `datetime.now()` are hard-wired, the gateway function is imported by name, and the only way to test it is to patch three things. The "test" most people write:

```python
from unittest import mock
from shop import orders_naive

def test_checkout():
    with mock.patch("shop.gateway.charge", return_value="rcpt"):   # wrong target
        result = orders_naive.checkout("ann", 500)
    assert result["status"] == "paid"
```

It fails here because the unpatched `charge` raises (our stub `gateway.charge` refuses to touch the network). In a real codebase where the call really reaches an HTTP API, the same mistake produces a real charge from a test run.

### 4.2 Improved design: inject the seams

`orders.py` takes its collaborators as parameters, typed with `Protocol`s:

```python
# src/shop/orders.py
from __future__ import annotations

import random
from collections.abc import Callable
from datetime import datetime
from typing import Protocol

from shop.gateway import PaymentDeclined


class Gateway(Protocol):
    def charge(self, user: str, amount_cents: int) -> str: ...


class Clock(Protocol):
    def now(self) -> datetime: ...


def _default_ids() -> str:
    return f"ord-{random.randint(1000, 9999)}"


class Checkout:
    def __init__(self, gateway: Gateway, clock: Clock, new_id: Callable[[], str] = _default_ids) -> None:
        self._gateway = gateway
        self._clock = clock
        self._new_id = new_id

    def checkout(self, user: str, total_cents: int) -> dict[str, str]:
        if total_cents <= 0:
            raise ValueError("total_cents must be > 0")
        order = {"id": self._new_id(), "placed": self._clock.now().isoformat()}
        try:
            receipt = self._gateway.charge(user, total_cents)
        except PaymentDeclined:
            return {**order, "status": "declined"}
        return {**order, "status": "paid", "receipt": receipt}
```

What changed and why:

| Before | After | Reason |
|---|---|---|
| `from gateway import charge` and call | `Gateway` Protocol passed to `__init__` | Test supplies a fake; no patching |
| `datetime.now()` | `Clock` Protocol | Deterministic timestamps |
| `random.randint` inline | `new_id` callable with a default | Deterministic ids, production default unchanged |
| No input validation | `ValueError` on non-positive totals | A decision made visible and testable |
| Returns `dict` with mixed keys | `dict[str, str]` and one construction path | Easier assertions |

The production default is wired at the composition root (the app's startup, Lesson 2.2); `Checkout` never builds its own collaborators.

### 4.3 The tests

`tests/conftest.py` provides a **fake** gateway and a fake clock:

```python
# tests/conftest.py
from datetime import datetime

import pytest

from shop.gateway import PaymentDeclined


class FakeClock:
    def __init__(self, now: datetime) -> None:
        self._now = now

    def now(self) -> datetime:
        return self._now


class FakeGateway:
    """A fake: a working in-memory implementation, not a script of canned answers."""

    def __init__(self) -> None:
        self.charges: list[tuple[str, int]] = []
        self.decline_users: set[str] = set()

    def charge(self, user: str, amount_cents: int) -> str:
        if user in self.decline_users:
            raise PaymentDeclined(user)
        self.charges.append((user, amount_cents))
        return f"rcpt-{len(self.charges)}"


@pytest.fixture
def clock() -> FakeClock:
    return FakeClock(datetime(2024, 1, 2, 3, 4, 5))


@pytest.fixture
def gateway() -> FakeGateway:
    return FakeGateway()
```

`tests/test_orders.py`:

```python
# tests/test_orders.py
import pytest

from shop.orders import Checkout


@pytest.fixture
def checkout(gateway, clock):
    return Checkout(gateway, clock, new_id=lambda: "ord-1")


def test_paid_order(checkout, gateway):
    assert checkout.checkout("ann", 500) == {
        "id": "ord-1", "placed": "2024-01-02T03:04:05", "status": "paid", "receipt": "rcpt-1"}
    assert gateway.charges == [("ann", 500)]


def test_declined_order_is_reported_not_raised(checkout, gateway):
    gateway.decline_users.add("bob")
    assert checkout.checkout("bob", 500)["status"] == "declined"
    assert gateway.charges == []


@pytest.mark.parametrize("bad", [0, -1])
def test_rejects_non_positive_total(checkout, gateway, bad):
    with pytest.raises(ValueError):
        checkout.checkout("ann", bad)
    assert gateway.charges == []
```

Notes: the tests assert outcomes (`status`, `receipt`, `gateway.charges`), not call choreography. The declined path and the invalid-total path both assert that **no charge was made**; those negative assertions catch the double-charge class of bug.

The mock pitfalls, each as a passing test that demonstrates the trap (`tests/test_mock_pitfalls.py`):

```python
# tests/test_mock_pitfalls.py
from unittest import mock

import pytest

from shop import orders_naive


def test_patch_where_it_is_used():
    with mock.patch("shop.orders_naive.charge", return_value="rcpt-9") as m:
        result = orders_naive.checkout("ann", 500)
    assert result["status"] == "paid" and result["receipt"] == "rcpt-9"
    m.assert_called_once_with("ann", 500)


def test_patch_where_it_is_defined_does_not_work():
    with mock.patch("shop.gateway.charge", return_value="rcpt-9"):
        with pytest.raises(RuntimeError, match="real network"):
            orders_naive.checkout("ann", 500)   # orders_naive already holds its own reference


def test_autospec_catches_wrong_signature():
    with mock.patch("shop.orders_naive.charge", autospec=True) as m:
        m.return_value = "r"
        with pytest.raises(TypeError):
            m("only-one-argument")


def test_unspec_mock_accepts_anything():
    m = mock.Mock()
    m.charge("a", "b", "c", nonsense=1)          # no error: the mock has no spec
    m.assert_called_once  # noqa: B018 -- attribute access, not a call: asserts nothing
    assert m.charge.called


def test_misspelled_assert_is_rejected_by_modern_mock():
    m = mock.Mock()
    with pytest.raises(AttributeError):
        m.assert_called_once_wiht(1)
    with pytest.raises(AttributeError):
        m.called_once_with(1)      # 3.12+ rejects names like called_once_with (3.13.5 checked)
```

`tests/test_env.py` demonstrates `tmp_path` and `monkeypatch` isolation; `tests/test_props.py` holds the Hypothesis tests of Section 3.7 and a characterization test. The whole package runs with `python -m pytest` using `pythonpath = ["src"]` in the pytest configuration (or after an editable install); 24 tests passed locally.

## 5. Production perspective

**Maintainability.** Tests are code: fixtures instead of copy-paste, no logic beyond arrange/act/assert, behavior-revealing names.

**Correctness: what to test.** Boundaries (0, 1, max, max+1, empty), error paths, state transitions, and the "must not happen" assertions (no charge, no write, no email). Test behavior at the level that is stable: a refactor that keeps behavior should not break tests.

**The pyramid** (Lesson 4.2 expands): many fast unit tests, fewer integration tests against real components (a real PostgreSQL in a container, real HTTP through the app's test client), very few end-to-end tests. Mocks cannot tell you your SQL is valid; do not mock the database in a test whose purpose is the query (Lesson 2.3).

**Suite speed.** Measure with `pytest --durations=10`; parallelize only after tests are order-independent (the pytest-xdist plugin provides `-n`; third-party).

**Security.** Tests must never contact real third-party services or use production credentials. Use obviously fake secrets (`s3cret`) and assert they do not appear in output (Lesson 1.3). A guard fixture that blocks sockets protects you from your own mistakes.

**CI.** Same command locally and in CI; fail the build on test failure, type errors (Lesson 1.3), and, if the team agrees, a coverage floor. Coverage measures executed lines, not asserted behavior: 100% coverage with weak assertions proves little. Treat the number as a smoke detector, not a goal.

**What a senior engineer does differently.**

- Writes the failing test first for a bug fix, and shows it failing on the old code (the project's gate demands this).
- Designs seams for time, randomness, I/O and network before they are needed.
- Uses fakes for owned collaborators and mocks sparingly; reads a mock-heavy test as a design smell.
- Treats flakiness as a defect with an owner and a deadline.
- Pins down legacy behavior before changing it and separates "refactor" commits from "behavior change" commits.
- Follows the team's test style; proposes changes with evidence.

**Common beginner mistakes and diagnosis.**

| Symptom | Likely cause | Diagnose |
|---|---|---|
| Test passes but the bug exists | Wrong patch target; no assertion; mock without spec | Break the production code on purpose: does the test fail? (mutation check by hand) |
| Passes alone, fails in the suite (or vice versa) | Shared state: module-level objects, wider-scope fixtures, env/cwd changes | Run the test alone, run with `-p no:randomly` or in reverse (`pytest tests/a.py tests/b.py` order swap), bisect by file |
| Fails on some days or hours | Real time/timezone/locale, randomness | Search for `now(`, `time()`, `random`, `uuid4`; inject |
| Fails only in CI | Environment difference: missing env var, working directory, Python version, parallelism | Print `sys.version`, `os.getcwd()`, relevant env; reproduce in a clean container |
| Mocks everywhere, refactor breaks all tests | Tests coupled to implementation | Identify which assertions are about calls rather than outcomes; replace with a fake |
| `AttributeError` on a mock chain | `MagicMock` auto-creates attributes; typo accepted | Use `spec`/`autospec` |
| Slow suite | Real I/O, `sleep`, broad fixtures | `--durations=10` |

### 5.1 Optional: concurrency and profiling orientation

Concurrency causes most non-reproducible failures; async testing is Lesson 2.6. For slow code, `pytest --durations=10` then `python3 -m cProfile -s cumulative` (method in Lesson 4.4).

## 6. Failure laboratory

Mode A. A teammate asks you to review this test before merging. Predict (1) whether it passes, (2) whether the production code is actually tested, (3) every defect you can find in it, **before running** it. The file is `shop/orders_naive.py` from Section 4.1.

```python
from unittest import mock
from shop import orders_naive

def test_checkout_charges_once():
    gateway = mock.Mock()
    gateway.charge.return_value = "rcpt-1"
    with mock.patch("shop.gateway.charge", gateway.charge):
        try:
            result = orders_naive.checkout("ann", 500)
        except Exception:
            result = {"status": "paid"}
    gateway.charge.assert_called_once
    assert result["status"] == "paid"
```

### Reveal (read after predicting)

It **passes**, and it tests nothing:

1. The patch target is `shop.gateway.charge`, but `orders_naive` calls its own imported name, so the real `charge` runs, raises `RuntimeError`, and the `try/except Exception` swallows it.
2. The fallback `result = {"status": "paid"}` fabricates the expected answer, so the final assert is a tautology.
3. `gateway.charge.assert_called_once` lacks parentheses: no assertion occurs (the call never happened anyway).
4. The bare `Mock` has no spec, so even a correct patch would not catch a signature change.
5. The test would never fail when the production code is broken: this is the key property to check in review.

Systematic diagnosis for "does this test test anything?":

1. **Break it on purpose**: change production code to return `"declined"`, or comment out the charge call. Does the test fail? If not, it proves nothing. This hand-run mutation check is the single most valuable review technique.
2. Look for `try/except` and conditionals inside the test body: they can swallow failures.
3. Check every assertion is an executed expression (`assert`, `assert_called_once_with(...)` with parentheses), and that a failing value would produce a failing result.
4. Confirm the patch target is the lookup site, by asserting the mock was actually called (`m.assert_called_once_with(...)`) or by running with `autospec=True`.

```python
import time

STOCK = {"A1": 10, "B2": 0, "C3": 5}
THRESHOLD = 3
_reservations = []

def reserve(sku, qty):
    if qty < 0:
        raise ValueError("qty")
    have = STOCK.get(sku)
    if have is None:
        return False
    if have - qty < 0:
        return False
    STOCK[sku] = have - qty
    _reservations.append((sku, qty, time.time()))
    return True

def restock(sku, qty):
    STOCK[sku] = STOCK.get(sku, 0) + qty
    return STOCK[sku]

def low_stock():
    return sorted(s for s, q in STOCK.items() if q < THRESHOLD)

def report():
    lines = []
    for sku, qty, ts in _reservations:
        lines.append(f"{sku}:{qty}@{int(ts)}")
    return "\n".join(lines)
```

## 10. Engineering review

Checklist before submitting:

- **Fails for the right reason.** For every test, can you name the production change that would turn it red? Did you actually try it for at least five tests?
- **Determinism.** No real clock, randomness, network, or order dependence. Run the suite alone, reversed, and twice in a row.
- **Isolation.** Every fixture's scope is justified; no module-level state survives a test; `tmp_path` for files; `monkeypatch` for env/cwd.
- **Doubles.** Each mock/patch has a stated reason; patch targets are lookup sites; `autospec` where signatures matter; fakes typed against the real Protocol.
- **Assertions.** Outcomes over choreography; negative assertions for "must not happen"; no `assert x is not None` as the only check; no try/except in tests.
- **Properties.** Each Hypothesis property states a real contract, with constrained inputs and a decision about failing examples.
- **Legacy discipline.** Characterization commits are separate from behavior changes; surprising results are labelled, not silently "fixed".
- **Readability.** Test names, helper names, parametrize ids tell the story without reading the body.

Explain your design decisions: (1) which seams you added and why those; (2) which doubles you chose for which collaborator; (3) the weakest part of your suite; (4) how you would introduce these practices to a team that has none, without imposing tools unasked.

## 11. Mastery gate

Pass = 80/100 with **no critical failure**.

Critical failures:

- A test that cannot fail (swallowed exception, missing assertion, tautology, wrong patch target) in the submitted suite.
- Use of real time (`sleep`, unpatched `now`), real network, or the real working directory in tests.
- Order dependence (suite fails when reversed or when a single test is run alone).
- Bug-fix tests without evidence that they failed before the fix.
- Behavior changes mixed into the seam/refactor commit.
- Inability to explain "patch where it is used" with a live demonstration.

Required evidence: pytest output in normal and reversed order, the three mutation-check results, `FINDINGS.md`, `NOTES.md`, commit history, and your closed-book Section 8 solution.

If failed: remedial exercise. Take five tests from your own suite, break production code to check each (hand mutation), record which tests stayed green, rewrite those tests until each fails for the right reason, and add one fake replacing one mock. Then redo the failed project criteria on `reserve` alone.
