## 1. Engineering problem

A nightly job loads a 4 GB export into a database. Version one reads the file with `f.read().splitlines()`, builds a list of parsed dicts, then inserts them in a loop. It works on the 20 MB sample, and in production the container is killed for exceeding its memory limit. The "fix" is a bigger container. Then one malformed row on line 2,311,907 raises `ValueError`, the job dies, and half the rows are committed because there is no transaction. Someone wraps the loop in `try/except Exception: pass` and now bad rows vanish silently. Finally, the file handle is never closed on the error path and the scheduler eventually runs out of descriptors.

Four independent failures, four standard answers: unbounded memory (**generators**), half-finished side effects and leaks (**context managers**), silent data loss (deliberate **exception design**), lost root cause (**chaining**).

## 3. First-principles explanation

### 3.1 The iterator protocol

(Language guarantee.) An **iterable** has `__iter__()` returning an **iterator**. An iterator has `__next__()`, which returns the next value or raises `StopIteration`, and `__iter__()` returning itself. A `for` loop is: `it = iter(x)`, then call `next(it)` repeatedly until `StopIteration`.

```python
# run-check
class CountdownIter:
    def __init__(self, n): self.n = n
    def __iter__(self): return self
    def __next__(self):
        if self.n <= 0:
            raise StopIteration
        self.n -= 1
        return self.n + 1

class Countdown:                      # iterable: hands out a FRESH iterator each time
    def __init__(self, n): self.n = n
    def __iter__(self): return CountdownIter(self.n)

c = Countdown(3)
print(list(c), list(c))               # [3, 2, 1] [3, 2, 1]: re-iterable
it = iter([1, 2])
print(list(it), list(it))             # [1, 2] []: an iterator is single-use
```

Consequences you must internalize:

- **Iterators are single-pass and stateful.** Passing one to two consumers means the second sees nothing (the Section 6 lab).
- Containers (`list`, `dict`, `set`, `str`, `Countdown` above) are iterables that create independent iterators.
- Many builtins return iterators, not lists: `map`, `filter`, `zip`, `enumerate`, `reversed`, `dict.items()` views (re-iterable views, not iterators), `open()` file objects (iterator over lines).

### 3.2 Generators

A function containing `yield` is a **generator function**: calling it runs **no body code**; it returns a generator object (an iterator). Each `next()` resumes the body until the next `yield`; the local variables and position are frozen in between. When the body returns, `StopIteration` is raised (its `.value` carries the return value).

```python
# run-check
def gen():
    print("start"); yield 1
    print("mid");   yield 2
    print("end")

g = gen()
print("created")             # nothing from gen's body has run yet
print(next(g)); print(next(g))
try:
    next(g)
except StopIteration:
    print("stop")
```

Output order: `created`, `start`, `1`, `mid`, `2`, `end`, `stop`. A generator expression `(f(x) for x in xs)` is the compact form; `sum(i*i for i in range(4))` needs no extra parentheses.

**Memory behavior.** A list of a million ints allocates storage for all of them at once. A generator holds one frame and yields on demand. The streaming guarantee is only as good as the weakest stage: one `list(...)`, `sorted(...)` or `.read()` in the pipeline brings the whole input back into memory. Measure with `tracemalloc` (Section 4.3) instead of estimating.

```python
# run-check
import sys
big = [i for i in range(1_000_000)]
gg = (i for i in range(1_000_000))
print(sys.getsizeof(big) > 100 * sys.getsizeof(gg))   # True (getsizeof is shallow: it is a sanity check, not a measurement)
print(sum(gg))                                       # 499999500000
```

**Laziness trade-offs.** Errors surface when consumed, not created; one pass only; no `len()` or indexing; resources opened inside stay open until exhaustion, `close()` or collection.

### 3.3 `send`, `close`, `yield from` (basics)

A `yield` is also an expression: `x = yield value` receives whatever the caller passes to `gen.send(x)`. A generator must be "primed" with `next()` before the first `send`. `gen.close()` raises `GeneratorExit` inside the generator at the `yield`, so `finally` blocks run. `yield from sub` delegates to a sub-generator and evaluates to its return value.

```python
# run-check
def running_avg():
    total = n = 0
    avg = None
    while True:
        x = yield avg
        total += x; n += 1
        avg = total / n

a = running_avg(); next(a)
print(a.send(10), a.send(20))        # 10.0 15.0

def inner():
    yield 1
    return "r"
def outer():
    r = yield from inner()
    print("got", r)
    yield 2
o = outer(); print(next(o)); print(next(o))    # 1, then "got r", then 2

def g2():
    try:
        yield 1; yield 2
    finally:
        print("cleanup")
x = g2(); next(x); x.close()          # prints cleanup
```

`send` is the ancestor of `async`/`await` (Lesson 2.6); in ordinary backend work you will mostly write plain `yield` pipelines.

### 3.4 `itertools` toolkit

Learn these by name; they replace hand-written loops and stay lazy. (`batched` 3.12+, `pairwise` 3.10+.)

```python
# run-check
import itertools as it
print(list(it.islice(it.count(10), 3)))               # [10, 11, 12]
print(list(it.batched(range(7), 3)))                  # [(0, 1, 2), (3, 4, 5), (6,)]
print(list(it.pairwise("abcd")))                      # [('a','b'), ('b','c'), ('c','d')]
print(list(it.accumulate([1, 2, 3, 4])))              # [1, 3, 6, 10]
print(list(it.chain([1], [2, 3])))                    # [1, 2, 3]
print([(k, len(list(g))) for k, g in it.groupby("aabaa")])   # [('a',2),('b',1),('a',2)]
```

The last line is the classic trap: `groupby` groups **consecutive** equal keys; sort first (or use a dict) if you want global grouping. Also: each group iterator is invalidated when you advance the outer iterator; consume it first. `itertools.tee` duplicates an iterator but buffers the gap between its copies: if one copy races ahead you have rebuilt a list.

### 3.5 Context managers

A context manager defines `__enter__` and `__exit__(exc_type, exc, tb)`. `with cm as x:` calls `__enter__` (its result is `x`), runs the body, then **always** calls `__exit__`, passing the exception details if the body raised. If `__exit__` returns a truthy value the exception is suppressed; otherwise it propagates. (Language guarantee.) Prefer returning `None`/`False` implicitly; suppression should be explicit and rare.

```python
# run-check
import contextlib

class Res:
    def __enter__(self):
        print("open"); return self
    def __exit__(self, et, ev, tb):
        print("close", et.__name__ if et else None)
        return False                     # do not suppress

try:
    with Res():
        raise KeyError("k")
except KeyError as e:
    print("propagated", e)

@contextlib.contextmanager
def tx():
    print("begin")
    try:
        yield
    except Exception:
        print("rollback"); raise         # re-raise: the caller must still see the failure
    else:
        print("commit")

try:
    with tx():
        raise RuntimeError("x")
except RuntimeError:
    pass
with contextlib.suppress(FileNotFoundError):    # explicit, narrow suppression
    open("/nonexistent")
with contextlib.ExitStack() as stack:           # N resources decided at runtime
    for _ in range(2):
        stack.callback(print, "released")
```

`@contextmanager` turns a generator with exactly one `yield` into a context manager: code before `yield` is `__enter__`, the yielded value is `as x`, code after is `__exit__`. If the body raises, the exception is thrown into the generator **at the yield**, so you must use `try/finally` (or `except`/`else`) around the `yield` for cleanup to run. A frequent bug is writing cleanup after a bare `yield` with no `try/finally`: it is skipped on error.

Also worth knowing: `contextlib.closing`, `contextlib.chdir` (3.11+), `tempfile.TemporaryDirectory`, `threading.Lock`. Note `sqlite3.Connection` as a context manager commits or rolls back but does **not** close the connection (check the docs).

### 3.6 The exception model

Exceptions form a class hierarchy rooted at `BaseException`. `Exception` is the root of "normal" errors. `KeyboardInterrupt`, `SystemExit` and `GeneratorExit` derive from `BaseException` directly so that `except Exception` does not eat them.

```text
BaseException
 +-- KeyboardInterrupt, SystemExit, GeneratorExit
 +-- Exception
      +-- ValueError, TypeError, KeyError (via LookupError), AttributeError, ...
      +-- OSError (FileNotFoundError, PermissionError, TimeoutError, ...)
      +-- YourBaseError           <- your module's root
           +-- BadRecord          (caller-input problem)
           +-- StorageError       (infrastructure problem)
```

**Chaining.** Inside an `except` block, raising a new exception sets `__context__` automatically (shown as "During handling of the above exception, another exception occurred"). `raise New from old` sets `__cause__` explicitly ("The above exception was the direct cause"). `raise New from None` suppresses the context display. Always translate low-level exceptions into your domain exceptions **with `from`**, so the root cause survives in logs.

```python
# run-check
try:
    try:
        int("x")
    except ValueError as e:
        raise RuntimeError("bad config") from e
except RuntimeError as e:
    print(repr(e.__cause__))                      # the ValueError

try:
    try:
        1 / 0
    except ZeroDivisionError:
        raise KeyError("oops")                    # implicit context
except KeyError as e:
    print(repr(e.__context__), e.__suppress_context__)   # ZeroDivisionError(...) False

e = ValueError("x"); e.add_note("user_id=3")      # 3.11+: attach context without wrapping
print(e.__notes__)

try:
    raise ExceptionGroup("batch", [ValueError(1), TypeError(2)])   # 3.11+
except* ValueError as eg:
    print("V", eg.exceptions)
except* TypeError as eg:
    print("T", eg.exceptions)
```

Exception groups exist for concurrent failures (`asyncio.TaskGroup`, Lesson 2.6); do not use them for ordinary single-error flow.

### 3.7 Designing exceptions

Rules that hold in most codebases (convention and opinion, defend deviations):

1. **One base class per package/module** (`class IngestError(Exception)`), so callers can `except IngestError` at a boundary without catching bugs.
2. **Exception types encode what the caller can do**, not where it happened: `BadRecord` (skip/report), `StorageError` (retry or abort), `ConfigError` (fix deployment). Do not make a class per line of code.
3. **Carry data as attributes** (`line_no`, `reason`) and keep messages human-readable. Do not make callers parse message text.
4. **Catch narrowly, as close to the failure as you can handle it.** `except Exception` belongs at process boundaries (request handler, job runner, thread top-level), where you log with traceback and convert to a response or exit code.
5. **Do not use `assert` for runtime validation**: assertions are removed under `python -O`.
6. **Never** write bare `except:` (catches `KeyboardInterrupt`/`SystemExit`), `except Exception: pass`, or `return` in `finally` (it silently discards the in-flight exception; Python 3.14 emits a warning for this, PEP 765, VERIFY in the 3.14 "What's New"):

```python
# run-check
def f():
    try:
        raise ValueError("lost")
    finally:
        return "swallowed"           # the ValueError disappears
print(f())
```

### 3.8 EAFP vs LBYL

EAFP ("easier to ask forgiveness than permission"): try the operation, handle the exception. LBYL ("look before you leap"): check first.

- Prefer EAFP when the check and the use can be separated by another actor (file existence, permissions, key presence in shared dicts, DB row existence). `if os.path.exists(p): open(p)` has a time-of-check/time-of-use race; `try: open(p) except FileNotFoundError:` does not.
- Prefer LBYL when the check is cheap, **local**, and the failure is common rather than exceptional (validating user input before the expensive step), or when exception handling would be too broad (a `try` around 20 lines will catch bugs in unrelated lines: keep the `try` body to the one operation that can raise).
- Cost: a `try` block that does not raise is nearly free in CPython; raising is comparatively expensive. Where failure is the common case in a hot loop, measure.

### 3.9 Resource safety

Anything that must be released (file, socket, lock, transaction, temp dir) is acquired in a `with` or registered on an `ExitStack`. CPython refcounting often closes files on scope exit, but that is an implementation detail and fails when a traceback or cycle holds a reference.

## 4. Worked example: a streaming NDJSON importer

Requirement: read a newline-delimited JSON file of `{"user": ..., "amount": ...}`, insert into a database in batches, each batch atomic. Bad records are collected and reported, not fatal. Database failures are fatal and keep their cause.

### 4.1 Naive version (what not to ship)

```python
# not runnable as-is: illustrative
def import_file(path, conn):
    rows = []
    for line in open(path).read().splitlines():       # whole file in memory; handle leaked
        try:
            d = json.loads(line)
            rows.append((d["user"], d["amount"]))
        except:                                       # swallows everything, even Ctrl-C
            pass
    for r in rows:                                    # one commit at the end, or per row?
        conn.execute("INSERT INTO payments VALUES (?, ?)", r)
    conn.commit()
```

Defects: memory proportional to the file; file never closed; bare `except: pass` (silent data loss, no line numbers); `amount` unvalidated; no atomic batches or rollback; bad data and infrastructure failure indistinguishable.

### 4.2 Improved version

```python
# run-check
import json
import sqlite3
import tempfile
from collections.abc import Iterable, Iterator
from contextlib import contextmanager
from itertools import batched          # Python 3.12+
from pathlib import Path


class IngestError(Exception):
    """Base class for everything this module raises on purpose."""


class BadRecord(IngestError):
    def __init__(self, line_no: int, reason: str) -> None:
        super().__init__(f"line {line_no}: {reason}")
        self.line_no = line_no
        self.reason = reason


class StorageError(IngestError):
    """The database refused a batch. Not retried by this module."""


def read_lines(path: Path) -> Iterator[tuple[int, str]]:
    with path.open(encoding="utf-8") as f:       # closed when exhausted or closed
        for line_no, line in enumerate(f, start=1):
            if line.strip():
                yield line_no, line


def parse(lines: Iterable[tuple[int, str]], rejects: list[BadRecord]) -> Iterator[tuple[str, int]]:
    for line_no, line in lines:
        try:
            obj = json.loads(line)
            record = (str(obj["user"]), int(obj["amount"]))
        except (json.JSONDecodeError, KeyError, ValueError, TypeError) as exc:
            rejects.append(BadRecord(line_no, f"{type(exc).__name__}: {exc}"))
            continue
        yield record                              # yield OUTSIDE the try block


@contextmanager
def transaction(conn: sqlite3.Connection) -> Iterator[sqlite3.Connection]:
    try:
        yield conn
    except BaseException:
        conn.rollback()
        raise
    else:
        conn.commit()


def load(conn: sqlite3.Connection, rows: Iterable[tuple[str, int]], batch_size: int = 1000) -> int:
    total = 0
    for batch in batched(rows, batch_size):
        try:
            with transaction(conn):
                conn.executemany("INSERT INTO payments(user, amount) VALUES (?, ?)", batch)
        except sqlite3.Error as exc:
            raise StorageError(f"batch of {len(batch)} failed") from exc
        total += len(batch)
    return total


with tempfile.TemporaryDirectory() as d:
    p = Path(d) / "in.ndjson"
    p.write_text('{"user":"a","amount":5}\nnot json\n\n{"user":"b"}\n{"user":"c","amount":"7"}\n')
    conn = sqlite3.connect(":memory:")
    conn.execute("CREATE TABLE payments(user TEXT NOT NULL, amount INTEGER NOT NULL)")
    rejects: list[BadRecord] = []
    n = load(conn, parse(read_lines(p), rejects), batch_size=2)
    print(n, [str(r) for r in rejects])
    print(conn.execute("SELECT * FROM payments").fetchall())
    try:
        load(conn, [("x", None)])
    except StorageError as e:
        print(e, "<-", repr(e.__cause__))
```

Observed output: `2 [...]` where the rejects are line 2 (`JSONDecodeError`) and line 4 (`KeyError: 'amount'`); rows `[('a', 5), ('c', 7)]`; and `batch of 1 failed <- IntegrityError('NOT NULL constraint failed: payments.amount')`.

What changed and why:

| Change | Reason |
|---|---|
| Three generator stages (`read_lines` -> `parse` -> `load`) | Constant memory; each stage has one job and is testable alone with a list as input |
| `with path.open` inside the generator | File closes on exhaustion, error or `close()` |
| `yield record` after the `try` | An exception thrown into the generator at the `yield` (by `.throw()`) or raised by a consumer must not be caught by the parse error handler. Keep the `try` body to the operation that can fail |
| Narrow exception tuple | Programming errors (`NameError`, `AttributeError`) are not "bad records" and still crash loudly |
| `BadRecord` collected in a list passed in | Rejects are data, available for a dead-letter report; the pipeline continues |
| `transaction` context manager | Commit or rollback is guaranteed per batch; it re-raises so failures are not swallowed |
| `except BaseException` in `transaction` | Rollback must also happen on `KeyboardInterrupt`; the exception is re-raised, never suppressed |
| `StorageError(...) from exc` | Translation to the domain type without losing the driver's exception |
| Injected `rows` iterable in `load` | `load` does not know about files; trivial to test |

Design note: the `rejects` out-parameter is explicit and local, fine for a batch job. Alternative: yield a tagged `Ok | Err` value, which adds a type to every stage.

### 4.3 Proving the memory claim

Method, not numbers (do not quote figures you did not measure):

```python
# run-check
import tracemalloc

def squares(n):
    for i in range(n):
        yield i * i

def peak(consumer):
    tracemalloc.start()
    consumer()
    _, p = tracemalloc.get_traced_memory()
    tracemalloc.stop()
    return p

small = peak(lambda: sum(squares(10_000)))
large = peak(lambda: sum(squares(1_000_000)))
as_list = peak(lambda: sum(list(squares(1_000_000))))
print(large < as_list / 50, abs(large - small) < 100_000)   # streaming does not grow with n; the list does
```

The assertions compare ratios and thresholds you can justify; they are not benchmark claims. In your project, apply the same idea to your importer with a generated input file.

## 5. Production perspective

**Correctness.** For every stage decide: what happens on bad input, and who finds out? Swallowed errors are data loss with a delayed fuse; whether to crash on the first bad row is a requirements question for the ticket owner.

**Resource safety.** Descriptor exhaustion, held locks and uncommitted transactions are production incidents that look like "random hangs". Every acquisition in `with`. Review rule: any `open(`, `connect(`, `acquire(` not directly under a `with` or an `ExitStack` needs a comment explaining why.

**Observability.** Log once, at the boundary, with traceback (`logger.exception`, Lesson 1.3); not at every layer. Chaining with `from` puts the whole story in that one entry.

**Testing.** Assert behavior on error paths: exception type, `__cause__`, rollback performed, file closed. Test laziness with `next()` once and check side effects.

**Security.** Do not put `str(exc)` in HTTP responses (SQL fragments, paths); return a stable error code and keep detail in logs. Cap line length if the source is hostile.

**Performance.** Batching cuts per-statement overhead; measure the batch size. For tiny in-memory data a list comprehension is simpler.

**What a senior engineer does differently.**

- Defines the failure taxonomy (reject, retry, abort) before writing the loop.
- Keeps `try` bodies tiny and `except` tuples specific.
- Puts a limit on every unbounded thing: line length, batch size, retry count.
- Knows what is *not* atomic (a batch is; the whole file is not) and documents it.

**Common beginner mistakes.**

| Symptom | Cause | Diagnose |
|---|---|---|
| Second pass over data is empty | Iterator reused | `iter(x) is x`? then it is one-shot |
| `ValueError: I/O operation on closed file` in a generator pipeline | Lazy object outlived its `with` | Section 6 |
| Errors "disappear" | Bare/broad `except`, `finally: return` | `grep -n "except:\|except Exception"`; read each handler |
| Cleanup skipped on error in `@contextmanager` | No `try/finally` around `yield` | Raise inside the `with` in a test and observe |
| `groupby` yields repeated keys | Input unsorted | Print the keys |
| Traceback shows only the wrapper error | `raise New` without `from` inside `except`, or `from None` used reflexively | Look for "During handling" vs "direct cause" |
| Job hangs on interrupt | `except BaseException`/bare `except` without re-raise | Search for handlers without `raise` |

## 6. Failure laboratory

Mode A. Predict the output of this program **before running**: which lines print, and in what order? Write down your prediction.

```python
# run-check
import tempfile
from pathlib import Path

def read_numbers(path):
    with open(path) as f:
        return (int(line) for line in f)

with tempfile.TemporaryDirectory() as d:
    p = Path(d) / "n.txt"
    p.write_text("1\n2\n3\n")
    nums = read_numbers(p)
    try:
        print(sum(nums))
    except ValueError as e:
        print("ValueError:", e)
    g = (int(x) for x in "123")
    print(sum(g), sum(g))
```

Also answer: why is this bug especially nasty in a larger codebase, and give two different fixes.

### Reveal (read after predicting)

Output:

```text
ValueError: I/O operation on closed file.
6 0
```

1. `read_numbers` returns a **generator expression** without consuming it. The `with` block exits (closing the file) as the function returns, before a single line has been read. The consumer fails later, far from the cause.
2. The second `sum(g)` is `0`: the generator is exhausted. No exception, silently wrong total.

Fixes for 1: (a) make `read_numbers` itself a generator (`with open(...) as f: for line in f: yield int(line)`), so the file stays open while consumed; (b) return a list (`[int(l) for l in f]`) if the data is small and eager is acceptable; (c) pass the open file in from the caller, who owns its lifetime. For 2: materialize (`list`) when you need two passes, or recompute from the source, or compute both aggregates in one pass.

Systematic diagnosis for "iterator pipeline fails strangely or gives short results":

1. For each stage ask: is this object a generator/iterator or a container? (`iter(x) is x`.)
2. Count consumers: how many times is it iterated? More than once means a bug.
3. Find where each resource is opened and where it is closed; draw the lifetime on paper and mark when the data is actually *read*.
4. Reproduce with a tiny input and `next()` by hand.
5. Add a test that consumes the pipeline fully and asserts the exact output, and one that asserts the resource was closed after.

## 10. Engineering review

Checklist:

- **Streaming.** Is there any `list(`, `sorted(`, `.read()`, `.readlines()` on the main data path? Each needs a justification.
- **Resources.** Is every acquisition under `with`/`ExitStack`? Walk each exit path: normal, bad record, storage error, `KeyboardInterrupt`.
- **Exceptions.** Does every `except` name the narrowest type? Is every translation done with `from`? Is there any handler that neither handles nor re-raises?
- **Atomicity.** Can you state precisely what is committed after a failure at batch k?
- **Tests.** Do error-path tests assert behavior (rollback happened, file closed), not only that an exception occurred?
- **Determinism.** No sleeps, no real time, no dependence on test order.
- **Security.** What can an attacker-controlled file do: huge lines, huge numbers, path in output messages?
- **Operability.** Can an on-call engineer tell from the summary and rejects file what happened?

Explain your design decisions: (1) why did you pick your duplicate-handling approach and what does it cost; (2) which failures are fatal and why; (3) where does your code deliberately trade memory for simplicity, if anywhere; (4) which part would you change first if requirements added a second input format.

## 11. Mastery gate

Pass = 80/100 with **no critical failure**.

Critical failures:

- Whole-input materialization on the data path (or a memory test that passes only because the input is tiny).
- A bare `except`, an `except Exception: pass`, or a `finally: return`.
- A path where a batch can be partially committed.
- A resource opened outside `with`/`ExitStack` without justification, or not closed on an error path (shown by a test).
- Exceptions translated without `from`, losing the cause.
- Inability to explain in the defense why the Section 6 program fails.

Evidence required: green test output, memory-test output at two sizes, the failure-semantics table, `DECISIONS.md`, and your closed-book Section 8 solution.

If failed: remedial exercise. Take your failing area and write a 40-line focused program demonstrating it correctly (for example: a generator pipeline over a temp file with an injected failure at record N, proving cleanup with a recording file wrapper), then re-run the failed project criteria on a reduced scope (one stage + the loader) and resubmit.
