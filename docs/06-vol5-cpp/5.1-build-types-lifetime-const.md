## 1. Engineering problem

You inherit a 40-file C++ tool that "works on my machine". On a colleague's machine it prints garbage; in CI it fails to link with `multiple definition of`; at `-O2` it behaves differently from `-O0`. None of these is a compiler bug. Each follows from three facts Python hid from you:

1. C++ is compiled in separate pieces (translation units) stitched together by a linker. The One Definition Rule (ODR) is enforced partly by the compiler, partly by the linker, partly by nobody.
2. You manage object lifetimes. A reference or pointer to an ended object is not a catchable error; it is undefined behavior (UB): the language places no requirements on the program, including "works fine in testing".
3. The type system is permissive in places (implicit conversions) and strict in others (const, narrowing in braces). Using the strict parts turns runtime bugs into compile errors.

Handled poorly: a function returns `std::string_view` into a temporary and works for months (small-string optimization hides it) until an input is longer. A header defines a helper without `inline` and links until a second `.cpp` includes it. In quantitative work these become silent wrong numbers, not crashes. This lesson gives you the model to prevent these bugs and the tooling (warnings, sanitizers, CMake) to catch the rest.
## 2. Learning objectives

By the end you can, without references:

1. Run each GCC pipeline stage separately, state what it produces, and explain from linker output why a `multiple definition` or `undefined reference` occurred.
2. Write from a blank directory a CMake project with a library, an executable, a CTest test, `-Wall -Wextra -Wpedantic`, C++20 without extensions and an opt-in ASan+UBSan build.
3. Write a header safe to include from many TUs (guard, no non-`inline` definitions) and demonstrate a violation that breaks the link.
4. Initialize with braces, predict which conversions are diagnosed as narrowing, and identify variables left indeterminate.
5. Choose between value, `const T&`, `T&`, `T*`, `std::string_view` and `std::span<const T>` parameters and justify the choice by ownership and lifetime.
6. Make a class const-correct and explain `const int*`, `int* const`, `const int* const`.
7. Reproduce and diagnose a dangling view, an out-of-bounds read and a signed overflow with sanitizers, stating which a sanitizer is guaranteed to catch (none are guaranteed).
## 3. First-principles explanation

### 3.1 The compilation pipeline

```
 main.cpp --preprocess--> main.ii --compile--> main.s --assemble--> main.o --\
 util.cpp --preprocess--> util.ii --compile--> util.s --assemble--> util.o ---+--link--> a.out
```

- Preprocess (`g++ -E`): textual. `#include` pastes a file's text; `#define` substitutes; `#if` selects. The result is one translation unit (TU); the compiler never sees your `#include` lines.
- Compile (`-S`): parse, type-check, optimize, emit assembly, one TU at a time and in isolation. Compiling `main.cpp`, the compiler knows only the declarations it was shown.
- Assemble (`-c`): an object file with machine code and a symbol table (symbols defined, symbols needed).
- Link: resolve every needed symbol to exactly one definition and lay out the executable.

Consequences: a declaration (`int twice(int);`) says "this exists somewhere"; a definition gives the body. Compile errors concern one TU; `undefined reference` and `multiple definition` come from the linker and concern symbols across TUs. Headers are re-parsed per TU, so heavy headers slow builds. Try it:

```bash
g++ -std=c++20 -E src/main.cpp | wc -l      # thousands of lines from <iostream> etc.
g++ -std=c++20 -c src/textstats.cpp -o /tmp/ts.o && nm -C /tmp/ts.o   # T = defined, U = needed
```
### 3.2 The One Definition Rule (ODR) and headers

Language rule ([basic.def.odr]): every non-inline function and variable that is odr-used has exactly one definition in the program. Classes, inline functions and templates may be defined in several TUs if all definitions are identical.

- Detectable: a non-inline function defined in a header included by two `.cpp` files. Verified (GCC 14.2.0, GNU ld): `multiple definition of 'twice(int)'`. Fixes: declare in the header and define in one `.cpp`; mark it `inline` (here meaning "identical definitions in several TUs are permitted", not "please inline"); `constexpr` (implicitly inline); or give it internal linkage (unnamed namespace/`static`), rarely wanted in headers.
- Undetectable (ill-formed, no diagnostic required, IFNDR): two TUs define the same class or inline function differently, for example because a macro changes a member list. The linker keeps one arbitrarily and nothing warns you. Never vary a type's layout with macros that differ between TUs.

Include guards solve a different problem: the same header twice in one TU. Without a guard, `struct P { int x; };` twice yields `redefinition of 'struct P'` (verified). Use `#ifndef`/`#define`/`#endif` or `#pragma once` (not ISO, but supported by GCC, Clang, MSVC); follow the project convention (Lesson 0.1).

Hygiene: no `using namespace std;` in headers; include what you use; headers compile standalone; put code in a namespace.
### 3.3 CMake in one page

CMake does not compile anything; it generates build files (Makefiles or Ninja files) from a description. Modern CMake is target-based: you declare targets and attach properties to them.

```cmake
cmake_minimum_required(VERSION 3.20)
project(textstats VERSION 0.1.0 LANGUAGES CXX)

set(CMAKE_CXX_STANDARD 20)            # requested standard
set(CMAKE_CXX_STANDARD_REQUIRED ON)   # fail instead of silently decaying
set(CMAKE_CXX_EXTENSIONS OFF)         # -std=c++20 instead of -std=gnu++20

add_library(textstats_lib src/textstats.cpp)
target_include_directories(textstats_lib PUBLIC src)

add_executable(textstats src/main.cpp)
target_link_libraries(textstats PRIVATE textstats_lib)
```

- `PRIVATE`: needed to build this target; `INTERFACE`: needed by consumers; `PUBLIC`: both. The include directory is PUBLIC because consumers include the header.
- Out-of-source build: `cmake -S . -B build && cmake --build build`.
- Build type (single-config generators): `-DCMAKE_BUILD_TYPE=Debug|Release|RelWithDebInfo`. With GCC/Clang these typically add `-g`, `-O3 -DNDEBUG`, `-O2 -g -DNDEBUG` (CMake defaults; check with `--verbose`). `NDEBUG` disables `assert`.
- Tests: `enable_testing()` + `add_test(NAME x COMMAND exe)`; run `ctest --test-dir build` (CMake 3.20+).

### 3.4 Warnings and sanitizers

`-Wall -Wextra -Wpedantic` (GCC, Clang): `-Wall` is a curated set (the name is historical), `-Wextra` adds more, `-Wpedantic` flags non-ISO extensions. Treat warnings as defects; use `-Werror` in your own CI but not in build files others consume (a newer compiler adds warnings and breaks them). Add `-Wshadow -Wconversion` as you grow.

Sanitizers (`-fsanitize=address,undefined -fno-omit-frame-pointer -g`): ASan detects heap/stack overflow and use-after-free/scope (LeakSanitizer is included on Linux); UBSan detects specific UB such as signed overflow and bad shifts. They cost several times in speed and extra memory, and find only bugs that execute: a test amplifier, not a proof.

### 3.5 Types and initialization

`int`'s width, `char`'s signedness and `long`'s width are implementation-defined; use `<cstdint>` types when you mean a width and `std::size_t` for sizes.

```cpp
int a;        // default-initialized local: INDETERMINATE; reading it is UB (before C++26)
int b{};      // value-initialized: 0
int c{5};     // list-init: narrowing is diagnosed
double e = 3.9;
int f = e;    // legal, silently 3
// int g{e};  // narrowing conversion
```

Verified (GCC 14.2.0): `int c{d};` with a `double d` gives `warning: narrowing conversion ... [-Wnarrowing]`. The standard requires a diagnostic; GCC makes it a warning for non-constant expressions and `-pedantic-errors` an error. Treat the diagnostic as an error.

- Signed overflow is UB; unsigned arithmetic wraps modulo 2^N (both language guarantees).
- Out-of-range conversion to a signed type was implementation-defined before C++20 and is modular in C++20. Verified: `static_cast<std::int32_t>(3'000'000'000L)` printed `-1294967296`.
- Mixed signed/unsigned comparison converts the signed operand: `-1 < 1u` is false (verified); GCC's `-Wall` warns via `-Wsign-compare` in C++.
- C++26 turns reads of uninitialized locals into "erroneous behavior" (P2795; erroneous behavior, not UB, in C++26 - confirm your compiler's support before relying on it). Do not depend on it.
### 3.6 Scope vs lifetime

Scope is a compile-time region where a name is visible; lifetime is a run-time interval in which an object exists. Most dangling bugs live in the gap.

| Storage duration | Begins | Ends | Example |
|---|---|---|---|
| automatic | block entry | block exit | locals |
| static | program start / first use | program end | globals, `static` locals |
| dynamic | allocation (`new`) | `delete` | heap objects (Lesson 5.2: use RAII) |
| thread | thread start | thread end | `thread_local` |

```
 stack                                   heap
 | main: std::string s --ptr-----------> "hello"
 | f():  local x   <- gone after return; a reference/pointer to x now dangles
```

A temporary lives to the end of the full expression, except that binding it directly to a local `const T&` or `T&&` extends its lifetime to that reference's scope. The exception does not apply through a function return or through `std::string_view`.
### 3.7 Values, references, pointers

- A value (`T x`) owns its object. Copying copies the object.
- A reference (`T&`, `const T&`) is an alias for an existing object. It cannot be rebound and (practically) cannot be null. It does not own.
- A pointer (`T*`) is an object holding an address; it can be null, reseated and used in arithmetic. It does not own, unless you make it (Lesson 5.2 gives owners proper types).

Parameter-passing guide (convention, widely used; the C++ Core Guidelines F.15-F.16 cover this):

| Intent | Parameter type |
|---|---|
| read a cheap type (int, double, small struct) | `T` by value |
| read an expensive type | `const T&` |
| read a string without owning/copying | `std::string_view` (by value) |
| read a contiguous sequence | `std::span<const T>` (by value) |
| modify caller's object | `T&` |
| optional/nullable object | `T*` (non-owning) or `std::optional<T>` |
| take ownership / sink | `T` by value then `std::move` (Lesson 5.2) |

### 3.8 const correctness

`const` is a promise checked by the compiler. Read declarations right to left:

```cpp
const int* p1;        // pointer to const int: cannot modify *p1, can reseat p1
int* const p2 = &x;   // const pointer to int: can modify *p2, cannot reseat p2
const int* const p3 = &x;
```

A `const` member function (`int get() const`) promises not to modify the object's observable state and is the only kind callable on a const object. `mutable` members (caches, mutexes) are the escape hatch. Casting away const (`const_cast`) and then writing to an object that was originally defined const is UB; if the object was non-const originally the write is legal but almost always a design smell.

Const is not deep for pointers: a `const Widget` containing `int* data` lets you modify `*data`. Const protects the pointer, not what it points to.

### 3.9 Arrays, strings, views

- C arrays decay to pointers when passed and lose their size. Prefer `std::array<T,N>` or `std::vector<T>`.
- `std::string` owns its characters (short strings may live inline: small-string optimization, an implementation detail).
- `std::string_view` (C++17) is pointer plus length, owns nothing, may not be null-terminated. Excellent parameter; dangerous return value, member or long-lived local.
- `std::span<T>` (C++20) is the same for any contiguous sequence: `std::span<const int>` accepts a C array, `std::array`, `std::vector` or pointer+length.

A view is valid only while its source is alive and unmodified (a reallocating `push_back` or string append invalidates views into it).
### 3.10 Structs and classes

`struct` and `class` differ only in default access. Convention: `struct` for plain data with no invariant; `class` when the constructor establishes an invariant that members preserve (private data). Mark single-argument constructors `explicit` unless implicit conversion is the point.
### 3.11 Undefined behavior

UB means the standard imposes no requirements. The optimizer may assume UB never happens, so it can delete checks and produce results contradicting the source. Families: memory (out-of-bounds, use after free/scope, null dereference, data races: Lesson 5.6); arithmetic (signed overflow, division by zero, bad shifts); object model (uninitialized reads pre-C++26, writing to a const object, aliasing violations, ODR violations).

Do not confuse: implementation-defined (compiler must document: `sizeof(int)`), unspecified (one of several valid behaviors: argument evaluation order), undefined. UB is a bug whether or not it shows; sanitizers find some, narrow interfaces (checked sizes, `at()`) prevent more.
## 4. Worked example: `textstats`

Goal: a `wc`-like tool: for each file argument (or stdin when none), print `lines words bytes label`. Exit codes: 0 on success, 1 if any file could not be read, 2 on stdin read failure.

Layout (blank repository):

```
textstats/
  CMakeLists.txt
  src/textstats.hpp
  src/textstats.cpp
  src/main.cpp
  tests/test_textstats.cpp
```

### 4.1 Design choices

- Logic (`analyze`) is separate from I/O (`main`): testable without files, no failure modes.
- `std::string_view` parameter: reads, owns nothing, accepts `std::string`, literals and substrings without copies. `noexcept`: it allocates nothing.
- Bytes, not characters; words split on ASCII whitespace only. These are stated limits; a test pins them.
- `std::size_t` counters. Whole-file read is simplest; the trade-off is memory proportional to file size (the project removes it).

### 4.2 `src/textstats.hpp`

```cpp
#ifndef TEXTSTATS_HPP
#define TEXTSTATS_HPP

#include <cstddef>
#include <string_view>

namespace ts {

struct Stats {
    std::size_t lines = 0;
    std::size_t words = 0;
    std::size_t bytes = 0;
};

// Counts newline characters, whitespace-separated words, and bytes.
// A final line without a trailing '\n' still counts as a line (unlike wc).
Stats analyze(std::string_view text) noexcept;

}  // namespace ts

#endif  // TEXTSTATS_HPP
```

`Stats` has default member initializers, so `Stats s;` is fully initialized (no indeterminate members). This is the cheap defense against uninitialized reads.

### 4.3 `src/textstats.cpp`

```cpp
#include "textstats.hpp"

namespace ts {

namespace {
constexpr bool is_space(char c) noexcept {
    return c == ' ' || c == '\t' || c == '\n' || c == '\r' || c == '\v' || c == '\f';
}
}  // namespace

Stats analyze(std::string_view text) noexcept {
    Stats s;
    s.bytes = text.size();
    bool in_word = false;
    for (const char c : text) {
        if (c == '\n') {
            ++s.lines;
        }
        if (is_space(c)) {
            in_word = false;
        } else if (!in_word) {
            in_word = true;
            ++s.words;
        }
    }
    if (!text.empty() && text.back() != '\n') {
        ++s.lines;
    }
    return s;
}

}  // namespace ts
```

Why a hand-rolled `is_space` rather than `std::isspace`: `std::isspace` takes an `int` that must be representable as `unsigned char` or `EOF`; passing a negative `char` is UB, and it depends on the C locale. A tiny explicit function avoids both. The unnamed namespace gives the helper internal linkage (no ODR exposure).

### 4.4 `src/main.cpp`

```cpp
#include <fstream>
#include <iostream>
#include <iterator>
#include <span>
#include <string>
#include <string_view>

#include "textstats.hpp"

namespace {

// Returns false on I/O failure; `out` is unspecified in that case.
bool read_all(std::istream& in, std::string& out) {
    out.assign(std::istreambuf_iterator<char>(in), std::istreambuf_iterator<char>());
    return !in.bad();
}

void print(const ts::Stats& s, std::string_view label) {
    std::cout << s.lines << ' ' << s.words << ' ' << s.bytes << ' ' << label << '\n';
}

}  // namespace

int main(int argc, char** argv) {
    const std::span<char*> args(argv, static_cast<std::size_t>(argc));
    if (args.size() == 1) {
        std::string text;
        if (!read_all(std::cin, text)) {
            std::cerr << "textstats: error reading stdin\n";
            return 2;
        }
        print(ts::analyze(text), "-");
        return 0;
    }
    int status = 0;
    for (const char* path : args.subspan(1)) {
        std::ifstream f(path, std::ios::binary);
        std::string text;
        if (!f || !read_all(f, text)) {
            std::cerr << "textstats: cannot read '" << path << "'\n";
            status = 1;
            continue;
        }
        print(ts::analyze(text), path);
    }
    return status;
}
```

Choices to defend:

- `std::span<char*>` over `argv` replaces unchecked `argv[i]` arithmetic with range-for and `subspan(1)`. `subspan(1)` on an empty span is UB; the `size() == 1` branch above only covers `argc >= 1`. The C++ standard ([basic.start.main]) allows `argc == 0`, and a launcher can start a program that way; Linux 6.12 could not reproduce it (checked: `execve` with an empty `argv` yields `argc == 1`, because the kernel inserts an empty argument), so test with a stub that calls `run(0, nullptr)`. The challenge in section 8 makes you handle it.
- `const char* path`: says the loop does not modify the argument strings.
- Errors to `std::cerr`, results to `std::cout`, distinct exit codes, processing continues after a bad file (like `wc`).
- `std::ios::binary`: no newline translation. `in.bad()` distinguishes real I/O errors from end-of-file.

### 4.5 `CMakeLists.txt`

```cmake
cmake_minimum_required(VERSION 3.20)
project(textstats VERSION 0.1.0 LANGUAGES CXX)

set(CMAKE_CXX_STANDARD 20)
set(CMAKE_CXX_STANDARD_REQUIRED ON)
set(CMAKE_CXX_EXTENSIONS OFF)

add_library(textstats_lib src/textstats.cpp)
target_include_directories(textstats_lib PUBLIC src)
target_compile_options(textstats_lib PRIVATE -Wall -Wextra -Wpedantic)

add_executable(textstats src/main.cpp)
target_link_libraries(textstats PRIVATE textstats_lib)
target_compile_options(textstats PRIVATE -Wall -Wextra -Wpedantic)

option(TS_SANITIZE "Build with ASan+UBSan" OFF)
if(TS_SANITIZE)
  target_compile_options(textstats_lib PUBLIC -fsanitize=address,undefined -fno-omit-frame-pointer)
  target_link_options(textstats_lib PUBLIC -fsanitize=address,undefined)
endif()

enable_testing()
add_executable(test_textstats tests/test_textstats.cpp)
target_link_libraries(test_textstats PRIVATE textstats_lib)
target_compile_options(test_textstats PRIVATE -Wall -Wextra -Wpedantic)
add_test(NAME textstats COMMAND test_textstats)
```

The warning flags are GCC/Clang syntax; MSVC uses `/W4`. For a cross-compiler project you would guard with `if(MSVC)`. Making the sanitizer flags PUBLIC on the library propagates them to the executable and tests through `target_link_libraries`, so the whole program is instrumented consistently (mixing instrumented and uninstrumented code reduces coverage and can cause false reports).

### 4.6 `tests/test_textstats.cpp`

A hand-rolled harness (no dependency): a file-local `expect(bool, const char*, int line)` that prints `FAIL line N: <expression>` and counts failures, wrapped by an `EXPECT(cond)` macro whose only job is to capture `#cond` and `__LINE__` (one of the few acceptable macro uses). `main` returns `EXIT_FAILURE` if any check failed, which is what CTest looks at. The cases, all verified to pass under ASan+UBSan: `analyze("").lines == 0`; `analyze("").words == 0`; `analyze("one").lines == 1`; `analyze("one\n").lines == 1`; `analyze("a b\tc\n").words == 3`; `analyze("  \n \n").words == 0`; `analyze("a\n\nb\n").lines == 3`; `analyze("héllo").bytes == 6` (UTF-8: `é` is 2 bytes; the source file must be saved as UTF-8). Write the file yourself; real projects use Catch2, GoogleTest or doctest.
### 4.7 Build and run

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Debug -DTS_SANITIZE=ON
cmake --build build
ctest --test-dir build --output-on-failure
printf 'hello world\nfoo' | ./build/textstats      # -> 2 3 15 -
./build/textstats nope src/main.cpp; echo $?        # error for 'nope', counts for main.cpp, exit 1
```

Verified outputs with the code above: stdin case printed `2 3 15 -`; the missing file printed `textstats: cannot read 'nope'` and the final exit status was 1; CTest reported `100% tests passed out of 1` under ASan+UBSan.

## 5. Production perspective

Maintainability: one target per component, minimal headers, helpers in unnamed namespaces, warnings on from the first commit (adding `-Wall` to a 100k-line codebase later is a project).

Correctness: initialize everything, prefer `const` by default, views for parameters and owners for members, never return a reference or view to a local. Run tests in Debug, Release and under sanitizers: the builds differ in behavior only if you have UB or rely on unspecified behavior. Never benchmark a Debug build, and never quote numbers you did not measure (method: Lesson 4.4).

Security: out-of-bounds access and use-after-free are the dominant memory-safety vulnerability classes in C++. Defensive measures at this level: bounds-checked access (`at`, spans with explicit sizes), no raw `new`/`delete`, sanitizers in CI, treating file contents and `argv` as untrusted.

Failure handling and testing: a CLI's contract is its exit codes and stderr messages; decide and test them. Unit-test pure functions; test the executable end-to-end via CTest `add_test(COMMAND ...)` checking exit codes.

What a senior engineer does differently: reads the first compiler error, not the last; reduces a failure to a 15-line reproducer before theorizing; builds with two compilers and sanitizers in CI; treats a warning as a question to answer; keeps the build a single command.

Common beginner mistakes and diagnosis:

| Mistake | Symptom | Diagnose |
|---|---|---|
| Non-`inline` definition in header | `multiple definition of` at link | `nm -C` on the objects; move or mark inline |
| Missing include guard | `redefinition of` | `g++ -E`; the text appears twice |
| Returning a view/reference to a local | Works, then garbage, or only in Release | ASan; `-Wreturn-local-addr` |
| Uninitialized member | Result differs per run/build type | `-Wall -Wextra`; `{}` defaults |
| Signed/unsigned loop mixup | Infinite loop or huge index | `-Wsign-compare`; range-for |
| Unchecked I/O | Silent empty result | Check stream state; test failure paths |
## 6. Failure laboratory

Predict the outcome of each program before running it. Write your prediction (compile error? link error? output? crash? "UB, anything") in your failure log first. Compile all with `g++ -std=c++20 -Wall -Wextra -Wpedantic -fsanitize=address,undefined -g`.

Program A:

```cpp
#include <iostream>
#include <string>
const std::string& pick(const std::string& a, const std::string& b) {
    return a.size() >= b.size() ? a : b;
}
int& counter() { int c = 0; return c; }
int main() {
    const std::string& r = pick("alpha", "be");
    std::cout << r << '\n';
    std::cout << counter() << '\n';
}
```

Program B:

```cpp
#include <climits>
#include <iostream>
#include <string>
#include <string_view>
#include <vector>

std::string make() { return "a string long enough to defeat the small-string optimisation"; }

int main(int argc, char** argv) {
    const char mode = argc > 1 ? argv[1][0] : 'n';
    if (mode == 'd') {
        std::string_view sv = make();
        std::cout << sv << '\n';
    } else if (mode == 'o') {
        std::vector<int> v(3);
        std::cout << v[3] << '\n';
    } else if (mode == 'i') {
        int x = INT_MAX;
        x += argc;
        std::cout << x << '\n';
    }
}
```

Questions: For A, which lines produce compiler warnings? Which line is the UB and what is the exact lifetime reason? For B with modes `d`, `o`, `i`: which does ASan catch, which UBSan, and what happens without sanitizers at `-O0` and `-O2`?

### Reveal (read after predicting)

Program A (verified, GCC 14.2.0): warnings `reference to local variable 'c' returned [-Wreturn-local-addr]` and `possibly dangling reference to a temporary [-Wdangling-reference]` (a heuristic warning, GCC 13+; absence proves nothing). ASan reported `stack-use-after-scope` when `r` was printed. The string literals become `std::string` temporaries that die at the end of the `pick(...)` initializer; lifetime extension applies only when the reference is initialized directly from the temporary, not from a function's return value. `counter()` returns a reference to an automatic variable: UB at use. Both lines are UB; ASan stopping at the first hides the second.

Program B (verified):

- `d`: ASan `heap-use-after-free`. The temporary string dies at the end of the declaration; `sv` points into freed heap memory. With a short string the characters sit inside the dead temporary and may appear to work.
- `o`: ASan `heap-buffer-overflow` at `v[3]`: `operator[]` is unchecked. A just-past-the-end index is reliably caught; a wild index may land in another live allocation and not be.
- `i`: UBSan `runtime error: signed integer overflow: 2147483647 + 2 cannot be represented in type 'int'`. Without UBSan the output is unpredictable by definition; at `-O2` the optimizer may assume no overflow and delete checks such as `x + 1 < x`.

Diagnosis procedure (log it, Lesson 0.3): (1) shrink to the smallest input, record compiler, flags, build type; (2) rebuild `-O0 -g -fsanitize=address,undefined`; (3) read the report's three stacks: bad access, free, allocation; (4) state the lifetime fact: "X ended at line N, Y used at line M"; (5) fix ownership, not symptoms (return by value, store a `std::string` not a view); (6) add a regression test that fails under sanitizers.
