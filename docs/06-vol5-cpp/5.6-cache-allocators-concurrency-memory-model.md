## 1. Engineering problem

A market-data handler keeps a million order records. A teammate converts the `std::vector<Order>` to a `std::list<Order>` "to make cancels O(1)". Another moves a hot counter into a struct shared by four worker threads, adding no locks because each thread writes "its own" field, and throughput falls with every thread added. A third stops workers with a plain `bool done` flag; the build passes review, tests pass at `-O0`, and in release the shutdown hangs. Three different bugs, one cause: programs are executed by machines with caches, cores and optimizers, and reasoning from the source alone is not enough.

## 3. First-principles explanation

### 3.1 The cache hierarchy

CPU cores are far faster than main memory, so hardware keeps recently used data in small fast caches: per-core L1 (tens of KB), L2 (hundreds of KB to MB), a shared L3 (MB to tens of MB). Read yours with `lscpu`. Memory moves between levels in **cache lines**, typically 64 bytes on x86-64 (`getconf LEVEL1_DCACHE_LINESIZE`; other architectures differ). Consequences, each a hypothesis you can test:

- **Spatial locality**: touching `a[i]` brings `a[i+1..i+15]` (for 4-byte ints) along for free. Sequential access also lets the hardware prefetcher run ahead.
- **Temporal locality**: data reused soon after is still cached.
- **Pointer chasing** (linked lists, trees) serializes misses: you cannot know the next address until the current load completes. Whether a list traversal is slow depends on whether nodes happen to be adjacent in memory; a list built by sequential allocations may be fast, and one whose order was shuffled (sorted, spliced) is typically not. Measure with the order your program really has.
- Working-set size matters more than element count: a loop that fits in L2 behaves differently from one that streams from DRAM.

```
core0 [L1][L2] \
core1 [L1][L2]  >-- shared L3 --- DRAM        data moves in 64-byte lines
core2 [L1][L2] /
```

Big-O from 5.4 counts operations; this section says what each operation costs. Both are needed.

### 3.2 AoS vs SoA

Array of structures: `vector<Particle>` with all fields together. Good when you use most fields of one element at a time. Structure of arrays: one vector per field. Good when a loop reads one or two fields of many elements: the unused fields do not occupy cache lines or memory bandwidth, and the loop can be vectorized more easily. SoA complicates code (parallel indexes, inserts touch every array) and AoS can win for random access of whole elements; choose by access pattern, then measure (`layout_bench.cpp` below).

### 3.3 Benchmarking method

A benchmark answers one question under stated conditions. Rules:

1. Write the hypothesis and the decision it informs *before* running.
2. Benchmark the code you ship: `-O2` (or your release flags), no sanitizers, `NDEBUG` as in release.
3. **Prevent dead-code elimination**: the compiler may delete work whose result is unused. Consume results through an optimizer barrier (`do_not_optimize` below uses a GCC/Clang `asm volatile`; Google Benchmark provides `benchmark::DoNotOptimize` and `benchmark::ClobberMemory` for the same purpose; both compiled and ran in 1.8.3).
4. **Prevent constant folding**: inputs must not be compile-time constants.
5. **Warm up**: first runs pay for page faults, cold caches, lazy initialization, frequency ramp-up.
6. **Repeat and report spread** (min, median, max), not one number. A max/min ratio far from 1 means noise.
7. **Cross-check correctness**: both variants must compute the same answer; a fast wrong loop is a bug.
8. Vary the size across cache boundaries (fits L1, fits L2, fits L3, exceeds L3).
9. Control the environment: AC power and performance governor if you can (`cpupower frequency-set -g performance` needs root and the `cpupower` tool; not run here), pin to a core (`taskset -c 2 ./prog`), close other work, same compiler and flags, note the CPU model. Thermal throttling and turbo change results between runs.
10. A compiler barrier (`asm volatile("" ::: "memory")`) only constrains the compiler; it emits no CPU fence and is not a synchronization primitive.

Noise sources: frequency scaling, other processes, SMT siblings, page-fault timing, allocator state, ASLR changing alignment, a cold branch predictor. When two numbers differ by less than the spread of repeated runs, you have not shown a difference.

Hand-rolled harness (used below). Google Benchmark is the usual tool in teams; it adds automatic iteration counts, statistics and output formats, and is a dependency to be agreed with the team (install via a distro package such as `libbenchmark-dev`, or CMake `FetchContent`).

```cpp
// file: bench.hpp  (C++20)  Hand-rolled harness. GCC/Clang inline asm; other compilers need their own mechanism.
#pragma once
#include <algorithm>
#include <chrono>
#include <vector>

// Forces the compiler to treat v as used and memory as possibly changed, so work feeding v is not deleted.
template <class T> inline void do_not_optimize(const T& v) {
#if defined(__GNUC__) || defined(__clang__)
    asm volatile("" : : "r,m"(v) : "memory");
#else
    static volatile const void* sink;  // weaker fallback; MSVC needs its own mechanism
    sink = &v;
#endif
}
inline void clobber_memory() {
#if defined(__GNUC__) || defined(__clang__)
    asm volatile("" : : : "memory");  // compiler barrier only: emits no CPU instruction
#endif
}

struct Stats { double min_ns, median_ns, max_ns; };

// Runs f() once as warm-up (page faults, cold caches, lazy init), then `reps` timed runs.
// Report the spread, not only one number: a wide max/min ratio means a noisy measurement.
template <class F> Stats measure(F&& f, int reps = 15) {
    f();
    std::vector<double> t;
    for (int i = 0; i < reps; ++i) {
        const auto a = std::chrono::steady_clock::now();
        f();
        clobber_memory();
        const auto b = std::chrono::steady_clock::now();
        t.push_back(std::chrono::duration<double, std::nano>(b - a).count());
    }
    std::sort(t.begin(), t.end());
    return {t.front(), t[t.size() / 2], t.back()};
}
```

### 3.4 Allocators and `std::pmr`

General-purpose `operator new` is a locked, fragmentation-managing, cache-cold path; a million small allocations cost a million trips. Strategies: reserve capacity (`vector::reserve`), pool or arena allocation, and allocator-aware containers. C++17's `std::pmr` (polymorphic memory resources, `<memory_resource>`) lets a container use a runtime-selected `std::pmr::memory_resource` without changing its type beyond `std::pmr::vector<T>`:

- `monotonic_buffer_resource`: bump-pointer allocation from a buffer (falling back to an upstream resource); `deallocate` does nothing; everything is released at once when the resource is destroyed. Fast, tiny per-allocation overhead; memory is not reused until then. Right for per-request or per-frame scratch data.
- `unsynchronized_pool_resource` / `synchronized_pool_resource`: size-class pools; the second is thread-safe.
- `new_delete_resource()`: the default behind `operator new`.

Properties that matter: elements of a `pmr::vector<pmr::string>` propagate their container's resource (uses-allocator construction), the resource must **outlive** every object using it, `monotonic_buffer_resource` is not thread-safe, and a long-running loop on a monotonic arena grows without bound. Counting upstream calls verifies the claim "this removed the allocations":

```cpp
// file: pmr_demo.cpp  (C++20)
#include <cstdio>
#include <memory_resource>
#include <string>
#include <vector>

// Counts how often the upstream resource is asked for memory.
class CountingResource : public std::pmr::memory_resource {
    std::pmr::memory_resource* up_;
public:
    std::size_t allocs = 0, deallocs = 0;
    explicit CountingResource(std::pmr::memory_resource* up = std::pmr::get_default_resource()) : up_(up) {}
private:
    void* do_allocate(std::size_t n, std::size_t a) override { ++allocs; return up_->allocate(n, a); }
    void do_deallocate(void* p, std::size_t n, std::size_t a) override { ++deallocs; up_->deallocate(p, n, a); }
    bool do_is_equal(const std::pmr::memory_resource& o) const noexcept override { return this == &o; }
};

int main() {
    CountingResource heap_counter;
    {
        std::pmr::vector<std::pmr::string> v{&heap_counter};  // strings and the vector share this resource
        for (int i = 0; i < 1000; ++i) v.emplace_back("a string long enough to avoid the small-string optimization");
    }
    std::printf("plain resource: %zu allocations\n", heap_counter.allocs);

    CountingResource upstream;
    {
        alignas(std::max_align_t) static char buf[1 << 20];  // 1 MiB stack/static arena
        std::pmr::monotonic_buffer_resource arena{buf, sizeof buf, &upstream};
        std::pmr::vector<std::pmr::string> v{&arena};
        for (int i = 0; i < 1000; ++i) v.emplace_back("a string long enough to avoid the small-string optimization");
    }  // arena releases everything at once; individual deallocations were no-ops
    std::printf("monotonic arena: %zu upstream allocations\n", upstream.allocs);
}
```

Observed (g++ 14.2): the first block reported 1011 requests to the resource (1000 string buffers plus the vector's growth steps), the second reported 0 upstream allocations because everything fit in the 1 MiB buffer. That proves allocation *count*, not speed; time it with the harness.

### 3.5 Threads, mutexes, condition variables

`std::thread` (or C++20 `std::jthread`, which joins in its destructor and supports stop tokens) runs a callable on a new OS thread. Destroying a joinable `std::thread` calls `std::terminate`; prefer `jthread` or join in a scope guard. Shared mutable data needs one of: a mutex (`std::mutex` with `std::lock_guard`/`std::unique_lock`/`std::scoped_lock`; the last takes several mutexes without deadlock), an atomic, or no sharing (thread-local or per-thread partial results combined after `join`).

`std::condition_variable` waits for a *condition over shared state* protected by the same mutex. Always wait with a predicate: `cv.wait(lk, pred)` re-checks after spurious wakeups and after missed notifications. Notify after changing the state; notifying while holding the lock is correct but may wake a thread that immediately blocks; unlocking first is a common refinement. The state change must happen under the mutex even for a `bool`, otherwise the wakeup can be lost.

Deadlock needs a cycle of waits: avoid by a global lock order, by holding one lock at a time, or by `std::scoped_lock`. Don't call unknown code (callbacks) while holding a lock.

### 3.6 Data races are undefined behaviour

Two accesses to the same memory location, at least one a write, at least one non-atomic, with no happens-before ordering between them, form a **data race**, and the standard makes the whole program's behaviour undefined (language guarantee; cppreference "Memory model"). The compiler may assume no other thread modifies a non-atomic variable and keep it in a register (the failure lab shows this).

### 3.7 `std::atomic` and `memory_order` at the practical level

`std::atomic<T>` makes individual operations indivisible and race-free. The `memory_order` argument says what *other* memory operations are ordered around it:

| Order | Guarantee (practical) | Use for |
|---|---|---|
| `seq_cst` (default) | one global total order of all seq_cst operations, plus acquire/release | when in doubt; correct by default |
| `release` (store) + `acquire` (load) | everything written before the release-store is visible to the thread whose acquire-load reads that stored value | publishing data via a flag; unlocking/locking |
| `acq_rel` | both, on read-modify-write | reference-count-style decrements, exchange |
| `relaxed` | atomicity only, no ordering of other memory | independent counters, stop flags where no other data is published |

Rules of thumb: start with `seq_cst`; relax only with a proof of the happens-before edges you need and a measurement that shows the gain (on x86-64 many orders compile to the same load/store instructions, so gains show mostly elsewhere; check your target); never use relaxed to publish non-atomic data. `mutex` lock/unlock already supply acquire/release. Lock-free is not wait-free and not automatically faster; `is_lock_free()` tells you if a type is implemented without a lock on your platform.

Message passing (verified under TSan: clean; replacing both orders with `relaxed` made TSan report a data race on `payload`):

```cpp
// file: mp.cpp  (C++20)  Message passing with release/acquire. Try breaking it: make both orders relaxed and run under TSan.
#include <atomic>
#include <cstdio>
#include <thread>

int payload = 0;                 // plain data, protected by the flag's happens-before edge
std::atomic<bool> ready{false};

int main() {
    std::thread producer([] {
        payload = 42;                                  // (1) ordinary write
        ready.store(true, std::memory_order_release);  // (2) publishes everything before it
    });
    std::thread consumer([] {
        while (!ready.load(std::memory_order_acquire)) std::this_thread::yield();  // (3) pairs with (2)
        std::printf("payload = %d\n", payload);        // (4) guaranteed to see 42
    });
    producer.join();
    consumer.join();
}
```

### 3.8 False sharing

Cores keep caches coherent per cache line. If two threads write *different* variables that sit on the *same* line, the line ping-pongs between cores even though no data is logically shared. The fix is layout: align or pad hot per-thread data to separate lines (`alignas(64)`), or accumulate in thread-local variables and combine at the end. `std::hardware_destructive_interference_size` (C++17, `<new>`) names the size, but GCC warns it is ABI-unstable (`-Winterference-size`), so many projects use a constant verified for their targets. Hypothesis to write before running: padding separates the counters onto different lines, so the padded version scales and the packed one does not.

```cpp
// file: false_sharing.cpp  (C++20)  Measures; make a hypothesis BEFORE running. Build -O2 -pthread, no sanitizers.
#include <atomic>
#include <chrono>
#include <cstdio>
#include <new>
#include <thread>
#include <vector>

constexpr long kIters = 20'000'000;
constexpr std::size_t kLine = 64;  // typical x86-64 line (getconf LEVEL1_DCACHE_LINESIZE printed 64 on the test machine)
// std::hardware_destructive_interference_size exists in <new> (C++17) but GCC warns that it is ABI-unstable (-Winterference-size); we use a constant.

struct Packed { std::atomic<long> v; };                 // neighbours share a cache line
struct alignas(kLine) Padded { std::atomic<long> v; };  // one line each (sizeof == 64)

template <class Counter>
double run(unsigned threads) {
    std::vector<Counter> c(threads);
    for (auto& x : c) x.v.store(0);
    const auto t0 = std::chrono::steady_clock::now();
    {
        std::vector<std::jthread> ts;
        for (unsigned i = 0; i < threads; ++i)
            ts.emplace_back([&c, i] { for (long k = 0; k < kIters; ++k) c[i].v.fetch_add(1, std::memory_order_relaxed); });
    }
    const auto t1 = std::chrono::steady_clock::now();
    long sum = 0;
    for (auto& x : c) sum += x.v.load();
    if (sum != static_cast<long>(threads) * kIters) { std::puts("WRONG SUM"); std::exit(1); }
    return std::chrono::duration<double, std::milli>(t1 - t0).count();
}

int main() {
    const unsigned n = std::min(4u, std::thread::hardware_concurrency());
    std::printf("sizeof(Packed)=%zu sizeof(Padded)=%zu threads=%u\n", sizeof(Packed), sizeof(Padded), n);
    for (int rep = 0; rep < 5; ++rep)
        std::printf("rep %d: packed %.1f ms, padded %.1f ms\n", rep, run<Packed>(n), run<Padded>(n));
}
```

Observed (i7-10510U, 4 threads, 20 million relaxed `fetch_add` each, g++ 14.2 `-O2`, laptop with frequency scaling): packed runs took about 950 to 1600 ms and padded about 190 to 215 ms across five repetitions. Same ordering in every repetition; the exact ratio is machine-specific. Run it yourself and compare against your hypothesis.

### 3.9 Thread safety documentation

Every class that may be touched by more than one thread states: which operations are safe concurrently; what lock or protocol guards which data (invariants); the lifecycle (construction, shutdown, destruction while in use); whether callbacks run under a lock; exception behaviour; and blocking behaviour. The standard library's convention: distinct objects are independent, a single object is not safe for concurrent mutation unless documented.

```cpp
// file: blocking_queue.hpp  (C++20)
#pragma once
#include <condition_variable>
#include <cstddef>
#include <deque>
#include <mutex>
#include <optional>
#include <stdexcept>
#include <utility>

// THREAD SAFETY: every member function may be called concurrently from any threads (the class is thread-safe).
// INVARIANTS (guarded by m_): q_.size() <= cap_; closed_ only changes false -> true.
// LOCK ORDER: m_ is the only lock; no user code (T's constructors aside from move) runs while it is held except T's move.
// SHUTDOWN: close() wakes everyone; push() then returns false; pop() drains remaining items, then returns nullopt.
template <class T>
class BlockingQueue {
    std::mutex m_;
    std::condition_variable not_empty_, not_full_;
    std::deque<T> q_;
    const std::size_t cap_;
    bool closed_ = false;

public:
    explicit BlockingQueue(std::size_t cap) : cap_(cap) {
        if (cap == 0) throw std::invalid_argument("BlockingQueue: capacity must be > 0");
    }
    BlockingQueue(const BlockingQueue&) = delete;
    BlockingQueue& operator=(const BlockingQueue&) = delete;

    // Blocks while full. Returns false (and drops v) if the queue is closed.
    bool push(T v) {
        std::unique_lock lk(m_);
        not_full_.wait(lk, [&] { return q_.size() < cap_ || closed_; });  // predicate form: handles spurious wakeups
        if (closed_) return false;
        q_.push_back(std::move(v));
        lk.unlock();                 // notify without holding the lock: the woken thread need not block on it
        not_empty_.notify_one();
        return true;
    }
    // Blocks while empty and open. Returns nullopt only when closed AND empty.
    std::optional<T> pop() {
        std::unique_lock lk(m_);
        not_empty_.wait(lk, [&] { return !q_.empty() || closed_; });
        if (q_.empty()) return std::nullopt;
        T v = std::move(q_.front());
        q_.pop_front();
        lk.unlock();
        not_full_.notify_one();
        return v;
    }
    void close() {
        { std::lock_guard lk(m_); closed_ = true; }
        not_empty_.notify_all();
        not_full_.notify_all();
    }
};
```

## 4. Worked example

### 4.1 Layout experiment: AoS vs SoA, vector vs list

The program below measures a one-field scan (AoS vs SoA), and a sum over `std::vector` vs a *sorted* `std::list` (so node order differs from allocation order). It prints min, median, max per element and cross-checks that both layouts compute the same sum. It asserts no outcome.

```cpp
// file: layout_bench.cpp  (C++20)  Measures; asserts nothing about the outcome. Build: -O2, no sanitizers.
#include <cstdio>
#include <list>
#include <numeric>
#include <random>
#include <vector>

#include "bench.hpp"

struct ParticleAoS { double x, y, z, vx, vy, vz, mass; int id; };  // 64 bytes with padding on common ABIs
struct ParticlesSoA { std::vector<double> x, y, z, vx, vy, vz, mass; std::vector<int> id; };

int main() {
    std::mt19937 rng(1);
    std::printf("%-22s %10s %14s %14s %14s\n", "case", "n", "min ns/elem", "median ns/elem", "max ns/elem");
    for (std::size_t n : {std::size_t{1} << 12, std::size_t{1} << 16, std::size_t{1} << 20}) {
        std::vector<ParticleAoS> aos(n);
        ParticlesSoA soa;
        soa.x.resize(n);
        for (std::size_t i = 0; i < n; ++i) { aos[i].x = static_cast<double>(i % 100); soa.x[i] = aos[i].x; }
        double sa = 0, ss = 0;
        auto row = [&](const char* name, Stats s) {
            const double d = static_cast<double>(n);
            std::printf("%-22s %10zu %14.3f %14.3f %14.3f\n", name, n, s.min_ns / d, s.median_ns / d, s.max_ns / d);
        };
        row("sum x, AoS", measure([&] { double s = 0; for (const auto& p : aos) s += p.x; sa = s; do_not_optimize(s); }));
        row("sum x, SoA", measure([&] { double s = 0; for (double v : soa.x) s += v; ss = s; do_not_optimize(s); }));
        if (sa != ss) { std::puts("MISMATCH: layouts disagree"); return 1; }  // correctness before speed

        std::vector<int> vec(n);
        for (int& v : vec) v = static_cast<int>(rng());
        std::list<int> lst(vec.begin(), vec.end());
        lst.sort();  // relinks nodes: traversal order no longer matches allocation order
        long s1 = 0, s2 = 0;
        row("sum, vector", measure([&] { long s = 0; for (int v : vec) s += v; s1 = s; do_not_optimize(s); }));
        row("sum, list (sorted)", measure([&] { long s = 0; for (int v : lst) s += v; s2 = s; do_not_optimize(s); }));
        if (s1 != s2) { std::puts("MISMATCH: containers disagree"); return 1; }
    }
}
```

Procedure: (1) write your hypothesis per row, with expected direction and which size should show the largest gap, and why; (2) `g++ -std=c++20 -O2 layout_bench.cpp -o lb`; (3) `taskset -c 2 ./lb` three times; (4) compare; (5) if the result contradicts you, find out why before concluding (compiler vectorization, working set vs cache size, node placement) - `-S` output from 5.5 helps.

### 4.2 Stop flag: a data race that works at `-O0`

```cpp
// file: stopflag.cpp  (C++20)  Failure lab: usually hangs at -O2. Run with: timeout 5 ./stopflag ; echo $?
#include <chrono>
#include <cstdio>
#include <thread>

bool stop = false;  // plain bool shared between threads: a data race

int main() {
    long spins = 0;
    std::thread worker([&] {
        while (!stop) ++spins;  // the compiler may load `stop` once, since no other thread "can" change it
    });
    std::this_thread::sleep_for(std::chrono::milliseconds(100));
    stop = true;
    worker.join();
    std::printf("worker stopped after %ld spins\n", spins);
}
```

Observed with g++ 14.2: built `-O0`, it printed `worker stopped after 61010165 spins` and exited; built `-O2`, the same source ran until `timeout 5` killed it (exit status 124). Built with `-fsanitize=thread`, TSan reported `data race`. The fix:

```cpp
// file: stopflag_fixed.cpp  (C++20)
#include <atomic>
#include <chrono>
#include <cstdio>
#include <thread>

int main() {
    std::atomic<bool> stop{false};
    long spins = 0;  // written only by the worker, read after join (join synchronizes)
    std::thread worker([&] { while (!stop.load(std::memory_order_relaxed)) ++spins; });
    std::this_thread::sleep_for(std::chrono::milliseconds(100));
    stop.store(true, std::memory_order_relaxed);
    worker.join();
    std::printf("stopped, spins > 0: %d\n", spins > 0);
}
```

Relaxed is enough because the flag publishes no other data; `spins` is read only after `join`, which synchronizes.

## 5. Production perspective

**Performance.** Measure before restructuring: AoS to SoA changes every call site. Fix the biggest structural cost first: allocation counts, pointer-heavy structures, layout, then threads. Profile with the 5.5 workflow; hardware counters (`perf stat -e cache-misses`; counters were denied inside a container) show cache behaviour.

**Correctness.** Run every concurrent test under TSan (and separately ASan+UBSan) in CI; races that never fail in 100 normal runs can fail the 101st on different hardware. Keep the lock-protected region small and free of callbacks. Prefer message passing and per-thread data to shared mutable state. Atomics with non-seq_cst orders need a written argument in the code.

**Failure handling.** A task that throws inside a raw `std::thread` calls `std::terminate`; a pool must capture exceptions (`std::packaged_task` stores them in the future). Shutdown must have a defined protocol (drain or discard), and the destructor must not deadlock when called from a worker. Bounded queues give back-pressure; unbounded queues convert overload into memory exhaustion.

**Observability.** Expose queue depth, task latency histogram, and rejected-task counts. Operations: pin cores and set thread count from `std::thread::hardware_concurrency()` (a hint that may return 0; the container CPU quota may be smaller than the host core count).


**Senior habits.** Make the measurement part of the change (a benchmark in the PR), refuse "lock-free" without a stated reason, and design so threads share nothing until a defined merge point.

**Beginner mistakes and diagnosis.** (1) Benchmarking `-O0` or unused results: look at the assembly or vary the code and see no change. (2) `wait` without a predicate: sporadic hangs or spurious wakeup bugs; add the predicate. (3) Locking different mutexes in different orders: hang; get thread stacks (`gdb -p PID`, `thread apply all bt`) and look for a cycle. (4) Per-thread counters in an array of plain ints: false sharing. (5) Using `relaxed` everywhere because it is "faster": TSan or a stress test on a weakly ordered machine finds it.

## 6. Failure laboratory

Predict first, in writing. Each of the following is a flawed claim or program.

**Flaw A (benchmark).** A teammate reports "SoA is 8x faster" from this code at `-O2`:

```cpp
for (int r = 0; r < 100; ++r) { double s = 0; for (auto& p : aos) s += p.x; }  // result never used
```
and the same loop over `soa.x`. What would you expect the compiled code and the timings to look like, and why is the claim worthless even if the numbers are real?

**Flaw B (lost wakeup).** What is wrong here, and how could a consumer hang forever?

```cpp
// consumer                       // producer
std::unique_lock lk(m);           ready = true;          // no lock held
cv.wait(lk);                      cv.notify_one();
```

**Flaw C (false sharing hidden as "threads don't scale").** `std::array<std::atomic<long>, 4> counters` is incremented by four threads, one element each. All correct, no race. What do you expect when going from 1 to 4 threads, and what single change tests your explanation?

### Reveal (read after predicting)

**A.** The loop has no side effects, so at `-O2` the compiler may remove it entirely (a measured time near zero, or identical times for both layouts, is the evidence; check with `-S`). If times are real, the loop was not removed, but nothing proves the work measured is the work you ship; add a barrier, cross-check, and report spread. The 8x is worthless without the method.

**B.** The consumer checks no predicate and the producer modifies `ready` outside the mutex. If the notification fires before the consumer begins waiting, the notification is lost and `wait` blocks until a later notification that may never come. Also `wait` may wake spuriously with the condition false. Fix: producer sets `ready` under the lock (`{ std::lock_guard g(m); ready = true; }`) then notifies; consumer uses `cv.wait(lk, [&]{ return ready; })`. Diagnosis: reproduce with a sleep before `wait` (shape of the hang), then attach a debugger or use TSan (flags the unsynchronized `ready`).

**C.** Eight-byte counters sit eight to a line, so four threads write the same line; scaling is poor or negative. Test: pad each element to its own line (`alignas(64)` wrapper). `false_sharing.cpp` is that experiment; observed here: padded was roughly five times faster at four threads (your ratio will differ). Do not conclude the hardware is "slow at atomics"; the control experiment (padded) isolates the cause.
