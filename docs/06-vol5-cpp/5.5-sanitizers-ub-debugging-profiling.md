## 1. Engineering problem

A service that passed its tests for months starts returning corrupted totals under load, crashes once a week with a different stack each time, and gets slower after an "unrelated" compiler upgrade. Three different failures, one root family: **undefined behavior** (UB) that tests did not trigger deterministically, and performance beliefs nobody measured. The engineer who guesses adds prints, which change timing and hide the race; the engineer with tools reproduces under a sanitizer, reads a report that names the line, the allocation site and the free site, and fixes the cause.

This lesson is the toolbox and the method (0.3 and 4.4 applied to C++): reproduce, minimize, classify the symptom, choose the instrument, read its evidence, fix the cause, add a regression test, record it.

## 2. Learning objectives

1. Classify any given C++ failure (crash, hang, wrong output, leak, slow) and choose the first tool with a reason, then demonstrate it on a minimal program.
2. Build the same program with ASan+UBSan and with TSan using one script, and read a sanitizer report from the access site, allocation site and free site to a root cause in under 10 minutes per case.
3. Explain, with a compiled example and its assembly, why an optimizing compiler may delete a check that relies on signed overflow or a null test after a dereference.
4. Produce a core dump, state how you would open it in gdb or lldb, and use `bt`/`frame`/`print`/watchpoint commands.
5. Configure a warning set and a static-analysis pass (`-Wall -Wextra -Wpedantic`, `-fanalyzer`, clang-tidy) and justify each enabled group, with a policy for false positives.
6. Run a profile-driven optimization: baseline, sample, hypothesize, change one thing, remeasure, confirm identical output; write down what the profile did and did not show.
7. Complete an autopsy report for each of six broken programs: symptom, tool, evidence, root cause, fix, regression test, and why the program "worked" before.

## 3. First-principles explanation

### 3.1 What UB is and why optimizers exploit it

The C++ standard defines the behavior of **well-formed programs on valid inputs**. For some operations it says "the behavior is undefined": it places no requirement on the implementation (language guarantee, in the standard). Compilers use this as a contract: *the programmer promised this never happens*, so code paths that would require it can be assumed unreachable. This lets them delete checks, keep values in registers, vectorize, and reorder. UB is not "implementation-defined" (implementation documents a choice) and not "unspecified" (one of several valid outcomes): after UB occurs, **nothing** is guaranteed, including behavior *before* the UB point in the optimized program.

Consequences: a program with UB can pass every test, behave differently at `-O0` vs `-O2`, change with an unrelated edit, and be a security hole. Sanitizers and warnings are the only practical defence, because "it works on my machine" proves nothing.

Catalogue (each demonstrated in `ub_catalog.cpp` below unless noted):

| UB | Example | First detector |
|---|---|---|
| Signed integer overflow | `INT_MAX + 1` | UBSan `signed-integer-overflow` |
| Shift by >= width or negative | `1 << 32` | UBSan `shift` |
| Null / invalid pointer dereference | `*p` with `p == nullptr` | UBSan `null`, ASan |
| Out-of-bounds access | `arr[4]` on `int[4]`, `v[v.size()]` | UBSan `bounds` (arrays), ASan (heap/stack/global) |
| Use after free / dangling reference | reference into a reallocated vector, `string_view` of a temporary | ASan |
| Misaligned access | `*reinterpret_cast<int*>(buf + 1)` | UBSan `alignment` |
| Division by zero | `10 / 0` (integers) | UBSan `integer-divide-by-zero` |
| Flowing off the end of a non-void function | missing `return` | `-Wreturn-type`, UBSan `return` |
| Reading uninitialized (indeterminate) values | `int x; use(x);` | `-Wmaybe-uninitialized` (heuristic), MSan (clang), valgrind memcheck |
| Data race | two threads, one writes, no synchronization | TSan |
| Violating strict aliasing | read a `float` through an `int*` | `-Wstrict-aliasing` (observed: g++ 14.2 `-Wall -O2` warned `dereferencing type-punned pointer`); no reliable runtime sanitizer (UBSan does not check aliasing) |
| Invalid comparator (not strict weak ordering) | `a <= b` in `std::sort` | ASan sometimes (observed: `heap-buffer-overflow` sorting 1000 equal ints with `<=`), `-D_GLIBCXX_DEBUG` (observed: aborts with a debug-mode diagnostic from `std::sort`) |
| ODR violation, modifying a const object, unsequenced side effects | `i = i++ + 1` | warnings, review |

### 3.2 Sanitizers

Compile-time instrumentation plus a runtime library. Build with `-g`, `-O1` or `-O2` (sanitizers work at `-O0` too; re-run at your release level as UB bites differently), and `-fno-omit-frame-pointer` for better stacks.

| Sanitizer | Flag (GCC and clang) | Finds | Cost / limits |
|---|---|---|---|
| ASan (+LSan on Linux x86-64) | `-fsanitize=address` | heap/stack/global overflow, use-after-free, double free, leaks (observed: `LeakSanitizer: detected memory leaks`) | about 2x average slowdown per the ASan wiki, plus a memory overhead the wiki does not quantify (measure your workload); incompatible with TSan |
| UBSan | `-fsanitize=undefined` | the table above marked UBSan; add `-fno-sanitize-recover=undefined` to abort on first error (observed exit code 1) | small; reports and continues by default |
| TSan | `-fsanitize=thread` | data races *that occur in the executed run* | several-fold slowdown; not exhaustive; cannot combine with ASan |
| MSan | `-fsanitize=memory` | uninitialized reads | **clang only**; uninstrumented libraries can cause false positives or missed reports (Clang docs; a trivial `std::string`/iostream program ran clean here); observed with clang 18 `-O0 -g`: `WARNING: MemorySanitizer: use-of-uninitialized-value` in `pick`, but at `-O1` the same program printed `zero` with no report because the optimizer had already folded the uninitialized path: test at `-O0` and at the level you ship |

Useful environment options (observed to work): `UBSAN_OPTIONS=print_stacktrace=1`. Observed: with g++ 14.2 and with clang 18 on Linux, a lambda returned with a dangling by-reference capture was reported as `stack-use-after-return` with no option set (so detection is on by default in these versions; with `ASAN_OPTIONS=detect_stack_use_after_return=0` it was not reported and the program printed a value). The ASan wiki lists the option only among aggressive-diagnostics flags, so older toolchains need `=1`; check `ASAN_OPTIONS=help=1` for yours. A sanitizer error is a bug until proven otherwise; suppress only with a written reason.

### 3.3 Warnings and static analysis

Compiler warnings are free static analysis. Baseline: `-Wall -Wextra -Wpedantic`. Candidates to add and evaluate in your codebase: `-Wshadow -Wconversion -Wsign-conversion -Wold-style-cast -Wnull-dereference -Wformat=2`; treat as errors (`-Werror`) in CI for your own code, not necessarily for third-party headers or across compiler upgrades. Observed: g++ warned (without extra flags) when a function returned the address of a local, and `-Wall` warned about a missing return; `-Wall -Wextra -O2` caught the uninitialized `result` but `-O0` did not (flow analysis needs optimization).

`g++ -fanalyzer` (GCC 10+; observed in 14.2) found the same uninitialized use with a CWE tag; GCC's documentation has described C++ support as limited (not re-read for this edit), so treat silence as no evidence. **clang-tidy** (observed with clang-tidy 18: `bugprone-use-after-move` flagged use after `std::move`) runs checks such as `bugprone-*`, `performance-*`, `modernize-*`, `cppcoreguidelines-*`; adopt incrementally with a checked-in `.clang-tidy`, fix by category, and never "fix" a finding you do not understand. Hardening flags (libc++ equivalent, observed with clang 18: `-D_LIBCPP_HARDENING_MODE=_LIBCPP_HARDENING_MODE_FAST` traps on `v[5]` of a 3-element vector): `-D_GLIBCXX_ASSERTIONS` (observed: turns `v[i]` out-of-range into an assertion abort with a readable message), `-ftrivial-auto-var-init=zero|pattern` (GCC 12+; observed: makes uninitialized locals deterministic, which hides the bug in production; use `pattern` in testing to make it loud), `-fstack-protector-strong`.

### 3.4 Debuggers and core dumps

Build with `-g -O0` (or `-Og`) for debugging; at `-O2` variables are optimized away, lines jump. gdb basics: `gdb ./prog`, `break file.cpp:42`, `run args`, `bt` (stack), `frame N`, `info locals`, `print expr`, `next`/`step`/`finish`, `watch var` (stop when written), `continue`, `up`/`down`; `set print pretty on`. lldb equivalents: `lldb ./prog`, `b file.cpp:42`, `r`, `bt`, `frame variable`, `p expr`, `n`/`s`, `watchpoint set variable var`. To stop where ASan is about to report: break on `__asan::ReportGenericError` (observed with clang 18: gdb stops there and `bt` shows `__asan_report_load4` and your frame); with GCC 14's libasan break on `__asan_report_load4` / `__asan_report_store*` instead (observed). Observed gdb: `watch x` gives `Hardware watchpoint`, `Old value`, `New value`. lldb inside a container that forbids `personality` needs `settings set target.disable-aslr false`; then `watchpoint set variable x` stopped on the write.

Core dumps: `ulimit -c unlimited; ./prog` writes a core file if the kernel policy allows. Observed here: after `abort()`, a file named `core.<pid>` appeared in the working directory (`/proc/sys/kernel/core_pattern` was `core`). On systemd machines the pattern often pipes to `systemd-coredump` and you use `coredumpctl` (documented behavior; not reproduced, no systemd in the test container). Open with `gdb ./prog core.<pid>` then `bt`; the binary must be the exact build that crashed, with debug info. Production: keep symbol files per release.

**valgrind** (observed: `Conditional jump or move depends on uninitialised value(s)` at the `if` of the Bug 4 program): `valgrind --leak-check=full ./prog` needs no recompile, runs far slower than native, reports uninitialized reads (memcheck) - the practical substitute for MSan on a g++-only toolchain. Do not combine with ASan.

### 3.5 Profiling workflow

1. Define a representative workload and a baseline (wall time, repeated runs, `-O2` build). 2. Sample, do not guess. 3. Form one hypothesis. 4. Change one thing. 5. Remeasure; verify outputs identical. 6. Stop when the goal is met.
- **perf** (Linux; option names checked with `perf record -h` / `perf stat -h`: `-F`, `--call-graph`, `-e`; output NOT observed because the test container denied perf events, so expect to need privileges or a relaxed `kernel.perf_event_paranoid`): build `-O2 -g -fno-omit-frame-pointer`; `perf record -F 99 -g ./prog`; `perf report`; `perf stat ./prog` for counters (hardware counters may be unavailable in VMs/containers). Flame graphs are generated from perf output with separate scripts (not part of perf; not tried here).
- **gprof** (observed working): `g++ -O2 -g -pg prog.cpp`, run once (writes `gmon.out`), `gprof -b ./prog gmon.out`. Instrumentation-based call counts plus sampled time; coarse (0.01 s samples), ignores time in shared libraries, and perturbs inlining. Use it to learn the workflow where perf is not available.
- Pitfalls: profiling `-O0` (the hot spots differ), tiny workloads (noise), I/O waits invisible to CPU samples, sampling skid, a profile of the wrong input. For cache and benchmark methodology see 5.6.

### 3.6 Reading assembly

Compiler Explorer (godbolt.org; UI not re-checked): pick "C++", an "x86-64 gcc 14.x" compiler, flags `-std=c++20 -O2`; the right pane maps source lines to instructions; add `-fsanitize=address` to see instrumentation. Locally: `g++ -std=c++20 -O2 -S -masm=intel -fno-asynchronous-unwind-tables x.cpp -o x.s`. System V x86-64 ABI (platform ABI document): integer arguments in `rdi, rsi, rdx, rcx, r8, r9`, return value in `rax`/`eax`; `xor eax, eax` zeroes; `lea` is often used as an adder; `ret` returns. You are reading to answer a question ("was my check kept?", "was the loop vectorized?", "is this call inlined?"), not to read everything.

## 4. Worked example

### 4.1 Evidence about UB and the optimizer (observed with g++ 14.2)

```cpp
// file: asm_demo.cpp  (C++20)
int sum_to(int n) {        // sum of 0..n-1
    int s = 0;
    for (int i = 0; i < n; ++i) s += i;
    return s;
}
bool always_true(int x) { return x + 1 > x; }       // signed overflow is UB
int deref_then_check(int* p) {
    int v = *p;              // dereference first...
    if (p == nullptr) return -1;  // ...so this check may be deleted
    return v;
}
```

Compile with `g++ -std=c++20 -O2 -S -masm=intel -fno-asynchronous-unwind-tables asm_demo.cpp` and look at each function. Observed at `-O2`:

- `always_true` compiled to `mov eax, 1` / `ret`: the comparison vanished because signed overflow cannot happen. The `-O0` output also loaded the constant `mov eax, 1` without comparing, so GCC folds this expression even without optimization.
- `deref_then_check`: the `-O2` code is `mov eax, DWORD PTR [rdi]` then `ret`; the `p == nullptr` test is gone, because `*p` was already executed and so `p` cannot be null. With `-fno-delete-null-pointer-checks` the `test rdi, rdi / je` reappeared.
- `sum_to` at `-O2` became an unrolled-by-two loop using `lea edx, 1[rdx+rax*2]` (adds `i` and `i+1` per iteration); that is an optimization, not UB, and it is what you see when "the loop looks different".

Rule: never write a check that can only be true after UB has occurred. Test the precondition first (bug 3 below).

### 4.2 The ub_catalog program under UBSan

```cpp
// file: ub_catalog.cpp  (C++20)  usage: ./ub_catalog <1-7>
#include <climits>
#include <cstdio>
#include <cstdlib>
#include <cstdint>
#include <cstring>

int no_return(int x) { if (x > 100) return 1; }  // case 7: flows off the end of a non-void function

int main(int argc, char** argv) {
    const int which = argc > 1 ? std::atoi(argv[1]) : 0;
    volatile int zero = 0, big = INT_MAX, thirty_two = 32;  // volatile: keep the compiler from folding
    int arr[4] = {1, 2, 3, 4};
    volatile int idx = 4;
    switch (which) {
        case 1: std::printf("%d\n", big + 1); break;                       // signed overflow
        case 2: std::printf("%d\n", 1 << thirty_two); break;               // shift count >= width
        case 3: { int* p = nullptr; std::printf("%d\n", *(p + zero)); } break;  // null dereference
        case 4: std::printf("%d\n", arr[idx]); break;                      // out of bounds (array of known size)
        case 5: { alignas(8) unsigned char buf[16] = {}; auto* p = reinterpret_cast<int*>(buf + 1);
                  std::printf("%d\n", *p); } break;                        // misaligned access
        case 6: std::printf("%d\n", 10 / zero); break;                     // integer division by zero
        case 7: std::printf("%d\n", no_return(1)); break;                  // missing return
        default: std::puts("usage: ub_catalog <1-7>");
    }
}
```

`g++ -std=c++20 -g -fsanitize=undefined ub_catalog.cpp -o ubc` then `./ubc 1` ... `./ubc 7`. Observed messages: `signed integer overflow: 2147483647 + 1 cannot be represented in type 'int'`; `shift exponent 32 is too large for 32-bit type 'int'`; `load of null pointer of type 'int'`; `index 4 out of bounds for type 'int [4]'`; `load of misaligned address ... for type 'int', which requires 4 byte alignment`; `division by zero`; `execution reached the end of a value-returning function without returning a value`. The compiler also warned at build time for case 7 (`-Wreturn-type`).

### 4.3 The autopsy method, then bugs 1 to 3

Method: (1) reproduce with the smallest input; (2) classify; (3) pick the cheapest instrument that can *see* the class; (4) read the evidence bottom-up (where is the bad object from, who invalidated it, who used it); (5) state the root cause as a sentence of the form "X assumed Y, but Z made it false"; (6) fix the cause, not the symptom; (7) add a regression test that fails before and passes after; (8) record in the failure log (0.3). Build line used for bugs 1, 2, 3, 6: `g++ -std=c++20 -Wall -Wextra -Wpedantic -g -fsanitize=address,undefined X.cpp -o X`.

**Bug 1: off by one.**

```cpp
// file: bug1_off_by_one.cpp  (C++20)
#include <cstdio>
#include <vector>

int main() {
    std::vector<int> v(8, 1);
    int sum = 0;
    for (std::size_t i = 0; i <= v.size(); ++i) sum += v[i];  // intends: all 8 elements
    std::printf("sum = %d\n", sum);
}
```

ASan reported `heap-buffer-overflow`, `READ of size 4`, top frame `main bug1_off_by_one.cpp:8`, and `is located 0 bytes after 32-byte region` with the allocation made by `operator new` via `std::allocator<int>::allocate`. "0 bytes after" is the signature of an off-by-one on the end. Root cause: `<=` against `size()` for a zero-based index. Fix: range-for. Also observed: `-D_GLIBCXX_ASSERTIONS` without ASan aborts with `Assertion '__n < this->size()' failed` naming `operator[]`.

**Bug 2: reference invalidated by `push_back`.**

```cpp
// file: bug2_invalidated_reference.cpp  (C++20)
#include <cstdio>
#include <string>
#include <vector>

int main() {
    std::vector<std::string> names{std::string(40, 'a')};
    const std::string& first = names[0];
    names.push_back(std::string(40, 'b'));  // size 1 == capacity 1 in libstdc++: reallocates
    std::printf("%c\n", first[0]);
}
```

ASan: `heap-use-after-free`, `READ of size 8`, three stacks: the access (line 10), `freed by thread T0 here` (the reallocation inside `push_back`, line 9), and `previously allocated by` (line 7). Reading the three stacks in order gives the story. Root cause: a reference into a vector's storage outlived an operation that may reallocate (5.3: iterator invalidation rules). Fix: take the reference after the last mutation, hold an index, or copy.

**Bug 3: overflow check that the compiler deletes.**

```cpp
// file: bug3_overflow_check.cpp  (C++20)
#include <climits>
#include <cstdio>

bool will_overflow(int x) { return x + 1 < x; }  // intended: detect INT_MAX

int main(int argc, char**) {
    int big = INT_MAX - 1 + argc;  // argc == 1 at run time: INT_MAX, not a compile-time constant
    std::printf("will_overflow(INT_MAX) = %d\n", will_overflow(big));
}
```

Observed: built with plain `g++ -O0` AND `-O2` it printed `will_overflow(INT_MAX) = 0`; built with `-fsanitize=undefined` UBSan printed `signed integer overflow: 2147483647 + 1` at the `x + 1` and the program printed 1 (instrumented, so the add is performed); built with `-O2 -fwrapv` (defines wraparound; a non-standard dialect, a patch not a design) it printed 1. The programmer's mental model was "int wraps"; the language's rule is "int overflow is UB", so the optimizer proved `x + 1 < x` false. Fix: test `x == INT_MAX` before adding, or use `__builtin_add_overflow` (GCC/clang extension) or check with wider types.

### 4.4 Profiling a hot spot (gprof, observed)

`prof_demo.cpp` removes duplicates from 60,000 ints.

```cpp
// file: prof_demo.cpp  (C++20)
#include <algorithm>
#include <cstdio>
#include <random>
#include <vector>

__attribute__((noinline)) bool contains(const std::vector<int>& v, int x) {  // linear scan: the hidden hot spot
    return std::find(v.begin(), v.end(), x) != v.end();
}
__attribute__((noinline)) std::vector<int> dedupe(const std::vector<int>& in) {
    std::vector<int> out;
    for (int x : in) if (!contains(out, x)) out.push_back(x);  // O(n * unique)
    return out;
}
__attribute__((noinline)) long checksum(const std::vector<int>& v) {
    long s = 0;
    for (int x : v) s += x;
    return s;
}
int main() {
    std::mt19937 rng(1);
    std::vector<int> in(60000);
    for (int& x : in) x = static_cast<int>(rng() % 30000);
    const auto out = dedupe(in);
    std::printf("%zu unique, checksum %ld\n", out.size(), checksum(out));
}
```

Run `g++ -std=c++20 -O2 -g -pg prof_demo.cpp -o pd && ./pd && gprof -b ./pd gmon.out`. Observed: output `25847 unique, checksum 387228006`; the flat profile attributed essentially all sampled time to `contains` (called 60,000 times) and none to `checksum` or the loop body. Your times will differ; the shape should not. Hypothesis: linear scan makes `dedupe` O(n * unique). Change one thing (a hash set, Challenge 2), re-run, require identical output, re-profile.

## 5. Production perspective

**CI policy.** One job builds and runs the test suite with ASan+UBSan (`-fno-sanitize-recover=undefined`); another with TSan if there are threads; a third at your release `-O2` without sanitizers. Fuzz and stress tests give sanitizers inputs the unit tests lack. Keep the baseline warnings clean; a warning-noisy build teaches people to ignore warnings.

**Release builds.** Sanitizers are for test and staging; they change memory layout and speed. Production crashes need symbols, core or minidump collection, and a way to map a stack back to a commit. Never ship `-fsanitize=undefined` with recover mode on as a "safety net".

**Security.** Memory errors are the major source of exploitable bugs in C++ code (language-level fact: no bounds checking by default). Defensive measures: sanitizers in CI, hardened standard-library assertions (`_GLIBCXX_ASSERTIONS`; libc++: `_LIBCPP_HARDENING_MODE`, observed to trap with clang 18), no raw owning pointers (5.2), bounds-checked access (`at`, `std::span` with assertions) on untrusted indexes.

**What a senior engineer does differently.** Reproduces before theorizing; minimizes a failing case; treats a sanitizer report as a bug, never as noise; keeps a corpus of past failures as regression tests; profiles with a stated hypothesis; knows that a profiler shows where time goes, not why.

**Beginner mistakes and diagnosis.** (1) Adding `printf` to a race (it changes timing): use TSan. (2) Debugging `-O2` in a debugger and trusting variables: rebuild `-O0`/`-Og`. (3) "Fixing" by zero-initializing everything to make the symptom go away: the logic bug stays. (4) Reading only the top ASan frame: read free and allocation stacks. (5) Optimizing without a profile: the dedupe example in 4.4 shows the actual hot spot is rarely the code you suspect.

## 6. Failure laboratory

Three programs. For each, write what you expect to happen **before** running: output, whether it differs between runs, and which tool will see it.

**Bug 4: uninitialized variable.**

```cpp
// file: bug4_uninitialized.cpp  (C++20)
#include <cstdio>

int pick(int n) {
    int result;
    if (n > 0) result = n * 2;
    return result;  // n <= 0: reads an indeterminate value
}

int main(int argc, char**) { std::printf("%d\n", pick(argc - 1)); }
```

**Bug 5: counter without synchronization.**

```cpp
// file: bug5_race.cpp  (C++20)
#include <cstdio>
#include <thread>

int counter = 0;  // plain int shared between threads

int main() {
    auto work = [] { for (int i = 0; i < 100000; ++i) ++counter; };
    std::thread a(work), b(work);
    a.join();
    b.join();
    std::printf("counter = %d (expected 200000)\n", counter);
}
```

**Bug 6: comparator.**

```cpp
// file: bug6_comparator.cpp  (C++20)
#include <algorithm>
#include <cstdio>
#include <vector>

int main() {
    std::vector<int> v(1000, 7);  // many equal elements
    std::sort(v.begin(), v.end(), [](int a, int b) { return a <= b; });  // "descending-ish, inclusive"
    std::printf("sorted %zu elements\n", v.size());
}
```

Questions: for bug 4, does `-Wall -Wextra` warn at `-O0`? at `-O2`? What do you see when run, and does it change between runs? For bug 5, is the final value always 200000? Will `-fsanitize=address` flag it? For bug 6, what are the bugs' *categories* and why might `-O2` without a sanitizer run it without any visible problem?

### Reveal (read after predicting)

**Bug 4.** Observed: `-Wall -Wextra` gave **no** warning at `-O0` and `warning: 'result' may be used uninitialized [-Wmaybe-uninitialized]` at `-O2`; `-fanalyzer` reported `use of uninitialized value 'result' [CWE-457]`. The printed value changed between builds (32753 in an ASan+UBSan build, 0 in an `-O2` build): an indeterminate value is whatever the stack held. `-ftrivial-auto-var-init=zero` printed 0, `=pattern` printed `-16843010`, which is 0xFEFEFEFE as a signed int (a compiler-chosen fill pattern). Neither ASan nor UBSan detects it; valgrind and MSan at `-O0` reported it (observed; MSan at `-O1` did not). Root cause: a path through `pick` returns without assigning.

**Bug 5.** Observed: the plain ASan+UBSan build printed `counter = 137354` once; the value varies run to run (lost updates from non-atomic read-modify-write). ASan/UBSan are silent. `-fsanitize=thread` printed `WARNING: ThreadSanitizer: data race` with `Read of size 4` on one thread and a `Previous write of size 4` on the other, both at line 8. Because the data race is UB, "usually works" is not a property you can rely on: an optimizing compiler is allowed to keep `counter` in a register for the whole loop. Fix and trade-offs in the solutions (atomic vs mutex vs per-thread partial sums; 5.6).

**Bug 6.** Two classes: it is UB (`<=` violates strict weak ordering: `comp(a,a)` must be false), and it can be a memory error. Observed: under ASan, `heap-buffer-overflow` inside libstdc++'s `__unguarded_partition` (the partition loops rely on the comparator being false for equal elements to stop at a sentinel, otherwise they run off the end); compiled `-O2` with no sanitizer, the same program returned normally. Diagnosis procedure for all three, in order: (1) did a warning say so, (2) which sanitizer's class matches the symptom, (3) is the failure nondeterministic (race or uninitialized) or deterministic (bounds, lifetime), (4) is there a path-dependent state (initialized on only some paths).

## 10. Engineering review

- Does every fix address the root cause sentence, not the symptom?
- Is each regression test red on the broken version and green on the fix, under the right variant?
- Does the harness fail the build on the first sanitizer report (no "continue and ignore")?
- Are warnings clean at both `-O0` and `-O2` (flow-sensitive warnings differ)?
- Did you check the fixed programs at the release optimization level too?
- Is the evidence observed output, not remembered output? Are unverified items clearly marked?
- Is each profiling claim backed by a before/after pair on the same input with the same flags?

Explain your decisions: why that tool first? what would a second, independent tool have told you? what is the cheapest way to make this class of bug impossible rather than detected (type, container, ownership)?

## 11. Mastery gate

Pass = 80/100, no critical failure. Critical failures: (1) a "fix" that merely suppresses the report (sleep, zero-init to hide, `-fwrapv` as a fix for an invalid check, a sanitizer suppression without a root cause); (2) an unobserved output presented as observed; (3) a race "fixed" without TSan evidence; (4) a profiling conclusion drawn from an `-O0` build; (5) a fixed program still showing any sanitizer error.

Evidence: dossier, harness run transcript, and a live diagnosis: you are given one new unseen broken program (<= 60 lines) and must classify, choose a tool, and state the root cause within 30 minutes without notes (Mode A).

If failed: remedial exercise: write five new 15-line programs, one per UB class that you missed, predict the tool and report line first, then verify; repeat the live diagnosis with a fresh program.
