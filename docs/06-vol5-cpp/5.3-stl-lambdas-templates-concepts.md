## 1. Engineering problem

A risk engine needs to find the 5 largest exposures per desk, remove expired positions in place, and apply a user-supplied weighting function to millions of values. A first implementation in C++ hand-writes loops, a `std::map` for everything, a `std::function` for the weighting, and a template that accepts any type and produces 400 lines of error text when someone passes the wrong one. It is slow in the wrong places (node-based containers, type-erased calls in the hot loop), unsafe in others (a lambda stored for later that captured a local by reference), and unreadable.

The standard library's containers, algorithms and ranges encode decades of correct, tested loops with documented complexity. Lambdas and templates let you plug your logic into them without virtual calls. Concepts (C++20) make the requirements on template arguments explicit and the error messages short. This lesson teaches you to choose the right container by its complexity and invalidation rules, write algorithms as compositions instead of loops, capture state in lambdas without creating dangling references, and write templates only where they pay for themselves.

## 2. Learning objectives

By the end you can, without references:

1. Select a standard container for a stated access pattern using complexity and iterator-invalidation guarantees, and justify rejecting two alternatives.
2. Replace hand-written loops with `<algorithm>`/`std::ranges` calls and C++20 view pipelines, including projections, `std::erase_if` and the sorted-range algorithms, stating each one's precondition.
3. Write lambdas with correct capture lists, identify a dangling capture by inspection, and reproduce it under ASan.
4. Choose between a template parameter, `std::function`, and a function pointer for a callback, and justify it by ownership, allocation and inlining.
5. Write function and class templates, predict type deduction results (`auto`, `T`, `T&&`), and implement a perfect-forwarding factory.
6. Constrain templates with standard and custom concepts and read a "constraints not satisfied" diagnostic.
7. Implement a generic container with a conforming iterator, verified by `static_assert` on iterator concepts, and tested under sanitizers.

## 3. First-principles explanation

### 3.1 Containers and complexity guarantees

The standard states complexity requirements for operations; they are guarantees in the interface (not implementation details), though constant factors and memory layout are not specified. Complexity in big-O hides cache behavior: contiguous containers are often faster than asymptotically better node-based ones for small and medium sizes. That is an empirical statement: measure (Lesson 4.4); never assume.

| Container | Layout | Lookup | Insert/erase | Notes (language/library guarantee unless stated) |
|---|---|---|---|---|
| `std::array<T,N>` | contiguous, fixed | `[i]` O(1) | n/a | size fixed at compile time |
| `std::vector<T>` | contiguous | `[i]` O(1) | `push_back` amortized O(1); middle O(n) | reallocation invalidates all iterators and references |
| `std::deque<T>` | chunked | `[i]` O(1) | both ends O(1); middle O(n) | insertion at either end invalidates all iterators but not references to existing elements; insertion in the middle invalidates both (checked against cppreference's invalidation table) |
| `std::list<T>` | doubly linked | O(n) | O(1) given an iterator | stable iterators/references; not random access |
| `std::map/set` | balanced tree (typically red-black, implementation detail) | O(log n) | O(log n) | ordered; insertion invalidates nothing |
| `std::unordered_map/set` | hash table | O(1) average, O(n) worst case | O(1) average | rehash invalidates iterators, not references |
| `std::flat_map` (C++23) | sorted vectors | O(log n) | O(n) | test `__cpp_lib_flat_map` (checked: undefined in libstdc++ 14.2 and libc++ 18) |

(Table facts for complexity and invalidation were checked against the cppreference container pages. `deque` insert/erase is linear in the distance to the nearer end, so O(1) at the ends and O(n) in the middle.)

Default choice: `std::vector`. Use `std::unordered_map` for key lookup without ordering, `std::map` when you need ordered iteration or stable iterators, `std::deque` for queues with front removal, `std::list` almost never (profile first). `operator[]` on a map inserts a default-constructed value if the key is missing (verified: `m["missing"]` returned 0 and `m.size()` became 1); use `find`, `contains` (C++20) or `at` for lookups.

Container adaptors (`stack`, `queue`, `priority_queue`) restrict an underlying container's interface.

### 3.2 Iterators and ranges

An iterator abstracts a position. Categories (C++20): input, forward, bidirectional, random access, contiguous (plus output). `std::sort` requires random access (verified: `std::sort` on `std::list` fails with `no match for 'operator-'`).

`begin()`/`end()` form a half-open range `[begin, end)`. An iterator equal to `end()` must not be dereferenced.

C++20 ranges add:

- `std::ranges::` algorithms taking a whole range and projections: `std::ranges::sort(ps, {}, &P::age)` (verified) sorts by a member without a lambda.
- Constrained overloads: `std::ranges::sort(list)` fails with a `constraints not satisfied` diagnostic instead of an error deep in `<bits/stl_algo.h>` (verified).
- Views (`std::views::filter`, `transform`, `take`, `reverse`, `iota`): lazy, non-owning range adaptors composed with `|`. A view does no work until iterated and re-evaluates on each iteration pass.

```cpp
auto result = v | std::views::filter([](int x) { return x % 2 == 1; })
                | std::views::transform([](int x) { return x * x; });
for (int x : result) std::cout << x << ' ';       // verified: v {1,2,3,5,8} gave "1 9 25"
```

Views borrow from their source: if the source is destroyed or modified, the view is invalid. (Rvalue containers passed to `views::all` are moved into an `owning_view`; observed with GCC 14.2 `-std=c++20`. Older libraries predating P2415 reject this.) `std::ranges::to` is C++23 (materialize a view into a container); in C++20 you construct the container yourself.

### 3.3 Algorithms

Prefer a named algorithm over a raw loop: it states intent and is tested. The ones to know: `find`/`find_if`, `count_if`, `any_of`/`all_of`/`none_of`, `transform`, `accumulate` (`<numeric>`, left fold in order), `reduce` (C++17, unspecified order, requires associative and commutative operation), `sort` (O(N log N) comparisons), `stable_sort`, `partial_sort`, `nth_element` (average linear), `partition`, `unique`, `remove`/`remove_if`, `lower_bound`/`upper_bound`/`equal_range` (require a partitioned/sorted range; O(log N) comparisons), `min_element`/`minmax_element`, `iota`, `copy_if`.

Erase-remove: `remove_if` does not shrink the container; it moves the kept elements forward and returns the new logical end:

```cpp
w.erase(std::remove_if(w.begin(), w.end(), pred), w.end());    // classic idiom
std::erase_if(w, pred);                                         // C++20, same effect, harder to misuse
```

Comparators passed to `sort` or ordered containers must be a strict weak ordering (irreflexive, transitive, equivalence is transitive). `<=` as a comparator violates it: the behavior is undefined (the sort may read out of bounds). Algorithms that need sorted input (`lower_bound`, `binary_search`, `set_intersection`) have UB-or-wrong-answer behavior on unsorted data.

### 3.4 Lambdas and captures

A lambda expression creates an unnamed closure type (a class with `operator()`), and an object of it. Captured variables become members.

```cpp
int k = 3;
auto by_val = [k](int x) { return x * k; };          // copies k at creation
auto by_ref = [&k](int x) { return x * k; };         // refers to k: k must outlive the closure
auto mutates = [k]() mutable { return ++k; };        // modifies the closure's own copy
auto moved   = [p = std::make_unique<int>(1)] { return *p; };   // init-capture (C++14); move-only closure
```

Rules:

- `[=]` and `[&]` default captures hide what is captured; prefer explicit lists in any closure that outlives the current statement.
- `[=]` inside a member function captures `this` (a pointer), not a copy of the object's members. Implicit capture of `this` through `[=]` is deprecated in C++20 (verified: GCC warns `implicit capture of 'this' via '[=]' is deprecated in C++20`); write `[this]` or `[*this]` (copy of the object) explicitly.
- The dangling capture trap: a closure that captures by reference (or `this`) and escapes the scope that owns the captured object. Calling it is UB. Verified under ASan:

```cpp
std::function<int()> mk() { int local = 41; return [&local] { return local + 1; }; }
int main() { auto f = mk(); std::cout << f() << '\n'; }    // UB: ASan stack-use-after-return
```

  In my GCC 14.2 run ASan reported `stack-use-after-return` without extra options; the detection of use-after-return depends on the toolchain and runtime flags (`ASAN_OPTIONS=detect_stack_use_after_return=1` on some), so treat a clean run as meaningless.

- Closures converted to `std::function` or stored for later (callbacks, threads, tasks) must capture by value or hold owners (`shared_ptr`, `weak_ptr` with `lock()`).
- Generic lambdas (`[](auto x) {...}`, C++14) are templates in disguise. C++20 allows `[]<typename T>(T x) {...}`.

### 3.5 `std::function` vs templates vs function pointers

| Mechanism | Type | Call cost | Allocation | Use when |
|---|---|---|---|---|
| Template parameter `F` (`template <typename F> void run(F f)`) | the exact closure type | direct call, inlinable | none | algorithm-style APIs; you do not need to store heterogeneous callables |
| `std::function<R(Args...)>` | type-erased | indirect call through a pointer; cannot inline across it | may heap-allocate for larger callables (small-buffer size is implementation-defined) | store callables of different types in one variable or container; stable ABI/interface; callbacks registered at run time |
| Function pointer `R(*)(Args...)` | pointer | indirect | none | C APIs; stateless callbacks (captureless lambdas convert to it) |
| `std::move_only_function` (C++23) | type-erased | like `std::function` | like `std::function` | store move-only callables (`std::function` requires copyable ones); checked: `__cpp_lib_move_only_function` is defined by libstdc++ 14.2 (`-std=c++23`) but not by libc++ 18 |

Rule: algorithms and hot loops take templates; registries and long-lived callbacks take `std::function`. Quantify the difference by measuring in your workload, not by quoting someone else's numbers.

### 3.6 Function and class templates; type deduction

```cpp
template <typename T>
T maxof(const T& a, const T& b) { return a < b ? b : a; }
maxof(3, 7);              // T = int
maxof<double>(1, 2.5);    // explicit
// maxof(1, 2.5);         // error: conflicting deductions for T (int vs double)
```

A template is not code; it is a recipe. The compiler instantiates a separate function or class for each distinct set of arguments, in each TU that needs it (the ODR permits this; identical instantiations are merged by the linker). Consequences: definitions must be visible where used, so templates live in headers; errors appear at instantiation; compile time and binary size grow with instantiations.

Deduction rules you must know (verified outputs):

- By-value `T` parameter: top-level const and references are dropped; arrays and functions decay: `show_deduction("hi")` deduced `T = const char*`.
- `const T&` parameter: binds anything; `T` excludes const.
- `T&&` where `T` is a deduced template parameter is a forwarding reference: it binds lvalues (T deduced as `X&`) and rvalues (T deduced as `X`). `auto&&` is the same. A `std::vector<T>&&` is not a forwarding reference: it is an rvalue reference.
- `auto x = expr;` drops reference and top-level const; `auto& x` keeps const; `decltype(auto)` preserves exact type and value category (use sparingly).
- Class template argument deduction (C++17): `std::pair p{1, 2.5};`, `std::vector v{1, 2, 3};`.
- `if constexpr` (C++17) discards a branch at compile time, so code valid only for some `T` can live in one function.

Class templates: member functions are instantiated only if used. Dependent names that are types need `typename`. Specialization exists, but prefer overloading and concepts to specializing function templates.

### 3.7 Concepts and constraints (C++20)

A concept is a named compile-time predicate on template arguments. It documents requirements and makes failures readable.

```cpp
template <typename T>
concept Addable = requires(T a, T b) { { a + b } -> std::convertible_to<T>; };

template <Addable T>
T sum_all(const std::vector<T>& v) { T acc{}; for (const auto& x : v) acc = acc + x; return acc; }

template <std::integral T> constexpr T gcd_(T a, T b) { return b == 0 ? a : gcd_(b, static_cast<T>(a % b)); }
auto twice(std::invocable<int> auto f, int x) { return f(f(x)); }       // abbreviated function template
```

Verified: `sum_all(std::vector<int>{1,2,3})` gives 6, `std::string` elements concatenate, and `sum_all(std::vector<S>{})` for an empty struct `S` gives:

```
error: no matching function for call to 'sum_all(std::vector<S>)'
note: constraints not satisfied
```

Read these diagnostics bottom-up: the last "required from here / the required expression is not satisfied" line names the failing requirement. Standard concepts live in `<concepts>` (`std::integral`, `std::floating_point`, `std::convertible_to`, `std::same_as`, `std::regular_invocable`, `std::totally_ordered`, ...), `<iterator>` and `<ranges>` (`std::forward_iterator`, `std::ranges::range`, `std::ranges::forward_range`, ...). A `requires` clause can follow the template head or the declarator. Concepts check syntax and basic semantics requirements are only documented: a concept cannot prove that your `operator<` is a strict weak ordering.

### 3.8 Perfect forwarding (introduction)

A function that passes its arguments on to another should preserve whether each is an lvalue or an rvalue:

```cpp
template <typename T, typename... Args>
std::unique_ptr<T> make(Args&&... args) {
    return std::unique_ptr<T>(new T(std::forward<Args>(args)...));
}
```

`std::forward<Args>(args)` casts to rvalue only if `Args` was deduced as a non-reference type, i.e., the caller passed an rvalue. Verified: `make<Widget>(s)` with `std::string s` copied (original intact), and `make<Widget>(std::move(s))` moved. Use `std::forward` only in forwarding-reference templates and only once per argument; using an argument after forwarding it is a use-after-move. Variadic templates (`typename... Args`, `args...`) are the mechanism behind `emplace_back`, `make_unique`, `std::thread`'s constructor and `std::function`.

### 3.9 When NOT to use templates

- A concrete type works: a non-template function compiles once, gives better errors and can live in a `.cpp`.
- Runtime polymorphism is the requirement (plugin chosen at run time, heterogeneous container): use virtual functions or `std::function`.
- Only one instantiation exists: you paid compile time and readability for nothing (YAGNI).
- You need a stable ABI or hidden implementation: templates expose their definitions.
- You cannot test the generality: every concept is an interface needing two satisfying types and one failing type.
- The team does not use heavy metaprogramming (Lesson 4.1: understand team standards first).
## 4. Worked example: `RingBuffer<T, N>`

A fixed-capacity FIFO queue with value semantics, constrained, with a conforming forward iterator, so it works with range-for and `std::ranges` algorithms. It is a teaching container: it requires `T` default constructible because storage is `std::array<T, N>` (a production version would use uninitialized storage and placement new, which is beyond this lesson).

### 4.1 Design decisions

- Compile-time capacity `N` as a non-type template parameter: no allocation, no invalidation on push.
- `push` returns `bool` (full is an expected condition, not exceptional); `pop` returns `std::optional<T>` (empty is expected).
- `push` is a forwarding template constrained with `std::assignable_from<T&, U&&>`, so one function serves `const T&` and `T&&` without two overloads.
- Iterator is a const forward iterator over logical order, implemented with index arithmetic modulo `N` (head offset), not raw pointers (the physical layout wraps).
- Class-level `requires` documents what `T` must support.

### 4.2 Code (verified: compiles clean at `-Wall -Wextra -Wpedantic`; tests pass under ASan+UBSan)

```cpp
#pragma once
#include <array>
#include <cassert>
#include <concepts>
#include <cstddef>
#include <iterator>
#include <optional>
#include <type_traits>
#include <utility>

template <typename T, std::size_t N>
    requires(N > 0 && std::default_initializable<T> && std::is_move_assignable_v<T>)
class RingBuffer {
public:
    using value_type = T;
    using size_type = std::size_t;

    [[nodiscard]] static constexpr size_type capacity() noexcept { return N; }
    [[nodiscard]] size_type size() const noexcept { return size_; }
    [[nodiscard]] bool empty() const noexcept { return size_ == 0; }
    [[nodiscard]] bool full() const noexcept { return size_ == N; }

    // Returns false (and does not modify the buffer) if full.
    template <typename U>
        requires std::assignable_from<T&, U&&>
    bool push(U&& value) {
        if (full()) return false;
        buf_[(head_ + size_) % N] = std::forward<U>(value);
        ++size_;
        return true;
    }

    std::optional<T> pop() {
        if (empty()) return std::nullopt;
        std::optional<T> out{std::move(buf_[head_])};
        head_ = (head_ + 1) % N;
        --size_;
        return out;
    }

    T& front() { assert(!empty()); return buf_[head_]; }
    const T& front() const { assert(!empty()); return buf_[head_]; }

    class const_iterator {
    public:
        using iterator_category = std::forward_iterator_tag;
        using iterator_concept = std::forward_iterator_tag;
        using value_type = T;
        using difference_type = std::ptrdiff_t;
        using pointer = const T*;
        using reference = const T&;

        const_iterator() = default;
        reference operator*() const { return rb_->buf_[(rb_->head_ + idx_) % N]; }
        pointer operator->() const { return &**this; }
        const_iterator& operator++() { ++idx_; return *this; }
        const_iterator operator++(int) { auto t = *this; ++idx_; return t; }
        friend bool operator==(const const_iterator& a, const const_iterator& b) {
            return a.rb_ == b.rb_ && a.idx_ == b.idx_;
        }

    private:
        friend class RingBuffer;
        const_iterator(const RingBuffer* rb, size_type i) : rb_{rb}, idx_{i} {}
        const RingBuffer* rb_ = nullptr;
        size_type idx_ = 0;
    };

    [[nodiscard]] const_iterator begin() const noexcept { return {this, 0}; }
    [[nodiscard]] const_iterator end() const noexcept { return {this, size_}; }

private:
    std::array<T, N> buf_{};
    size_type head_ = 0;
    size_type size_ = 0;
};
```

Why each piece exists:

- `std::optional<T> out{std::move(buf_[head_])}` moves the element out; the slot keeps a moved-from `T`, overwritten by assignment on the next push (hence `move_assignable`).
- `std::forward_iterator` checks the member types, default constructibility, equality and `operator++`; the test asserts it with `static_assert`.
- The iterator stores the container pointer and a logical index, so it survives `push`; it must not be used after `pop` removes its element. Write validity rules in the container's documentation.
- An in-class `friend operator==` is found by argument-dependent lookup; C++20 rewrites `!=` from it.

### 4.3 Tests (verified)

```cpp
using R = RingBuffer<int, 3>;
static_assert(std::forward_iterator<R::const_iterator>);
static_assert(std::ranges::forward_range<const R>);

R r;
EXPECT(r.push(1) && r.push(2) && r.push(3));
EXPECT(!r.push(4) && r.size() == 3);                 // full
EXPECT(r.pop().value() == 1);
EXPECT(r.push(4));                                   // wraps around the physical array
std::string out; for (int x : r) out += std::to_string(x);
EXPECT(out == "234");                                // logical order
EXPECT(std::ranges::find(r, 3) != r.end());          // works with std::ranges algorithms
EXPECT(std::ranges::distance(r) == 3);
RingBuffer<std::string, 2> s;                        // lvalue push copies, rvalue push moves
std::string lv = "lvalue"; EXPECT(s.push(lv) && lv == "lvalue");
```

The wrap-around case (`pop` then `push` at full capacity) is the one that catches index bugs; tests that never wrap prove little.

### 4.4 Algorithms in one place (verified)

```cpp
std::vector<int> v{5, 3, 8, 1, 9, 2};
std::sort(v.begin(), v.end());                       // 1 2 3 5 8 9
auto it = std::lower_bound(v.begin(), v.end(), 5);   // index 3 (requires sorted)
std::erase_if(v, [](int x) { return x > 8; });       // removes 9
std::ranges::sort(ps, {}, &P::age);                  // projection: sort by member
```

Naive vs improved: a hand-written sort loop, an index loop calling `erase` inside, and a `std::function` parameter become `std::sort`, `std::erase_if` and a template or `std::invocable` parameter. What changed: a complexity guarantee, no invalidation bug, no type-erased call in the loop.
## 5. Production perspective

Maintainability: algorithms and named lambdas for non-trivial predicates; small constrained templates in headers, non-template code in `.cpp`. A constraint is documentation the compiler enforces.

Correctness: know each algorithm's precondition (sorted, strict weak ordering, valid range); never keep iterators across mutation (Lesson 5.2); capture by value in anything stored.

Performance: choose containers by access pattern; `reserve` when the size is known; avoid `std::function` in hot loops and `std::list` by default; contiguous storage helps the cache (Lesson 5.6). Never quote speedups you did not measure: release build, realistic sizes, repeated runs (Lesson 4.4).

Security and failure handling: invalid iterators and out-of-range indexing are memory-safety bugs (`at()` at trust boundaries, sanitizers in CI); a non-strict-weak comparator can make `std::sort` read out of bounds; compare `find` results with `end()`; `optional::value()` throws `std::bad_optional_access`, `operator*` on an empty one is UB.

Testing: test templates with two or more types (including a move-only one); `static_assert(!Concept<Type>)` for rejection cases; `static_assert` the iterator concepts.

Senior habits: start with `std::vector` and no raw loops; write the concept before the template; refuse `[&]` in anything that escapes the scope; read cppreference for an algorithm's complexity and precondition before using it; read the first compiler error and the last "required from here".

Common mistakes:

| Mistake | Symptom | Diagnose |
|---|---|---|
| `[&]` or `[=]`-with-`this` closure stored | garbage or crash later | ASan; audit capture lists of escaping closures |
| `remove_if` without `erase` | size unchanged, garbage tail | read the return-value contract |
| `lower_bound` on unsorted data | wrong index | `std::is_sorted` assert in debug |
| Comparator with `<=` | crash or hang in sort | strict weak ordering; ASan |
| `map[key]` for lookup | map grows silently | `find`/`contains`/`at` |
| `std::move` instead of `std::forward` | lvalues silently moved from | counting types |
| Unconstrained template | 200-line errors | add a concept; read the last note |
## 6. Failure laboratory

Predict before running. Compile with `g++ -std=c++20 -Wall -Wextra -Wpedantic -fsanitize=address,undefined -g`.

Program A:

```cpp
#include <functional>
#include <iostream>
#include <string>

struct Button {
    std::string name = "ok";
    std::function<void()> on_click;
    void arm() { on_click = [=] { std::cout << name << '\n'; }; }
};

int main() {
    std::function<void()> cb;
    {
        Button b;
        b.arm();
        cb = b.on_click;
    }
    cb();
}
```

Program B:

```cpp
#include <algorithm>
#include <iostream>
#include <list>
#include <ranges>
#include <vector>

std::vector<int> make() { return {1, 2, 3, 4}; }

int main() {
    std::vector<int> v = make();
    auto evens = v | std::views::filter([](int x) { return x % 2 == 0; });
    v = {1, 3, 5};
    for (int x : evens) std::cout << x;
    std::cout << "|\n";

    std::list<int> l{3, 1, 2};
    std::sort(l.begin(), l.end());       // (1)
    std::ranges::sort(l);                // (2)
}
```

Questions: A) Does it compile cleanly? Any warning? What does it print, and what is the defect in terms of lifetime? B) What does the first loop print and why? Which of (1) and (2) compile, and how do the two diagnostics differ in usefulness? Remove (1) and (2) to run the first part.

### Reveal (read after predicting)

Program A (verified, GCC 14.2.0): it compiles with `warning: implicit capture of 'this' via '[=]' is deprecated in C++20 [-Wdeprecated]`. ASan reports `stack-use-after-scope` at the print. `[=]` in a member function captures the `this` pointer, not a copy of `name`; copying the `std::function` copies that pointer; `b` is destroyed at the end of the inner block, so `cb()` reads a dead object's member. Fix: `[name = name]` or `[*this]` to capture by value (copies the object), or hold the owner in a `shared_ptr` and capture it (`weak_ptr` + `lock()` if the closure must not extend the lifetime).

Program B (verified): the first loop printed nothing, only `|`. A view is lazy: the filter runs when iterated, after `v` was replaced with `{1, 3, 5}`, which has no even element. (Modifying the underlying container after the view is created but before it is first iterated is well-defined here; non-const `begin()` caches its result (cppreference), so mutating the source after the first iteration can leave that cached iterator invalid under the container's ordinary invalidation rules; do not mutate the source while a `filter_view` over it is in use.) (1) fails with `error: no match for 'operator-'` from inside `<bits/stl_algo.h>`: the message points into library internals. (2) fails with `no match for call to ... __sort_fn` and `note: constraints not satisfied`: the diagnostic names the broken requirement (`random_access_range`). Both reject the program; the concept-constrained one tells you why in terms of the interface. Use `std::list::sort()` (a member) for lists.

Diagnosis procedure for template or lifetime errors: (1) read the first error, then jump to the last "required from here" or constraint note; (2) reduce to the smallest call that fails; (3) for lifetime bugs, draw who owns each captured or viewed object and when it dies; (4) check iterator/capture lifetimes against the container invalidation rules; (5) fix by changing capture mode, ownership or the constraint; (6) add a test that would fail before.
